拿出定制 Bundle 的数据块，第一眼看到的不是乱码。大片结构可以直接读，偏偏部分压缩 token、长度和距离持续出错。如果整块都被加密，不会留下这么多可读的东西；如果完全没处理，解压也不该总在这些地方失败。

这种局部损坏本身就是线索：处理很可能只落在少量位置，其余字节保持原样。可读字符串能让人提出这个猜想，却回答不了变换是什么、落在哪里。要把猜想变成结论，需要一个候选实现去预测一组具体位置，再看这组预测能不能让解压长度、目录和 node 关系同时对上。

上一篇已经把小包的数据块长度固定为 2301 字节。这一篇就用这一个输入，把 VFSAES 的抽取、流变换与散回走一遍。

候选从哪里来#

候选来自 AnimeStudio 的 VFSUtils.cs，本文核对的是提交 1ccfbc16bf7fe625e8295bac8074ac3b1b9a065b。正式版支持在 9726651d 中加入，和先前 CB3 的参数分开处理。

钉住提交不是形式。公开仓库会继续变，识别式、SBox 和字段变换随时可能被改写；引用一个固定版本，读者打开链接看到的才是本文实际用过的那份代码。

这份实现一开始只是拿来试的输入。真正让它站住的是本机资源自己的反应：物理区间吻合，严格解压长度吻合，node 关系吻合。后来还原启动壳，又从本机代码里拿到了一部分独立线索，放在文末再说。

长输入只抽每块开头的几个字节#

VFSAES 入口按长度分成两条路。length <= 256 时整个输入做流变换；更长的输入按 16 字节分块，从每块开头取一小段，拼进一个 256 字节的临时缓冲，变换完再按原位置写回去。

这正好解释了开头看到的损坏形状。不满 16 字节的尾部原样保留；输入很长时只取前 256 块、每块一字节，绝大部分内容根本不进变换。较短的长输入则会从每块取多个字节。

代入 2301 字节的数据块：blockCount = 143，step = 1，选中位置是 0、16、32、…、2272，共 143 字节进入临时区，末尾 13 字节不成块。同一个小包的块目录只有 101 字节，落在整体流变换那一支。两者共用入口，抽取方式却完全不同，分析时不能拿一个的结论去套另一个。

141 处变化，143 个选中位置#

对候选变换前后的数据块做差分，变化一共 141 处，全部满足 offset % 16 == 0，最后一处在 2272。

看到这个数字，很容易反推出一条“每块选一个字节、共 141 个”的规律，再去找 141 从哪来。这一步是错的。按选择规则，选中的仍是 143 个位置；其中两处输入字节恰好与变换结果相同，变换实际做了，差分里却看不出来。

差分只回答“这次哪些字节变了”，而“哪些位置被处理”由规则决定。变化集合是规则、该位置的输入值和密钥流三者叠加的结果。如果把 141 写进算法参数，就等于把这一份输入上的偶然相等当成了格式定义，换一个包立刻就会错位。

稀疏方案里这类混淆尤其常见，因为处理位置本来就少，少掉一两个看起来也像规律。比较差分时，要分清它描述的是“被改变的位置”还是“被选中的位置”。

AES 轮结构只用来生成密钥流#

VFSAES 的轮函数长得像 AES-128：SubBytes、ShiftRows、MixColumns、AddRoundKey，末轮省略 MixColumns，RCON 也沿用标准常量。但 SBox 换成了一张自定义的 256 字节表，所以通用 AES 库不能拿来直接替代。

更关键的是它的用法。数据本身并不进入轮函数：加密轮处理的是当前 IV，得到 16 字节 keystream 后与输入异或，再由 keystream 推出下一个 IV，组织方式接近 OFB。

这个结构决定了上一节的现象：输出只是输入与密钥流的异或，某个位置上的密钥流字节为零，输入就原样留下。临时缓冲里补的零也走同一条流，只是散回时不写出去。key、IV 和 IV 演进用的 XOR key 见文末速查；SBox 的完整字节表放在固定版本的 VFSUtils.cs 里，对照着轮函数看比贴在正文里更方便。

解压之后，目录字段还要各自还原#

块目录经过 VFSAES 和标准 LZ4 之后，还不是能直接读的结构。计数、尺寸、标志和名称各自套了一层整数变换：乘常量、循环移位、异或，node 名称则按下标逐字节异或。具体常量列在文末速查表里。

有一处容易抄错：计数字段的中间步骤包含小端读取与端序反转，不能简化成“对大端整数异或一个常量”。读取顺序本身参与了结果，某些取值下两种写法碰巧一致，这种巧合不能代替正确的读取顺序。

字段全部还原后，小包呈现为一个 2301 字节的压缩块，解压得到 6116 字节，再切成 6100 与 16 字节两个 node。前面所有的密码和字段操作，到这里才落到一个可以检验的资源边界上：长度对上了，node 也对上了。

可以带走的做法#

遇到“大部分可读、少数位置坏掉”的数据，先把损坏位置的分布当成格式线索，看它是否按固定步长出现。拿到候选后，用规则推出选中位置，再拿它和差分结果对账：数量对不上时，先查那几个位置的密钥流是否为零、输入是否恰好等于输出，而不是改规则去迁就差分。最后让严格解压长度和 node 切分来做终审，单靠可读字符串变多不足以说明候选正确。

把稀疏选择、密钥流生成和字段还原拆成三段看，一次字节变化或一次解压失败就能落回具体某一步。启动生成篇接着讲上面那段汇编里被外置的指令，怎样在加载后重新接回原函数。
