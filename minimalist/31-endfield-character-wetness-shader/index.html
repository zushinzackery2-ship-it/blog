角色淋了雨、蹚过水、或者被技能泼了一身，屏幕上看到的都是“变湿”。如果把它做成一个 Wetness 标量，三件事会立刻说不通：蹚水需要一条跟着世界水面走的水线，淋雨需要衣服上的水滴和流痕，还要在躲进屋檐后慢慢变干；玩法事件则完全不看天气和水体，直接把一队角色推到目标湿润度。

终末地的做法是先把三种来源分开记录，再压进同一份逐 Draw 数据交给 Shader。到了材质这一侧，衣服、面部和头发又各自选了不同的坐标系：衣服用三平面投影，面部沿脸部 UV 做双相位滴流，头发干脆不绑定雨水贴图，用程序化 cell 生成湿膜。下面沿着这条数据流，从状态写入一直走到法线、粗糙度和高光，最后再说像素程序是怎样从 Shader 资源里取回来的。

状态、资源与材质响应分成三层#

状态层只回答角色有多湿、水面在哪里；纹理资源提供不同尺度的水迹；材质层按自己的几何参数化去解释这些输入。三层一旦合并成一个参数，水线、遮挡、面部 UV 约束和头发的高光方向都会一起丢掉。

同一角色身上还有两套看起来相似、其实无关的系统。局部泼水走 decal projector：按模型节点找 Transform，在给定时长内插值 projector alpha。场景表面的 Wetness、VerticalFlow 与 Ripple 属于相机级的 Rain Wetness Feature。它们都不进入本文讨论的逐 Draw 湿润。

三个来源挤进一个浮点槽#

逐 Draw 数据的槽位有限，三种湿润强度又只需要 8 位精度，于是控制器把它们和积雪一起打包成四个字节。写入端统一调用 EntityRenderHelper.SetFloatToCustomPerDraw，按调用上下文可以对上四个通道值：1 是世界空间水面高度（relativeHeight + characterPivotY），8 是平滑后的雨淋强度，16 是水体浸润强度 m_wetness，24 是玩法目标值的平滑结果。

Shader 端的读法从另一个方向印证了这套编码：CustomPerDrawData[2].x 先 asuint，再按字节移位。

x 在类型上是 float，语义上却是四个 UNorm8。移植时如果把它当普通强度去插值，四个通道会一起损坏。水面高度需要完整浮点精度，所以单独放在 y；z 是角色溶解的调度偏移，与湿润无关。

水线跟着世界水面，干湿跟着平滑时间#

水线没有用一张角色空间的动态浸水 mask，而是直接拿世界水面高度和像素世界高度相减。衣服像素程序里是这样：

u * u * (3 - 2u) 是 DXBC 展开后的 Hermite smoothstep，0.2 与 2.857143 是这份程序里的立即数，给水线一段软边。好处是角色沿斜坡走进水里时，水线始终水平地贴着水面；玩法湿润通过 max 提供一个和水面无关的全身基底。移植到 Z-up 引擎时，水面与像素位置要一起换轴和长度单位，软边常量也要随长度尺度换算。

雨淋强度从哪里来，取决于角色头顶有没有遮挡。角色传感器分别维护 waterRaycastAge 和 rainRaycastAge，按对象类型取检测间隔，把雨淋射线写进批量 RaycastCommand 队列，再配合命中数组、睡眠集合和 round-robin 调度按 sensor 回填结果。也就是说，遮挡检测是带预算的角色级调度，而不是每帧每人一条射线。停雨时分支清零 age、撤销 isRaining 并触发状态回调。

三种强度都经过 SmoothedFloat：环境变化只设置目标值和平滑时间，当前值逐帧逼近；来源消失后先等各自的 dry delay，再平滑回落。所以躲雨后衣服不会立刻变干，也不存在一个全局的 0 到 1 计时器。

衣服：三平面投影让水滴不依赖 UV#

衣服由许多分开的部件拼成，UV 岛的尺度各不相同。如果水滴沿 UV 采样，袖口和背后的水滴大小会对不上。Clothing 程序因此对两张雨水纹理都做三平面采样，投影权重来自法线：

三个平面各采样一次，按 weight 混合，水滴和流痕的密度就和 UV 无关了。两张纹理分工明确：

  • T_actor_common_rain_01_M（t10）是全身水滴。R/G/B 参与法线和覆盖，A 进入 0.8 - A 与 0.45 - A 两级阈值链；再叠加 _Time 和多组立即数生成的 cell/hash 错相，水滴不是简单地滚动一张静态图。
  • T_actor_common_rain_02_M（t11）是纵向流痕。R/G 按 2*x-1 解码法线 XY，B 决定覆盖，A 调制法线幅度。B 和 A 的图像相关系数约 0.753，看图会以为是重复通道，DXBC 里两者却走进不同的计算。

水滴、流痕和程序化滴落 mask 最后汇合，扰动法线再与角色原法线组合。

值得留意的是两套坐标：水线用绝对位置 v2.xyz + cb0[44].xyz，雨水与积雪投影用另一组输入 v8.xyz。这个选择决定纹理怎样跟随运动，世界坐标投影在角色移动时会滑动，角色局部坐标会跟着走，蒙皮又会改变表面对应关系。可惜写入 v8 的顶点程序不在这次提取范围内，它究竟是对象坐标还是蒙皮前坐标，目前还说不准。

面部：沿脸部 UV 做双相位滴流#

脸是三平面投影最不适合的地方：水珠应该沿脸颊往下淌，还要避开眼睛和嘴。Skin 程序于是改用模型 UV v1.xy，同一张 FaceDrip 沿 V 轴采样两个只差 0.005 的相位，构造出连续移动的边缘：

FaceDrip 是 T_actor_common_rain_03_M（Skin t11），FaceDroplet 是 T_actor_common_rain_04_M（Skin t12）。通道关系如下：

  • FaceDrip.RG 解码法线 XY 并重建 Z。
  • FaceDrip.A 的两次相位采样与 FaceDroplet.B 相乘，形成移动覆盖；FaceDrip.B 与 FaceDroplet.B 形成另一层滴流和水珠 mask。
  • FaceDroplet.B 约束脸部有效区域，FaceDroplet.A 在另一条视角与法线链里调制湿高光。

04.B/A 呈现的是特定脸部 UV 分区，这张图不能当成任意网格都能平铺的通用水滴图。换脸型复用这套材质时，衣服纹理靠空间投影可以直接用，面部纹理必须重绘区域遮罩或 rebake 到新 UV。现有程序里只有法线、遮罩和 BRDF 标量，没有视差、折射或独立清漆 Pass。

移植时还有两处容易出错。Unity 的 _Time.x 是秒数除以 20，若直接传秒数，相位应写成 0.04 * seconds，第二相位仍加 0.005；照搬 0.8 会让水流快二十倍。另外采样指令是 sample_b_indexable，bias 来自常量缓冲，衣服和头发也一样。保留导数采样和可调 Mip Bias，比固定 mip0 更不容易在远处和斜视角出现混叠。

头发：没有雨水图，照样有湿膜#

头发的几何是细长发片，既不适合三平面投影，也没有可以绘制水滴的连续 UV。Hair 参数表里能看到四个角色雨水属性名，但 132 个相关参数记录的局部 texture register 全是 0xFF，也就是一张都没绑定。属性名出现在表里，不等于程序真的采样它。

所选的 Hair 基础程序（blob 90 / 参数 0）照样读取 packed wet。湿润超过阈值后，它用 v9 和尺度常量构造稳定坐标，再由时间 hash 与程序化 cell 生成局部湿膜的法线、覆盖和高光。程序后面确实还有一次 t11 采样，但绑定的是 _CharacterSnowEffectTex，只在 snow 通道超过 2.55/255 时进入，和雨水无关。

头发本来就有 _Specular、_Metallic 和一组各向异性参数。湿润分支没有另起一套材质，而是用湿膜改变法线、颜色调制和各向异性高光强度。头发因此能共享角色的湿润状态，又不必共享衣服的水滴纹理。

湿润改变的不只是粗糙度#

回到 Clothing，totalWet 在扣掉材质级的雨水屏蔽后进入材质响应：

超过阈值后，各层分别作用在 BRDF 输入上：

  • 粗糙度：baseRoughness = 1 - _Smoothness，第一层湿膜把它拉向 min(baseRoughness, 0.05)，水滴与程序化层再在约 0.9 和 0.01 之间调制局部粗糙度。
  • 金属度：lerp(_Metallic, 0, wetMask)，水膜覆盖处表面趋向 dielectric。
  • 高光色：标准链路含 0.04 * _Specular，与有效 Metallic 和 Base Color 合成。

湿膜、水滴和流痕尺度不同，法线扰动和粗糙度变化一起决定闪光的形态，颜色还会进入 NPR 的中间色空间。把湿润理解成“Roughness 设成一个常数”，会同时丢掉形态和颜色两部分。NPR 常量缓冲没有完成整体具名映射，反汇编里的 0.308、0.88 等中间值不宜当成通用的 Base Color 暗化比例。

路径本身是标准的，但这批 Unity 2021.3 资源有几处会让人得出错误结论。真实名称在 m_ParsedForm.m_Name，高层 m_Name 是空的。程序引用在 m_PlayerSubPrograms，只看 m_SubPrograms 会以为 Shader 没有程序。有效引用放在 progVertex 字段里，m_GpuProgramType=25 和 DXBC 头却说明它是 ps_5_0，按字段名筛 progFragment 只会得到零条。entry offset 是各 segment 内的局部偏移，主 Shader 的 segment 0 只有 entry table，拼接后按全局 offset carve 会截错字节。参数记录对齐后，起点 +10 是局部 texture register，0xFF 表示未绑定，头发的结论就靠这一字节。

参数 blob 同时给出 cbuffer 成员的 byte offset，DXBC 再把 cbN[index] 和 tN 的实际消费串起来。名称、槽位、指令三者对上，一个材质语义才算落实。

本文用到的三份 ps_5_0 都取自 SubShader 0 / Pass 0，t10 / t11 / t12 均是各自程序内的局部绑定，换其他变体需要重新对应：

可以带走的做法#

这套湿润把“湿”拆成两半：状态只负责来源和时间，用四个字节塞进一个逐 Draw 浮点槽；外观交给每类材质按自己的拓扑选坐标，衣服用空间投影避开 UV 岛，脸用 UV 换取区域控制，头发用程序化湿膜省掉贴图。读类似的 Shader 时，先找状态在哪里打包，再按材质找各自的坐标系，最后用参数表的槽位和指令的实际消费互相核对，纹理名和图像只能当候选。
