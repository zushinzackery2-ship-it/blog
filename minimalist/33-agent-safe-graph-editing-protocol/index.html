让模型写有状态宿主：把不可逆动作拆成可检查的状态转换

让模型改一份有状态的宿主——引擎资产、IDE 工程、数据库、云控制台——真正危险的不是调用失败。失败会报错，报错能重试。危险的是调用成功之后留下一个没人能解释的中间状态：节点建出来了但没连线，参数类型被字符串猜错，写进了另一个同时打开的项目，或者响应太大把上下文淹没、模型下一步只能继续猜。

这类状态的共同点是不会抛异常。它们要么在几步之后才表现为别的错误，要么根本不表现，只是结果不对。

所以安全性不来自沙箱——沙箱管的是「能不能做」，这里的问题是「做对了没有」。它来自一条结构性约束：

每一个不可逆动作之前，都必须有一个可检查的动作；并且这个检查在无法诚实完成时必须拒绝，而不是放行。

下面四条是这条约束展开后的具体形态。证据取自一个 Unreal 编辑器的 MCP 桥接实现，但每一条都不依赖引擎这个宿主。

检查在前，不可逆在后#

上半部分全是可以反复执行、不留痕迹的动作，下半部分每一步都改变宿主。分界线的意义不在于「先检查后执行」这句废话，而在于：当上半部分的某个检查无法诚实完成时，正确的动作是让整条链停下。下面三节各自是这条原则的一种具体失败。

能力必须运行时发现#

代码里注册了一个操作，不等于当前这个会话能执行它。宿主的模块是按进程加载的：某个插件没启用、某个子系统没初始化、某个版本根本没这个功能，注册表都不知道。

把静态的操作清单直接当成工具列表暴露给模型，等于向它承诺了一批可能不存在的能力。模型据此制定计划，失败发生在执行时——而那时它已经写了一半。

正确的顺序是：模型先查询当前实例实际启用了什么，再取目标操作的参数定义，最后才构造调用。这条查询不能来自本地清单，必须来自宿主自己的回答。

由此还引出一个只在长期维护里显形的问题：本地合同与宿主实现会各自演进。需要一个专门的比对动作，报告「本地声明有、宿主没有」和「宿主有、本地没声明」两类差异。它不能把缺失的实现「注册出来」，只能报告不一致——但没有它，漂移会以运行时错误的形式随机出现。

schema 必须从执行体派生#

模型最容易犯的错误是猜字段名和枚举值。给它一份 schema 能解决大半，但手写的 schema 会漂移：执行体改了参数名，schema 还是旧的，于是模型按 schema 构造出一个必然失败的调用，且错误信息指向宿主而不是指向 schema。

解法不是「维护得更勤」，是让两者不可能不一致——从类型化包装函数的签名派生 schema：参数名、JSON 类型、枚举取值、必填与默认值全部来自同一份源。改了执行体，schema 自动跟着改。

同一份派生结果还应当被计划校验复用。这样「模型看到的字段」「校验检查的字段」「执行体接受的字段」是同一个东西，而不是三份需要人工对齐的副本。

要说清这道校验的边界：它只能拒绝明显错误——操作不存在、能力未启用、必填缺失、风险等级不可接受。一个字符串可能格式正确却不是现有资产路径，一个引脚名可能存在却类型不兼容，这些要等宿主的写后诊断。计划校验的准确含义是「在不改变宿主状态的前提下，先拒绝掉能拒绝的」。

干跑无法诚实模拟时必须拒绝#

这是四条里最容易做错的一条，因为做错的版本看起来更好用。

干跑的价值全部建立在「它的通过等于真实执行会通过」上。一旦某类操作无法在不触碰宿主的前提下完整模拟，继续返回「预览成功」就是在制造假证据——调用方会把它当成已验证的计划，然后直接提交。

具体的失败形态：一批操作里既有「创建节点」又有「连接刚创建的节点」，后者通过一个批内临时标识引用前者。真实执行时宿主会先建出节点、拿到真实 id，再解析引用；干跑时没有宿主参与，这个引用无从解析。

此时有三种做法，只有一种是对的：

  • 假装解析成功，返回预览通过——制造假证据，最坏。
  • 静默跳过无法模拟的操作，只报告其余部分通过——同样是假证据，而且更难发现。
  • 返回明确的「该组合不支持干跑」，要求把创建与连接拆成两批，或显式承认这次是真实执行。

第三种看起来最不方便，但它是唯一让调用方知道自己站在哪的做法。

还有一条常被默认的语义要写清楚：干跑不等于自动回滚。它表示这次调用不应提交变更，不表示宿主具备事务能力。能否完整模拟编译、类型检查和资产状态，由具体操作决定，不由这个布尔值决定。

写后差异属于协议#

写操作返回「done」是没有信息量的。模型接下来只有两个选择：重新读取整个宿主状态来确认发生了什么，或者假设成功继续往下写。前者烧掉全部上下文预算，后者把错误累积到更深处。

所以写操作的返回必须自带：受影响的对象、结构完整性检查、宿主的编译或校验诊断、以及一个可以用来拉取后续增量的令牌。模型据此知道「改了什么」，不必重读。

这里有两个容易混淆的细节。

干跑返回的拟建 id 不能被报告为「已改变」。 否则调用方会以为状态已经变了，跳过真正的执行。

响应体积的门与能力的门必须分开。 高密度读取请求（完整图 + 全部节点参数）应当被默认拦下并返回紧凑替代方案，但错误码要说清这是上下文预算限制，需要显式确认才继续。如果用「不支持」来回答一个其实支持、只是响应太大的请求，模型会得出宿主没有这个能力的结论，然后绕路去做更糟的事。

超过阈值的完整响应应当外置成带 TTL 的快照，返回句柄而不是内容。要注意它是响应的快照，不是新的数据源：过期后应当返回结构化的「已过期」，而不是回退去重新查询宿主——那会让两次读取之间的状态差异被静默吞掉。

目标身份必须是会话状态#

前面四条都假设「写到哪」是确定的。这个假设经常不成立。

两个宿主实例同时运行时——两个编辑器、两个数据库连接、两个云账号——「当前那个」不是一个确定的指代。连接成功也不能证明目标正确：两条连接都会成功。

这类错误的特征是不报错。它安静地把变更写到另一个项目，几小时后才以「我明明改了怎么没生效」的形式出现。

所以实例身份必须进入会话状态，并且每次数据面调用前重新核对：显式选定的目标仍存活就继续用；目标消失就报错要求重新选择，而不是自动挑一个；自动模式下只有唯一实例时才允许重新绑定；多个实例并存又没有选择依据时，拒绝调用。

切换实例后还要清掉按能力缓存的结果——模块能力属于具体进程，不属于这个协议。

协议买不到什么#

这条链能消除的是猜测，不是风险。三类失败落在它之外。

宿主语义。 资产不存在、路径解析到多个对象、图类型与资产类型不匹配、引脚方向不兼容、宿主编译失败、包只读——协议层无法预知这些，只能保证它们以结构化的码、消息和诊断返回。这里最该抵制的诱惑是加一层「失败就重试一次」的兜底：重试会掩盖目标状态，把一次可定位的失败变成长期查不出的偶发问题。

版本 ABI。 宿主插件与引擎小版本、编译器和模块 ABI 绑定，跨版本必须重新编译。参数 schema 一致完全不能推出二进制兼容——这两件事在不同的层上。

权限边界本身。 协议约束的是调用路径的形状，不是可以做什么。要真正收窄，只能在能力目录里不暴露那些操作：没有任意脚本执行入口，没有任意反射写属性，写权限只开放到已定义的操作集合。这是设计决策，不是协议自动带来的。

把这三类和前面四条分清楚很重要。前四条挡住的是「模型不知道自己在做什么」，这三类属于「做的事本身可能不成立」——用协议去兜后者，只会让前者也变得不可信。
