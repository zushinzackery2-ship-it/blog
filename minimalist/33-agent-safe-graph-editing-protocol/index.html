文本化协作：让人和 Agent 都能接着编辑

我希望 Agent 参与编辑以后，人仍然能自然地改同一份内容。可以让它整理一段材质逻辑，自己继续看画面、调颜色；也可以直接修正它的结果，再把后面的工作交回去。

这种协作看起来很普通，却与“把软件控制权交给 Agent，等它全部做完”有很大差别。双方都在持续形成判断，也都可能产生有价值的修改。

文本化吸引我的一个原因，就是它让这些修改能够被放在一起理解。协作有了共同的内容，而不必只通过一连串操作指令沟通。

修改本身可以成为交流材料#

假设 Agent 调整了材质的粗糙度，人同时改了颜色。两处变化本来可以共同保留，但如果每次交接都只认一份完整结果，就很容易覆盖另一方的工作。

能够看见“各自改了什么”以后，这个问题就变得具体。粗糙度与颜色是两项独立选择，可以分别讨论，也可以一起观察最终效果。

如果双方恰好修改同一个参数，差异也说明了真正的分歧在哪里。人不必从整份资产里猜测 Agent 的意图，Agent 也有机会理解人刚刚作出的调整。

这让我觉得，差异是一种很有效的协作材料。它比重新描述全部状态更简洁，又比一句“已经改好了”保留更多信息。

草稿让思考有自己的空间#

编辑并不总是一步到位。某条连接先尝试接起来，再发现另一种组织更清楚；某组参数暂时保留，只为了比较两种效果。这些过程都需要草稿。

如果每一个尝试都立刻进入大家正在使用的场景，协作就会变得紧张。人看到的状态不断变化，Agent 也可能被尚未完成的操作打断。

文本工作区让一组修改可以先作为完整想法存在。参与者有机会整理、比较和讨论，再把认为合适的结果带回软件。草稿由此保留了探索的空间，也减轻了共享环境承受的干扰。

我看重的并不是把所有编辑都变慢，而是让使用者能够决定什么时候还在思考，什么时候准备让其他人看到这份变化。

冲突说明双方在作出不同选择#

协作中的冲突很容易被视为工具故障。但有些冲突恰好说明双方都在认真修改同一个地方。

一方删掉一个节点，另一方仍然围绕它增加连接，背后可能是两种不同的设计方向。工具可以把分歧呈现得更清楚，却无法仅凭哪个版本更新，就替人判断哪个方向更合适。

我希望这样的时刻能够回到作品本身：这个节点还承担什么作用，新连接想解决什么问题，两种意图有没有共同保留的可能。

能把冲突缩小到具体变化，协作就保留了讨论的余地。整份内容被悄悄覆盖以后，这种机会反而消失了。

人能够接手，自动化才更容易深入#

使用者是否愿意交给 Agent 更多工作，与自己能否重新接手有关。结果容易阅读、修改容易定位，人就不必在“全部自己做”和“完全交出去”之间选择。

文本提供了一种连续的参与方式。人可以改几行，Agent 可以继续整理更大一段结构，双方都围绕同一份内容工作。最终的视觉与运行结果，又让这些选择回到共同可见的作品上。

我希望文本化 MCP 带来的协作，是参与方式变得灵活。谁来修改可以变化，工作仍然能接得上；谁提出了不同判断，也能在具体差异里被理解。
