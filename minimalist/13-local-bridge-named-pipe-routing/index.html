命名管道不是标准 MCP 传输层的替代品，也不是零开销通道。当前实现保留 MCP 客户端熟悉的 stdio，把命名管道放在 Python 网关与长期运行的 Unreal Editor 插件之间：外层保持兼容，内层解决编辑器生命周期、实例发现和本地路由。

选型结论#

本地重量级编辑器的 MCP 通信有三个约束：MCP 客户端应继续使用标准连接方式；编辑器由开发者独立启动，不能跟随网关进程退出；多个编辑器实例必须能被发现并稳定绑定。

当前实现因此分成两段：

命名管道不是唯一可行的本地 IPC。回环 TCP、Unix Domain Socket、共享内存加同步原语都能覆盖部分需求。这里选择 Windows 命名管道，是因为它能用稳定名称表达本机端点、无需分配端口，并能把 Editor PID 直接编码进实例路由。它仍有系统调用、缓冲和数据复制成本，价值主要来自生命周期与发现模型。

回环 TCP 的成本不在 bind，在发现链路#

回环 TCP 是可用方案，不应被描述成结构上错误。当前项目没有选择它，主要是端点发现和多实例路由会额外引入一套端口管理协议。

端口冲突与选择成本#

开发者同时打开多个 UE 项目时，每个 Editor 实例如果都监听 TCP 端口，就需要动态选择可用端口。端口选择本身不难，难点是让 MCP 网关可靠地知道“哪个端口对应哪个项目”：

问题具体表现
临时端口范围Windows 动态端口默认 49152–65535，但其他应用（Docker、Node.js、游戏）也会占用
端口复用设置SO_REUSEADDR 在 Windows 上行为与 Linux 不同，需要平台适配
客户端发现服务端选了随机端口，客户端如何知道？需要额外发现机制（文件、注册表、广播）

端口管理的成本不在于 bind()，而在于维护一条从 Editor 到 Python 网关的发现链路。命名管道同样需要发现，但 EditorBridge.<pid> 已同时给出传输端点和实例标识，不必再维护“PID/项目路径 → 端口”的独立映射。

性能不是单独成立的选型理由#

回环 TCP 会经过 socket 与 TCP/IP 实现，命名管道则经过 Windows Named Pipe 与内核缓冲。两者都不是零成本，也都通常涉及用户态与内核态之间的数据复制。JSON 编码、解析和 UE 主线程执行成本也不会因为换成命名管道而消失。

TCP 的 Nagle 策略可以关闭，拥塞与缓冲行为也受系统实现和 socket 配置影响，不能一概写成每条本地消息都会承担同样代价。没有同环境基准测试时，不应声称两者存在固定的微秒级差距。

本项目选择命名管道的可验证收益是：没有端口分配与防火墙规则；管道名天然携带 PID；Windows 可以用同名的多个管道实例承接并发连接。是否比回环 TCP 更快，需要单独测量，不作为架构成立的前提。

两段传输服务的是两段生命周期#

stdio 和命名管道在当前架构里不是竞争关系，而是分别服务两段生命周期。

维度MCP stdio 段回环 TCP 桥接备选当前命名管道桥接
连接双方MCP Client ↔ Python ServerPython Server ↔ EditorPython Server ↔ Editor
生命周期网关通常由客户端启动并跟随会话Editor 可独立运行Editor 可独立运行
发现方式MCP 客户端配置命令端口 + 实例映射管道名包含 PID

Server-First 架构#

Unreal Editor 插件启动后创建按 PID 命名的管道；Python MCP Server 由标准 MCP 客户端通过 stdio 启动：

这条链路分别保留了两边需要的语义：

  • MCP 侧兼容：客户端只需要支持 stdio，不需要实现 Windows 管道传输。
  • Editor 侧独立：关闭 Agent 或 Python Server 不会关闭 Editor，也不会丢失编辑器内缓存与编译状态。
  • 实例路由：每个 Editor 使用 EditorBridge.<pid>，多项目不会争用同一个固定端点。

Windows 的一个已连接管道实例只服务一个客户端。并发能力来自同一名称下创建多个 server instance；当前 UE 插件固定启动 4 个 pipe worker，而不是让单个连接自动复用任意数量客户端。

按字节读取就必须显式声明消息边界#

命名管道桥接传输的是项目内部 envelope，不是 MCP 客户端直接发送的 JSON-RPC 帧。桥接层按字节读取数据，因此需要显式消息边界。

MCP stdio 方案用换行符分隔消息（每条 JSON 一行）。命名管道采用长度前缀方案：

接收方先读 4 字节得到长度，再读对应字节数。无论底层怎么分包，逻辑消息边界由长度头部确定。

帧协议解决的问题：

机制作用
长度前缀明确 JSON 消息边界，避免粘包
固定头部长度接收方永远先读 4 字节，无需扫描分隔符
最大帧限制当前上限 64 MiB，异常长度在分配 body 前被拒绝

端点名里带上进程标识，命名空间就是实例表#

开发者可能同时打开多个 UE 项目（如主项目 + 插件测试）。单一固定管道名只能服务一个 Editor 实例。

命名策略是把进程 PID 编码进管道名：

每个 Editor 实例有独立的通信端点。直接做实例选择的是 Python 网关，MCP Client 只调用 facade 工具。

多实例管理流程：

场景机制
单实例网关自动绑定唯一活跃的 EditorBridge.*
多实例bridge_instance_list 查询项目名与 PID，bridge_instance_select 将当前 MCP 会话显式绑定到其中一个实例
自动绑定实例重启下一次调用重新枚举并自动绑定新的唯一实例
显式绑定实例退出返回实例失效错误，要求重新 list/select，避免静默切换到另一个项目

实例发现方式：

  1. 管道枚举：Python 网关通过 Windows FindFirstFileW / FindNextFileW 枚举 \\.\pipe\EditorBridge.*。
  2. 实例识别：网关临时连接每个管道并调用 project_context_get，读取项目名和 .uproject 路径。
  3. 会话绑定：一个 stdio MCP 会话对应一个 Python 进程，模块内 InstanceManager 因而自然成为会话级状态；它保存选中的管道名和自动/显式模式。

管道命名空间本身就是活跃实例表。Editor 退出后端点消失，不需要另外清理注册表文件；但显式绑定状态仍必须检测目标 PID 是否还存在。

宿主主线程不能被 I/O 等待占用#

Unreal Engine 主线程负责渲染和 Tick，不能被管道等待阻塞。当前插件使用 I/O worker 与游戏线程两层：

I/O worker：4 个 FRunnable 分别维护一个同名 pipe instance，使用 overlapped I/O 接受连接、读取长度头和 body、写回响应。每个请求完成后关闭连接；Python 端也是每次调用重新 connect、write、read、close。

游戏线程：worker 收到完整 body 后，通过 AsyncTask(ENamedThreads::GameThread, ...) 投递整个 operation 分派。当前实现没有独立的通用业务工作线程；需要访问 UObject 的解析、执行和响应构造都在游戏线程完成。

worker 等待 future 时持续检查停止标志，避免 ShutdownModule 在游戏线程等待一个永远无法执行的任务。这个设计保护了关闭路径，但单个重操作仍可能占用游戏线程并让 Editor 短暂卡顿。

分层好处：

  • 管道连接和读写不会阻塞游戏线程
  • UObject 不跨线程传递，worker 与游戏线程之间只交换字符串
  • 4 个 pipe instance 允许多个 MCP 会话占用不同连接槽；业务 operation 最终仍在同一个游戏线程串行执行

断线不等于事务回滚#

命名管道的连接语义让错误处理有明确边界：

错误原因处理
管道断开Editor 崩溃、实例退出或请求结束关闭本次 handle；下一次调用重新连接并重新检查实例
帧损坏长度头部超出最大帧限制断开连接，避免读入无效数据
读取超时对端无响应（如 UE 卡死）Python 网关取消 overlapped I/O 并返回 bridge timeout；默认请求超时为 30 秒
写入失败对端缓冲区满或已断开检查返回值，失败即断开
JSON 解析失败bridge body 非法返回结构化 bridge error，或关闭当前请求连接

传输层没有跨请求复用的连接状态，但业务写操作可能已经在 UE 中产生变更。断线不能等价为事务回滚；写入安全仍要依赖 dry_run、写后检查、compile diagnostics、diff token 和明确的保存步骤。

错误处理策略：

  • Editor 侧：关闭当前 pipe handle，worker 回到同名 server instance 的监听循环，Editor 继续运行。
  • Python 侧：每个工具调用重新连接当前管道；自动选择模式可在唯一实例重启后重新绑定，显式选择模式则要求用户重新确认目标实例。

兼容性由外层网关提供，不由内层传输提供#

MCP Client 连接的是 Python MCP Server。工具发现、参数校验、tool result 和 JSON-RPC 生命周期都由这一层按 MCP SDK 处理：

  • MCP 客户端仍按 stdio 配置启动 ue-node-nexus-mcp。
  • 对外只暴露 6 个 facade 工具；内部 operation registry 不直接进入 MCP tool list。
  • Python 网关把 facade 请求转换成 bridge envelope，再把 UE 响应裁剪为 minimal、full 或 artifact 引用。

命名管道只属于网关内部实现：

  • MCP Client 不需要 CreateFileW、管道枚举或重连代码。
  • bridge envelope 不是标准 MCP 消息，不能让通用 MCP 客户端绕过 Python 网关后直接连接 Editor。
  • 如果替换桥接 IPC，只要保留 Python facade 与 UE operation 合同，MCP 客户端配置可以不变。

因此这里能声明的是“对标准 MCP 客户端保持兼容”，而不是“命名管道本身完全兼容标准 MCP”。

边界#

这套通信设计的关键不是用命名管道取代 stdio，而是把两种进程关系拆开：MCP Client 与 Python Server 保持标准 stdio；Python Server 与独立运行的 Unreal Editor 使用按 PID 命名的本地桥接。这样既保留通用客户端兼容，也让 Editor 生命周期、多实例发现和会话绑定成为显式结构。

长度前缀解决消息边界，4 个 pipe worker 提供有限并发槽，所有 UObject operation 则统一回到 GameThread。这个边界也说明方案不能被简单复制到所有重量级工具：其他宿主必须重新实现自己的主线程调度、实例身份和能力合同；非 Windows 平台还需要换成相应的本地 IPC。

Windows 命名管道是当前 UE 桥接实现。Unix Domain Socket 可以复用长度前缀与网关分层思路，但端点发现、权限、并发和宿主线程模型仍需重新设计与验证。
