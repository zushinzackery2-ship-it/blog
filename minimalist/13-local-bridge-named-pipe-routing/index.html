MCP 与长期工作：会话结束，内容仍然留下

Agent 的一次会话，通常比一项工作短。一个场景可能要改几天，一组材质可能反复调整几周；中间会换模型、开新对话，也会有一段时间完全由人接手。

如果每次重新连接，都像第一次见到这个项目，使用体验就会很割裂。之前的修改在哪里，编辑器为什么还开着，哪些结果已经保存，这些事情又要重新解释一遍。

我希望 MCP 接入的软件具有另一种连续性：会话来来去去，工作仍然留在项目里。新的 Agent 面对的是已有内容，可以从这里接着做。

项目比连接更接近工作的真实形状#

从通信的角度看，一次连接有清楚的开始与结束。但从使用者的角度看，工作通常围绕一个项目、一份文档或一个场景展开。

编辑器里的当前状态、文件中的草稿、已经保存的版本，都属于这项工作。它们没有理由随着一次聊天结束而失去意义。

这也是我看重文本工作区的原因之一。文件给工作提供了独立于会话的存在方式。即使宿主暂时关闭，内容仍然可以阅读、搜索和讨论；重新打开软件后，编辑又能回到真实结果上。

连接因此更像一次参与工作的机会。它让 Agent 接触已有项目，而项目本身保留连续性。

自动化可以融入人的工作过程#

人手动打开一个编辑器，可能一边调整场景，一边让 Agent 处理其中一部分内容。此时，Agent 只是参与者之一。

如果工具把软件完全当作本次任务的附属物，结束任务时顺手关闭，便会与人的工作发生冲突。类似的问题也会出现在重新启动时：一个仍在使用的项目，被当成需要重新创建的临时环境。

我更喜欢自动化融入已有工作过程的设计。软件里有人的操作，也有 Agent 的修改；任务结束可以意味着 Agent 暂时离开，而作品与编辑状态继续存在。

这样的体验会降低接入自动化的心理负担。使用者可以随时让 Agent 参与某一部分，也可以随时接手，不必围绕工具重新安排整个工作方式。

重连后仍然认识自己的工作#

连接断开时，使用者真正关心的通常是刚才那次修改怎么样了。软件也许已经完成操作，只是结果还没有传回来；也可能还停在处理中。

如果这段工作在项目中留下了可以查看的内容和结果，重连就有了依据。人和 Agent 能重新认识当前状态，而不用仅凭上一段对话猜测。

这种连续性也让不同模型之间的切换更自然。模型可以有不同的理解和能力，但它们面对同一份作品、同一组变化，就有机会继续同一项工作。

稳定的环境让 Agent 更容易被替换#

把全部过程绑在某个 Agent 身上，短期可能显得省事，长期却会让工作依赖一段难以迁移的上下文。

稳定的项目环境让这种依赖减轻。模型承担思考和编辑，文件与软件保留结果。人可以选择更合适的模型，也可以自己完成剩余部分。

我希望 MCP 带来的正是这种自由：让更多参与者接入工作，同时让工作本身保持独立。会话结束以后，留下的内容仍然值得阅读，也仍然能够继续修改。
