大世界里的建造物、地形装饰、批量渲染对象，数量大、种类多、还要能并行更新。官方 DOTS 能扛这类负载。另有一套自成体系的 Archetype ECS，概念上仍是 Entity、Archetype、组件掩码、Chunk、Job，句柄、掩码、管理器和 System 组织却做了另一组选择，并和上层面向对象的玩法框架叠在一起。

这套 ECS 的样本来自《明日方舟：终末地》的 IL2CPP 产物。这个系列一共四篇：本篇拆存储与查询，第二篇走列数据的两个边界（渲染出口与流式入口），第三篇讲同步线索为什么只能停在「字段存在」，第四篇整理性能数字的口径。四篇的证据都来自同一份样本，后两篇讨论的判断标准与具体游戏无关。

能在编译期或数据结构上固定的，它就固定下来：组件类型封顶、管理器做成值类型、注册前移到源生成器。换来的是运行时路径短、开销可预期。逻辑和渲染再拆成两个 World，两类访问各写各的数据。

双层混合结构#

整套系统分三部分：上层的面向对象玩法框架、下层的数据导向 ECS、以及把两者接起来的桥。

下层沿用了 Entities 的叫法——EntityManager、EntityQuery、LocalToWorld，块视图叫 BlockRange——实现是自己写的。角色和战斗留在面向对象那一层，密度高、适合并行的对象沉到 ECS。

实体只是带代计数的句柄#

实体不带数据。对外是一个 8 字节句柄，低 32 位是全局下标，高 32 位是代计数，也可以当成一个 u64 传：

下标指向一张槽位表。每个槽位只回答三件事：这个实体现在属于哪个 archetype、在块里的第几行、当前代计数是多少。

句柄要算活着，下标和代计数都得非 0，下标还得落在表内，槽位得有行，两边的代计数还得对上。销毁后的空槽与版本校验会让旧句柄失效；当前可见托管包装没有展开销毁时版本写入、槽位回收或 swap-back 的具体实现，因此这里只确认句柄校验边界，不把回收算法写死。槽位复用后，过期句柄仍需通过版本比较才能被接受。

创建和销毁都提供批量接口，槽位表能扩，也能主动回收。无效句柄就是全零。

描述符和数据页分开#

EntityType 是一个 4 字节 archetype 注册表下标；相同组件集合的实体共用一份 EntityTypeInstanceData 描述符。描述符本身定长：前面放掩码、指针和计数，后面内联一张最多 64 项的组件表。实体数据放在旁边单独分配的原生缓冲里，容量由 capacity 管。

64 这个数字是描述符定长换来的：每种组件 8 字节，表必须收得住。全局类型上限是掩码给的 128，单块能同时装下的种类更少一档。

签名的低 64 位可以单独用。组件 id 落在前 64 个时，热路径只搬半段掩码。

memory 按列存。同一块里所有实体的同一种组件排在一起。第 i 行、组件 C 的地址是 memory + offset * capacity + i * size；列与列之间按 capacity 预留，不能用活跃实体数 count 推下一列。批量读写先解析列描述符和行号，再做一次乘加。

查询命中后，一块 archetype 对外就是一个只读视图，能拿到某列指针、整列数组，以及一段连续的实体句柄。句柄和组件走同一套行号。

共享组件另开一条槽。掩码只有 64 位，数据按 archetype 存一份。适合这一类对象共用同一份参数。

EntityManager 也做成值类型，只带着两张表的指针，多个入口按 ref / out 传递：

现代 Unity.Entities.EntityManager 同样是值类型，但它包装官方 World 的访问入口。这里的管理器布局更直接，只有两个表指针。玩法 World 和渲染 World 各拿一份这样的管理器，互不共享表；这能确认布局和隔离关系，不能单凭结构推出热路径零分配或所有调用都必须 ref。

结构一变就迁块，没变就不动#

加删组件会改实体的组件集合，实体必须换到新的 archetype。即时改和延迟改分开。

加组件时先看目标是不是已经在当前签名里。在，只写数据。不在，就把旧组件表拷一份、接上新项，按新签名去注册表查：有就复用 id，没有就建一块新描述符、算各列起点。然后在新块分配一行，按组件 id 对齐后逐列拷旧数据、写入新值，再改槽位上的 archetype 和行号，旧行回收。

删组件走同一套，只是表在变短。批量删除先按掩码过滤旧表；过滤完和原来一样，直接返回。真的少了东西，才注册新块并搬列。加和删是两条独立的搬迁，拷贝都按列做，SoA 布局保持连续。也可以按 id 把某个组件从源实体迁到目标实体，语义是搬走。

Job 跑在块上时，结构变更改走延迟路径。延迟路径是一条命令队列：创建、附加、移除、改值、销毁、查询各占一个操作码。每条命令带着句柄，以及一份 {组件 id, 大小, 数据指针} 快照。

创建可以先发临时句柄。同一条队列里后面的附加操作先写这个临时 id，回放时再翻译成真正的槽位。并行 Job 往队列里写，用并行写入器；回放在主线程做完，缓冲可以回收再用。只要延迟删除，另有一条窄口。

用 128 位掩码换常数时间匹配#

archetype 的签名是固定 16 字节、两个 u64：

组件 id 除以 64 选字，余数选位。整段掩码一次就能搬完，组合就是移位和按位运算。类型总数被钉在 128，包含和排除都是常数时间的位运算。

查询语义直接落在这两个判断上：签名是否覆盖 include，以及是否避开 exclude。两个都过，这块才算命中。多个 id 拼成一张掩码时，用固定参数个数的重载，避免查询入口再走变长循环。

DOTS 的掩码位数是活的。这里用上限换确定性。项目得把组件种类压在 128 以内；单块再被 64 个表项收一档。

查询在切分时就定好并行度#

功能就是 Job。查询和调度是一条链，并行度在查询阶段定下来。

构造器先往两张列表里追加组件：WithAll 进 include，WithNone 进 exclude。真正执行时，用当前管理器把列表收成两张 16 字节掩码。

得到的是一张懒视图：它指着这个 World 的整张 archetype 表，带着 include / exclude，长度等于表长。枚举时才一块块做位运算，过了才交出该块的只读视图。

要并行，必须先物化命中结果，再按 worker 数切开。jobCount 从查询入口一直传到切分；传 -1 就用运行时的默认 worker 数。切分由 Burst 做：先把命中的块收进 groups，再按 worker 数切成若干 BlockRange。

立即路径把这两份列表交给主线程。延迟路径只留指针，外加一个长度单元，给 IJobParallelForDefer 当“稍后才知道有多少份工作”。

BlockRange 在已经物化的 groups 上划一段区间，首尾两块还可以只取一部分行：

大小不一的 archetype 可以被切成工作量接近的 N 份。并行粒度是查询结果上的工作区间，数据页大小由各块自己的容量决定。

常见写法是两个 Job 接力。查询 Job 拿着管理器和 jobCount，在 worker 里把结果写进延迟容器。处理 Job 只拿结果指针和业务数据，按区间下标取列。主线程可以在查询尚未结束时就把处理 Job 挂上去。

主线程上的小规模读写仍然可以直接枚举那张懒视图。需要立刻知道命中数时，走立即结果。

逻辑和渲染各用一张表#

玩法和渲染各有一份 EntityManager，也就是各有自己的槽位表和 archetype 表。句柄只在自己那张表里有效。

跨 World 是一对多。玩法实体上挂一张定长绑定表，最多记下 512 个渲染句柄，负责绑定、解绑和查询是否已有渲染体；再用一个无数据的标签参与查询。渲染实体上挂自己的 Binder：自身句柄、指向玩法共享数据的下标、以及渲染类别。

同步方向是玩法写、渲染读。玩法把逻辑状态交过去，由渲染侧改可见性、材质和 TRS。必须写渲染表的操作，会显式传入渲染那份管理器，避免写错 World。

渲染实体用完了先进池。池子预分配一批句柄，用水位控制，生成和回收走回调；不够再扩容。结构变更集中在扩容的时刻。

LocalToWorld 同时留着当前帧和上一帧的矩阵、一个层级句柄、脏标记和计算帧号。父子关系放在旁边的层级容器里：每个节点是本地 TRS、父节点下标和脏位。更新 Job 一边消费查询切出来的工作区间，一边拿着层级数组，按句柄把本地变换收成世界矩阵。父节点改了，整条链路的实体仍留在原来的 archetype。

渲染 World 的块还按网格、反射探针、水面、贴花这类职责分类，查询可以按类交给不同的 Job。

组件 id 在编译期发完#

组件是标了特性的结构体；下面的 C 片段只表达 Attribute 的有效字段，不等同于托管 ECSComponentAttribute 对象布局：

源生成器在编译期发 id、生成描述符，并把常用泛型方法展开。每个组件带一个常量 ID，运行时直接返回这个常量。isTag 就是空的标记组件，和 DOTS 里空的 IComponentData 一类。

DOTS 主要靠运行时的 TypeManager 注册。这里把注册提前，运行时走常量 id。

这些选择指向同一件事：能固定的就固定，换运行时的确定性和短路径。值类型管理器少一次托管分配，定长掩码把匹配压成位运算，编译期注册去掉反射，双 World 把读写拆开。

描述符是元数据，DOTS 的 16KB chunk 是数据页。这套设计的数据页按容量另开，并行时再按 jobCount 把多块的行切成工作区间。它更适合种类多、单类规模中等、结构变更勤的对象。

这组取舍适合什么负载#

核心负载如果是大世界里种类多、加删组件勤、而且逻辑和渲染能分开的对象，自己做一套 Archetype ECS 也成立。管理器做成值类型、掩码定长、注册前移、World 按读写拆开，能留下 ECS 的数据布局，同时把运行时行为和切分粒度收在自己手里。

代价也清楚：组件种类有上限，单块表项只有 64 个，Job 之间的更新顺序要自己排，开发流程要靠源生成器托住。

值得看的是这几条判断：哪些东西值得用编译期换运行时，哪些数据值得为读写解耦付一份同步，查询结果按什么粒度切给 worker。
