在大型 Unity 项目里，当需要承载大量、种类繁多、可高度并行处理的实体——大世界里的建造物、地形装饰、批量渲染对象——官方的 DOTS/Entities 是常见选择，但不是唯一路线。这里解析另一种可行方案：一套自成体系的 Archetype ECS。它沿用 Entities 的概念体系（Entity、Archetype、组件掩码、Chunk、Job），但在句柄打包、组件掩码、内存布局、System 组织上做了不同取舍，并和上层面向对象的玩法框架组成双层结构。

结论先放这里：这套设计的核心偏好是”能在编译期或数据结构上固定下来的就固定下来”——用组件类型上限、值类型管理器、编译期注册，换取运行时的确定性和低开销；再用逻辑与渲染的双 World，把两类访问模式彻底分开。下文用通用命名描述这套设计，聚焦结构、关系和取舍本身。

双层混合结构#

整套系统分三部分：上层的面向对象玩法框架、下层的数据导向 ECS、以及把两者连接起来的桥接层。

下层是重点。它在命名上沿用了 Entities 的体系（EntityManager、EntityQuery、LocalToWorld，以及对应 ArchetypeChunk 的 BlockRange），但是一套独立实现，而不是对官方 DOTS 的封装。上层用面向对象表达角色、战斗这类玩法，下层用数据导向承载高密度、可并行的对象。

实体句柄与版本号#

实体本身不持有数据，只是一个 8 字节句柄：

句柄对外按一个 u64 传递：低 32 位是 globalIndex，高 32 位是 version。globalIndex 指向一张全局槽位表，每个槽位记录该实体当前落在哪个 archetype、哪一行，以及自己的代计数：

存活校验按四步进行：句柄的 globalIndex 和 version 都不为 0；globalIndex 在槽位表范围内；槽位的 entityIdx 不是 -1（非空）；槽位的 version 等于句柄携带的 version。最后一步是关键——实体销毁时把槽位的 entityIdx 置 -1、version 自增，于是所有旧句柄的 version 都对不上，天然防住了句柄复用带来的 ABA 问题。

Archetype 的内存布局#

Archetype（这里叫 EntityType，本质是一个 4 字节 id）决定一组实体的组件集合。相同组件集合的实体共享一个 archetype 块，块的描述结构固定 576 字节（0x240）：

每种组件的列位置由一张描述符数组记录，它内联在块结构末尾，不是外部指针：

memory 指向的原生内存采用 SoA（Structure of Arrays）列存：同一 archetype 里所有实体的同一组件连续排列，而不是把一个实体的所有组件挨在一起放。这样遍历某个组件时访问是连续的，对 cache 和 SIMD 都友好。

管理器本身也是值类型，只有两个指针，按引用传递以避免装箱：

这是和官方 DOTS 的第一个明显分歧：Unity.Entities.EntityManager 是持有 World 状态的 class，而这里是一个 16 字节的 struct，热路径上零托管堆分配。代价是所有需要它的方法都得用 ref 传参。

加删组件会改变实体的组件集合，也就要在 archetype 之间迁移：注册或查找目标 archetype、把保留下来的组件列逐列拷贝到新块、更新槽位里的 entityType 和行号、旧块回收该行。批量删除组件时，先遍历当前 archetype 的组件描述符，用掩码逐位判断哪些保留；如果没有任何组件被删就直接返回，只有集合真正变化时才走迁移。

定长 128 位组件掩码#

一个 archetype 的组件签名用固定 16 字节的位掩码表示：

定位规则很直接：组件 id 的 id / 64 是字下标，id % 64 是字内位号。掩码整体是 16 字节，读写可以用一条 SSE 指令搬运，组合掩码就是移位加按位操作。这带来两个特征：组件类型总数上限是 128；掩码的比较、包含、排除都是常数时间的位运算，不需要哈希或变长结构。

掩码结构自带的方法直接对应查询语义：ContainsComponentMask 是 include 判断（archetype 是否包含要求的全部组件），ExcludesComponentMask 是 exclude 判断（archetype 是否避开了排除的组件）。一个 archetype 命中查询，当且仅当它同时通过这两项。

和官方 DOTS 变长位数的组件掩码相比，这是一个用上限换确定性的取舍：只要组件类型控制在 128 种以内，位运算的开销就是可预期的常数。

无 System 层：查询即并行调度#

这套 ECS 里没有 SystemBase 或 ISystem 这样的 System 基类。承担 System 角色的是 IJob 加 Burst 编译的委托——每个功能是一个 Job，比如把 TRS 批量算成矩阵、批量更新渲染数据。

查询和调度是连在一起的。查询构造器分别累积 include 和 exclude 两个掩码，执行时先把两个掩码物化，再遍历所有 archetype 按掩码过滤，得到一个 archetype 迭代器，然后按块大小把每个匹配 archetype 切成若干 BlockRange。BlockRange 就是官方 DOTS 里 ArchetypeChunk 的对应物：一个 archetype 块内连续若干行实体的视图，是 Job 并行的最小粒度。

jobCount 参数贯穿过滤、切分与调度全链路

一个 jobCount 参数从查询入口一直传到块切分和 Job 调度，也就是说并行度在查询阶段就确定了下来。还有一条延迟查询路径，返回一个可以在 worker 线程里迭代 BlockRange 的延迟结果，对应官方 DOTS 的 IJobChunk 模式，让 Job 在工作线程内消费查询结果而不阻塞主线程。

逻辑与渲染分成两个 World#

系统同时维护两个独立的 World，各自有独立的槽位表和 archetype 注册表：

Gameplay World 承载对象的逻辑数据，由玩法逻辑写入。Renderer World 承载渲染相关组件，由渲染 Job 读取并交给 GPU。两者通过 Binder 组件做逻辑到表现的单向同步，好处是渲染侧的读取不会和玩法侧的写入争用同一份数据。

Renderer World 里的 archetype 还有一层显式分类，用一个枚举预定义了几个渲染类别：网格、反射探针、水面、贴花投射等。这和它承担的批量渲染、Culling 职责对应——按渲染类别组织 archetype，每类交给各自的 Job 批处理。

组件在编译期注册#

组件都是标了特性的 struct：

开发者用这个特性标记一个 struct，源生成器（SourceGenerator）在编译期为它生成组件 id、ComponentType 描述符，以及各种泛型方法的实例化。isTag 对应无数据、只作 archetype 标记的 tag 组件，等价于官方 DOTS 里空的 IComponentData。

这是和官方 DOTS 的又一处分歧：DOTS 主要在运行时通过 TypeManager 注册组件类型，而这套设计把注册前移到编译期，运行时不需要反射。

与官方 DOTS 的取舍对照#

几处差异连起来看，指向的是同一种偏好：把可以在编译期或数据结构上固定下来的东西固定下来，换取运行时的确定性和低开销。值类型的管理器省掉托管分配，定长掩码把组件匹配压成常数时间位运算，编译期注册免掉运行时反射，双 World 把逻辑和渲染的读写彻底分开。576 字节的块描述比官方 16KB 的 chunk 小得多，单块承载的实体密度低，更适合中小规模、种类繁多、结构频繁变化的对象，而不是一次性铺开的超大批同质数据。

架构取舍的可借鉴之处#

当项目的核心负载是大世界里种类繁多、频繁增删组件、且逻辑与渲染可以解耦的对象时，直接用官方 DOTS 并不是唯一解。自己实现一套 Archetype ECS，把 EntityManager 做成值类型、把组件掩码定长化、把注册前移到编译期、把逻辑和渲染拆成两个 World，能在保留 ECS 数据布局优势的同时，换来更可控的运行时行为和更贴合业务的块粒度。代价是组件类型上限、需要自己维护 Job 之间的更新顺序、以及一套要靠源生成器兜底的开发流程。

真正可借鉴的不是具体的字段布局，而是这几个取舍背后的判断标准：哪些东西值得用编译期换运行时，哪些数据值得为读写解耦付出一份同步成本。
