同一批建造物，玩法要更新产出和连接，渲染要处理矩阵、可见性与材质。数量上来以后，逐个对象调用的方法会把访问分散到许多位置。Archetype ECS 的做法是把组件集合相同的实体放在一起，再沿连续的组件列处理它们。

《明日方舟：终末地》的 IL2CPP 样本里，可以看到一套自研的 Archetype ECS。它使用 Unity Jobs、Burst 和 Collections，同时保留上层面向对象的角色、战斗与生命周期框架。Binder 把两层连接起来：玩法对象负责行为，适合批量处理的数据进入 ECS。

这套设计最有意思的地方，是存储块与工作区间分别组织。描述符和组件列决定数据放在哪里，查询切分再决定每个 worker 处理哪些行。理解这个区别，就能把句柄、掩码和 Job 接成一条完整路径。

系列后续分别讨论渲染提交与流式补写、fence 字段的归属误判与性能数字的统计对象。

EntitySlot 是便于说明的别名，原类型名为 EntityInstanceData。字段偏移按值类型起点归一化，统一减去这份 IL2CPP dump 的 0x10 基准。末尾 padding 虽不参与查找，仍占四字节；按 12 字节索引会从第二项开始读错。

接受一个句柄，要同时检查下标与代计数非零、下标落在表内、槽位有行，以及两个版本相同。这样即使槽位被复用，旧句柄也必须通过新的版本比较。创建、销毁提供批量接口，无效句柄是全零。

句柄保存的是位置索引。组件数据搬到另一个 archetype 后，只需更新槽位中的类型和行号，调用方继续使用原句柄。

EntityManager 本身是值类型，持有槽位表与 archetype 表的两个指针，常以 ref / out 传递。现代 Unity.Entities 的管理器同样是值类型；这里可直接看到的区别，是这两个表指针构成了管理器的核心布局。

组件集合改变，实体就迁到新块#

加组件时，先查当前签名。已有该组件，直接写值；需要改变集合，才按新签名查注册表，复用或创建描述符，在目标块分配一行，再按组件 id 逐列复制旧数据、写入新值。最后更新槽位并回收旧行。

删除组件走相应的过滤与迁移。批量删除若没有改变组件表，便直接结束；确实少了组件，才搬到新的 archetype。结构变更的成本因此来自分配与列搬运，普通改值仍留在原列上。

并行 Job 执行时，结构变更可以写入延迟命令队列。创建、附加、移除、改值、销毁和查询各有操作码，命令保存句柄以及组件 id、大小和数据指针。先创建的临时句柄，可以被同一队列的后续命令引用，回放时再映射到真实槽位。

并行写入器负责收集命令，回放阶段应用结构变更并复用缓冲。收集和应用分开后，正在遍历的组件列就有了明确的结构变更时机。

掩码匹配选出块，查询切分选出行#

组件签名是两个 u64。组件 id 除以 64 选择字，余数选择位。查询的 include 与 exclude 也收成相同的 128 位掩码：签名要覆盖 include，并避开 exclude，才交出该块的只读视图。

这个匹配对每块只检查固定数量的机器字。整个查询仍需遍历候选 archetype；固定宽度减少的是每次签名比较的动态工作。

WithAll、WithNone 构造阶段先记录组件列表，执行时再收成掩码。直接枚举得到的是懒过滤视图；需要并行处理，则先把命中的块收进 groups，再由 Burst 按 jobCount 切成若干 BlockRange。传 -1 使用运行时默认 worker 数。

区间可以跨块，首尾块也可以各取一部分行。这样容量不同、活跃行数不同的 archetype，能够被组织成几份工作量接近的任务。数据页按自身容量分配，任务数量则由查询入口决定。

常见用法是两个 Job 接力：查询 Job 持有管理器与 jobCount，把结果写入延迟容器；处理 Job 用 IJobParallelForDefer 消费稍后才确定长度的区间。主线程可以先挂上依赖，处理 Job 等查询完成后开始。小规模即时读写仍可直接枚举懒视图。

两个 World 分开存储，用 Binder 连接对象#

Gameplay World 和 Renderer World 各有一份管理器，各自拥有槽位表与 archetype 表。句柄中的下标因此只在所属 World 中解释。

玩法实体保存一张最多 512 个渲染句柄的绑定表，并用 HasRenderer 标签参与查询。渲染实体上的 Binder 保存自身句柄、玩法共享数据下标和渲染类别。一项玩法对象可以对应多个渲染实体。

这类更新由玩法状态流向渲染数据：渲染侧据此更新可见性、材质与 TRS，需要写入渲染表的操作显式接收 Renderer World 的管理器。Binder 负责连接两边，具体写入仍发生在各自的表上。

渲染实体可进入带生成、回收回调的池，由水位决定何时扩容。LocalToWorld 同时保留当前矩阵、上一帧矩阵、层级句柄、脏标记和计算帧号。更新 Job 结合旁边的层级数组，把本地 TRS 汇总为世界矩阵；父节点变动只更新变换，组件集合保持原样。

这些矩阵随后进入渲染提交链。双 World 的价值首先体现在数据所有权和访问路径上，实际吞吐仍取决于更新与同步的具体负载。

固定元数据，把灵活性留给调度#

生成代码里的组件 ID 是常量，运行时直接返回它；Attribute 还记录布局与是否为无数据标签。从生成结果可以确认注册信息已被固定下来，源生成器的具体分配策略则需要源码才能展开。

与 Unity.Entities 对照时，这几项差异最值得保留：

维度Unity.Entities这套实现
组件筛选类型与 archetype 查询结构，依版本演变固定 128 位签名
Archetype 元数据由官方内部结构管理0x240 定长描述符、64 项组件表
存储与调度SoA；常见调度单位为 ArchetypeChunkSoA；查询区间可以跨越数据块
管理器值类型，包装 World 访问入口值类型，核心布局为两个表指针
延迟结构变更EntityCommandBuffer命令队列、临时句柄与并行写入器
多 World默认 World 与自定义 World玩法与渲染分开存储，一对多绑定

定长掩码、内联表和常量 id 都减少了运行时动态发现元数据的工作，也带来了组件数量上限。双 World 让读写关系清楚，却仍需要传递玩法变化；跨块切分让调度更灵活，Job 依赖也要随之组织。

沿句柄到组件列，再沿查询到工作区间看下来，这套 ECS 的取舍就具体了：数据布局保持稳定，工作如何分配则由查询层决定。
