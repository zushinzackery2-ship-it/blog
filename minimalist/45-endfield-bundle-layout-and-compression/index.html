外层 VFS 已经交出了正确的文件字节，通用解析器却仍然读不到对象。最小的那个包只有 2461 字节，开头是 40 19 9A FE，没有 UnityFS\0，标准识别方式在第一个字节就走不下去。

但它并不是一团随机数据。继续往下看，熟悉的资源组织都还在：头部指向一个块目录，目录描述压缩块和 node，解压出来仍是 SerializedFile 加 .resS。变的是每一层的编码方式，而不是层次本身。这给了一个可操作的思路：不必从零猜格式，只要把每一层的编码逐个换回来，再让各层之间的长度关系替我们判断换得对不对。

候选公式来自 AnimeStudio 的正式版兼容实现，我固定在提交 1ccfbc16 上核对。公开实现在这里扮演的是假设，本机样本负责检验它。这条资源恢复路线发生在后续启动壳还原之前。

先确认是哪一版头#

同一个游戏的不同测试版本用过不同的头布局，字段解释一旦套错版本，后面每一步都会得到看似合理的错误数字。所以第一件事是判断样本属于哪一版。

正式版头用前两个大端 uint32 做自校验，记为 a、b：

样本满足这条关系，不满足 CB3 的候选关系，于是后面统一按正式版解释。解出的头给出 encodingFlags = 8、headerSize = 48、块目录压缩前后为 0x65 和 0x89 字节、flags = 0x243。块目录因此占据 [0x30, 0x95)；flags & 0x200 要求目录之后按 16 字节对齐，数据从 0xA0 开始。

这个 0xA0 先记下来。小包只有一个压缩块，它从哪里开始、占多少字节，最后必须恰好落在物理文件尾上，这会是整篇最有力的一条约束。

一个对不上的 size 字段#

按候选公式解出的头部 size 是 0xE370CDAAE370C437，截成 32 位也还是 0xE370C437，与 2461 相去甚远。

这里最容易走错的一步，是相信字段名，开始反复调整公式，直到它“看起来像文件长度”。可是同一时刻，目录区间、块区间和 node 覆盖都能独立闭合；如果坚持让这个值等于物理长度，反而会把一个已经能完整解析的样本判为失败。

所以我把它放下了：边界改用输入流本身的长度确定，再检查每个压缩块是否落在流内、解压结果能否容纳全部 node。size 的解析结果原样保留，它真正的含义留给找到实际消费它的代码时再解释。一个字段叫什么，不如其他结构是否已经自洽重要。

两种失败把两条处理链拆开#

块目录和数据块都要先经过 VFSAES 变换，自然的假设是它们后面也走同一种解压。实际试下来并非如此，而失败信息本身就说明了问题出在哪一层。

块目录这边很顺：原始字节交给标准 LZ4，报 invalid match distance 26037；先做 VFSAES 再交给标准 LZ4，输出恰好 137 字节，正是头里声明的 0x89。

数据块却不一样。原始字节直接交给 LZ4Inv，报 invalid match distance 34048；做完 VFSAES 交给标准 LZ4，报 invalid match distance 22；做完 VFSAES 交给 LZ4Inv，才输出恰好 6116 字节。于是两条链是：

其中 distance 22 最有帮助。密码变换已经做过，标准 LZ4 却在很靠前的位置失败，说明剩下的是解压格式问题，和 key 无关。如果此时回头继续调 key，就会把两个独立阶段搅在一起，永远调不出来。

判断“成功”也要比看到字符串更严格。解压器可能在出错之前先吐出一段可读前缀，所以这里要求两件事同时成立：消费的正好是目录给出的输入范围，输出正好是声明的长度。

LZ4Inv 只改了两处#

LZ4Inv 保留了 literal、match 和扩展长度的整个状态机，只动了两处编码。

第一处是 token。标准 LZ4 把 literal 长度和 match 长度分别放在高、低半字节；LZ4Inv 把它们按两位一组交错：

第二处是 match distance，从标准的小端 uint16 改成了大端。这两处必须一起还原。只改一处时同样会报非法距离，而某一次距离是否合法还取决于解码器当时已经输出了多少字节，所以单看一条报错，分辨不出是 token 还是端序出了错。

固定版本的实现见 LZ4Inv.cs。VFSAES 的抽取与散回在下一篇展开。

三个长度在同一处闭合#

块目录解压后，计数、尺寸、标志、offset 和名称还各有一层字段逆变换，常量与字节顺序见参数篇。还原出来的目录很短：一个压缩块，压缩 2301 / 0x8FD 字节，解压 6116 / 0x17E4 字节，标志 5；两个 node，都叫 CAB-d29c4e95cbb3b4d25d7f11ebc90d49ca，一个是 SerializedFile，一个带 .resS 后缀。

三条约束各管一段：物理文件尾约束输入范围，解压长度约束压缩处理，node 约束输出切分。它们在同一组结果上同时成立，比找到一个像样的 CAB 名称有说服力得多。前面放下 size 字段的理由也在这里：真正的边界早已由这三条给出。

重封装：把剩下的工作交还通用解析器#

拿到全部 node 以后，没有必要让解析器学会定制头和 LZ4Inv。写一个标准 UnityFS 容器即可：签名 UnityFS\0，格式版本 6，引擎版本 2021.3.34f5，块数据 hash 用解压数据的 MD5；块按 None 压缩写入，压缩与未压缩长度相同，后面追加解码出的资源字节。

这一步只换容器，SerializedFile 和 .resS 的字节保持原样。最小包的产物长 6319 字节，UnityPy 读到两个对象：一个 4×4 Texture2D T_default_mro_MRO 和一个 AssetBundle。输入与产物的 SHA-256 记在文末，作为后续回归的基线。

从小包到完整资源组#

同一套实现随后恢复了 InitBundle 的 1048 个包，解析出 19,370 个 Unity 对象，解包错误为零；三个大型角色 Shader 包也继续读到了 subShaderBlobs、segment 和 DXBC 程序，后续分析见角色湿润篇。

包的数量说明这套实现跑过多大的语料，但多块、多 node、目录位于文件尾这些分支是否被走到，要看实际输入的布局，不能拿总包数代替。

可以带走的做法#

面对一个“熟悉但不认识”的容器格式，这次有三点可以直接复用。先挑最小的样本，让头、目录和尾部的关系一眼就能核对。把公开实现当作假设，用相互独立的长度约束去检验它，比如“偏移加压缩长度等于文件尾”“node 之和等于解压长度”，而不是相信某个字段的名字。最后，认真读失败信息：同一个输入在不同组合下给出的不同错误，往往能直接告诉你哪一层已经对了、哪一层还没对，从而避免回头去调一个本来没有问题的参数。
