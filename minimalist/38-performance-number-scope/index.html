性能数字中的整帧、提交与分批开销

终末地渲染分享的记录里，有几组很容易被放在一起的数字：早期通用路径难以稳定到 30 帧，后续架构面向旗舰机以 60 帧为目标，Render Path 本身的 CPU 开销约为 1ms。

转述成“渲染优化到了 1ms”以后，句子明显更简洁，含义却改变了。前两项谈整套方案的表现与目标，后一项谈某段提交工作。数字还在，原来被测量的对象却不见了。

理解这组材料，更有价值的方式是把数字放回工作本身：CPU 在准备什么，GPU 在执行什么，哪些阶段相互依赖，哪些可以同时进行。

60 帧是整帧目标#

60 帧对应约 16.67ms 的帧间隔。角色更新、剔除、渲染提交、阴影与后处理等工作，都要在整条时间线上配合完成。

从通用路径转向自研 ECS、连续存储、多线程剔除与原生提交，改变的是多个阶段。材料里的目标帧率不能当成已经测得的所有机型结果，也无法单独分配给其中某项优化。

整帧时间还不是各模块耗时的简单总和。CPU 与 GPU 可以重叠工作，多个 Job 也可能并行。某一项耗时下降以后，最终帧间隔是否跟着下降，取决于它当时是否阻挡了后续进度。

例如，两项独立任务同时运行，耗时分别为 3ms 和 5ms，等待两者完成需要约 5ms；若它们前后依赖，就接近 8ms。同样两组数字，执行关系已经改变了答案。

两个 1ms 可能来自不同阶段#

分享记录中的 Render Path 约 1ms，指向提交路径本身，排序和分批另有开销。另一组记录提到分批在 Android 上约 3ms、PC 上约 1ms。

PC 上两个阶段恰好都接近 1ms，很容易让人把它们当成同一项统计。但一个描述提交，一个描述分批，而且来自不同测试记录。

它们仍然能提供有用信息：不同平台上，准备批次和提交工作的相对成本可能变化。理解这种差别，有助于解释为什么某项架构选择在一个平台上更值得投入。

把这些时间加起来构造一帧，则还缺少共同的场景、采样时刻和执行关系。

候选数量解释了剔除在做什么#

材料还记录过候选对象数量的下降：某个移动端案例从 50 万降到数万，PC 案例从 60 万降到约 6 万。

这些数字描述剔除结果。它们说明后续需要处理的对象集合被缩小，却无法直接换算成提交耗时。剩余对象的网格复杂度、材质状态与分批方式，都会继续影响成本。

同样的对象数量，如果大部分共享状态，可能形成较少批次；如果状态频繁变化，准备和提交就会有另一种形态。因此，数量减少与耗时下降存在联系，但中间还有工作内容和执行方式。

静态结构能把统计接回代码#

IL2CPP 样本中可以看到按阴影、PreZ、GBuffer、Forward、透明与扭曲分类的绘制次数字段，也能看到进入原生层的 GPU 时长查询。

这些结构帮助解释程序在统计什么，却没有给出分享场景中的实际耗时。一次绘制次数与一次时间采样，是不同的数据；字段名称与 Pass 对应，也不意味着已经确认每次累加来自哪个列表。

把材料放在一起时，可以得到这样的关系：

记录数字或形式对应工作
早期方案难以稳定到 30 帧当时整套通用路径的表现
后续方案旗舰机目标 60 帧整帧设计目标

这张表保留了数字各自的主语。真正要比较优化前后，还需要回到同一场景中的时间线。

一个放弃的方案也解释了取舍#

分享材料中，还有一项没有采用的光照数据压缩方案。模型压缩能够减小数据量，但解码在部分中低端设备上持续占用 2ms 以上 GPU 时间，最终没有进入该方案。

这条记录有价值的地方，是把存储收益与运行成本放在了一起。压缩率很好，并不意味着它适合当时的帧预算；运行时持续发生的工作，可能比一次性的包体收益更影响体验。

它也不适合与另一台机器上的 1ms 提交时间直接比较。两项成本属于不同处理器、不同阶段和不同场景，真正的取舍发生在各自的产品目标里。

性能数字离开对应的工作以后，很容易变成一个漂亮结论。把主语和执行关系保留下来，读者才能理解优化究竟改变了什么，以及这份经验可以怎样帮助自己的分析。
