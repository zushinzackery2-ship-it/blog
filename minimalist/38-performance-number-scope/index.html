技术分享里的性能数字，被转述一遍之后往往就错了。不是数字错，是覆盖范围被悄悄换掉。

终末地的一次公开分享里出现过这么几组：通用路径稳定不到 30 帧；接入自研 ECS 和原生管线后旗舰机目标 60 帧；Render Path 本身约 1ms。三句话之间没有矛盾，但它们描述的是三个不同的东西——第一句和第二句是整条方案的整帧对比，第三句是单个模块的一段路径。合成一句「渲染优化到 1ms」，就同时改掉了主语和范围。

这篇不是要复现这些数字——终末地的 IL2CPP 产物里没有对应的计时器，也没有分享里的测试场景。要提炼的是口径纪律：一个性能数字必须带着它覆盖的段落一起说，否则它在下一次转述中一定会变形。

帧率描述整条链，不描述模块#

早期实验套用引擎通用路径，只做简单排序，结果是难以稳定到 30 帧。后来换成一整条链——自研 ECS、连续内存、多线程剔除、一次排序、原生管线——旗舰机目标 60 帧，单帧预算 16.66ms。

30 到 60 这个提升属于整条链。加载、剔除、排序、绑定、跨语言调用各贡献多少，没有分项采样。任何把这个提升归给其中某一项的说法，都是替原材料补了一个它没做的实验。

16.66ms 也不是某个模块的配额，它是整帧上限，还要分给角色、阴影、后处理和玩法。分享里单独划过一刀：留给 CPU 遮挡和剔除的只有零点几毫秒。软件遮挡本身不是新想法，贵的是把它压进这个预算——深度图构建要和视锥、LOD 并行，图的是线程之间不留空等。

四格之和不等于 16.66ms：它们的测试上下文不同，不是同一次采样的分解

图里四格并排，但不能相加。它们不是一次采样的分解，是不同场景、不同机型下各自给出的案例。并排只是为了标清各自覆盖哪一段。

1ms 只覆盖提交路径#

原话是：这套架构把两端 Render Path 本身的 CPU 开销压到约 1 毫秒。紧接着有一句补充：这只是其中一个模块，排序和分批另有开销。

两个限定词都在原文里。「两端」指移动端和 PC 各一份案例，不是所有机型；「本身」把范围锁在提交路径，不含剔除和排序。把 1ms 写成整帧结论，和原文直接冲突——不是过度概括，是与原文相反。

另一场整理给过分批的数字：Android 约 3ms，PC 约 1ms。这个 1ms 和上面那个 1ms 不是同一段。 移动端上分批可能比提交更贵；PC 上两段碰巧都落在 1ms 附近，仍然要分开记。数值相同最容易诱发合并，这里恰好是最该拆开的地方。

托管层对不上这两段毫秒，因为计时在原生实现里。托管侧能看见的是一份绘制次数统计和一个 GPU 时长取值：

六个字段的语义类别与阴影、PreZ、GBuffer、Forward、透明、扭曲各个 Pass 对齐。但要说清一件事：当前调用图没有证明每个字段由某个具体的列表句柄累加。字段名对得上 Pass 分类，不等于计数来源已确认——这和上一篇讲的是同一个问题。

GPU 时长和路径开关的 getter 都转入原生层，托管统计对象本身只保存次数与采集开关。dump 里也没有 1ms、3ms、16.66ms 这些常量，没有和分享场景对应的计时器名字。要毫秒就得自己采样，读不出来。

压缩比描述剔除结果，不描述提交耗时#

分享给过两组候选到实画的压缩比：某款移动芯片上 50 万候选压到数万；PC 上 60 万压到约 6 万。压缩发生在视锥、LOD、软件遮挡之后，排序之前。

这两个数字很容易被拿来推「达到 1ms 需要压到多少条」。这个推理不成立：对象复杂度、材质状态、硬件、分辨率、提交模式都会改变每条 draw 的成本。同样的条数在不同材质分布下能差好几倍。

能确定的只有口径关系——候选数量描述剔除的结果，1ms 描述提交的耗时，两者之间没有可外推的换算。

托管层在这里也只能看到一半：剔除前把参数和视角句柄交给原生，建列表时再传标志、光照模式和层掩码，收回一个 u32 句柄。句柄背后有多少条 draw、键上还剩多少对象，托管侧没有计数器。能看见压缩之前的入口，看不见压缩之后的条数。

把口径写成表#

这是最实用的一步：每个数字配一列「不能当成什么」。

口径数字覆盖范围不能当成
早期通用路径稳定不到 30 帧引擎通用 Render Path，只做简单排序某一次 draw 的耗时
接上整条链旗舰机目标 60 帧ECS、连续内存、多线程剔除、一次排序、原生管线一起上所有机型的保底帧率
单帧预算16.66ms60 帧的整帧上限某个模块的配额总和
CPU 遮挡 / 剔除零点几毫秒软件遮挡加视锥、LODRender Path
Render Path约 1ms移动端与 PC 案例的提交路径本身整帧；不含排序和分批
批处理移动端约 3ms，PC 约 1ms另一场整理给出的分批开销和上一行同一个 1ms
剔除压缩50 万→数万；60 万→约 6 万移动芯片与 PC 各一份案例提交耗时
托管绘制统计六类次数阴影 / PreZ / GBuffer / Forward / 透明 / 扭曲1ms 或 3ms

「不能当成」这一列是表格的重点。只写覆盖范围，读者仍会自己去合并；把常见的误读预先否掉，转述时才不容易走形。

角色面数一类的资产约束是另一组内容，描述的是场景规模，不是帧时间。它既不能单独解释通用路径的瓶颈，也不能用来推导提交耗时。

没被采纳的方案也要标价#

有一笔取舍没进上面的表：用模型去压光照数据和包体，压缩率和工作流都过得去，但运行时解码在部分中低端设备上要持续吃掉 2ms 以上的 GPU，最后没有装上。

这条值得单独记，因为否决理由本身是性能信息。它告诉后来的人：这个方向已经量过，卡在运行时解码的持续成本上——不是没想到，是想到了并且付不起。没有这条，同一个方案会被重新提出、重新实现、重新否决一遍。

同时这个 2ms 也不能和前面的数字比。它和 Render Path 的 1ms、遮挡的零点几毫秒来自不同模块、不同测试上下文，谈不上「谁更值」。这里能表达的取舍只有一句：持续的运行时解码成本没有被接受。

边界#

这些数字是特定场景、特定机型上的案例，不是可以外推到所有大世界项目的基准。能从静态样本复现的只有三样：口径对应到哪一段路径、六类 draw 怎么数、开关打开后热路径进哪一层。毫秒要自己采。

真正可迁移的是说法本身：说帧率时写整条链，说 1ms 时写提交，说压缩比时写剔除，说 3ms 时写分批，说托管统计时写次数。 混在一句里，缺口不会消失，只会转移到读者的理解里——而那时已经没人能发现它。
