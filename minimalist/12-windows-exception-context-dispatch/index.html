Windows 异常机制：执行现场的分发与恢复

程序命中断点后暂停，调试器显示寄存器与调用栈；按下继续，线程又从暂停处运行。这个日常操作包含了 Windows 异常机制最有用的特性：系统把执行现场交给处理链，处理完成后，还可以按选定的现场恢复线程。

访问违规、软件断点和硬件单步会产生不同的异常记录，但它们都借助这条分发过程进入用户态。理解它们的差异，首先要把“发生了什么”与“线程当时处于什么状态”分开。

异常记录与线程上下文互相补充#

异常记录保存异常码、异常地址和附加参数。访问违规的参数能够说明读、写或执行访问，以及涉及的地址；软件断点则以另一种异常码进入处理链。

线程上下文保存寄存器状态。在 Windows x64 中，RIP 指向执行位置，RSP 表示栈位置，通用寄存器保存参数与中间值，EFlags 和调试寄存器则与单步、断点状态有关。

二者结合后，一次异常才变得具体。同样是 EXCEPTION_SINGLE_STEP，可能来自 Trap Flag，也可能来自某个硬件断点。异常码指出事件类别，DR6、命中地址和追踪器当前状态共同说明这次事件的来源。

Guard Page 则有独立的 STATUS_GUARD_PAGE_VIOLATION，不能只因为它涉及内存访问，就按普通访问违规处理。

调试器先得到一次机会#

附加调试器时，异常通常先以 first-chance 事件交给调试器。调试器可以处理它，也可以选择让进程自己的处理器继续判断。“首次机会异常”因此并不意味着程序即将崩溃，很多异常会在后续代码中正常处理。

进入进程内的分发后，VEH 先于常规栈式 SEH 处理器获得机会。VEH 是进程级的处理器列表；SEH 则与当前线程的栈帧和代码作用域相联系。这解释了二者常见的分工：前者适合统一观察调试事件，后者适合由了解局部状态的代码处理错误。

顶层异常过滤属于用户态未处理异常路径。UnhandledExceptionFilter 与应用通过 SetUnhandledExceptionFilter 安装的回调，受调试器是否存在、启动包装与异常路径影响，不能固定排在 second chance 之后。当用户态仍未处理异常时，调试器才可能得到 second-chance 机会；再未处理，便进入终止或系统错误处理。

主要关系可以写成：

调试器参与之后，一些异常甚至不会到达进程内的处理器。反调试逻辑常利用的，正是这种可观察的分发差异。

处理结果改变了后续路径#

VEH 常见的返回值是 EXCEPTION_CONTINUE_SEARCH 和 EXCEPTION_CONTINUE_EXECUTION。前者继续寻找处理器，后者表示当前异常已经得到处理，可以尝试恢复执行。

SEH 中还存在执行处理块的选择。它会进入相应的展开和处理过程，与直接按原上下文恢复是不同的控制流。

上下文也会沿处理过程传递。某个 VEH 修改后选择继续搜索，后续处理器仍可能看到并使用修改后的现场；并不是只有修改者自己返回继续执行，修改才有机会生效。最终采用什么状态，取决于后续处理结果。

恢复还要求异常本身允许继续。如果异常被标记为不可继续，强行返回继续执行会引出新的异常。RIP 能被修改，只说明处理器可以影响执行位置，并不意味着任意位置都拥有正确的栈、寄存器和程序状态。

断点恢复是在安排下一次执行#

软件断点会改变原指令所在的字节。调试器命中后，通常要恢复原指令，按断点类型处理指令指针，让原指令获得一次执行机会，再重新布置断点。这里同时存在代码字节与线程现场两份状态。

执行硬件断点通常在目标指令执行前报告命中。若恢复后仍立即满足同一个断点条件，就可能再次触发。追踪器会通过调整观察槽位，或按架构语义使用 RF 等方式安排恢复。数据断点与执行断点的报告时机又有所不同，不能共用对“当前指令”的同一种解释。

Guard Page 具有一次性触发的特点。访问使系统清除 guard 状态后，原指令才有机会继续。如果在重试前立刻给同一页重新加上 guard，访问可能反复命中。因此，持续监控常把恢复页面保护安排在后续单步点；这期间其他线程也可能访问该页，记录就未必覆盖每次访问。

这些机制真正的共同点，是把下一次执行安排好。异常回调里的几处寄存器修改，会决定线程继续运行、重复命中，还是转到另一个处理位置。

控制流追踪利用的是有限的停顿#

DR 与 VEH 组合时，可以先把少量候选入口放进调试寄存器，让基本块内部正常运行。命中后，处理器读取现场，记录到达的位置，再布置下一组观察点。

这种组织减少了相对于逐指令单步的异常次数，但一个入口命中仍然只是一次观察。若中间发生异常转移，或被调用函数没有正常返回，原先预测的后继就可能失效。追踪状态需要随实际事件更新，才能让记录的路径保持可解释。

异常处理本身也会改变运行时序。高频输出、重型符号解析和争用锁会放大停顿，所以实际追踪器通常只在现场保存必要信息，把后续整理移到正常执行路径。

对异常机制的理解最终会回到最初那个断点：暂停时得到的既是现场，也是恢复所依据的状态。分发过程决定谁能解释它，恢复过程决定线程怎样从这里继续。
