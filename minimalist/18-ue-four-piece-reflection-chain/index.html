四件套定位：GNames 解析名字，GObjects 登记对象，GWorld 给出场景上下文，ProcessEvent 执行函数调用协议。按顺序串起来，就能从名字定位对象，再进入场景，再发起任意 UFunction 调用。

四件套是什么#

UE 逆向里常说的四件套——GNames、GObjects、GWorld、ProcessEvent——对应四条必须运行时恢复的全局链路。这些符号是目标进程里真实存在的全局入口，而非源码里的类名：

组件全局入口职责
GNamesFNamePool 或 TNameEntryArray把 FName 索引解析成可读字符串
GObjectsTUObjectArray / FUObjectItem 数组全局枚举对象、校验对象索引
GWorld.data 段指向当前 UWorld 实例的指针进入当前运行场景
ProcessEventUObject 虚表中的反射调用函数发起任意 UFunction 调用

数据依赖顺序：GNames 解析对象名字 → GObjects 枚举并索引对象 → GWorld 进入场景 → ProcessEvent 发起函数调用。每一步都是先定位全局符号，再恢复它指向的结构布局。

1. GNames：名字池入口#

GNames 是 UE 里 FNamePool（新版）或 TNameEntryArray（旧版）的全局实例。逆向工程里把它放在第一位，是因为它是所有名字的根：没有 GNames，FName 就只是一个无意义的整数索引。

GNames 定位#

GNames 的定位方式随版本不同有两条路径：

  • 旧版 TNameEntryArray：搜索代码段中引用 InitializeSRWLock/RtlInitializeSRWLock 且附近出现 "ByteProperty" 字符串的构造函数，再通过 lea rcx, [GNames] / call Constructor 模式（签名 48 8D 0D ? ? ? ? E8）反推出全局数组地址；
  • 新版 FNamePool：扫描可写内存，找第一个包含 None、ByteProperty、IntProperty 等已知名字的 chunk，确认 FNameEntry 头大小和 stride 后，再在可写节中找指向该 chunk 的指针并回推 FNamePool 基址，同时验证 MaxChunkIndex、ByteCursor、ChunksStart 等布局。

无论哪条路径，最终目标都是拿到 GNames 的模块偏移，以及把 ComparisonIndex 拆成 chunk + index 的规则（默认块偏移位 0x10，即每块 64K 个条目）。

FName 字段恢复#

FName 本质是 GNames 里某个条目的索引句柄，而非字符串。逆向时不需要依赖源码里的类型名，只需从对象内存中恢复字段布局和大小。

运行时从对象身上取下 Name 字段的内存，按以下规则恢复 FName 布局：

模式大小字段布局
默认8 字节ComparisonIndex + Number
WITH_CASE_PRESERVING_NAME12 字节ComparisonIndex + Number + DisplayIndex
FNAME_OUTLINE_NUMBER4 字节只有 ComparisonIndex，实例号另存在 NamePool 条目中
两者同时开启8 字节ComparisonIndex + DisplayIndex

判断逻辑是运行时推断：先通过 UObject::Name 与相邻字段（Class 或 Outer）的间距估算 FNameSize，再抽样检查对象名字里 Number 落在 [1,4] 区间的比例，以及 ComparisonIndex 是否等于 DisplayIndex，最终确定当前进程是哪种 Name 布局。UE5.7 等版本还需要再用一个已知属性（如 PlayerStartTag）的实际大小做一次后校正。

名字解析#

GNames 就位、FName 布局确认后，FName::ToWString() 就能按 ComparisonIndex 拆出 chunk + index，从 GNames 对应条目中读出原始字符串。如果是 FNAME_OUTLINE_NUMBER，实例号要从 NamePool 条目中单独读取；否则按 Number 追加 _0、_1 等实例后缀。

所以 GNames 在四件套里承担的是名字语义层：它让后续 GObjects 里的对象枚举、类名匹配、UFunction 名字查找都成为可能。

2. GObjects：对象登记表#

源码里叫 GUObjectArray，逆向工程里通常直接叫 GObjects。实际分析时不依赖这个源码类名，只关心它在内存中的布局：一个指针/分块数组，元素是 FUObjectItem，每个 item 里有一个对象指针和若干元数据。

FUObjectItem#

GObjects 定位与 TUObjectArray 形态#

GObjects 自身是一个 TUObjectArray 全局实例。常见做法是先在 .data 段搜索候选地址，再验证它是否符合已知的固定/分块布局：

  • 固定数组（UE4.11–4.20 默认）：FUObjectItem* Objects，字段为 Objects / MaxObjects / NumObjects；
  • 分块数组（UE4.21+ 默认）：FUObjectItem** Objects，字段为 Objects / MaxElements / NumElements / MaxChunks / NumChunks，另有 Back4Blood、Multiversus、MindsEye 等非标布局。

验证约束包括：NumElements < MaxElements、MaxElements 上限、NumChunks 范围、每块元素数对齐、各 chunk 指针可读等。固定数组还会额外验证 ObjectsButDecrypted[5].Object 的 Index 字段等于 0x5。

一旦确认，记录 GObjects 的模块偏移或绝对地址，后续 GetByIndex(Index) 就按对应公式取 FUObjectItem->Object。

UObject 关键字段偏移#

逆向时通过运行时扫描恢复每个字段的偏移，而不是直接套用源码头文件：

字段恢复方法
Vft对象首地址通常就是虚表指针
Flags在多个对象内存中统计常见标志值，确认稳定偏移
Index抽取已知数组下标对象，验证对象内存中的索引值与数组位置一致
Class寻找可读 UClass 指针，并用类对象自指/继承链特征交叉验证
Name排除已定位字段后，寻找可按当前 FName 布局解析的位置
Outer寻找指向其他 UObject 的有效指针，并排除 Class、Index 等已知字段

3. GWorld：运行时上下文#

GWorld 是一个指向当前 UWorld 实例的全局指针。UWorld 本身也是一个 UObject，同样被 GObjects 登记。在四件套里，GWorld 提供“当前场景”的语义入口。拿到 GWorld，就拿到了正在运行的 UWorld 实例，进而可以访问 OwningGameInstance、PersistentLevel、Actors 等场景对象。

GWorld 定位#

GWorld 定位不依赖硬编码地址，而是在 .data 段扫描一个指向 UWorld 实例的全局指针槽位：

  1. 先从 GObjects 里收集所有对象地址并排序；
  2. 在 .data 段按指针宽度遍历，读取每个槽位的值；
  3. 检查槽位值是否落在已收集的对象地址集合中，再读取对应对象的 Class 和 Flags，验证它确实是一个 UWorld 实例而不是 ClassDefaultObject；
  4. 对通过验证的候选槽位做 16 次稳定性读取，选出值不变的稳定槽位，记录其模块内偏移作为 GWorld。

4. ProcessEvent：反射调用的执行入口#

逆向视角下，ProcessEvent 是目标进程 UObject 虚表中的函数指针，不需要外部实现。核心任务是定位它的虚表索引和模块偏移。

UFunction 的最小字段#

逆向时不需要恢复 UFunction 的完整源码布局，只需要两个关键偏移：

FunctionFlags 在 ProcessEvent 定位时作为特征码使用；ExecFunction 缓存了目标函数的 native C++ 函数指针，对应源码里的 Func。返回值通过遍历 UFunction 的属性链，找到带 ReturnParm 标志的属性来确定。

ProcessEvent 虚表索引定位#

ProcessEvent 的定位有两条路径：

  1. 主路径：虚表扫描 + 特征匹配

    取 GObjects[0] 的虚表，遍历每个槽位，检查函数体前 0x400 字节内是否出现 FunctionFlags 访问模式，并且前 0xF00 字节内出现 native 标志访问模式。匹配到的槽位即为 ProcessEvent。

  2. Fallback：字符串定位

    如果虚表扫描失败，搜索字符串 L"Accessed None"，找到它所在的函数，再取下一个函数起点作为 ProcessEvent 候选，回虚表里确认索引。

native 函数标志与参数结构#

调用时，如果目标函数带 Native 标志，会临时把 FunctionFlags |= 0x400，调用完成后再恢复。这是为了让某些对 native 标志敏感的 ProcessEvent 路径能正确分发。参数结构需要按函数属性链布局，返回值/输出参数如果涉及 FString、TArray 等游戏内存类型，需要在作用域结束时正确释放。

5. 四件套如何串成一条链#

从逆向工程视角看，四件套不是源码里的类名，而是四条必须恢复出来的运行时信息：

组件全局入口作用
GNamesFNamePool / TNameEntryArray把 FName 索引解析成可读字符串
GObjectsTUObjectArray / FUObjectItem 数组全局枚举对象、验证 Index
GWorld.data 段指向当前 UWorld 实例的稳定指针槽位进入当前场景上下文
ProcessEventUObject 虚表中的反射调用函数发起任意 UFunction 调用

数据依赖顺序：GNames 解析对象名字 → GObjects 枚举并索引对象 → GWorld 进入场景 → ProcessEvent 发起函数调用。

这些步骤都不是依赖源码硬编码，而是运行时推断或扫描。FName 大小由对象字段间距和 NamePool 内容推断；GObjects 由 .data 段指针和数组元数据验证；GWorld 由全局指针槽位扫描并确认指向 UWorld；ProcessEvent 由虚表特征匹配或字符串 fallback 定位。

6. 结论#

名字解析、对象枚举、场景入口、函数调用这四个能力首尾相接，就是一条可直接操作的反射链：GNames 把 FName 索引解析成可读名字，GObjects 让对象可被全局枚举和索引校验，GWorld 把对象链接入当前场景，ProcessEvent 则让任意 UFunction 能被外部调用。

需要强调的是这四步都不靠源码硬编码，而是运行时推断出来：FName 大小由对象字段间距和 NamePool 内容推断，GObjects 由 .data 段指针和数组元数据验证，GWorld 由全局指针槽位扫描并确认指向 UWorld，ProcessEvent 由虚表特征匹配或字符串 fallback 定位。
