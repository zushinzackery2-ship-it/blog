资源目录里有一个 Base64 文件，看起来很像索引，很容易让人以为加密入口就在这里。拿它去试 key、换 counter，怎么调都对不上，因为终末地的 VFS 读取根本不从这个文件开始：调用链先算出一个哈希路径，再去读那里的 .blc。

这是外层分析的第一处转折，也定下了后面的做法：文件看起来像什么不重要，程序实际从哪里读、读完交给谁，才决定该解哪份数据。总览把保护分成两层，外层负责把文件字节交出来，这一篇只走这一层。文中 RVA 均对应初次资源分析所用的 Windows x64 GameAssembly.dll。

GetVFSBlockHashPath 这一步说明了前面为什么一直对不上：真实输入是哈希路径下的 .blc，而 index_main.json 属于另一条清单链。输入选错了，在它上面调 key 或 counter 只会制造更多无效组合。

解密由 XXE1 完成。类名经过混淆，看不出用途，成员却暴露得很彻底：32 字节 key、12 字节 nonce、16 个 uint32 状态、sigma/tau 常量、64 字节工作块，以及一个 QuarterRound。再对一下轮结构，就能认定这是 ChaCha20。算法确定之后，剩下的问题只有三个参数从哪里来。

key：让指令决定是哪种运算#

公共 key 由 GetCommonChachaKeyBs 生成。它拼出一段 Base64，解码后和一个解锁串一起送进 Beyond.Security.IOOO000iiI 做字节变换：

这种“密文加一段字符串”的结构，最容易让人凭经验猜成异或。加、减、异或都像简单混淆，得出的 key 却完全不同，所以这里不猜，直接看内层 _IIiiIIIoO（0x2F800B0）的循环：两边各取一个无符号字节，执行 sub，写回低八位。

指令只能说明程序这么算，这组 key 对不对，还要等索引自己来验。

nonce 与 counter：参数写在协议里#

.blc 的前 12 字节按小端读作 uint32 protocol = 3 加 uint64 seed，这 12 字节就是 nonce，ChaCha20 处理的载荷从偏移 12 开始，载荷末尾则是解密后索引内容的 CRC32。nonce 和校验值都放在文件里，不需要从别处推。

初始 counter 也不必猜。DecryptCreateBlockGroupInfo 在 0x3076C52 执行 mov r9d, 1，紧接着在 0x3076C62 调用 XXE1 的构造函数。这个 1 应该和 protocol 一样当作协议的一部分记下来。

有了索引自带的 CRC，就可以把相近的假设一次排除干净。在 0CE8FA57.blc 上，我把四种 key 处理（Base64 原始字节、逐字节加、异或、减 unlock）和 counter 0、1、2 两两组合，12 种里只有“减法 + counter 1”通过，正好是指令给出的那一组。它解析出组名 InitBundle，存储 CRC 与计算 CRC 都是 2FD48B5F。为排除自写实现本身的错误，又用 PyCryptodome 跑了同一组输入，密钥流逐字节相同。

这一步的价值在于预期值来自客户端，不是分析者自己定的。指令给出候选，客户端保存的 CRC 做裁判，两边从不同方向指向同一组参数。

以 BundleManifest 组的 manifest.hgmmap 为例：它登记在 1CDDBF1F.blc，长度 46,497,641 字节，ivSeed=285540354 构造出 nonce 030000000200051100000000。解密输出的 MD5 为 F38E756A02A85B3EDDC7711B4C9AF654，和记录一致；再用 Brotli 展开，得到 137,816,398 字节。

索引用 CRC 核对，文件用 MD5 核对，Brotli 能完整展开说明内容已经可以进入下一步格式处理。三道检查沿客户端自己的处理顺序依次接力，任何一个参数错了都会在最近的那一道停下。

文件交付之后#

回头看，这一层能顺利收束，靠的是三个可以搬到别的目标上的习惯。输入以调用链为准，不以文件长相为准，开头那个 Base64 文件就是反例。参数能从指令里读出来的就别枚举，sub 和 mov r9d, 1 各自省掉了一整片猜测空间。验证要用程序自己保存的校验值，CRC 和 MD5 是客户端写下的预期，比任何“看起来解对了”都可靠。

但文件层结束不等于资源可读。encrypted=false 的记录由外层原样交出，InitBundle 最小包的 MD5 也能对上，里面却仍是定制 Bundle。下一篇从这个小包的头和目录出发，说明它怎样变成标准 Unity 对象。
