一张能正常打开的贴图，只证明字节被解释成了图像。它可能来自错误的 draw，可能采用了不同的采样视图，也可能只保存角色外观中的一层输入。

运行态提取中，最费时间的往往是把这些问题混在一起处理：颜色不对就交换通道，图案错位就翻转 UV，亮度不足就再乘一个系数。局部看起来接近了，整条转换链却越来越难解释。

更有效的分析顺序是先确认资源来自哪里，再确认字节怎样变成采样值，最后还原着色器怎样使用这些值。快照、像素和外观属于不同阶段，需要各自的证据。

同一把锁未必对应完整的一次 draw#

图形状态通常由多次调用逐步设置：切换着色器，绑定纹理和常量，设置输出，最后发起绘制。若只在任意 API 边界暂停，可能恰好停在切换中途。

此时着色器已经属于下一趟 draw，某些输入槽仍保留上一趟的资源。它们分别都有效，组合起来却从未参与过真正的绘制。仅凭着色器名称和渲染目标大小，很容易接受这份混合状态。

原始记录中，资源身份的分布帮助区分了稳定候选与过渡状态。它适合筛选和发现问题，但要形成可回放的输入，还需要把观察关联到实际 draw：确认事件位置，并在资源被覆盖之前保存该事件使用的数据。

CPU 侧的一把锁可以保护抓取代码自己的状态，不能自动冻结 GPU 执行。资源副本的时序、命令顺序和完成同步仍然需要单独成立。

同理，逐个请求纹理槽也可能跨越多个事件。纹理、采样器和常量来自同一绘制事件，后续计算才有一致的输入。若保存的是 draw 之前的渲染目标，它表示已有内容；验证 draw 的输出则需要对应的执行后状态。

资源身份与资源内容都要能追溯#

提取入口可以沿 GameObject、Renderer、Material 到 Texture2D。CPU 副本仍在时直接读取，副本已释放时再从图形资源读回。这条对象链帮助确定归属，图形 API 中的绑定则说明资源在某次绘制中的用途。

地址只在相应生命周期内有意义。对象销毁后地址可能复用，同一纹理也可能被逐帧改写。因此，离线分析还需要事件编号、资源描述和所保存内容的对应关系。

这篇文章所依据的 Unity 构建与模型提取篇一致。该构建中取得的对象布局，与这次绘制时实际绑定的资源，共同构成后续分析的起点。

存储格式与采样视图决定了数值含义#

GPU 资源的字节布局和着色器看到的数值不是同一层描述。TYPELESS 资源可以配合不同类型的视图；sRGB 视图还可能在采样时完成颜色解码。只保存底层格式，离线程序就可能漏掉或重复一次转换。

打包格式也不能按普通 RGBA 字节拆分。例如 R10G10B10A2 与 R11G11B10 的分量位宽、数值解释都不同。读回时的行跨度还可能包含填充，不能总用宽度乘像素大小定位下一行。

3D LUT 则提供了一个容易忽略的例子：着色器按宽、高、深采样，CPU 数组可能按深、高、宽排列。只用灰色测试时，三个分量相同，轴序错误也不显眼；使用非对称的颜色输入，才能区分这些排列。

翻转应由像素对应关系决定#

贴图经过读回、图像编码和引擎导入时，会遇到不同的行序与 UV 约定。是否需要翻转，取决于这条具体路径，不能仅凭引擎名称判断。

一个上下不对称的测试图能提供明确证据：标记四角，确认文件第一行对应哪个角，再检查目标采样路径的 v=0 落在哪里。这样才能分清变化发生在字节排列、导入过程还是采样坐标上。

全白底图和对称纹理不适合做这项验证。它们在翻转前后几乎相同，很容易让错误进入后续颜色分析。

确定对应关系后，可以选择一个边界统一行序，并记录这次转换。若文件已经翻转，着色器又使用 1-v，两个修正会互相抵消。模型的原始 UV 与图像编码约定分别保留，后续才容易判断哪一处需要变换。

角色颜色可能来自多份输入共同合成#

一些 toon 材质的底图接近白色，最终颜色主要由运行态调色板与遮罩决定。此时反复调整底图解码，并不能恢复角色外观。

同一样本的染色遮罩按 z → y → x → w 顺序参与合成。若使用的是逐层插值，顺序会改变结果，不能把几个通道随意重排成看起来熟悉的 RGBA 顺序。这些都是该着色器的具体语义，而非 Unity 材质的通用规则。

颜色空间也要沿数据流确认。sRGB 纹理可能已经由视图解码，上传的材质常量可能已经是线性值。再通过会执行颜色转换的属性接口传入一次，就可能重复转换。关键是确认每次转换发生在哪里，而不是仅凭属性叫 Color 还是 Vector 作判断。

通道矛盾意味着证据还没有对齐#

旧记录里有一个值得重新审视的判断：反汇编使用 alpha，但导出图的 alpha 接近常量，green 却含有空间变化，于是改用 green 复刻。

这个观察只能证明现有材料之间存在矛盾，尚不足以证明 green 是正确通道。可能的原因包括抓错资源、视图解释不同、压缩解码错误、采样前后的通道重排，或分析了另一种着色器变体。

即使替换通道后局部观感改善，也不能排除这些原因。需要回到同一事件的资源绑定与实际采样值，确认着色器究竟读到了什么。在这条关系闭合之前，应保留矛盾和未确定状态，避免把试出来的结果写成已经确认的规则。

这个例子也解释了为什么最终截图不能独自承担验证。多个错误可能相互抵消，得到接近的颜色；一旦更换材质或视角，抵消关系就消失了。

贴图与着色共同组成角色外观#

贴图可以保存底色、遮罩和查找表，却无法单独保存随视角变化的 MatCap、高光和轮廓光。若目标是复现运行态外观，这些部分仍要由相应的着色计算产生。

因此，一份可解释的提取结果，应能从最终像素追溯到对应事件，再追溯到纹理、常量、采样方式与着色器。抓取负责取得一致输入，解码负责恢复采样数值，坐标转换负责像素对应关系，着色器负责组合外观。

这些关系把最终颜色接回了具体输入。纹理翻转、重复颜色转换和错误通道即使都表现为画面异常，也能沿不同的数据路径找到原因。
