本文同样把已知的 Unity GameObject 作为输入，不讨论对象发现。先从组件槽取得 Renderer，由 Renderer +0x148/+0x158 读取材质 InstanceID 数组，再进入 Material 的属性表取得 Texture2D 引用。角色贴图随后分成两种来源：CPU 侧 provider 还在时直接跨进程读取；provider 为空、像素只在显存时，抓某趟 draw 从 GPU 读回。第二种来源的抓取时序、格式解码、行序方向和运行态染色都会静默出错。

本文不只讨论做法，也给出本次目标构建实际使用的资源链偏移和着色器寄存器映射。它们与模型篇使用同一份二进制 profile，只对该指纹成立；换版本必须重新从符号、反汇编和运行态探针闭合。

处理这类提取，有几条纪律反复被验证：

  • 抓取要在同一快照里原子完成，并按输入资源身份筛掉状态切换的过渡窗口；
  • 解码要分清资源格式和视图格式，打包格式按真实位布局解，单通道不广播；
  • 行序在 GPU 读回、图像文件、引擎采样之间只在一个编码边界归一化一次，不改 UV、不靠观感；
  • 很多角色材质的颜色根本不在贴图里，要反汇编像素着色器，用运行态材质值复现染色。

下面按抓取、解码、方向、颜色四段展开。

贴图的两类来源决定要不要抓 GPU#

如果纹理的 CPU 侧 provider 还在，跨进程读内存直接拿到像素即可，这条路和读网格顶点没有本质区别，不需要注入。真正需要抓 GPU 的是另一类：provider 已被释放、像素只存在于显存的纹理。这时要用一段最小的注入代码，在渲染时抓某趟 draw 绑定的资源读回。抓取本身的麻烦，几乎都集中在这条路上——它要在一个只能锁到 API 调用边界的环境里，拿到一份属于同一趟 draw 的、自洽的资源集合。

锁停在 API 边界，会命中状态切换的中途#

一趟 draw 的绑定是若干次 API 调用累积设置的：设着色器、设若干输入资源、设渲染目标、设常量，最后发起 draw。在只能锁到调用边界的前提下（例如 hook 住渲染上下文），锁抓到的是其中某一次调用后的瞬间。如果这一瞬间落在“着色器和渲染目标已设、输入资源还在从上一趟往本趟切”的中途，快照里的着色器和渲染目标是新的，输入资源却还是旧的。

问题的根源是：着色器和渲染目标是粗粒度特征，它们在过渡窗口里也成立。只用“等到目标着色器和目标渲染目标同时出现”做门控，就会把过渡窗口的快照也当成命中。把这件事量化会更清楚：对一个粗粒度门控做大量抽样，命中往往落成少数几个不同的资源身份簇——多数命中属于一个主簇，少数属于输入资源不同的过渡簇。两个簇的着色器和渲染目标完全一样，只有某个输入槽绑定的资源身份（格式、指针）不同。只用粗粒度门控，这些命中会被当成同一种，混进过渡簇的数据；而过渡簇的输入不属于目标 draw，用它回放就会错。

用输入资源身份做二次筛选#

修复是在候选报告层再加一层筛选：显式要求某个输入槽绑定的资源身份等于预期值，命中主簇才落盘，命中过渡簇计入被拒绝计数。这层筛选发生在报告层，不改变抓取本身。

与此相关的还有一条：渲染目标里的内容是快照那一刻已经存在的旧数据，不是接下来那趟 draw 的输出——拷贝发生在 draw 之前。所以不能把轮询到的渲染目标内容当成同趟 draw 的输出真值。能作为回放输入的，只有那些和绑定身份来自同一把锁、且通过资源身份二次筛选的输入资源、采样器和常量。这里的通用判断是：命中条件必须落在能唯一区分目标的资源身份上，而不是那些在过渡窗口里也成立的粗粒度特征。

常量和贴图必须来自同一快照#

比“抓对一趟”更深的一层是集合的时刻一致性。抓一组绑定资源时，逐槽单独请求是不可靠的：一个槽一次快照，彼此隔着毫秒和许多次 draw，拼出来的“一组”其实来自不同时刻。每条单看都真，合起来不自洽，而且没有任何单槽字段能暴露这件事；事后重读某个槽也救不了，那是又一次新快照。

正确做法是一次原子抓下整个窗口：用一次调用把目标范围内的槽同时取出，并且门控要在同一把锁里、在任何拷贝之前判定，不满足条件就零拷贝返回。让代数成立的那组常量，和参与运算的贴图，也必须来自同一快照——若它们是分别抓的，即使各自都真，代数也不成立，因为可能有多趟 pass 复用同一批资源槽而常量各不相同。把常量和贴图在同一快照里一起抓（给窗口请求带上常量读取），或者把门控收紧到能唯一锁定目标那趟，是让反解结果可信的前提。门控条件的选择也有讲究：不要用某个“边长恰好等于某值”这类本应由分析确定的特征当门控——那是发现，不是重试条件，拿它当门控会把一次发现变成死循环。

抓到的变换未必是你要的那个杠杆#

抓到一个资源，不等于它就是你要的那个杠杆。一个常见的错误预期是：既然抓到了输出级的某个变换（例如一张颜色分级 LUT），把它套到离线渲染上就该对齐。但这类变换很可能是压暗曲线或只在特定输入域成立的映射，直接套上去会把结果推到近黑，画面显著变差而不是变好。

所以拿到一个资源后，先验证它到底做了什么，而不是假设“抓到即可用”。验证手段可以很直接：用已知的极端输入（例如颜色立方体的八个角）喂进去，看输出是否落在预期的原色分级上；用可解析的反解确认残差足够小，说明数值本身可信。确认它是压暗而非增益之后，结论就变成“缺口在这个变换的上游”，排查方向也随之改变。这类负结果本身是有价值的：它排除了一整条“继续调这个变换”的岔路。反解和取均值时还有几条纪律：非线性变换要先转换再平均，LUT 这类曲线上 inverse(mean) != mean(inverse)；显示值是 8 位整数，反解要一并报告 ±0.5/255 对应的输入范围，如果比值的误差带比比值本身还宽，那就不是证据；输出被压到 0 或落在曲线肩部饱和区的样本没有可恢复的输入，不能用来推倍率。

解码要分清资源格式、视图格式与打包布局#

抓回来的字节要解码成像素，这里有三件容易混的事。

  • 视图格式不等于资源格式。采样器是按视图格式解码的。一个 TYPELESS 资源不带传输函数，套一个 sRGB 视图会让硬件在取值时线性化。抓取时要同时记录资源格式和视图格式，两者不一致时如实报告，不要只留一个。
  • 打包格式按真实位布局解。像 R11G11B10、R10G10B10A2 这类打包格式，若先 reshape 成带通道轴的形状再 view 成整型，最后一个轴会把几个字节塌成一个整数，凭空多出一根长度 1 的轴，下游所有按轴归约全部错位。打包格式要按其真实位布局解，而不是套通用的“末轴是通道”。
  • 单通道格式不要广播。A8 之类单通道纹理采样时硬件返回 (0,0,0,a)，值只在 alpha。如实解成 (0,0,0,a)，不要广播到 RGB——广播会凭空造出一个着色器从没采样到的值，正好是这类静默错误的温床。

3D 纹理有两个会静默出错的坐标约定#

以 3D LUT 这类体数据为例，把它读进来时有两个约定弄反了在中性数据上完全看不出来，只在有色数据上才错。

第一是轴序。红/绿/蓝分量分别索引纹理的宽/高/深，而解码后数组的轴顺序往往是（深, 高, 宽, 通道）。于是颜色 (r, g, b) 要按 volume[b, g, r] 取。弄反轴序，在中性对角线（r=g=b）上取到的仍是对的，只有偏色区域才错——正好是抽查最容易忽略的形态。

第二是格子轴的映射。着色器把编码值夹到 [0,1] 后，通常再映射到纹理坐标区间（如 [0.5/N, 1-0.5/N]），落在首末格的中心。这时“输入值 → 格号”的换算是 cell = coord*N - 0.5。若直接用 (i+0.5)/N 当着色器输入，等于把纹理坐标当成了输入值，每个值偏半格。这类半格误差要靠“编码值 → 格”的正确换算消除，并写进测试，用远小于半格的阈值把反汇编字面量的舍入残差和真正的半格错误区分开。

行序在 GPU、图像与引擎之间的对齐#

纹理从 GPU 显存搬到离线文件、再导入引擎显示，会依次经过几套对“第 0 行在哪、v=0 采样哪一行”约定不同的系统。只要这些约定之间的隐式翻转次数是奇数，画面就整体上下颠倒。

这三套约定只在各自系统内部自洽，跨系统衔接时没有谁保证方向一致。以 D3D11 的 staging 读回为例，resource 的 row 0 对应着色器 v=0 一侧采样到的第一行；位图类格式（如 PNG）约定 row 0 在图片顶部；而 Unity 的 Texture2D 约定 v=0 采样图片底行。把 API 的 row 0 原样写进文件 row 0、再交给一个 v=0 在底部的引擎，同一像素的 v=0 就从“着色器的第一行”被搬到“图片底行”，净效果是一次垂直翻转。

判断这类问题，先把管线拆成若干边界，数清楚当前一共发生了几次隐式翻转，目标是让总翻转次数为偶数。实现上最稳的做法不是在中间多翻几次凑偶数，而是在一个明确的编码边界上做一次归一化，其余环节全部保持原样。关键是把三件独立的事分开，不要互相顶替。

行序属于编码边界，UV 是网格上的采样坐标应逐分量原样保留，颜色由材质与着色器决定。用改 UV（例如加 1-v）去抵消行序错配，等于把两件独立的事耦合起来，之后任何一处再出问题都无法单独定位。

方向要用可判定的审计验收#

方向不能用“看起来对不对”来判。很多纹理的内容对这种判断不敏感：近白或纯色底图上下翻转几乎看不出来；左右对称的图案翻转后仍然对称；带明确方向特征的区域可能只占一小块。更容易误导的是，主色贴图本身近白、真实颜色来自运行态材质与着色器，这时“颜色不对”会被错当成行序或解码问题，反过来又用调方向去解释颜色，两个独立问题互相套住。

方向正确性应由可判定的审计给出：对每张纹理确认引擎采样的 v=0 到底对应文件顶行还是底行，统计是否全部同向；或比较修改前后的图像，确认二者恰好相差一次垂直翻转、没有夹带其他改动。这类审计只回答“方向”，不回答“颜色像不像”，因此不会被内容观感带偏，它和 UV 的正确性也应分成两套审计各自独立通过。

颜色常常不在贴图里#

到这里，抓取、解码、方向都对了，还可能复现不出画面里的颜色——因为有一类角色材质，主色贴图本身是近白或纯白的 toon 底图，最终颜色是运行时在像素着色器里算出来的。第一步是个廉价的判定：如果对贴图做通道交换、tint 相乘、切换解码变体都无法逼近目标颜色，就说明颜色不是贴图内容，而是材质与着色器共同算出来的。这时继续在贴图上试错没有意义，方向应转向反汇编着色器。通用 PBR 查看器的默认外观不能作为颜色正确性的判据——它不会执行这套运行时染色。

编译后的着色器字节码（如 DXBC）在进程堆里以标准容器存在，全进程扫描能扫出成百上千个，但扫描无法把某段字节码归属到某个材质。归属只能从材质对象指针一路游走：渲染器持有材质数组，材质持有 shader 引用，shader 对象上带有可读的名称字段，顺着这条链才能拿到目标那一段并反汇编。特征筛选（着色器 profile、贴图数与材质槽数一致、输出目标数量）只能缩小候选，最终归属仍要靠对象指针。反汇编时还有一个静默坑：反汇编 API 常返回 NUL 结尾缓冲，不按 NUL 截断就会把文本 asm 当成二进制写出。

本构建的 Normal 像素着色器已提取到稳定证据：DXBC digest 前缀为 2949ad91d26f，profile 是 ps_5_0，使用 t0/t2/t3/t4/t5 并输出 5 个 SV_TARGET。atlas 门控量 _UVOffset.x 位于 cb1[123].x，实际计算是 uv = uv + cb1[123].x * (remapped - uv)。8 组 palette 的色槽基址依次是 cb1[28]、[38]、[48]、[58]、[68]、[78]、[88]、[98]，对应强度在 cb1[32]、[42]、[52]、[62]、[72]、[82]、[92]、[102]；mask 合成顺序由 asm 钉死为 z -> y -> x -> w。

Face 变体给出了更具体的运行态常量表。cb2 中 _MainColor_0 在字节 0x070（cb2[7]），_MainColor_R 在 0x080（cb2[8]）；_BaseColor_*_1 覆盖 0x0D0..0x100（cb2[13..16]），_BaseColor_*_R 覆盖 0x110..0x140（cb2[17..20]），_BaseColor_*_4 覆盖 0x150..0x180（cb2[21..24]），第 7 组 RGB 在 0x190/0x1A0/0x1B0（cb2[25..27]），第 8、9 组分别在 cb2[29..32] 与 cb2[33..36]，_MainColor_1..9 位于 cb2[37..45]。这些位置让离线复刻可以直接从同一 draw 的常量缓冲取值，不再靠颜色观感猜槽位。

染色复刻里必须精确复刻的三点#

调色板通常是若干组，每组对应几个色槽和一个独立强度。着色器按 UV 阈值算出一组权重，再按这些权重把色槽合成到底图上。还原时有三点错一个就会得到“接近但不对”的颜色。

第一，权重签名往往不是互斥枚举。当 UV 落在跨 tile 的区间时，同一像素可能同时命中多个权重。因此按图元拆分或缓存时，键必须是权重签名的组合（tuple），不能只存一个“组号”。第二，通道到色槽的合成顺序是固定的，必须照抄：哪个 mask 通道对应哪个色槽、以什么次序叠加，都由 asm 决定，凭直觉重排就会串色。第三，颜色乘法要在正确的色彩空间里做：贴图 RGB 一般要先从 sRGB 解到线性，乘运行态颜色后再编码回 sRGB；非颜色的 mask 通道则按原始数值归一化，不做色彩空间转换。

组数、区域级联与通道冲突#

染色逻辑还有三个地方要照抄 asm，不能凭“看起来应该是这样”去理想化。

同一套着色器，不同材质的调色板组数可能不同：有的有完整多组，有的只有一组全局调色板。如果离线复刻按 UV 区域权重去索引所有组，而某材质其实只有一组，被索引的其余组在数组里是零填充，覆盖区就会被染成黑色。这类“整片染黑”看着像贴图或 UV 出问题，实际是组数假设错了。稳妥做法是先读该材质的活动组数：只有一组时直接全局应用这一组的色槽，不再按区域索引不存在的组。

有些材质的“区域主色”不是一块块互斥的区间，而是一串按固定顺序的包含式级联：边界用包含比较，接缝处会同时命中相邻区域，未被前面区域取走的权重折回某个默认区。把它改写成整洁的互斥区间判断，接缝和默认区就会错。

还有一类需要并列记录、不能互相覆盖的证据冲突：着色器 asm 明明采样某个分量（比如 alpha），但导出的压缩纹理里该分量几乎恒定、真正带空间信息的是另一个分量（比如 green）。若照 asm 用 alpha，会得到一整片错误覆盖；用实际有内容的通道才恢复正常。正确处理是三条同时保留——asm 的采样结论不改、导出像素的通道统计结论不改、复刻按实际有内容的通道走，并明确标注这是一个已确认的例外。不能仅凭 asm 就断言实现，也不能仅凭像素统计就否定 asm，冲突本身就是结论的一部分。

线性运行态颜色被声明成 Color 会二次转换#

染色对了，还有一个颜色空间上的静默错误会让亮面发暗。运行态上传给着色器的颜色往往已经是线性值，不是可直接写到 Gamma 输出的显示色。如果在引擎里把承载它的属性声明成会做色彩空间转换的“Color”类型，这个本已线性的值会再被转一次，亮面因此塌成接近暗部的颜色。

修复是把该属性声明成向量类型、原样上传，并禁止在着色器里对它单独追加经验性提亮或 Gamma 常数。整个工程固定为线性空间：sRGB 纹理采样时解码，运行态颜色保持线性参与材质与 toon 光照，最终渲染目标再编码为显示 sRGB。判断这类问题时，先确认承载线性运行态颜色的属性有没有被声明成会二次转换的类型，比在着色器里加提亮更可靠。

最后一点和贴图无关但常被误当成贴图问题：视角相关的外观（如用视图空间法线查表的 MatCap、高光、rim）是光照项，逐帧随视角变化，必须在复刻着色器里实时算，不能烘进贴图。金属和高光区域的层次完全依赖它，缺失时会塌成一片平白，看着像“贴图不对”，其实是缺了实时光照。

边界与迁移#

这套贴图提取的边界是：抓取只保证拿到属于同一趟 draw 的自洽资源集合，解码只保证字节到像素的正确翻译，方向只归一化行序，外观复现由复刻着色器承担、不烘进贴图。可迁移的判断集中在几处：只能锁到 API 调用边界时，命中条件要落在能唯一区分目标的输入资源身份上，而不是过渡窗口里也成立的粗粒度特征；常量与贴图必须来自同一快照；抓到的变换先验证是不是你要的杠杆；解码要分清资源格式与视图格式、打包格式按位布局解、单通道不广播；行序只在一个编码边界归一化一次，不拿 UV 补偿，用审计而非观感验收；颜色不在贴图里时转向反汇编着色器，把权重签名当组合键、合成顺序和 sRGB/线性边界照抄，并检查承载线性颜色的属性有没有被二次转换。

这些点单看都不起眼，错一个就得到一个看着合理、其实不成立的结论——而且大多不会报错，只会安静地把一张“接近但不对”的贴图交给下游。
