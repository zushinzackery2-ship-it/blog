磁盘上的 UnityPlayer 有一些函数读到一半就断了：一条 call 指向段末一片全零的区域，call 后面又是一串填充字节。按静态反汇编的习惯，既不知道调用去了哪里，也不知道它回来后该执行什么。

程序运行起来却一切正常。原因是这段代码在磁盘上本来就不完整：被搬走的指令在启动时写进新分配的代码页，空白虚尾则被填上跳转入口和指针。 两者由同一个生产循环写出，外置指令执行完，再跳回原函数的续体。

这正是资源总览里归档入口附近反汇编读不通的原因。下面沿着四个问题走一遍：静态读取为什么看不见，谁在什么时候写入，一次受保护调用怎样执行，以及怎样把这条链离线折叠回文件。

调用目标是加载器给的一片零#

先看那片空白从哪来。PE 节有两个大小：文件里实际存了多少字节，映射到内存后占多大空间。原构建的 .tvm0 从 RVA 0x23C6000 开始，VirtualSize 为 0x17FFEA，SizeOfRawData 只有 0x17B000：

Windows 映射 DLL 时，多出来的这段虚拟空间一律填零。磁盘上找得到调用目标的地址，却找不到那里的内容，因为内容要等运行时才写进去。看到调用落在 VirtualSize 超出 RawSize 的部分，就可以确定有一个启动期的写手。

调用点本身的形状也说明了这一点。12 个原函数入口通过短跳转进入 .tvm0 的本机代码区，其中部分指令序列被外置，原位留下等长替换：

长度不变，下一条原指令的位置也就不变；代价是 call+5 落在填充上，不再是真正的后继。原构建有 312 个这样的调用点，每段被搬走的 body 长 6..34 字节，可能包含多条指令，只有 68 段恰好是一条。如果按 body 长度去猜“这里少了一条什么指令”，大多数情况都会猜错。

一条岔路：可执行段并不全是代码#

找写手之前，扫描 .tvm0 时冒出过一个看似相关的候选：RVA 0x24445B4 的 28 25 FB 01 10 00，解码出来是一条操作数指向虚尾的 sub。如果把它当成线索，就会去分析一条根本不会执行的指令。

问题在于 .tvm0 里还放着 Windows 的异常展开表。段属性可执行，不代表整段文件数据都是指令。沿 PE 异常目录对照，这六个字节是两个地址字段拼起来的：前四字节是某条记录的展开信息 RVA 0x1FB2528，后两字节属于下一条记录的函数起始 RVA 0x5F0010。前一条记录描述的代码在 .text+0x5F0000，只是一字节 ret。

排除它只需要读一次目录。更省事的做法，是在可执行段里扫描“引用虚尾的指令”之前，先把异常表这类已知数据区标出来。真正的写手要从启动时的记录消费循环去找。

写入发生在 EXE 入口之前#

写手藏在 EndfieldBase 里，时机由加载顺序决定。Endfield.exe 的初始导入是 EndfieldBase ordinal 1，所以 Windows 先加载这个依赖、执行它的进程附加入口，然后才进入 EXE 入口。

EndfieldBase 的 DLL 入口 +0x21F260 跳到 .tvm0 中的 +0x1444255，沿 VM 执行路径生成一张私有 RW 记录表。DllMain 返回后，EXE 在 +0xA9F0F 调用 ordinal 1，后者从 +0x23BDE0 跳到 +0x162B131，进入后续引导与记录消费路径。生产循环还依赖 UnityPlayer 已经映射，否则虚尾地址无处可写。三条前提汇到一处：

这里有一个容易走偏的地方：记录表是执行的产物。从磁盘字节码某处截取同样长度的数据，得不到它。想离线拿到这张表，就得把 DllMain 跑一遍。

每条记录同时描述入口、body 与续体#

原构建的表有 789 条记录，记录区占 20124 字节。每条是十六字节头加变长 body：

记录偏移内容
0 / 216 位虚尾槽 key / 常量 0xE8E6
4 / 6每条记录唯一的 16 位值 / 常量 0x7A8D
8continuation 编码，高 16 位为空间 tag
12 / 13body 长度码 / 三字节锚点 0x55E84E
16外置的 x64 指令字节

一条真实记录回答三个问题：哪个槽接住调用，执行哪些字节，从哪里回到原函数。

麻烦在于槽位置和续体低位都用了带 bias 与噪声子集和的加性编码，单看一个字段会得到多个候选。把记录接到调用点上要靠交叉约束：槽候选与磁盘 call 目标求交，再检查 continuation = call_site + body长度。两个条件同时成立时，匹配是唯一的。

789 条里只有 312 条对应真实调用点，其余 477 条的续体 RVA 为 0。生产循环照样为它们生成片段，但已验证的真实调用点没有指向这些槽。RVA 0 是 UnityPlayer 映像基址，所以它们在运行时的绝对指针不是空值，看起来和真记录一样“有效”。

消费循环把一条记录展开到两处#

生产帧拿到表基址、长度和记录区末尾后逐条推进。它用 NtAllocateVirtualMemory 分配 4 KiB RWX 页，把生成片段连续放进去，放不下就换页，原构建一共用了六页。

处理每条记录时，RBX 指向当前代码页里的片段起点，R15 指向 Unity 虚尾入口，R13 指向入口对应的八字节指针槽。循环先写虚尾：

第一条按小端写出 FF 25，第二条写入 RIP 相对位移 disp32 = 指针槽地址 − 虚尾入口地址 − 6，第三条把片段地址放进指针槽。原来全零的入口就成了 jmp qword ptr [rip+disp32]。

然后写代码页。+0x114C925 与 +0x114C92B 组合写入五字节 lea rsp,[rsp+8]，+0x4CE629 起的复制辅助代码把 record+16 的 body 复制到 RBX+5，最后补一条间接跳转和八字节续体指针：

每个片段 body长度 + 19 字节。虚尾入口、片段和续体在同一次迭代里接好，整张表处理完，受保护调用才开始被执行。

一次调用怎样跨过填充字节#

用一个具体调用点把上面的结构串起来。原构建 UnityPlayer+0x23C6053 外置了一条七字节指令：

原位是五字节 call 加两字节填充。某次运行中，对应片段位于 VA 0x49C0212：

call 压栈的返回地址是 +0x23C6058，正好落在填充上。片段第一条 lea rsp,[rsp+8] 把它丢掉，栈恢复成调用前的样子；执行完 body 后直接跳到 call_site+7，填充字节被跨过。

用 lea 调整 RSP 还有一个好处：它不改标志寄存器，body 算出的标志能原样交回原函数。静态阅读时如果把 call+5 当成后继，就会把填充当代码读，后面的控制流全部错位。

离线把执行链折叠回文件#

理解了运行时的样子，离线还原就是把这条链压平。离线执行 EndfieldBase DllMain 生成同一构建的记录表，再按上面的编码约束和磁盘调用点匹配 body。原构建得到 312/312，更新构建得到 171/171 个真实调用点。

最早的结果是 309 个。差的三个不是编码问题，而是入口扫描范围截掉了跨页函数的尾部；扩大到相邻页后，三个调用点和剩下的真实记录一一对上。约束是唯一匹配的，所以“覆盖不满”本身就是扫描有漏的信号。

重打包保留真实槽的位置，把槽入口改成相对 E9 跳转，片段放进虚尾剩余空间，片段末尾也改成相对跳转回续体。这样得到的文件不再依赖运行时代码页，适合继续离线分析。

验证时比较的是两份重打包结果：磁盘生成与运行时采集得到的片段，经过同一打包方式后，虚尾与重建 DLL 逐字节一致。原始运行时虚尾不能直接比，它是 FF25 加指向外部页的绝对指针，地址随进程映射变化。

换一个目标也能用的做法#

回到开头那条读不下去的 call：加载器提供了零空间，DllMain 生成指令记录，生产循环把记录写成片段与跳转，受保护函数再从续体接着跑。换一个目标时，这次的经验可以压缩成几条检查：

  • 调用或跳转落进 VirtualSize 超出 SizeOfRawData 的区域，就说明有运行时写手。先按加载顺序找写入时机，不要在磁盘上找内容。
  • call 后面紧跟填充时，先去目标处找丢弃返回地址的指令（这里是 lea rsp,[rsp+8]）和显式续体。替换长度只说明字节数，不说明指令数。
  • 在可执行段里扫描可疑引用之前，先用 PE 目录把异常表这类数据区排除掉。
  • 生成出来的表要靠执行初始化代码来复现。匹配时用多个独立约束求交，覆盖率不满时先查扫描范围。
  • 比对运行时结果时，先把绝对地址归一化，比较两份同样打包的产物。
