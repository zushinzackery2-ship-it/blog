Agent 调用写操作后，传统 API 返回”改完后的完整对象”。当对象是复杂状态数据时，这个返回会把上下文撑爆。上下文返回优化的核心思路是：请求描述”想要什么”，响应只确认”改了什么”，完整状态留在服务端。

一句话讲清#

Agent 只需要”改了什么”和”改得对不对”。状态留在服务端，AI 只持 token（diff_token、state_token、artifact_handle）。每次写操作附带后置检查（state_integrity、compile、dirty_state），默认 dry_run=true 先预演再执行。

一、命令式 vs 声明式#

命令式（Imperative）#

问题：Agent 只改了 1 处，却收到了完整世界。状态进入上下文后持续累积。

声明式（Declarative）#

Agent 只保存”改成功了没”、“改了什么”。

二、三种 Token#

Diff Token —— 变更的”收据”#

记录从某次操作前到操作后发生了什么变化：

变更用行式数组表示：[类型, 对象, 字段, 旧值, 新值]。紧凑、可读、不占上下文。

State Token —— 状态版本的”指纹”#

当前状态的指纹。它让服务端检测”状态是否失效”，避免让 Agent 在对话里长期保存状态。

当状态被外部修改时：

Agent 收到失效通知后，重新读取最新状态。同步方式从隐式携带改为显式失效。

Artifact Handle —— 大负载的”存根”#

默认响应只返回 handle，完整对象留在服务端：

需要时显式读取，默认上下文保持轻量。

三、写操作的响应形状#

声明式写操作返回变更摘要，而非完整对象：

默认回包保留：改了什么、改得对不对、两个 token。

四、后置检查内建在响应中#

每次写操作附带一组后置检查，同一响应中返回：

  • State Integrity：引用关系和关键字段是否完整
  • Compile：构建/编译是否成功
  • Dirty State：是否已修改、是否已保存

Agent 直接从同一响应拿到验证结果。

五、Dry Run 默认开启#

所有写操作默认 dry_run=true：

先返回”如果执行会改什么”，确认后再实际执行。这一步把安全边界前置。

六、小结#

Agent 真正需要的只是”改了什么”。把状态留在服务端、AI 只持 token，需要详情时再按需查询，默认对话里只带必要的锚点。

这是一种写操作返回合同的重新定义：从”命令-完整对象”变成”声明-确认-按需精读”。

实践来源：一个 MCP 桥接项目，写操作默认返回 delta，完整对象通过 read 或 artifact handle 显式获取。
