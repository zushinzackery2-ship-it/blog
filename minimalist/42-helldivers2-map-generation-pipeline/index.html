Helldivers 2 的地图生成方法是：预制资源池提供几何原料，seed 驱动球面 Voronoi、路线、Zone 和 stamp 的空间重组，最后每局烘焙高度图、导航网格和小地图。不是「若干套成品图只换兴趣点」，也不是「地形从噪声函数长出来」——运行时字符串区、插件 ABI 和类型库都指向这条混合流水线。

这是系列第二篇。上一篇处理星球领土图的球面 Voronoi 拓扑；这篇讲整套生成系统怎么组织、各阶段做什么。

依赖顺序总览#

这是数据依赖顺序，不是逐帧调度表。下面各节按这条链展开。

生成分五个阶段#

整条流水线按数据依赖分成五个阶段，每个阶段只吃前一阶段的产物，pass 名基本能望文生义：

  1. 输入与空间骨架——读 seed、载入球面 Voronoi 图、生成路线、划分 region 与 subregion，先把星球表面切成格子并连出主干路线（load_voronoi_diagram、generate_routes、setup_region、sort_routes_in_cells）。
  2. 任务点与地点候选——在骨架上撒任务点、撤离点、前哨候选，spread_locations 负责把它们摊开不扎堆（generate_mission_stamps、generate_extraction_locations、generate_outpost_locations）。
  3. Zone 收口——把候选和分区收敛成连贯可玩的区域：finalize_voronoi 定稿，cellular_automata_colony_even_out 用元胞自动机抹平锯齿边界，fix_unreachable_areas 补掉走不到的死角，calculate_mission_boundaries 圈出任务边界。
  4. Stamp、城市与地形——把预制块摆到格子上、连城市道路、渲染高度图（place_all_subregion_stamps、generate_city_roads、render_heightmap_voronoi）。
  5. 水体、导航与输出——灌水体、烤导航网格、渲染可玩区、截小地图（generate_water、setup_terrain_navmesh、render_playable_area、capture_minimap）。

在游戏模块里，这五个阶段对应五段连续的生成代码（合计约 13.5 万字节）。它们没有把几十个 pass 硬编码成一长串顺序调用，而是一个数据驱动的调度器：每个 pass 是登记表里的一条记录，记录里存着这一步要调的函数、绑定的输入输出缓冲和 pass 名，执行期照表往下走。数据驱动这一点是方法的核心——pass 的顺序和内容都是数据，调整地图生成行为不必改调度代码，这和后面那道插件接缝是同一种思路。

有些 pass 的登记记录里还带着内嵌常量——元胞自动机相关的那几条能复现出容量 1024、24 和浮点 0.5 / 1.0。这些是登记时写死的参数，具体含义随各 pass 实现而定。

资源等待点：预制块是原料，不是成品图#

第四、第五阶段中间夹着一串「排队—等待—消费」的 pass，这串东西是理解整套方法的关键。stamp（预制几何块）不是随地图一起加载好的整图，而是在生成过程里按需拉取的资源包：先 queue_stamp_packages 把要用的预制包排进队列，再用 wait_for_stamp_packages、wait_for_zone_packages、wait_for_content_* 一族 pass 等它们就位，然后 spawn_stamps 把它们摆到 Voronoi 骨架算好的位置上，之后才轮到 flatten、heightmap、route distance。

也就是说，预制块是程序化流程消费的原料，摆哪些、摆在哪由 seed 和前面的空间计算决定，而不是加载时就定死的整图。这也解释了导航网格、可玩区和小地图为什么排在最后（setup_terrain_navmesh、render_playable_area、capture_minimap）——它们是地形烤完之后的下游产物，每局现算。

插件接缝：几何在引擎，玩法在游戏#

引擎侧的 level_generation 插件只对外暴露一个入口 get_plugin_api，游戏用一个约定好的 api id 向它要函数表：

这张自定义函数表只有四个入口：接入 dl_bin、接入 dl_typelib、执行球面 Voronoi、释放结果。几何调用约定很干净——输入是一段连续的 float32 x/y/z 点集，输出是一份内含四个动态数组的结果描述，结果的所有权归调用者，用完必须通过配套的释放入口交回。游戏侧拿到函数表后缓存起来，之后每次生成都从这里进出。

关键在于这道接缝把职责切得很清楚：插件里找不到 ScenarioSettings、ZoneSettings 或任何任务/权重词汇，而 mission stamp、route、flatten、navmesh 这些 pass 名全在游戏模块里。插件只管 DataLibrary 资源和球面 Voronoi 几何原语；planet 布局、region 参数、stamp 放置、seed 推进全在游戏侧。 几何是可复用的纯函数，玩法是喂给它的数据。

种子与生成输入#

生成阶段有独立的 seed pass。遥测事件 RestartedLevelGeneration 携带 initial_seed 和 32 位 number_of_restarts，由客户端拼装后上报后端——生成过程记录初始种子，并且可能整体重启。

输入侧字段名包括：param_planet_index、planet_hash、planet_region_hash、planet_environment_hash、level_id、difficulty、enemy_faction、tactical_objective_points、time_of_day。initial_seed 作为 DataLibrary 反射字段喂进生成流程，各 pass 在 seed 之后按登记表依次消费随机选择。

客户端本地生成#

五段函数、pass 调度器、资源等待点和插件几何调用都在客户端 game.dll 里完成；不存在「服务器下发地图几何、客户端只落地」的接缝。服务器侧拿到的是 initial_seed 和重启次数这类回执。

结论#

Helldivers 2 的地图生成方法是：authored 星球模板 + 球面 Voronoi 空间骨架 + 多 pass 地点与 stamp 放置 + 每局地形烘焙。预制 stamp、planet setup、region 配置提供原料；seed 驱动各阶段的随机选择；heightmap、navmesh、小地图是生成下游产物。

自己做同类系统时，最值得照搬的是插件接缝：几何原语独立成模块，输入输出是纯数据数组，所有权用配对释放函数锁死；权重、候选、种子留在数据和消费者侧。生成器换玩法不用动几何代码，几何升级也不牵连任务配置。
