在进程外分析 IL2CPP，首先遇到的往往是一个名称与地址脱节的问题：GameAssembly 中有大量 native 代码，但类名、字段名和方法定义组织在另一份 metadata 中。把这份数据定位出来，才能将机器代码重新接回类型系统。

对保留常规 metadata 布局的目标，可以利用 header 中各个表的范围与相互关系寻找候选。这个办法的价值在于结构约束，以及把昂贵的跨进程读取合并成批次。它依赖具体版本的布局，也需要完整数据来验证候选。

Header 提供一组可以交叉核对的约束#

常规 global-metadata.dat 的 header 包含标识、版本，以及各个数据区的偏移和长度。字符串、类型定义、方法定义、Image 和 Assembly 等表之间存在对应关系，随机内存很难同时满足这些条件。

候选验证可以逐步推进：先判断 header 是否符合目标版本，再检查表范围是否位于候选数据中，随后检查表长度能否按该版本的元素大小整除，最后验证表间索引和字符串引用。

这里容易混淆两种“数量”。header 中许多名称带 Count 或 Size 的字段实际记录的是字节长度，表项数量需要除以对应结构体大小。结构大小又可能随 Unity 版本和 metadata 子版本变化，因此版本号只是选择解析布局的一部分依据。

偏移加长度也要在足够宽的整数类型中计算，并检查溢出。一个回绕后落回有效区间的整数，不代表真实表范围有效。

读取方式决定定位成本#

若对每个候选地址都单独发起一次 ReadProcessMemory，定位过程可能被大量小读取拖慢。即使 header 验证本身很轻，跨进程调用和重复读取同一页仍然会占用时间。

原有实现 FindMetadataPointerByScore 采用另一种组织方式：先批量读取 GameAssembly 的相关节区，把其中像指针的值收集起来，再按这些指针指向的页面分组。

多个指针若落到同一页，就能共享一次读取。候选 header 跨页时，则需要补齐相邻可读区间；只验证完全落在单页里的候选，是实现上的覆盖限制。

从模块指针入手同样是一项假设：metadata 基址需要以可识别的形式留在扫描范围中。.data 和 .rdata 通常值得优先考虑，其他节区是否有用取决于实际引用。指针被编码、只保存在堆中，或 metadata 已被拆分时，这条路径就可能漏掉目标。

因此，运行时需要类型信息，并不等于地址空间中始终存在一份连续、原样的 global-metadata.dat。

评分用于排序，结构验证决定可信度#

原实现的 ScoreMetadataHeader 会先检查若干范围，再按有效表数量、推导体积、字符串池大小及 Image / Assembly 数量给候选评分。这适合把检查顺序集中到更像 metadata 的位置。

不过，更大的表并不天然更可信。一份较小的真实 metadata 可能排在一个较大的伪候选之后；给版本号设置宽泛区间，也不能替代对具体格式的支持。固定的 header 长度、表数量、对齐规则和体积阈值，都属于该实现针对样本作出的选择。

候选最终需要通过内容关系确认。例如，Image 的类型范围应落在 TypeDef 表内，类型的字段和方法范围应成立，字符串索引应指向有效字符串。若多个候选仍然成立，应保留差异继续核对，而不是把最高分直接当作事实。

这也解释了一个常见误判：读取候选末尾的一个字节，只能说明那个地址可读。它既不能证明中间没有不可读页面，也不能证明整个范围就是 metadata。

分块失败应被保留为失败原因；快照完整且关系自洽后，再进入类型系统恢复。

Metadata 恢复的是定义关系#

字符串池把名称接回索引，TypeDef 表把字段、方法和继承关系组织到类型下面，Image / Assembly 表进一步说明这些定义属于哪个模块或程序集。

实例字段的实际偏移、普通方法的 native 入口、泛型实例化后的布局和运行时 vtable，也需要结合生成代码的登记表与 runtime 状态。它们与 metadata 有明确联系，却不是从 header 扫描中直接得到的结果。

metadata 定位最有用的产物，是一份带版本依据、能够重复解析的快照。它把后续分析从“这个地址看起来像什么”推进到“这些定义如何相互引用”。字段偏移与方法入口的恢复，可以在这个基础上继续连接 Registration 数据。
