global-metadata.dat 是 IL2CPP 类型系统的静态入口。外部工具先在目标进程内存中找到这份 metadata，再从其中恢复类型、字段和方法的组织关系。

结论先行#

跨进程恢复 IL2CPP 类型系统大致两步：先定位并导出 global-metadata.dat，再解析 header 里记录的各个 metadata 表。

定位阶段避开 il2cpp_init 调用和导出符号依赖。关键是利用 metadata header 的强结构约束：它是一组密集的 (offset, size) 表描述。只要候选地址上的 header 同时满足版本、对齐、表边界、关键表大小等条件，就可以把误报压到很低。

解析阶段则把 metadata 当作一份静态索引：字符串池提供名称，TypeDef 表提供类型定义，FieldDef / MethodDef 表提供字段和方法定义，Image / Assembly 表提供代码组织关系。运行时字段偏移和 native 方法地址来自后续 Registration 表；metadata 负责恢复 C# 世界的静态轮廓。

1. 外部工具面对的边界#

IL2CPP 游戏运行后，UnityPlayer 和 GameAssembly 已经完成运行时初始化。进程内部可以通过 il2cpp_* API 查询类型、类、方法和对象；外部工具则处在另一条边界上：

  • 避开目标进程里的 IL2CPP 内部函数调用。
  • 把 PDB、导出符号视为可选信息。
  • 把 global-metadata.dat 原始文件路径视为可选信息。
  • 通过跨进程读取内存和模块信息来建立认知。

因此，第一步是先找到 metadata 在目标进程内存中的位置，再进入类型解析。

这件事成立的前提是：IL2CPP runtime 需要 metadata 才能把 token、类型名、字段名、方法名等静态信息映射回 managed 语义。换句话说，只要目标正常跑起来，metadata 就必须以某种形式存在于运行时地址空间中。

2. Metadata header 为什么适合做锚点#

global-metadata.dat 的开头是一段 header。它记录后续各个数据区的位置和长度，例如字符串池、类型表、字段表、方法表、Image 表、Assembly 表等。

这类 header 很适合做盲定位锚点，因为它同时满足几个条件：

条件作用
有固定开头结构可以快速读取候选并检查版本、表布局
表项由 (offset, size) 组成可以验证边界是否自洽
关键表有已知元素大小可以检查 imagesSize、assembliesSize 等是否整除
多个表互相约束随机内存很难保持整组条件一致

一个可信 header 至少要满足这些约束：

  • 版本字段处于已知 IL2CPP metadata 范围。
  • 非零 offset 按 4 字节对齐，并且位于 header 之后。
  • 非零 size 必须有对应的非零 offset。
  • 字符串池、Image 表、Assembly 表等关键区间必须存在。
  • 所有 offset + size 的最大值必须落在合理 metadata 体积范围内。
  • 关键表 size 能被对应结构大小整除。

这些检查用于把候选从海量内存位置压缩到极少数可信地址，单个条件只作为综合评分的一部分。

3. 为什么不逐位置验证 header#

最直观的方法，是读取 GameAssembly 里可能保存数据的节区，然后在每个 4 字节对齐的位置尝试验证 metadata header。这个方法思路直，但跨进程场景下成本很差。

问题不在验证逻辑，而在读取方式：

  • 每次 ReadProcessMemory 都有跨进程开销。
  • GameAssembly 的数据区可能有几 MB 到几十 MB。
  • 每个候选都读取一段 header，会制造大量小块读取。
  • 大多数位置缺少 metadata header 的整体结构。

更合理的做法是先找“指向 metadata 的指针”，再验证指针指向的页面。

5. Header 评分与综合条件#

单个条件不够可靠。比如版本号、字符串池大小、Image 数量，都可能在随机数据中偶然出现。ScoreMetadataHeader 的做法是先做硬约束过滤，再做综合评分。

硬约束包括：

  • 候选地址 4 字节对齐。
  • 页内剩余数据至少覆盖 0x120 字节 header 检查范围。
  • 版本字段符合指定版本，或在宽松模式下位于 10 到 100。
  • stringOffset/stringSize 非零，stringOffset 4 字节对齐，并且大于等于 0x100。
  • imagesOffset/imagesSize 与 assembliesOffset/assembliesSize 非零、对齐，并且分别能被 0x28 和 0x40 整除。
  • 31 组 (offset, size) 至少有 6 组非零有效项。
  • maxEnd 位于 0x20000 到 0x40000000。
  • string、images、assemblies 三个关键区间都落在 maxEnd 之内。

全部通过后再评分：

  • 非零 metadata 表越多，分越高。
  • 推导出的 metadata 总大小越大，分越高。
  • 字符串池越大，分越高。
  • Image / Assembly 数量越多，分越高。

找到最高分候选后，实现还会读取 metaBase + maxEnd - 1 做尾部可读性验证。尾部可读，说明候选推导出的 metadata 范围具备完整导出的基本条件。

8. Metadata 可以恢复哪些信息#

拿到完整 global-metadata.dat 后，可以恢复的是类型系统的静态语义。

数据区能恢复的信息
String 表类型名、命名空间、字段名、方法名、参数名
TypeDef 表类型定义、字段起点、方法起点、继承关系、接口关系
FieldDef 表字段名称、字段类型索引、metadata token
MethodDef 表方法名称、所属类型、返回类型、参数范围、metadata token
ParameterDef 表方法参数名称和类型
GenericContainer / GenericParameter泛型类型和泛型方法的参数定义
Image / Assembly 表程序集、模块和类型范围

9. Metadata 的信息边界#

metadata 记录的是静态定义，运行后生成或绑定的地址要从 Registration 和 runtime 结构中取得。

这些信息不在 metadata 里：

问题实际来源
实例字段在对象内存中的偏移Il2CppMetadataRegistration::fieldOffsets
方法的 native 函数地址Il2CppCodeRegistration::codeGenModules
类型大小和布局大小Il2CppMetadataRegistration::typeDefinitionsSizes
泛型实例化后的运行时类型Il2CppMetadataRegistration::genericClasses
vtable 运行时内容Runtime 初始化后构建的数据结构

这就是为什么 metadata 定位只是第一步。它解决“类型系统长什么样”，但不解决运行时地址映射。后者要继续进入 Registration 表。

10. 边界与风险#

这条路线依赖几个前提：

  • metadata 在目标进程内存中保持连续布局。
  • header 没有被加固工具改写或加密。
  • 目标模块地址范围和可读页面可以枚举。
  • metadata 版本与解析结构体基本匹配。

如果目标把 metadata 解密后拆散、重编码，或者只在短时间窗口中映射，单纯依靠 header 结构约束就不够了。这时需要先还原加载链路或抓运行时解密后的内存快照。

但对常规 Unity 2020-2023 IL2CPP 目标来说，metadata header 的结构性足够强，从指针入手、按页面验证、再对 header 评分，是一条很实用的外部定位路径。
