关于 Helldivers 2 的地图是怎么来的，流传最广的两种说法方向相反：一种说地图是做好的若干套成品，每局只随机换一批兴趣点；另一种说地形每局都从噪声里长出来。把 Steam Build 24036910 的运行时字符串区、level_generation 插件的导出函数表和同版本类型库放在一起审计，这两种说法都拿不出证据，能立起来的是第三种：预制资源池 + seed 驱动的空间重组 + 地形烘焙。

这是「Helldivers 2 地图生成」系列的第二篇。上一篇在几何拓扑层验证了星球领土图确实是无退化的球面 Voronoi/Delaunay 对偶结构；这一篇往上走一层，回答整套生成系统是什么架构。

这一篇做两件事：给上面这个分类补上可检查的证据，再把证据的边界画清楚——依赖顺序和资源等待点确实可证，seed 派生公式和候选权重在当前材料下不可证明。混着说这两类结论，是这类分析文章最常见的失真方式。

三种说法先要变成可观察差异#

要用证据区分这三种说法，得先把它们翻译成数据流上会留下的痕迹。

固定成品说意味着：加载阶段出现整图级资源，生成期不需要中途等待地点和区域资源包，也不需要 Voronoi、路线、细胞自动机这类计算阶段——查表不需要计算。纯噪声说意味着：生成期不该出现预制 stamp 资源包的排队与等待，几何应当来自噪声函数而不是资源文件。混合说的特征是两者交替出现：计算阶段推进空间结构，同时把预制资源包排队、等待、放置进这个结构里。

后面三节按这个标准过证据。样本固定为 Steam Build 24036910（引擎为 Stingray 1.8.0.0），所有结论只对这个构建负责。

生成逻辑集中在五段连续函数里#

运行时映像的字符串区保存了完整的 generation pass 名，而字符串锚点的指令引用把这些名字钉进五段连续的函数区间：

函数区间大小当前解释
0xB9B220–0xBA7DBF52,127 字节主阶段调度、输入准备、资源等待、早期地形
0xBA7DC0–0xBAF69430,932 字节Stamp、资源等待、高度与路线相关阶段
0xBAFAF0–0xBB890236,370 字节flatten、城市与车队路线、heightmap、stamp
0xBB89A0–0xBBA9988,184 字节stamp 旋转、路线距离、zone 高度
0xBBB160–0xBBD18C8,236 字节末段 stamp 生成

资源等待点插在计算阶段中间：预制包在生成过程里被排队、等待、消费

这里先声明证据强度。字符串在连续函数中的相对顺序、五个函数区间、资源等待点，是这份材料里最强的一级；每个阶段名对应的内部子任务边界只有中等强度。

同一构建的运行时内存映像把这五段函数的性质又推进了一步：它们不是被动的字符串容器，而是一个数据驱动的 pass 调度器。逐个 pass 由一段构造指令序列填一个描述子对象——+0x8 存这个 pass 的 step 函数指针，中间若干偏移存输入/输出缓冲的绑定，末尾固定偏移 +0x1988 存 pass 名字符串指针。也就是说，「阶段名」和「阶段代码」是被同一个描述子绑在一起登记的，执行期按这张登记表推进。这条证据把上面的顺序从「字符串在函数里的布局顺序」升级成「调度器登记的依赖顺序」。但仍然没有一次带时间戳的执行记录，所以它依然是依赖顺序，不能当成逐帧调度表。

资源等待点把「预制池」钉进流水线#

分类的关键证据在等待点。第一段函数（0xB9B220 起）内部，指令引用按出现顺序给出的子序列里有这样一段：

同一函数内的引用顺序是代码布局顺序，接近但不等于执行顺序——这个保留要说在前面。但它足以支撑两个结构判断。

第一，stamp 资源包的排队（queue_stamp_packages）、等待（wait_for_stamp_packages）和消费（spawn_stamps）交替嵌在生成逻辑中间，之后还跟着 flatten、heightmap、route distance 这些计算阶段。如果地图是整图成品，生成中途不需要等待 stamp、zone、faction、utility 这些分类资源包，更不需要在等待之后继续算高度图；如果地形纯由噪声生成，就不存在需要排队等待的预制 stamp 包。等待点前后都有计算，说明预制资源是被程序化流程消费的原料，不是结果本身。

第二，末段的 setup_terrain_navmesh、render_playable_area、capture_minimap、generate_danger_levels 证明导航网格、可玩区和小地图是生成结果的下游产物，每局烘焙，而不是随成品图一起加载的静态贴图。这是「地形烘焙」这一半分类的直接证据。

顺带处理一个可能的反例方向：字符串里确实有 setup_level_to_load、load_testlevel 这类名字，但上下文明确是测试与资源预览入口。另有设计师公开作品页记载过特殊任务使用整块大关卡的先例——那是设计事实，不是当前构建里通用「固定地图分支」的证据，它的选择条件在当前材料下仍是未闭合项。

接缝：几何原语在引擎插件，权重和种子在游戏侧#

这套系统在架构上最值得记录的一刀，切在引擎插件和游戏消费者之间。

level_generation 插件是一个 542,296 字节的独立模块，唯一导出是 Stingray 标准的 get_plugin_api。它的 selector 行为可以完整确认：

自定义函数表只有四个入口：接入一个 dl_bin 资源、接入一个 dl_typelib 资源、执行球面 Voronoi、释放结果。几何调用的 ABI 约束能确认到这个程度：

  1. 输入点是连续的 float32 x/y/z，stride 12；
  2. 结果是一个 48 字节描述，内含四个动态数组；
  3. 结果所有权归调用者，且必须交回配套的释放函数；
  4. 四个数组的元素布局没有证据，只能叫 array_0..array_3，不能替它们起 cell、edge、corner 这样的名字。

插件的字符串里没有 ScenarioSettings、ZoneSettings 这类游戏侧类型名，也没有任何任务、权重、预算词汇。反过来，mission stamp、objective、route、flatten、terrain、navmesh 这些 pass 名全部在 game 模块里。分工由此可证：插件负责 DataLibrary 资源接入和球面几何这一个原语；planet 布局、region 参数、任务约束、权重、stamp 放置和 seed 推进全部属于游戏消费者。

接缝两侧各自可证；四数组到游戏侧图结构的逐项映射不可证

这道接缝的游戏一侧，在同构建的运行时映像里能看到具体的绑定动作，而不只是推断。游戏通过标准的插件查询接口，用一个固定的 api id（0xE0DE385D）取到 level_generation 的函数表，把表指针缓存进一个全局槽；结果的释放走的是这张表里第四个入口（表偏移 +0x18），传入的是一枚由调用者持有的结果句柄。这把前面第 3 条约束——「所有权归调用者、必须交回配套释放函数」——从类型信息层面的推断，变成了运行时映像里可指认的调用序列：句柄先被缓存，用完后连同几组输出缓冲一起，通过这个释放入口显式回收。

但要强调，这段证据只覆盖接缝的游戏一侧。球面 Voronoi 的几何原语和那四个数组的元素布局在这份 game 模块映像里没有出现（它们在独立的插件模块内），所以四数组到 graph 字段的逐项映射还是缺一次 execute 调用的输入输出快照，仍留在边界外。

当前运行时样本里有 13 个地点实例和 800 个 stamp 资源，39 条 ZoneWeight 边全部来自同一个地点实例；Zone 自身携带的 stamp 资源与地点侧 stamp 资源交集为零，所以两者的连接靠 zone_id，不是资源哈希相等。这是「权重在数据侧」的实例级证据——但注意，39 条边给出的是连接关系，不是权重取值的分布规律。

历史固定样本里的 26 张星球领土图全部通过球面 Voronoi/Delaunay 对偶的闭式拓扑检查——512 个 cell、1530 条边、1020 个 corner，全部被 Euler 公式锁死，推导和检查清单见上一篇。这些图因此可以反过来当插件输出的结构验证器。但它验证的是消费者侧图结构的性质，不能证明这些图就是插件某次调用的直接序列化结果，也不能证明插件固定要求 512 个输入点。

种子：存在可证，公式不可证#

seed 在这套系统里的存在是有硬证据的。生成阶段名里有独立的 seed 一项；遥测记录 RestartedLevelGeneration 带 initial_seed 和 number_of_restarts 两个字段，说明生成过程记录初始种子并且可能整体重启。输入侧的字段名也齐全：param_planet_index、planet_hash、planet_region_hash、planet_environment_hash、level_id、difficulty、enemy_faction、tactical_objective_points、time_of_day。

运行时映像里这条遥测的发射指令序列可以看得更细：事件在客户端拼装，number_of_restarts 按 32 位整数序列化，连同 initial_seed 一起作为一条分析事件上报后端。方向是客户端往后端报，不是后端下发——也就是说是客户端在本地跑生成、记录初始种子和重启次数。另一处细节反过来划出边界：initial_seed 这个名字在代码映像里只作为一个反射式的数据字段名存在，没有任何指令直接引用它。这意味着种子是以数据字段的形式喂进生成的，它的派生逻辑不在这份代码映像的可见指令里。

到此为止。以下问题在当前材料下全部没有答案：initial_seed 的位宽、来源和与 planet、mission 标识的混合公式；每个阶段共享一个随机序列还是使用拆分子种子；重启时复用、递增还是重新混合初始种子；stamp 旋转、权重选择消耗随机数的先后。刷怪模块里已被证实的 64 位线性同余序列（这类确定性随机在设计上的作用见刷怪导演系统那一篇）也不能顺手挪用——在出现关卡生成侧的调用证据之前，不能宣称它就是地图的随机源，更不能宣称「相同 seed 必然复现相同地图」。

这条边界值得较真，因为「seed 存在」和「seed 公式已知」在传播中几乎必然被合并成一句。前者是字符串和遥测字段支撑的事实，后者需要一次完整的生成参数记录才能闭合，两者隔着一整类证据。

地图由客户端生成，服务器只收种子回执#

有一个常被追问但一直没定论的问题：地图是不是服务器算好下发的？把生成流水线的位置和上面那条种子遥测的方向合起来看，答案在当前构建里可以给到——不是。

整条生成流水线——五段函数、pass 调度器、资源等待点、插件几何调用——都在客户端的 game 模块里；initial_seed 和重启次数是客户端拼好后上报后端的分析事件，方向是客户端往上送。如果地图几何由服务器生成再下发，客户端既不需要在本地跑完这套 pass 流水线，也不需要把「我用的初始种子和重启了几次」回报给后端。这两件事同时成立，指向的是同一个结论：生成在客户端本地完成，服务器拿到的是种子和结果统计这类回执，而不是它在提供地图几何。

这条结论的强度定在「有方向证据 + 范围内无相反机制」这一级：它覆盖被审计的生成 pass 流水线和插件绑定路径，在这个范围里没有出现「接收服务器几何再落地」的接缝。它不排除后端在选星、任务编排这类更上游的环节里参与——那是另一套系统，不在本文的审计范围内。

不可证明清单#

先说清这轮新证据的类型，因为它决定了哪些项能动、哪些不能。上面几处用到的是同构建的运行时代码内存映像——它带的是指令、字符串锚点、立即数和插件绑定。它天然不含三样东西：堆里那些已加载的 DataLibrary 明文实例、独立的插件几何模块、以及一次带完整参数的单局生成记录。凡是要靠这三样才能闭合的项，代码映像原理上帮不上，缺的是那一类具体输入，而不是缺分析。

和上一版比，这张表短了一行：「服务器是否参与生成」不再挂在这里，它已经被上一节的方向证据收进了可证结论。其余各行没有凭空前进，但「还缺什么」从含糊的「捕获值」细化成了具体的输入类型——这本身就是把边界画得更准。

表里还有一类相反的陷阱：有值但不能乱用。环境配置里五组路径参数的典型值是 15/20/20（第 0 组全零且不建碰撞），它们是道路的材质和碰撞配置——数值真实存在，但把它解读成「任务点间距」就是给字段换了主人。CA 描述子里那几个内嵌立即数是同一类陷阱：数值是真的，但在没有符号的情况下把 1024 读成「网格是 32×32」、把 0.5 读成「翻转概率」，都是替语义未定的字段擅自命名。有实例值不等于语义已闭合，这一点和空缺项同样重要。

结论#

回到标题的三选一。当前证据支持的分类是：Helldivers 2 的地图由预制资源池提供几何原料，由 seed 驱动的 Voronoi、路线、Zone、stamp 阶段完成空间重组，再由每局的地形烘焙产出高度图、导航网格和小地图。固定成品说和纯噪声说各自缺少本应留下的痕迹。

对做自己项目的人，这份证据里可迁移的是那道接缝：把球面 Voronoi 这类可复用几何原语做成与业务无关的模块，输入输出收敛成纯数据数组，所有权用配对的分配与释放函数锁死；权重、候选、种子全部留在数据和消费者侧。这样生成器换玩法不用动几何代码，几何代码升级也不会牵连任务配置。

同样可迁移的是边界纪律。这一版并进了同构建的运行时代码映像，边界也确实动了几处：服务器不提供地图几何从空白变成有方向证据的可证结论，五段函数被确认成数据驱动的 pass 调度器，插件接缝的「调用者所有」从推断变成映像里可指认的调用序列。但动的都是代码映像能证明的部分；seed 派生公式、ZoneWeight 取值、细胞自动机的网格与邻居规则仍然未闭合，因为它们要的是堆内明文实例、独立插件模块或单局参数记录，而一份代码映像原理上不带这些。依赖顺序、等待点、结构不变量、绑定关系属于可证事实；派生公式、权重取值、重试参数属于未闭合项——两类结论在文中分开陈述，转述时也应该分开。本文只做固定构建样本上的离线结构审计，不与运行中的程序交互，也不分发任何原始资源。
