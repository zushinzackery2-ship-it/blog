终末地的资源读不出来，但失败的方式很有信息量。

.blc 索引解密后，路径、偏移、长度、MD5 和 encrypted 都能读到。按索引从 .chk 切出一个 .ab，MD5 与记录完全一致，文件还标着 encrypted=false。把它交给 UnityPy，得到的对象数却是 0。

问题出在两层各管不同的事：VFS 负责交付文件字节，定制 Bundle 负责把这些字节解释成 Unity 资源。 文件记录关闭加密，归档内部仍然可以使用另一套头、密码变换和压缩格式。

资源恢复因此从分清两层开始。外层沿 GameAssembly 的调用和指令确定参数；内层在恢复 UnityPlayer 的外置指令后，直接执行归档读取函数，把头、目录、密码变换和解压接成完整流程。文件结构则从另一侧核对这些操作的结果。

两层沿模块边界交接#

外层位于 GameAssembly 的托管 VFS 路径。.blc 保存索引，.chk 保存文件区间；索引用 ChaCha20 解密，文件记录在 encrypted=true 时再按自己的 nonce 解密。两种操作共用公共 key 与初始 counter 1。

内层进入 UnityPlayer 的 AssetBundle.LoadFromFile 实现。它识别定制头、恢复块目录，再对数据块进行稀疏 VFSAES 变换和 LZ4Inv 解压，取得 SerializedFile 与 .resS。

有些资源工具可以直接导入静态 .chk，从 VFSAES 开始处理，原因也在这里：这批 InitBundle 记录关闭了外层文件加密，Bundle 又连续排列，工具能够从当前位置识别内层头并逐包前进。对于加密记录或 .blc 索引，仍要先处理外层。

沿客户端看，VirtualFileSystem 管理 .blc/.chk 文件记录，UnityPlayer 的归档对象管理 Bundle 内部的块和 node。两个模块的交接点是文件字节，外层记录中的 encrypted 也只在文件层解释。

资源恢复与启动还原逐渐接上了#

资源恢复时，文件提供了可以反复重放的输入。索引 CRC32 与记录 MD5 核对外层结果；内层的原生函数给出字段和数据，再与离线恢复的结果逐字节比较。严格解压长度、块区间、node 覆盖和对象解析继续核对文件结构。SHA-256 由分析者计算，用于绑定输入或产物版本；它与客户端保存的校验值各有用途。

最小包恢复成 6319 字节的标准 UnityFS，解析出两个对象。随后处理 InitBundle 全组 1048 个包，共读到 19,370 个 Unity 对象，解包错误为零；三个大型角色 Shader 包也继续解析到了程序结构。这些数量描述资源语料，具体格式分支仍要看每个包的布局。

本次本地原生核对还修正了头部长度的旋转方向：还原后的 size 就是实际的 2461。当前安装索引已有 1052 个 Bundle，头部声明长度全部与记录长度一致；其中三份小包进一步完成了原生目录和数据块读取。早期对象扫描与这次代码核对，各自对应明确的输入和处理范围。

后续启动还原处理的是另一组对象：原构建 312 个、更新构建 171 个真实受保护调用点。EndfieldBase 先生成记录表，再把外置指令写入私有代码页，把入口和指针写进 UnityPlayer 虚尾。磁盘生成与运行时采集经过同一打包方式后，结果逐字节一致。

到这里，文件为何需要二次处理，以及某些引擎指令为何要等启动后才能执行，都有了各自的解释。两条分析路径互相帮助，计数与结论也各自落在所处理的对象上。

沿三个问题继续读#

外层参数、内层格式与常量推导各需要不同的上下文，拆开后更容易顺着一个问题读完：

  • VFS 索引与文件解密：沿调用链确定 key、nonce 与 counter，解释 CRC 和 MD5 怎样约束结果。
  • 定制 Bundle 的目录与压缩：从 2461 字节小包出发，连接头、块目录、LZ4Inv 与 Unity 对象。
  • VFSAES 的稀疏变换与参数：解释抽取、流变换与散回，区分选中位置和差分位置。
  • 启动壳的指令生成与虚尾填充：沿加载、记录消费与一次受保护调用，说明缺失的指令如何重新进入执行链。

路线选择本身见语义恢复与兼容复现。从正确的文件字节走到可读对象，并不只有继续拆保护这一条路；文件结构和内部执行，分别在适合它们的问题上提供信息。
