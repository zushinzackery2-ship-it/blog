拿到一份 IL2CPP 构建产物时，注册表中的计数很有吸引力。几万个类型登记、更多的方法规格，看起来像是一张能够量化整个项目的统计表。

这些数字确实有用，但它们统计的是不同层次的记录。泛型规格不等于独立机器码，类型登记不等于 C# 类，调用适配入口的数量也不能说明运行时调用有多频繁。

正确理解这些差别后，注册表适合帮助比较构建产物、发现需要继续调查的变化。它提供的是结构线索，还不足以独自评价项目复杂度、代码质量或性能。

两张表连接生成代码与运行时元数据#

IL2CPP 将托管代码转换成 C++，再编译为本机代码，同时生成运行时需要的登记数据。在常见的 Windows 构建中，可以从 GameAssembly.dll 观察这部分产物；其他平台的文件组织可能不同。

其中，代码注册表关联各类本机入口和代码模块，元数据注册表关联类型、泛型规格、布局等记录。它们与 metadata 文件、生成模块共同组成运行时解释代码的基础。

许多字段采用计数与数组指针配对的结构，但这只是定位线索。字段顺序、类型宽度、对齐和版本变化仍需要核对。看到一串合理的数量与地址，并不能直接确认整张表。

注册过程与运行时索引的关系，在注册表的运行态恢复中有更具体的展开。这里关注的是表已经定位之后，数量应该怎样解释。

泛型规格与代码入口并非一一对应#

考虑一个泛型方法在不同类型参数下使用的情况。运行时可能需要保存多份规格，以区分所属类型、方法参数和相应元数据；这些规格却可能共享同一段本机实现。

泛型共享策略、裁剪设置和 IL2CPP 版本都会影响这种关系。数组里有多少入口项，也不一定等于有多少个不同的函数地址，更不直接等于有多少个源码方法。

几个常见计数可以这样区分：

记录主要描述
Generic instances类型参数组合，可被不同泛型上下文复用
Method specs某个方法及其类型、方法泛型实参的规格
Generic method table方法规格与生成代码、调用适配等索引的关联
Generic method pointers生成的泛型代码入口表项

例如，List<int> 与另一个使用单个 int 参数的泛型类型，可能复用相同的参数组合记录，但它们仍是不同的泛型类型。把 generic instance 的数量直接当成具体泛型类数量，就混淆了组合与使用组合的对象。

因此，方法规格明显多于入口，并不奇怪。更值得调查的是两者的实际映射、共享地址，以及同样构建条件下映射怎样变化。

类型登记与类型定义也有不同粒度#

类型登记中可以出现基础类型、数组、指针、引用修饰和泛型实例等描述。一个源码类型可能引出多种使用形式，所以 typesCount 不能直接换算成类数量。

字段偏移表和类型大小表通常按类型定义组织。字段偏移计数描述的是外层布局记录的数量，不能当成整个项目有多少字段。一个类型对应的偏移记录内部，还可能包含多个字段位置。

在常见布局中，两组记录覆盖同一批类型定义，计数通常对应。这个关系可以帮助检查解析是否自洽，但仍要结合目标版本和实际结构，不能仅因两个数字相等就确认找到了正确表。

同样，某些 metadata usage 字段在不同版本中的组织会变化。某个计数为零，只能说明该字段在这份产物中的状态，不能推出运行时不使用元数据。

调用入口数量不能代替运行时行为#

Invoker 为某些动态调用场景提供适配入口，多个方法可能共享兼容的适配代码。它的数量描述生成了多少适配记录，不能说明反射调用在实际游戏中有多频繁。

未解析虚调用相关表项也类似。表的大小与运行过程中实际经过这些路径的次数不同，不能直接推出虚调用开销。

Reverse P/Invoke、Interop 等记录能帮助观察本机与托管边界需要哪些支持，但依赖库也会贡献相关条目。数量增加可以成为调查入口，还需要继续定位来源与用途。

构建记录保存了可用入口，运行记录才显示它们怎样被实际调用。性能判断还需要采样、计时或实际调用记录，相关问题见性能数字的统计口径。

模块数量描述组织结果，不能直接评价架构#

代码生成模块通常与程序集组织有关。模块增加，可能是新增库、程序集拆分，或构建工具的组织方式变化。

它不等于本机编译单元的数量，更不足以判断耦合度。一个程序集可以包含大量彼此清楚的模块，多个程序集之间也可能存在复杂依赖。架构质量需要看依赖关系和职责，而不是只看一个计数。

因此，注册表更适合作为进入构建产物的目录。通过模块继续找到生成代码与元数据，再分析它们之间的关系，才能形成更具体的判断。

构建变化会留下不同的计数#

同一项目两个版本的表项变化，通常比孤立的绝对数量更有意义。但比较前仍要确认 IL2CPP 版本、平台、裁剪级别、构建选项和依赖是否一致。

如果方法规格突然增加，可以继续检查新增程序集、泛型实参和共享策略。某个泛型密集型库可能是原因，工具链变化也可能是原因。计数指出变化位置，不能独自确定因果。

同样，类型登记增长不等于新增了同样数量的类；入口增多也不保证代码体积按比例增大。沿登记关系继续核对生成内容，才能把统计变化转成可解释的结论。

注册表的价值，正是在于为这种调查提供稳定入口。把每个计数放回它对应的记录层次，数字就能帮助定位问题；将它们直接换算成“项目有多复杂”或“运行有多慢”，反而会丢掉最重要的结构差别。
