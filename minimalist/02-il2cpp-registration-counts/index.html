每个 IL2CPP 构建的 Unity 游戏，都在 GameAssembly.dll 里藏了一份”户口本”——记录着泛型、类型、方法等 runtime 索引的规模。本文教你读懂这份”户口本”，用真实数据量化一个 IL2CPP 项目的复杂度。

结论#

IL2CPP 的 Registration 表是 AOT 编译器在 GameAssembly.dll 中写死的一份”户口本”，记录着泛型方法指针、方法规格、类型登记、调用入口、类型布局、代码模块等 runtime 索引的规模。这些数字描述的是 AOT 编译后的 runtime 索引规模，不是源码层的类/方法数量。不同项目的数字差异很大——小项目可能只有几千，中大型项目可达数万甚至数十万。

Registration 表是编译期产物的入口#

使用 Unity 的 IL2CPP 后端构建项目时，编译器会做两件事：

  1. 把你的 C# 代码翻译成 C++，再编译成机器码 —— 这些代码存在 GameAssembly.dll 里
  2. 生成一份”索引目录” —— 记录所有类型、方法、泛型实例的位置和关系，也存在 GameAssembly.dll 里

这份”索引目录”就是 Registration 表。它有两张：

  • g_CodeRegistration —— “代码入口表”，记录各种 native 代码入口的地址
  • g_MetadataRegistration —— “元数据索引表”，记录类型、泛型、方法规格等索引

它们不是源码统计，而是 AOT 编译器在生成 GameAssembly 时写死的二进制数据。通过解析它们，我们可以量化一个项目的 runtime 规模。

逐项解读#

Reverse P/Invoke Wrappers#

当 Native 代码需要回调 C# 代码时（比如 Windows API 的回调函数），IL2CPP 需要一层”翻译”来把调用约定、参数布局转换好。大多数项目这个数值很小（个位数到两位数），因为主动让 Native 调回 Managed 的场景不多。

Generic Method Pointers#

这是通常最大的一类。你的 C# 代码里写了 List<T>、Dictionary<K,V> 这样的泛型，IL2CPP 在 AOT 阶段会把它们实例化成具体的类型（如 List<int>、List<string>），每个实例对应一个 native 代码入口。

这个数字描述的是 AOT 展开后的具体代码入口数量，反映项目的泛型使用程度——泛型用得越多、类型参数组合越丰富，这个数字越大。

Invoker Pointers#

Invoker 是 IL2CPP runtime 的”统一呼叫台”。通过反射调用方法、或 runtime 需要做动态分发时，会通过 invoker 来调用目标方法。

Invoker 数量通常与 generic method pointers 同量级或略少，说明 runtime 可调度的”中转入口”规模。

Unresolved Virtual Calls#

AOT 编译时，有些虚调用、接口调用的目标要等运行时才能确定（比如泛型虚方法）。IL2CPP 会保留这些”待解析”的入口，在运行时通过 vtable 或其他机制找到真正的目标。

Interop Data#

与 Native 代码、COM、WinRT、P/Invoke 互操作相关的数据。纯 C# 项目可能为 0，有大量 P/Invoke 或 COM 互操作的项目这个数字会明显上升。

Codegen Modules#

IL2CPP 把生成的代码按模块拆分，每个模块通常对应一个程序集或代码单元。模块数量反映代码的组织粒度——模块越多，说明项目被拆成了更多独立的编译单元。

元数据注册表：运行时布局的档案库#

如果说 CodeRegistration 是”花名册”，MetadataRegistration 就是”档案库”——记录类型、泛型、方法规格等 metadata 索引。

总览#

项目规模特征通俗解释
Generic classes通常几千到几万泛型类的具体实例登记
Generic instances通常几千到几万泛型参数的不同组合
Generic method table通常与 generic method pointers 同量级泛型方法的登记关系
Types中小型项目几千，大型项目几万 ~ 数十万所有类型的登记项
Method specs通常是 generic method table 的 1 ~ 1.5 倍方法泛型规格
Field offsets与 type definition sizes 完全相等字段在内存中的偏移量
Type definition sizes与 field offsets 完全相等类型在内存中的大小
Metadata usages可能为 0，也可能有值运行时 metadata 使用记录

逐项解读#

Generic Classes#

这个数字描述 AOT 展开后产生的具体泛型类实例数量（如 List<int>、Dictionary<string, object> 等）。泛型用得越多，这个数字越大。

Generic Instances#

泛型参数的不同组合。比如 List<int> 和 List<string> 是两个不同的 generic instance。组合越丰富，说明泛型参数的使用越多样。

Generic Method Table#

与 CodeRegistration 里的 generic method pointers 数量通常接近，但含义不同：

  • Generic method table = “档案”，记录泛型方法的关系和元数据
  • Generic method pointers = “门牌号”，指向实际的 native 代码

两者数量接近说明”档案”和”门牌号”基本一一对应，但通常略有差异，因为有些档案条目属于抽象或间接调度场景。

Types#

包括基础类型（int、string）、数组、泛型实例、修饰类型（ref、指针）等。它描述的是所有类型登记项的总和。一个项目如果有大量泛型展开，这个数字会显著膨胀。

Method Specs#

通常是整张表中最大的一项。Method spec 描述方法的泛型规格——比如 void Foo<T>() 在不同 T 下的规格。

它比 generic method table 和 generic method pointers 都大，说明”规格记录”比最终的”代码入口”更多。这很正常：一个泛型方法模板可能对应多个规格，但只有部分规格会生成实际代码。

Field Offsets & Type Definition Sizes#

这两个数字永远相等，因为 IL2CPP 为同一批类型定义同时记录：

  • 字段偏移 —— 每个字段在对象内存中的位置
  • 类型大小 —— 整个类型占多少字节

它们共同反映了项目的类型定义规模。

Metadata Usages#

这个字段可能为 0，也可能有值。为 0 只能说明 generated registration 里没填这个数，不代表项目没有 metadata 使用。具体含义取决于 IL2CPP 版本和编译选项。

这些维度告诉我们什么#

泛型使用程度#

泛型相关表（generic method pointers、generic method table、method specs）通常是 Registration 表中最大的一类。如果这三个数字都在数万级别，说明项目大量使用了泛型——List<T>、Dictionary<K,V>、Task<T>、IEnumerable<T> 等现代 C# 特性被广泛使用。如果只有几千，说明泛型使用相对克制。

类型系统复杂度#

Types 的数量直接反映类型系统的规模。小项目可能只有几千，中大型项目几万到几十万。注意这里统计的是类型登记项——它包括基础类型、数组、泛型实例、修饰类型等所有 IL2CPP 需要登记的类型。

互操作强度#

Interop data 和 reverse P/Invoke 的数量反映项目与 Native 边界的复杂程度。纯 C# 项目可能接近 0，大量使用 P/Invoke、COM 或 WinRT 的项目这个数字会显著上升。

模块化程度#

Codegen modules 的数量反映代码的组织粒度。模块越多，说明项目被拆成了更多独立的编译单元（通常对应更多程序集）。模块过少可能意味着代码耦合度高，过多则可能意味着过度碎片化。

这些维度的边界#

容易误解的对象实际含义
C# 源码文件数量一个文件可能有几十上百个类型，registration 计数适合看 runtime 索引规模。
C# 类数量类型登记包括基础类型、数组、泛型实例等，不只包括类。
C# 方法总数method spec 是泛型规格，不是方法声明。
运行时对象数量这是编译期索引，不是运行时状态。
所有泛型实例都会被执行AOT 可能生成了一些实际上不会用到的代码。

这些维度能回答的问题#

场景 1：比较两个版本的规模变化#

两个版本的 GameAssembly（比如更新前后）对比 registration 表的计数，可以看出：

  • 泛型膨胀了多少？（generic method pointers 的变化）
  • 新增了多少类型？（types 的变化）
  • 模块化有没有变化？（codegen modules 的变化）

即使不知道绝对数值的大小，观察相对变化就已经很有价值——比如某个版本更新后 method specs 暴涨，很可能是因为引入了新的泛型密集型库。

场景 2：评估 Hook/注入的复杂度#

  • 泛型方法指针越多，Hook 泛型方法的工作量越大
  • Codegen modules 越多，代码分布越分散
  • Interop data 越多，与 native 的边界越复杂

场景 3：理解性能特征#

  • Method specs 多 → 泛型展开多 → 代码体积大 → 可能影响启动时间和内存占用
  • Invoker pointers 多 → 反射/动态调用场景多 → 可能有性能热点
  • Unresolved virtual calls 多 → 运行时虚解析开销大

边界#

Registration 表是 IL2CPP AOT 编译器留下的”户口本”，通过解析它，我们可以量化一个项目的 runtime 索引规模。以下是对各维度的概括：

维度典型规模含义
泛型规模几千 ~ 几十万generic method pointers / table / specs 的总量级
类型规模几千 ~ 几十万types 登记项的总量级
布局规模与类型规模正相关field offsets / type definition sizes 的记录数
调用规模与泛型规模同量级或略少invoker pointers 的总量级
模块规模几十 ~ 几百codegen modules 的数量
互操作规模0 ~ 几千interop data / reverse P/Invoke 的总量级

最后强调一点：这些数字描述的是 AOT 编译后的 runtime 索引规模，对应的是 IL2CPP 运行时登记项，而非源码层的类、方法或代码行数。不同项目的数字差异很大——小项目可能只有几千，中大型项目可达数万甚至数十万。它们帮助我们理解 IL2CPP 项目的”体型”和”结构”。

本文基于 Unity 2022 IL2CPP 产物分析经验撰写。文中提到的字段布局与命名以 Unity 2022.3.x 版本为准，不同 Unity 版本的 Registration 表结构可能存在差异。
