MCP 写入反馈：让修改的结果可以理解

把一个材质参数改掉，工具返回“成功”。看起来任务已经完成，但打开编辑器，材质可能还在编译，磁盘上也可能仍是旧版本。

人亲自操作时，会从界面变化、编译提示和未保存标记里理解这些状态。Agent 通过工具工作，这些原本看得见的信息就成了设计的一部分。反馈过于简略时，模型只能猜；反馈塞满整个对象时，真正有用的结果又可能被埋住。

我更在意的反馈，是让这次修改变得可以理解。它让使用者知道自己的意图在软件里走到了哪里，也让后面的工作有一个可靠的起点。

结果影响的是下一次判断#

写入反馈很容易被当成一次调用的结尾。实际上，它往往决定下一次行动。

如果参数已经改动，只是编译失败，后续讨论应该围绕编译问题展开。如果修改还停在预览阶段，再去调整“修改后的结果”，就会从一个尚未发生的状态出发。

完整对象也未必能消除这种误解。一个字段出现了新值，无法说明保存是否完成；一份很长的响应，也可能没有解释失败发生在哪一段。

因此，我希望反馈贴近编辑这件事本身：变化是什么，软件实际接受了什么，哪里打断了原本的预期。读者理解了这些，才知道该继续调整，还是重新考虑这次修改。

可理解的失败比含糊的成功更有用#

复杂软件里的编辑很少只有一个瞬间。资源可能正在加载，编译可能发现问题，保存也可能遇到文件状态变化。一次修改在中途停下，是工作中很普通的情况。

最让人困扰的往往是停下以后失去了线索。例如，一批材质里前两个已经保存，第三个编译失败。如果最后只剩一句“操作失败”，前面发生过的工作也一起变得不确定。

保留这些具体结果以后，失败就能进入正常讨论。已经完成的部分可以继续使用，出问题的部分有明确对象，使用者也不必为了确认状态重新检查整个工程。

这种体验让我觉得，工具反馈的质量很大程度上体现在失败时。它是否仍然保留了工作上下文，决定了一个小问题会不会变成一次重新开始。

文本中的意图与软件中的结果可以互相对照#

文本化让修改前后的差异很容易呈现，但文件表达的首先是编辑意图。软件接受以后，可能补全属性、规范化内容，也可能发现某个连接无法成立。

当这些结果能重新对应到原来的修改，文件就成为持续工作的依据。人可以沿着差异理解执行结果，Agent 也能在原来的内容上继续修正。

我不希望使用者必须读完一串调用历史，才能判断一个参数究竟有没有生效。编辑前后的内容，以及软件对这次变化的回应，通常更接近人真正想知道的事情。

这也是写入反馈与文本化相互补充的地方：文件保留了修改意图，结果说明它在软件里变成了什么。

信任来自看得懂的过程#

工具能完成多少动作，很容易在演示中展示。使用者是否愿意把连续工作交给它，则与结果是否清楚有关。

一次失败能够解释，未完成的工作能够接上，已经产生的变化能够确认，人就可以逐渐建立对工具的判断。反复返回模糊的“成功”，反而会迫使使用者每次都从头核实。

我希望 MCP 带来的信任来自这种可理解性。Agent 可以承担更多操作，人仍然知道自己的内容发生了什么。反馈由此成为编辑体验的一部分，贯穿每一轮修改。
