Metadata 提供类型和字段名称，Registration 提供它们的运行时位置。字段偏移、方法地址和类型布局属于 Registration 表，需要从 GameAssembly.dll 的运行时数据里恢复。

结论先行#

global-metadata.dat 解决的是静态语义，CodeRegistration 和 MetadataRegistration 解决的是运行时映射。外部工具要从 IL2CPP 目标中恢复可用的对象布局和方法地址，必须把这两部分接起来。

核心链路是：先用 metadata 拿到 typeDef index、fieldSlot、method token 这些静态索引，再定位 Registration 表，从 fieldOffsets、typeDefinitionsSizes、codeGenModules 等运行时数组里取出实际偏移和地址。

这也是跨版本字段偏移查询成立的原因：字段偏移不是靠硬编码表维护，而是由 IL2CPP runtime 自己生成并保存在 MetadataRegistration 中。只要能定位这张表，就能按 typeDef index 动态恢复字段布局。

1. Metadata 和 Registration 的职责边界#

IL2CPP 的数据可以分成两层：

层级代表数据解决的问题
静态 metadataglobal-metadata.dat类型、字段、方法、参数、assembly 的语义定义
运行时 registrationCodeRegistration / MetadataRegistration方法地址、字段偏移、类型大小、泛型实例等运行时映射

metadata 负责这些信息：

  • 有哪些类型。
  • 每个类型有哪些字段和方法。
  • 字段和方法叫什么。
  • 类型之间的继承和组织关系。

运行时映射则来自 Registration 表：

  • 某个字段在对象内存中的偏移是多少。
  • 某个方法的 native 函数地址。
  • 某个类型在运行时的大小是多少。
  • 某个泛型实例最终对应哪份运行时类型数据。

这些答案都要从 Registration 表里取。

2. 两张 Registration 表分别负责什么#

IL2CPP AOT 编译阶段会在 GameAssembly.dll 中生成两类全局登记表。

CodeRegistration 负责 native 代码入口：

数据用途
method pointers普通方法的 native 地址集合
generic method pointers泛型方法实例的 native 地址集合
invoker pointers运行时统一调用入口
codeGenModules按 assembly / module 组织的方法指针表

MetadataRegistration 负责运行时类型布局：

数据用途
genericClasses泛型类实例登记
genericInsts泛型参数组合
types运行时类型条目
fieldOffsets每个 typeDef 的实例字段偏移数组
typeDefinitionsSizes每个 typeDef 的类型大小和布局信息

可以把两者理解成同一套类型系统的两个方向：

外部工具需要两者一起工作。只有 metadata，没有 Registration，只能生成静态 dump；只有 Registration，没有 metadata，则很难知道某个数组槽位对应哪个 C# 类型或字段。

3. 为什么 Registration 需要扫描定位#

CodeRegistration 和 MetadataRegistration 没有导出符号。不同 Unity 版本、不同构建目标、不同游戏工程里，它们的地址都不一样。

外部工具一般只能拿到这些基础信息：

  • GameAssembly.dll 的模块基址和大小。
  • 模块节区信息，例如 .data、.rdata、.text。
  • 已导出的 metadata bytes。
  • metadata header 中能推导出的 typeDef 数量、image 数量等统计值。

Registration 扫描的思路不是找固定地址，而是找“结构体内部的数量关系”。这些数量关系来自 metadata 和 runtime 之间的对应关系。

两个最有用的锚点是：

锚点对应结构原因
codeGenModulesCount == imageCountCodeRegistration每个 metadata image 对应一个 codegen module
fieldOffsetsCount ≈ typeDefCountMetadataRegistration每个 typeDef 对应一组字段偏移槽

这就是双模扫描的基础。

7. Struct 和 enum 的偏移修正#

IL2CPP 中 class 和 value type 的布局语义不同。外部工具读取 struct / enum 字段时，经常需要处理对象头差异带来的偏移修正。

判断一个类型属于 class、struct 还是 enum，可以从 metadata 的继承关系推导：

类型判断方式
class普通引用类型，父类不是 System.ValueType / System.Enum
struct继承自 System.ValueType
enum继承自 System.Enum

因此字段偏移查询要结合类型种类解释 raw offset。同一个 raw offset 在对象实例和 value type 内部视角下可能产生偏差。

这个设计看起来细，但很重要。字段偏移查询如果因为短名冲突读错类型，后续跨进程读取会直接变成错误地址解释。

  • GameAssembly 基址改变。
  • 目标重新加载或切换进程。
  • Registration 定位失败或 metadata 重新导出失败。

缓存命中后，字段偏移查询就是普通 map 查询，不再需要重复扫描 GameAssembly。

10. 边界与风险#

这套方法依赖 IL2CPP 运行时数据结构仍然可读：

  • MetadataRegistration 必须能定位。
  • fieldOffsets 没有被加密或虚拟化保护。
  • metadata 必须完整，能够建立 typeDef 和 fieldDef 索引。
  • Registration 字段顺序必须与目标 Unity 版本匹配。
  • 静态字段不适用 fieldOffsets，需要查类型静态数据区。

它也不是反加固万能方案。如果目标对 Registration 表做了结构扰动、字段重排、运行时解密或访问陷阱，单纯数量锚点会失效，需要先分析保护层行为。

但在常规 Unity 2020-2023 IL2CPP 目标上，metadata + registration 组合已经足够恢复大部分对象布局和方法入口。

11. 结论#

IL2CPP 外部解析的核心不是单独解析 metadata，也不是单独扫描 registration，而是把两者接成一条链：

metadata 提供“名字和索引”，Registration 提供“地址和布局”。动态字段偏移查询正是利用这个分工：用 metadata 找到字段在类型中的槽位，再用 MetadataRegistration::fieldOffsets 读取运行时偏移。

这样做的价值是跨版本。外部工具不再需要为每个 Unity 版本维护一份字段 offset 表，而是把目标进程自己的 Registration 当作事实来源。只要 runtime 数据结构可读，字段偏移和方法地址就可以从目标本身恢复出来。
