拿到 global-metadata.dat 后，可以知道一个类型有哪些字段和方法，但这些定义还没有完整对应到目标进程中的地址。Registration 数据提供了继续连接它们的入口：类型定义索引对应布局数据，方法定义则通过模块、token 或泛型映射接到生成代码。

这里的“运行时恢复”，指的是从运行中的目标读取这些关系。Registration 中的许多数组本身由 IL2CPP 在生成代码阶段产生，随后在初始化时登记，并非运行时临时计算出的完整类型数据库。

两类登记数据连接定义与实现#

CodeRegistration 主要组织生成代码相关的数据，例如泛型方法指针、调用包装入口，以及按模块组织的 codeGenModules。具体字段与组织方式依赖版本；较老版本的普通方法表与较新版本的模块方法表，不能按同一种布局读取。

MetadataRegistration 则包含类型条目、泛型参数组合、字段偏移和类型大小等生成数据。它们参与 runtime 类型系统的建立，但已经膨胀的泛型类型、对象实例和当前 vtable 还可能需要继续查询运行时结构。

数量关系可以缩小候选范围#

Registration 的符号可能被剥离，地址也会随构建改变。扫描时可以利用 metadata 提供的数量作为锚点，再检查候选结构是否连接到有效数组。

例如，在已确认采用模块代码表的目标中，codeGenModulesCount 与 Image 数量的对应关系值得检查；fieldOffsetsCount、typeDefinitionsSizesCount 与 TypeDef 数量的关系也能帮助寻找 MetadataRegistration。

这些关系需要按具体版本确认。数字相等只产生候选，模块名称、数组边界、方法表结构和多个类型的布局一致性，才让候选更可信。已知注册调用或生成代码的引用关系，则能提供更直接的定位依据。

偏移需要结合存储位置解释#

字段表中的值不总是“加到对象指针上就能访问”。实例字段、静态字段和线程静态字段对应不同存储位置；某些特殊情况还使用标记值。

普通引用类型的实例字段通常相对于对象布局解释。静态字段则要结合类型的静态数据区，线程静态字段还涉及当前线程的存储。字段偏移表可以包含静态字段的相关偏移或特殊标记，因此也不能简单说静态字段与这张表无关。

值类型还有装箱与未装箱的区别。一个 struct 嵌在对象或数组中时，访问起点通常是其数据区；装箱后，外面又有对象头。若表中偏移采用带对象头的表示，而读取起点是未装箱数据，就需要按目标版本的语义转换。这个修正不能对所有值类型无条件执行，也不能把某个架构的对象头大小当成通用常量。

泛型会进一步影响布局。含有泛型参数的字段，其大小与排列可能取决于具体类型实参，这时开放类型定义的生成数据未必足以描述实际实例，需要结合已经构造的运行时类型。

方法定义与机器代码不是一一对应#

在按模块组织方法表的版本中，普通方法可以借助所属 Image、方法 token 和模块方法表寻找入口。具体槽位换算、有效范围和空值含义仍要遵循该版本格式。

抽象方法、被裁剪的代码或具有特殊实现方式的方法，不一定有一个可直接调用的独立 native 函数。泛型方法还可能共享实现，通过额外的泛型信息区分语义。invoker 也承担统一调用适配的职责，与方法体入口有不同用途。

因此，从定义查到指针后，还需要确认它代表方法体、包装入口还是共享实现，以及调用时需要哪些上下文。一个地址落在可执行页，只能证明它可能是代码，不能独自证明方法身份与调用约定。

缓存应绑定到具体进程实例#

名称到定义索引的查询适合缓存，Registration 定位结果也不必每次重扫。但缓存中的地址属于具体进程实例和模块装载。

PID 与模块基址都可能被复用。缓存身份应结合进程创建时间或等价实例标识、模块身份和装载状态；若数据会重新初始化，还需要对应的失效依据。类型短名也可能跨命名空间或程序集重复，查询缓存应保留完整类型身份，短名只用于明确无歧义的入口。

最终能够长期复用的是解析关系：用定义找到槽位，用登记数据解释生成布局，再用 runtime 状态补足实例语义。某次读取到的地址只是这套关系在一个目标进程中的结果。
