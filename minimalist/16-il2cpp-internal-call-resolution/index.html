某个 UnityEngine 属性第一次被访问时，会先经过名称查找，后面却直接跳到一个缓存地址。只看这段代码，很容易把缓存误认为属性结果；继续进入目标函数，才会发现每次访问仍然执行了引擎逻辑。

这里缓存的是 internal call 的 native 入口。它把 GameAssembly 中的 generated wrapper 与 UnityPlayer 中的引擎实现接起来，省掉的是重复解析名称的过程。

Wrapper 缓存了调用目标#

以常见的 UnityEngine.Camera::get_main() 为例，GameAssembly 一侧可以有一个很薄的包装函数。它先读静态函数指针；为空时调用 resolver，取得地址后写回；随后通过这个指针进入引擎。

两条路径都抵达真实实现。缓存中保存的并不是某个 Camera 对象，也没有因此固定住属性的返回结果。场景变化后，真实函数仍然可以返回不同对象。

这是理解惰性解析最重要的一点：入口查找与业务查询发生在不同层次，它们可以具有完全不同的频率。

名称在注册与解析两端相遇#

il2cpp_codegen_resolve_icall 接到名称后，将查询交给 InternalCalls::Resolve。解析成功，地址返回给 wrapper；解析失败，则进入缺少实现的异常处理。

另一端是 UnityPlayer 的注册过程。引擎将 internal call 名称与 native 函数配对，通过 il2cpp_add_internal_call 写入运行时登记数据。样本中的 RegisterModuleICalls_Core 按模块遍历名称表与函数表，完成一批这样的关联。

因此，目标函数的身份可以从两端对照：wrapper 请求哪个名字，注册代码又把这个名字交给了哪个函数。分析不必停在“两个函数名字看起来相近”的推测上。

s_InternalCalls 承担的是名称到函数指针的映射。具体容器和节点布局属于实现细节；在这份分析中，添加端写入的位置与解析端取出的位置相互对应，才让映射关系成立。

完整签名与短名称可以共同参与查找#

generated wrapper 使用的名称可能包含参数部分，例如 UnityEngine.Camera::get_main()；引擎登记的名称则可能省略括号部分。

在所分析的 resolver 路径中，完整名称先被查询。如果未命中，代码再截取左括号之前的部分重新查找。这解释了为什么 wrapper 中看到的字符串，与注册表中的 key 并不总是逐字相同。

完整签名仍有意义。对于重载方法，参数信息可以帮助区分实现；截去参数后的名称能否使用，取决于对应登记方式。名称解析中的这一步，是连接两端字符串的具体行为，而不是靠相似名称猜测落点。

进入 native 函数后，才开始执行 API 的语义#

wrapper 得到函数指针以后，控制流进入 UnityPlayer。对一个对象查询属性而言，这里可能继续查找引擎对象，再将它包装成脚本侧可见的对象。

这一层才说明 API 实际做了什么。名称表能解释调用目标，目标函数里的查找、分支与包装过程，才能解释返回值。

也正因为如此，首次访问与后续访问即使经过不同的 wrapper 路径，最终仍会执行这段逻辑。观察到静态函数指针长期不变，无法据此推导业务结果也被缓存。

Internal call 与普通方法登记相互衔接#

IL2CPP 已经为大量 managed 方法生成 native 代码，并通过 Registration 组织这些入口。internal call 处理的是其中需要转接到引擎实现的一部分 API。

一个 managed 调用因此可能先进入 GameAssembly 的包装入口，再通过 internal call 到达 UnityPlayer。metadata、生成代码登记与名称解析各自参与不同环节，共同构成从类型定义到真实执行的路径。

读懂这段间接调用以后，最初那个静态缓存也就有了清楚的含义：它保留了已经找到的引擎入口，让以后的调用直接从那里继续。
