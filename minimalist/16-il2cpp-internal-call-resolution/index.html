UnityEngine API 看起来像普通 managed 属性，IL2CPP 产物里却不是一条直接调用链。第一次访问时，generated wrapper 通过 internal call 名称惰性解析到 UnityPlayer 的 native 函数并缓存；后续访问直接跳到缓存地址。

机制总览#

IL2CPP 的 internal call 是一套把 managed API 注册、解析到 engine native 函数的机制。它解决的问题不是 metadata 解析，也不是普通 C# 方法的 AOT method pointer 查找，而是把一部分运行时需要引擎实现的 API，从 GameAssembly.dll 转接到 UnityPlayer.dll。

<API> 的调用链不是直接从 generated wrapper 跳到 <EngineFind>，而是先经过 internal call 解析。第一次调用走 resolver，后续调用只读缓存，跳到 UnityPlayer 的 native 函数。

这张图涉及两个边界。

第一，缓存发生在 generated wrapper 层。_il2cpp_icall_func 缓存的是 UnityPlayer native 函数指针，不是 Camera 对象，也不是 <EngineFind> 的结果。

第二，InternalCalls::Resolve 处理的是名称到函数指针的映射。它查询 s_InternalCalls，必要时把 <Namespace.API>::<Method>() 裁剪成 <Namespace.API>::<Method> 再查一次。注册这个名字的是 UnityPlayer 启动阶段的 RegisterModuleICalls_Core。

1. Internal call 在 IL2CPP 里的位置#

IL2CPP 并非所有 managed 方法都只靠 CodeRegistration 里的 method pointer 解决。一部分 UnityEngine API 的真实逻辑在引擎 native 层，例如场景、对象、相机、物理、渲染等模块。GameAssembly 侧是稳定入口，UnityPlayer 侧才是具体实现。

internal call 不替代 metadata，也不替代 registration。它补的是另一条桥：当某个 managed API 的实现属于引擎 native 层时，IL2CPP 通过字符串名找到对应 native 函数，再由 wrapper 跳过去。

_il2cpp_icall_func 是 wrapper 的静态缓存槽，初始为 0。第一次解析成功后写入 <NativeImpl> 地址。解析失败不写入空值，而是由 il2cpp_codegen_resolve_icall 抛出异常。

这个状态机是 internal call wrapper 的关键：解析只为找到 native 入口，真实业务逻辑每次仍然执行。对 <API> 来说，后续调用跳过的是字符串解析，不是 <EngineFind>。

3. resolver 的 name → function 映射#

il2cpp_codegen_resolve_icall 是 wrapper 调用的解析入口。它保存传入的 internal call name，然后调用 InternalCalls::Resolve。如果返回值非空，就把函数指针返回给 wrapper；如果返回值为空，则构造 MissingMethodException 并抛出。

resolver 的边界在于：不执行 <API> 的业务语义，只负责把字符串名解析成 native 函数指针。业务语义要等 wrapper 拿到函数指针并跳进 UnityPlayer 后才发生。

InternalCalls::Resolve 使用的全局注册表是 s_InternalCalls，访问模式符合树形 key/value 容器：按字符串 key 查找，命中后取节点中的 native 函数指针。分析中，Resolve 读取 value 的位置和 InternalCalls::Add 写入 value 的位置互相印证。

5. UnityPlayer 负责批量注册 engine native 函数#

s_InternalCalls 的数据来源于 UnityPlayer。UnityPlayer 的 RegisterModuleICalls_Core 遍历 Core 模块的 internal call 表，把 name/function 对交给 il2cpp_add_internal_call。GameAssembly 侧通过 InternalCalls::Add 写入 s_InternalCalls。

Core 模块注册函数使用两张并列表：函数表和名称表各一个指针，注册数量已知。循环每次取出 funcs[i] 和 names[i]，调用 il2cpp_add_internal_call(names[i], funcs[i])。

这说明 <NativeImpl> 不是靠字符串搜索猜出来的落点，而是 UnityPlayer 注册表显式绑定的结果。

6. native 落点才承载 API 语义#

<API> 解析出的 native 函数是 <NativeImpl>。这个函数不是 resolver，也不是 cache 管理逻辑，而是 UnityPlayer 侧实现。

核心行为：调用 <EngineFind>，找到 engine object 后调用 <WrapperFor> 包装成脚本侧可见对象；未找到则返回空对象。

关键：<API> 每次调用进入 <NativeImpl>，执行 <EngineFind>。_il2cpp_icall_func 只缓存”跳转目标 native 函数”，不缓存”每次调用的 engine object 结果”。

7. 逆向分析时的通用识别路径#

<API> 抽象成通用路径后，分析其他 internal call 按同一顺序推进。

这条路径的分析顺序：wrapper 缓存 → resolver 调用 → UnityPlayer 注册项 → native 函数行为。落点判断依赖注册表中的显式 name/function 绑定，不是单纯从 UnityPlayer 里找一个名字相近的函数。

证据边界#

基于 PE、PDB 与本地反汇编/表解析产物。关键实体角色：

  • generated wrapper：GameAssembly.dll 中的 wrapper，包含 cache slot 和 resolver 调用。
  • _il2cpp_icall_func：wrapper 的静态缓存槽，初始为 0。
  • il2cpp_codegen_resolve_icall：resolver wrapper。
  • InternalCalls::Resolve：查询 s_InternalCalls。
  • InternalCalls::Add：写入 s_InternalCalls。
  • RegisterModuleICalls_Core：UnityPlayer Core ICall 批量注册。
  • <NativeImpl>：UnityEngine API 的 native 落点。
  • <EngineFind> / <WrapperFor>：native 落点内部的查找与对象包装。

换 Unity 版本、构建配置或平台后，地址和符号名都可能变化，但“wrapper 惰性缓存 → resolver 查表 → UnityPlayer 注册 → native 落点”这条结构关系仍然是分析 internal call 的核心路径。

结论#

IL2CPP internal call 是 UnityEngine API 进入引擎 native 实现的一条桥。generated wrapper 不直接承载业务逻辑，而是维护一个惰性解析缓存；InternalCalls::Resolve 把字符串名映射到 native 函数指针；UnityPlayer 的注册函数在启动阶段把 name/function 对写入 GameAssembly 的 internal call 表。

<API> 展示的链路：第一次调用解析 <Namespace.API>::<Method>()，通过括号裁剪命中 <Namespace.API>::<Method>，拿到 <NativeImpl> 并写回 wrapper 缓存。后续调用直接跳到这个 native 函数，但每次仍执行 <EngineFind> 和对象包装逻辑。

所以整个闭环可以这样看：generated wrapper 提供入口，GameAssembly 保存映射，UnityPlayer 负责注册实现，最终由 native 函数承载语义。
