MCP 对话的上下文窗口有限，但工具返回的数据天然膨胀。优化不是”少返回点字段”，而是重新设计数据表示和加载策略：字段名字典化、数字索引替代长字符串、视觉符号表达结构、不同场景用不同”焦距”。

思路一句话#

上下文优化不是”少返回字段”，而是三层重构：工具定义层（常驻菜单→按需查询）、数据表示层（嵌套 JSON→字典索引文本）、加载策略层（一刀切→分层按需）。字典索引文本让字段名只出现一次，数字索引替代长字符串。

一、上下文压力的来源#

Agent 与 MCP Server 交互时，上下文被三部分占用：

  1. 工具定义 —— list_tools 返回的 schema
  2. 请求参数 —— Agent 构造的调用参数
  3. 工具返回 —— Server 返回的数据

传统优化只关注第 3 部分（压缩返回数据）。但第 1 部分（工具定义常驻）和第 3 部分（返回格式膨胀）同样重要。

解法：字典索引文本#

段含义
T类型字典：索引=类名
N节点表：索引:类型索引:显示名
V参数值表：节点索引:参数字段=值

字段名只在字典中出现一次。节点引用用数字索引。视觉符号表达结构。

四、按需加载：不同场景用不同”焦距”#

不是一刀切返回同一种格式，而是按场景选择：

场景格式内容
导航找节点tiny极简节点字典 + 边表
整图复刻indexed字典索引文本，不带位置
人读概览grouped按类型聚合，只返回输入视角
编辑单节点detail完整节点视图
调试排错full完整字段和真实 ID

这套”焦距”分级让导航、复刻、精读各取所需，不必每次都返回同一种格式。

六、Response Mode：同一接口的不同”焦距”#

同一工具支持多种返回粒度：

Mode行为
silent只返回成功/失败、错误计数
brief返回一句摘要
delta返回变更摘要和 diff token
summary返回当前状态摘要
full返回完整 data 负载
debug返回完整 envelope

写操作默认 delta。Agent 不需要完整状态，只需要”改了什么”。

七、小结#

上下文优化不是”少返回点字段”，而是三层重构：

  1. 工具定义层：从常驻菜单变成按需查询
  2. 数据表示层：从嵌套 JSON 变成字典索引文本
  3. 加载策略层：从一刀切返回变成分层、按需、可调焦距

落到实处就是几件事：字段名只出现一次，状态留在服务端，Agent 只持 token，完整数据按需精读。

实践来源：一个 MCP 桥接项目，支持 7 种图数据格式、6 种 response mode、4 级 capability 查询。
