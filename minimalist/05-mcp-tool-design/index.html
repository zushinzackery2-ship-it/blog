UE 的材质和蓝图由大量节点、引脚和属性组成。最直接的 MCP 设计是把编辑器操作逐个变成工具：创建节点、设置参数、连接引脚。功能很快就能覆盖全，但真正用起来，一次很小的修改也会拆成十几次调用，每次返回的节点 ID 要带到下一次，整张图的 JSON 反复进入上下文。图越大，模型越像在对话里手工维护一张中间状态表。

问题不在工具数量，而在编辑对象放在了哪里。人在编辑器里工作时，界面替他保存当前状态；拆成工具调用以后，这份状态只剩在模型的记忆里。UE Node Nexus MCP 后来的设计都围绕一件事：把状态从对话里搬到文件里，让 UE 继续做编译器和渲染器。

资产先变成一份可以改的文本#

UE 插件导出资产的真实结构，Python 在本地转成紧凑的 .nexus 文本。一个材质函数大致是这样：

每行是 id : Class(参数) @ x,y，连接写成 src[.pin] -> dst[.pin]。几个格式选择决定了它好不好编辑：

  • 只写非默认值。 删掉一行属性就等于恢复默认，文件长度跟着“改过什么”走，而不是跟着类定义走。
  • 节点 ID 是名字，不是导出顺序。 前面插入一个节点，后面的引用不会整体重排，改一个参数只产生一行 diff。
  • 值沿用 UE 的 ExportText。 颜色是 (R=1,G=0,B=0,A=1)，资产是 /Game/Path/Asset.Asset，模型不需要学一套新的值语法。
  • 解析不了的节点标成 @opaque(...)。 它可以移动、删除和连线，但参数不让改，避免在看不懂的结构上猜测写入。

完整导出和节点映射留在本地的 .nexus/base/，不进入模型上下文。于是 Agent 用的是最普通的工具：读文件、grep、字符串替换。这些能力模型本来就很熟练，不需要为每类资产重新学一套调用协议。

一次修改走完“文本 → UE → 文本”#

文本只表达编辑意图，最终能不能成立，要由 UE 判断。一轮修改的循环是：

  1. ue_sync("status") 给出每个资产的三方状态：clean、local-modified、ue-modified、both-modified、local-new 等。同时附带 ue_dirty 和 ue_saved_changed，能区分“编辑器里有未保存的改动”和“磁盘上的已保存文件变了”。
  2. Agent 编辑 .nexus 文件。
  3. ue_sync("lint") 离线检查未知类、属性、枚举、引脚、类型错误和悬空连接，这一步不需要打开编辑器。
  4. ue_sync("push") 默认只做 dry run，返回执行计划。确认后，每个资产在一个编辑器事务里应用（Ctrl+Z 可以整次撤销），然后编译，只保存被改动的包（不用 SaveAll），重新导出，再把文本改写成规范形式。
  5. 编辑器里有人改过时，用 pull 拉回来。

最后那次回读很关键：UE 可能补全属性、规范化数值，也可能拒绝某条连接。改写后的文本就是软件真正接受的内容，与提交前的版本做 diff，就能看出意图和结果在哪里不一致。编译错误以 file:line: message 的形式返回，直接指向文本里出问题的那一行。

反馈要说清楚走到了哪一步#

“成功”这个返回值信息太少。参数可能已经写进内存，材质却还在编译，或者磁盘上仍是旧版本。反馈如果把整个对象塞回来，真正有用的变化又会被埋掉。

Nexus 的写操作默认返回 minimal 摘要和一个 diff_token，需要细节时再用 ue_diff_get 按 token 分页读取变更；大块读取结果改用 artifact 句柄，响应里只带估算的 token 量。一个批次中途失败时，.nexus/pending/ 下留有 raw export 和 *.push.json 恢复记录；发布还绑定一个持久的 apply_id，响应丢了可以查回执，不必重新检查整个工程。前两个材质已经保存、第三个编译失败，这三种状态都能分别查到，而不是只剩一句含糊的“操作失败”。

多个参与者在同一份工作上协作#

人和 Agent、两个 Agent 同时改一个项目时，最怕的是某一方提交整份结果，悄悄覆盖了另一方的改动。0.5.0 在解码层之上加了本地版本库：每个 Agent 先 checkout 一个独立工作区，在里面编辑、commit，再 push。

发布时按共同祖先与当前 UE 内存状态做三方语义合并：一方改了粗糙度、另一方改了颜色，属于不同字段，可以自动合并；两方改了同一个字段，返回带 base/ours/theirs 的冲突和 merge_id，由 resolve 按冲突逐个选择。冲突被缩小到具体字段，讨论的就是“这个值该取哪个”，而不是“谁的整份文件更新”。发布前还会检查内存 revision、editor epoch 和依赖的 read set，避免把候选状态写到一个已经变化的编辑器上。

历史动作也照搬了熟悉的版本控制语义：log/show/diff/blame、branch/tag、restore/revert、stash、cherry-pick/rebase/amend、reflog。restore 和 revert 只改工作区，再次 commit/push 才会修改 UE。尝试中的修改可以先留在草稿里，不会立即打断别人正在用的场景。

会话结束了，编辑器和工作还在#

一次 Agent 会话通常比一项工作短。早期接入的问题是，工具把编辑器当成任务的附属物：任务结束就关掉，下次连接又重新启动，用户自己打开的编辑器也可能被重复拉起。

0.6.0 把编辑器生命周期提升到用户级。不同工作区操作同一个 .uproject 时复用同一个编辑器；bridge_instance_ensure 统一启动仲裁，Guard 阻止普通编辑器重复启动，用户自己打开的编辑器保留其所有权。使用权以租约表示：默认 300 秒没有实际工作就失效，最后一次释放后再留 120 秒宽限，心跳和状态查询不会延长期限；其他会话、未保存的包和恢复中的事务都会阻止退出。

再加上文本镜像本身就落在 <Project>/Saved/Nexus/ 下，换一个模型、开一个新会话，或者干脆由人手动接手，面对的都是同一份文件、同一段历史和同一个编辑器。连接只是一次参与工作的机会，工作本身属于项目。

查找也交给环境保存#

项目一大，时间常常花在修改之前：同名资产有几个，真正被引用的是哪一个。Nexus 的 Auto-Index 在编辑器里持久维护资产与目录索引，提供 auto_index_overview、auto_index_query 和用模糊名解析路径的 auto_index_resolve_path。新会话不用从目录遍历重新开始。

索引只用来提供方向。它可能落后于刚刚发生的修改，动态引用也未必完整，所以结论仍要回到资产本身去确认。代码仓库的同类思路做成了独立的 auto-index-mcp：查找结果直接带回定义和引用所在的源文件，而不是另给一份需要信任的摘要。

文字与画面各管一半#

文本让结构和变化清楚，却代替不了最终画面。材质对不对，往往看一眼渲染就知道。所以 Nexus 保留了 viewport_capture，可以显式选择 level、active 或 pie 视口截图；回执记录实际渲染的世界、视口类型和截图提交帧。高风险变更（Niagara、材质的 Custom/WPO 等渲染契约、函数接口）还要先在一份隔离的 UE 副本里完成 apply、compile、save、readback，并确认编辑器正常退出。

回头看，MCP 的工具面反而收窄了：对外只有 ue_context_get、ue_capability_get、ue_execute、ue_read、ue_diff_get、ue_plan_validate 和 ue_sync 七个门面，具体操作按名查询 schema 后再调用。功能接入只是起点。修改有落点、结果能回读、冲突能缩小、会话之后能接着做，这些能力把工具调用连成了真正的工作。
