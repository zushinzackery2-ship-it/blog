MCP 设计理念：让 Agent 拥有合适的工作环境

我以前看 MCP 设计，最先注意的是功能覆盖：软件里有哪些操作，Agent 能不能调用，能否用更少的工具完成更多事情。这个方向很容易取得可见的进展，每开放一个动作，就多了一项能力。

现在我更关心另一件事：这些能力放在一起以后，Agent 工作得是否舒服。

能创建节点、修改参数、连接引脚，不等于能顺畅地修改一段逻辑。一次编辑可能被拆成许多次调用，前一次返回的标识要带到后一次，修改意图则散落在整段对话中。工具确实都可用，但完成一件事仍然很费力。

这也是我转向文本化优先的原因。我希望 Agent 面对的是一份可以持续阅读和修改的内容，MCP 则把这份内容与真实软件连接起来。

开放动作之后，工作仍然需要组织#

把一个软件的按钮逐个变成工具，是很自然的设计起点。它沿用了软件已有的操作方式，功能也容易对应。

问题在于，人操作界面时一直看得见当前状态。节点在哪里、刚才改了什么、还有哪条连接没接上，这些信息同时留在眼前。拆成工具调用以后，模型看到的往往只是一连串局部结果。原本由界面承担的组织工作，被转移到了对话里。

于是，看起来很小的修改，也可能要求模型反复读取、记住标识、拼接关系。增加更多工具能够扩大可操作的内容，却未必减轻这种负担。

我对 MCP 的期待因此发生了变化：除了让 Agent 能碰到软件里的东西，还希望它能用合适的方式理解和组织自己的工作。

文本让修改有一个稳定的落点#

一份工作文件可以同时容纳结构、参数和它们之间的关系。Agent 修改时，相关内容就在同一处；人审阅时，也能直接看到这一轮变化。

更重要的是，文件不依赖某一段对话存活。任务中断了，草稿仍在；换了模型，修改仍在；隔几天再回来，差异和历史仍然说明工作进行到了哪里。

这让我觉得文本化的价值比节省一次响应的字符数大得多。它让编辑拥有了自己的状态，而不用把一切都寄存在模型的记忆里。搜索、局部修改、比较版本这些成熟能力，也随之进入了原本只能通过专用界面操作的内容。

对 Agent 来说，这是一种熟悉而连续的工作方式。对人来说，它又提供了能够检查和讨论的共同材料。

MCP 连接的是编辑意图与真实软件#

文本可以表达修改，却代替不了软件本身。材质最终要经过编译，场景最终要被渲染，运行结果也可能暴露文字中看不出来的问题。

我希望 MCP 在这里发挥作用：让本地组织好的修改能够进入软件，也让软件中的结果重新变得可读。Agent 可以围绕文件思考，人可以围绕差异审阅，编辑器则继续承担它擅长的执行与展示。

界面仍然很重要。看一张渲染结果，往往比阅读一大段参数更容易判断材质是否合适。文本与画面分别提供了不同的认识方式：前者让结构和变化清楚，后者让最终效果可感知。

这样的分工，让 Agent 可以使用自己的编辑方式，也让人继续保有对作品的直观判断。

我更看重工作能否继续#

一次演示里，Agent 成功调用工具，很容易让人觉得接入已经完成。但长期使用时，更影响体验的是那些连续发生的小事：修改能否接着改，出错后能否找到原因，人接手时能否看懂前面的工作。

文本化多了转换与同步的成本，我愿意为它付出的原因，也在这里。一件复杂工作会被反复阅读、调整和讨论，稳定的编辑载体能在这些往返中持续发挥作用。

我现在理解的 MCP 设计，是为 Agent 建立一个能长期工作的环境。功能接入是起点，修改能够留下来、被理解、被接手，才让这些功能真正连成工作。
