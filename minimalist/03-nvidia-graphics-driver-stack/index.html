本文基于 NVIDIA Windows 图形驱动样本，对其在 Vulkan、OpenGL、D3D、DXGI 与 WDDM 之间的模块职责和接口边界进行静态分析。不声称完整复原闭源驱动内部算法，只聚焦可验证的模块职责、加载路径、API 边界与证据强度。

先把结论摆出来#

nvoglv64.dll 是 Vulkan/OpenGL 用户态核心，同时承载 ICD 与 present layer，具备 D3DKMT adapter 枚举能力。nvldumdx.dll 与 nvd3dumx.dll 是 WDDM 用户态入口。nvwgf2umx.dll 具备 CreateDXGIFactory2 等 DXGI 边界。nvapi64.dll 通过 query interface 暴露能力。nvlddmkm.sys 是 WDDM kernel miniport，覆盖显存、队列、DMA、present sync 等行为域。

一、样本与环境#

本次样本来自一台 Windows x64 环境中的 NVIDIA 驱动安装目录。注册表信息显示当前显示设备为 NVIDIA GeForce RTX 系列 Laptop GPU，驱动版本为 32.x 系列，驱动日期为 2025 年。

关键样本如下：

模块角色
nvoglv64.dllOpenGL ICD、Vulkan ICD、NVIDIA Vulkan implicit layer 承载体
nvldumdx.dllWDDM 用户态驱动入口，导出多个 OpenAdapter* 与 NVIDIA thunk
nvd3dumx.dllNVIDIA D3D 用户态驱动入口之一
nvwgf2umx.dll大型 NVIDIA D3D 图形 UMD，具备 DXGI factory 与显示拓扑查询边界
nvapi64.dllNVAPI 查询入口，公开 nvapi_QueryInterface / nvapi_Direct_GetMethod
nvlddmkm.sysNVIDIA WDDM kernel miniport
vulkan-1.dllWindows Vulkan loader
dxgi.dllWindows DXGI runtime
d3d12.dll / D3D12Core.dllWindows D3D12 runtime 与核心组件

二、总体结构#

NVIDIA Windows 图形驱动栈可以粗略拆成两条主路径。

这两条路径并不是互斥的。Vulkan 是应用面对的渲染 API，Windows 下最终呈现仍会进入 WDDM、DxgKrnl、DWM、DXGI 相关显示模型；D3D 用户态驱动与 kernel miniport 则承担资源、adapter、队列、显存与故障处理等底层职责。

三、注册表与 manifest：驱动入口从哪里来#

Windows 显示驱动注册表给出了最直接的入口关系：

  • ServiceImagePath 指向 nvlddmkm.sys，说明它是 NVIDIA kernel miniport。
  • UserModeDriverName 指向 nvldumdx.dll，说明它是 WDDM 用户态驱动入口。
  • OpenGLDriverName 指向 nvoglv64.dll，说明它是 OpenGL ICD。
  • VulkanDriverName 指向 nv-vk64.json，说明 Vulkan loader 通过该 manifest 找到 NVIDIA ICD。

nv-vk64.json 中的 ICD.library_path 指向 nvoglv64.dll，并同时声明两个 NVIDIA instance layer：

Layer描述入口
VK_LAYER_NV_optimusNVIDIA Optimus layervk_optimusGetInstanceProcAddr / vk_optimusGetDeviceProcAddr
VK_LAYER_NV_presentNVIDIA GR2608 layervk_gr2608GetInstanceProcAddr / vk_gr2608GetDeviceProcAddr

这说明 nvoglv64.dll 不只是 OpenGL 驱动，也不是单纯 Vulkan ICD。它同时承载 Vulkan ICD、Optimus layer 与 present layer。

四、nvoglv64.dll：Vulkan ICD、OpenGL ICD 与 D3DKMT 边界#

nvoglv64.dll 的导出表能看到三类入口。

第一类是 OpenGL ICD 入口，例如：

  • DrvCreateContext
  • DrvDeleteContext
  • DrvSetContext
  • DrvSwapBuffers
  • DrvPresentBuffers
  • DrvGetProcAddress

第二类是 Vulkan ICD 入口，例如：

  • vkCreateInstance
  • vkEnumerateInstanceExtensionProperties
  • vkEnumerateInstanceVersion
  • vkGetInstanceProcAddr
  • vk_icdGetInstanceProcAddr
  • vk_icdGetPhysicalDeviceProcAddr
  • vk_icdNegotiateLoaderICDInterfaceVersion

第三类是 NVIDIA implicit layer 入口，例如：

  • vk_optimusGetInstanceProcAddr
  • vk_optimusGetDeviceProcAddr
  • vk_gr2608GetInstanceProcAddr
  • vk_gr2608GetDeviceProcAddr

仅看导出表已经能确认 nvoglv64.dll 在 Vulkan / OpenGL 用户态路径中的位置。进一步看导入与 IAT 引用，nvoglv64.dll 静态导入 GDI32.dll!D3DKMTEnumAdapters2，并在 .text 中存在对应 IAT 跳板：

模块边界 API指令形态
nvoglv64.dllGDI32.dll!D3DKMTEnumAdapters2jmp qword ptr [rip + ...]

这证明它已经从字符串证据进入代码引用层面，具备进入 D3DKMT adapter 枚举边界的代码路径。

nvoglv64.dll 的字符串里还出现了 Failed to initialize swapchain image (%d)。结合 Vulkan ICD / present layer 入口，可以把它定位为 Vulkan WSI / present 相关路径的高优先级观察对象。这个字符串适合作为 present 相关线索，但 GR2608 内部控制流、DXGI/DWM/WDDM 具体分支仍需要运行态调用栈或更细的代码路径证据。

五、nvldumdx.dll 与 nvd3dumx.dll：WDDM 用户态入口#

nvldumdx.dll 导出表显示它是 WDDM 用户态驱动入口之一：

  • OpenAdapter
  • OpenAdapter10
  • OpenAdapter10_2
  • OpenAdapter12
  • QueryOglResource
  • NVAPI_Thunk
  • NVENCODEAPI_Thunk
  • NVDEV_Thunk
  • GetNvCameraUsageMode

这些导出说明 nvldumdx.dll 处在 D3D runtime / WDDM runtime 与 NVIDIA 内部 UMD 能力之间。它既负责 adapter 打开，也提供 NVAPI、NVENCODE、NVDEV 等能力分发入口。

nvd3dumx.dll 也导出：

  • OpenAdapter
  • QueryOglResource
  • SetDependencyInfo

因此它可以视为另一条 D3D 用户态驱动入口。由于二者导出边界高度偏 WDDM / adapter，博客中应把它们描述为”D3D/WDDM 用户态边界”，而不是简单归类为某个单一 API 的实现文件。

六、nvwgf2umx.dll：DXGI factory 与显示拓扑边界#

nvwgf2umx.dll 是样本中体量最大的 NVIDIA 图形 UMD。它的关键价值在于静态导入与代码区引用都指向 DXGI / display topology 边界。

导入与 IAT xref 结果如下：

模块边界 API指令形态
nvwgf2umx.dlldxgi.dll!CreateDXGIFactory2jmp qword ptr [rip + ...]
nvwgf2umx.dllUSER32.dll!GetDisplayConfigBufferSizescall qword ptr [rip + ...]
nvwgf2umx.dllUSER32.dll!QueryDisplayConfigcall qword ptr [rip + ...]

三个关键点：

  • CreateDXGIFactory2 说明 nvwgf2umx.dll 具备进入 DXGI factory 路径的能力。
  • GetDisplayConfigBufferSizes 与 QueryDisplayConfig 说明它会查询 Windows display topology。
  • 这些不仅存在于导入表，.text 内也有 IAT 引用。

此外，nvwgf2umx.dll 的字符串中出现了多项 present timing 指标：

  • AvgCpuRenderAsyncPresentTimeUs
  • AvgCpuSimToAsyncPresentTimeUs
  • AvgCpuRenderPresentTimeUs
  • AvgCpuSimToPresentTimeUs
  • AvgCpuSimEndToPresentTimeUs

这些字符串可以作为它维护 present 性能观测或遥测字段的辅助证据；具体 present 函数的内部实现还需要继续结合代码路径确认。

因此，nvwgf2umx.dll 在文章中可以稳妥表述为：NVIDIA D3D UMD 中具备 DXGI factory、显示拓扑查询与 present timing 相关行为域的模块。

七、nvapi64.dll：公开 API 很少，能力通过查询分发#

nvapi64.dll 的导出表非常小，主要是：

  • nvapi_QueryInterface
  • nvapi_Direct_GetMethod

这符合 NVAPI 的常见使用方式：公开导出并不直接暴露大量功能函数，而是通过 query interface / method table 分发内部能力。

在驱动行为链中，NVAPI 更适合作为”控制面 / 扩展能力入口”理解，而不是渲染 present 主路径本身。

八、nvlddmkm.sys：WDDM kernel miniport 行为域#

nvlddmkm.sys 是 NVIDIA 内核侧 miniport。它公开导出很少，样本中只看到：

  • nvDumpConfig
  • wPreRelocCRCCopy

这说明关键逻辑不依赖公开导出暴露。分析它更适合从 PE 分区、内核导入、IAT xref 与调试字符串入手。

PE section 中可以看到典型驱动分区，例如：

  • _DDTEXT
  • _KTEXT
  • PAGE_DD
  • PAGE_K
  • PAGE_MCM
  • PAGEDATA

内核导入与 xref 证据显示它确实进入多个 Windows kernel 边界：

模块边界 API证据形态
ntoskrnl.exeKeInsertQueueDpc.text 与 _DDTEXT 多处 call 引用

ntoskrnl.exeMmGetPhysicalAddressPAGE_MCM 中存在 call 引用
ntoskrnl.exeMmMapIoSpace / MmUnmapIoSpace静态导入存在
ntoskrnl.exeEtwWriteTransferIAT call 引用

字符串证据则进一步显示它涉及以下行为域：

九、Vulkan present 与 DXGI/D3D 的关系#

一个容易混淆的问题是：如果应用使用 Vulkan，为什么还能看到 DXGI / D3D12 / WDDM 相关对象？

从本文证据看，这不是矛盾，而是 Windows 图形栈分层导致的正常现象：

  1. 应用面对的是 Vulkan loader，即 vulkan-1.dll。
  2. Vulkan loader 通过 nv-vk64.json 找到 nvoglv64.dll。
  3. nvoglv64.dll 同时提供 Vulkan ICD、VK_LAYER_NV_optimus、VK_LAYER_NV_present/GR2608。
  4. Vulkan WSI / present 最终仍要进入 Windows 显示栈。
  5. NVIDIA D3D UMD 中的 nvwgf2umx.dll 又具备 DXGI factory 与 display topology 边界。
  6. 最终下沉到 DxgKrnl / dxgmms2 / WDDM miniport，也就是 nvlddmkm.sys。

因此，“Vulkan 应用”与”DXGI/WDDM present 对象”不是二选一关系。Vulkan 是上层渲染 API，DXGI/WDDM/DWM 是 Windows 显示与调度模型的重要下游。

十、Overlay 与 capture 层的边界#

样本中还存在 Steam、EOS、OBS 等 overlay / capture layer。它们需要单独拆开，否则容易把驱动行为误判为 overlay 行为。

模块证据判断
SteamOverlayVulkanLayer64.dll导出 vkCreateSwapchainKHR / vkQueuePresentKHR 等 Vulkan hook 入口能介入 Vulkan present，但当前样本没有静态 DXGI/D3D 创建入口证据
GameOverlayRenderer64.dll有 Vulkan overlay present 相关符号Steam overlay 运行时组件，但当前样本没有 D3D12 创建证据
EOSOVH-Win64-Shipping.dll静态导入 D3D11CreateDevice / D3D11CreateDeviceAndSwapChain具备 D3D11 overlay swapchain 能力，不等同于 D3D12 创建证据
graphics-hook64.dllOBS Vulkan layer negotiate 入口capture layer 存在，但当前样本无静态 D3D/DXGI 创建入口证据

所以在博客表述中，overlay 层应写成”可能改写或包裹 Vulkan present 的外部层”，不要把它们直接等同于 NVIDIA 驱动内部行为。

十一、结论#

这次静态分析能锁定的，是模块在驱动栈中的位置和它们暴露的接口边界：哪个承担 Vulkan ICD、哪个进入 DXGI factory、哪个下沉到 WDDM miniport。这些都是可复查的外部证据——注册表、manifest、导出表、IAT 引用、字符串。

锁不到的是内部实现。GR2608 present 在 nvoglv64.dll 内部怎么分支，nvlddmkm.sys 的显存淘汰和 page fault 策略怎么决策——这些依赖运行态调用栈或控制流证据，静态只能看到边界入口，看不到内部走向。

要把某条路径真正打通，下一步是从这里给出的边界点出发，运行态抓调用栈，看代码实际怎么从 Vulkan present 走到 DXGI / WDDM。

分析环境：Windows x64，NVIDIA GeForce RTX 系列 Laptop GPU，驱动版本 32.x 系列。
