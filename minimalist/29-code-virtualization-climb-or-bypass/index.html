分析资源加载时，调用链进入一段保护代码，原本清楚的函数突然变成了间接跳转和难以解释的字节流。很自然的反应，是继续拆开保护，直到看见算法。

但当时想解决的问题是读取资源。对这个目标而言，另一条路线也有价值：找到能够处理同一批输入的实现，再把输出与已有记录、文件结构和解析结果对照。

终末地归档恢复采用了后一条路线。理解这次选择，需要把两个问题分开：受保护程序内部怎样执行，以及外部数据怎样才能得到相容的处理。

虚拟化让原来的指令语义换了一种载体#

常见的代码虚拟化会把部分逻辑转换成自定义指令，再由随程序携带的解释器执行。分析者看到的原生指令，很多是在维护虚拟状态、寻找下一段处理代码。

一个常见模型包含虚拟指令指针、上下文和 handler。调度可以集中在一个循环中，也可以分散到 handler 之间；有的保护还混合原生代码或动态生成代码。因此，实际实现未必具有一张清楚独立的 handler 表。

图中展示的是便于理解的解释器模型。原始业务的加法、取值或条件跳转，被分散到对虚拟状态的操作中，直接阅读原生代码就多了一层转换。

反汇编中出现异常指令序列，也可能来自数据混排、错误的起始位置、加密或普通控制流混淆。这样的现象会提示保护存在，却不能独自确定某一套虚拟机结构。

调用与错误路径把归档工作带进同一段代码#

在终末地样本中，托管资源加载最终进入 AssetBundle.LoadFromFile。继续到 UnityPlayer，归档头读取入口 0x674090 跳到 0x23CBC05；归档解密失败字符串的引用位于 0x23CD155。后两个位置都落在 .tvm0 中。

这些关系把归档功能与该代码区联系了起来。入口附近还有间接跳转与混淆式控制流，让普通的线性反编译难以继续。要说明具体虚拟指令怎样工作，还得进一步识别调度和状态更新；入口跳转本身也可能是转发桩，不能单凭它排除其他实现形态。

还有一个很有代表性的误导：同一模块中的 PROTECTED 字符串，看起来与归档保护有关，交叉引用却把它带到了 Vulkan 的 memory-property 枚举。名称提供了联想，使用位置才解释了它在程序里的含义。

资源恢复把注意力转向输入与输出#

如果要解释某个受保护分支内部的行为，继续恢复它的指令语义很有价值。对于当时的资源读取任务，文件本身则提供了另一批可观察信息。

外层 VFS 有校验记录，内层归档有长度、块目录和对象关系。公开兼容实现又提供了稀疏变换、整数混淆与 LZ4 方言的候选形态。分析因此能够围绕具体输入展开：哪种组合保持了文件结构，哪种组合在解压或对象解析时失败。

这并没有让保护代码变得容易解释，而是让资源恢复暂时不必依赖对它的完整解释。两条路线得到的知识不同：一条逐渐认识程序内部，另一条逐渐认识可观察的数据处理关系。

一次通过如何变成一组相互对应的结果#

最小样本只有 2461 字节，包含一个压缩块和两个 node。候选处理完成后，物理区间、解压长度、node 覆盖和 Unity 对象解析可以放在一起比较。

随后，记录扩大到 InitBundle 的 1048 个包，解析出 19,370 个 Unity 对象，解包错误为零；再继续处理数十 MB 的 Shader 包，读取其中的程序结构。

这些结果说明兼容实现可以处理这批资源。它们没有自动揭示 .tvm0 的内部指令，也不说明所有未来输入都会得到相同结果。这里最有用的认识，是每一种样本增加了什么信息：小包让格式关系容易观察，大量包暴露分支差异，大载荷则检验更长的数据路径。

完整的数据分析过程见终末地资源的两层保护。

隐藏状态会改变这种比较#

文件处理很适合做输入输出对照，一个原因是输入通常能够保存和重放。若处理结果还依赖调用历史、不可见计数器或其他运行状态，仅保存文件就不够了。

相同文件在不同历史下得到不同结果时，首先暴露的是对输入认识不完整。分析可能继续寻找那些状态，也可能转向内部执行过程，理解它们在哪里变化。

候选实现也很重要。已有相近格式时，比较可以围绕几个具体差异推进；完全未知的密码变换，则不会因为有校验值就自动产生正确候选。校验能够筛选答案，无法替代寻找答案本身。

这些差别解释了为什么同样遇到保护代码，后续工作量可能相差很大。

两条路线各自回答一个问题#

语义恢复通常会结合动态轨迹，识别对虚拟状态的操作，再把它们转换为更容易阅读的表达。这个过程让内部执行逐渐清楚，也可能继续帮助解释尚未见过的输入行为。

兼容复现则把工作集中到已有输入和可观察结果上。它适合当时的资源恢复，是因为文件、校验、候选格式和下游解析器都提供了可用材料。

这次经历让我更关注开始时真正想知道什么。面对一段复杂保护，继续进入内部是一种有价值的选择；把问题接回数据，也可能得到当下更需要的结果。
