逆到一半，需要的算法体落进了一个虚拟化保护的节。反汇编器在那一段吐不出正常函数：寄存器取反、交换、临时压栈，跳转目标是运行时拼出来的，然后 jmp reg 跳进一片按普通指令边界解不开的字节流。

第一反应通常是”那就去虚拟化”。去虚拟化——恢复调度器、虚拟寄存器、handler 表、字节码语义——是这行里最贵的一类工作之一，而且很多时候根本不需要做。是否投入这项工作，取决于目标要求的是内部语义，还是一份可验证的输入输出兼容实现。

这篇不重复某一次具体分析的流水账，只讨论代码虚拟化出现后的决策：怎样确认归属，怎样区分语义恢复与兼容复现，兼容复现需要哪些判据，以及它在哪些条件下失效。案例是一个商业客户端的自研归档容器，它把核心头读取整体交给了一个 .tvm0 节。

先说决策框架#

  • 代码虚拟化把原生指令换成一台自带小虚拟机的字节码。你看到的不是被加密的 x86，而是另一套指令集加它的解释器。
  • 确认自己撞上虚拟化，靠的是几类独立证据叠加，不是看节名。
  • 语义恢复与兼容复现的分界是目标：要修改内部判断、解释源语义，就需要恢复虚拟程序；只要求在限定输入上复现行为，可以验证兼容实现。
  • 兼容复现需要强判据、多条彼此独立的约束、候选实现和足量语料。缺少其中任何一项，结论强度都会下降。
  • 拿不到候选且输出空间太大、算法带隐藏状态、目标要求修改内部逻辑、或者没有强判据时，兼容复现无法闭合。

为避免把”定位到虚拟化节”写成”已经恢复算法”，后文所有结论按三层表达：

等级能支持的结论归档容器案例

代码虚拟化改变了什么#

普通的加壳是把代码压缩或加密，运行时再解开——因为迟早要解回原生指令执行，静态分析拦不住多久。代码虚拟化换了个思路：它不把你的指令解回来，而是把它们翻译成另一套指令集，再随程序塞进一台解释这套指令集的虚拟机。

这台虚拟机的形状是固定的：

  • 调度器（dispatcher）：一个取指-译码-执行的循环。它按虚拟指令指针取出下一个虚拟操作码，去 handler 表里查地址，跳过去。
  • handler 表：每个虚拟操作码一个 handler，每个 handler 做一小步——一次加法、一次取内存、一次压栈。
  • 虚拟寄存器与虚拟栈：真实寄存器里存着虚拟指令指针（VIP）和虚拟栈指针（VSP），虚拟寄存器映射到一块上下文内存。
  • 字节码：你原来的函数，被编译成这套虚拟指令集的一段字节流。

执行时，原生代码走到一个入口桩，保存上下文、跳进虚拟机；调度器从 VIP 读操作码、查表、跳进 handler；handler 动一下虚拟状态、推进 VIP，再跳回调度器或直接串到下一个 handler。

这套结构直接解释了为什么线性反汇编在这里失效：字节流不是 x86，是虚拟指令集；调度是寄存器间接跳（jmp reg），静态拿不到目标；handler 之间夹着数据；操作码往往还逐条编码或轮转。你按普通函数边界去解，很快会撞到 sti、浮点指令和越界跳转目标——那不是代码错乱，那是你在把虚拟指令当 x86 读。

去虚拟化贵，也贵在这套结构：你要先认出调度器和 handler 表，把每个 handler 的语义提升成一条 IR，再顺着字节码把整段程序翻回来，最后化简掉混淆才看得到原始逻辑。这是一整条工具链的工作量，不是读几屏反汇编。

归属确认需要哪些证据#

看到一个独立命名的节就断言”这是虚拟化”是不够的——节名可以是任何东西，.vmp0、.tvm0、.enigma 或者干脆伪装成 .text。要确认，需要几类彼此独立的证据同时指向同一结论：

  • 节布局独立：PE 节表里有一个独立节，虚拟大小、原始数据区和权限与普通 .text 分开。
  • 实现整体转交：一个普通命名的函数，第一条指令就跳进那个节。不是编译器常见的尾调用，是把整个函数体交出去。
  • 错误路径同归属：这个功能相关的错误字符串，唯一的 RIP-relative 引用也落在那个节里。功能的正常路径和异常路径都经过它，才说明逻辑真的在里面。
  • 控制流形态：入口附近是寄存器取反、交换、临时压栈、运行时拼跳转目标再 jmp reg；线性解码很快得到不成立的指令序列。这是调度/解释路径的特征。

四条叠起来才能下”算法体归属于这个虚拟化节”的结论。单独任何一条都可能误判——尤其是字符串。在同一个 UnityPlayer.dll 里搜 PROTECTED 会命中，但查交叉引用会发现它属于 Vulkan 的 memory-property 枚举，跟归档保护毫无关系。字符串命中必须配调用上下文看，孤立的命中不是证据。

要强调的是，确认”它是虚拟化”和”它做了什么”是两件事。前者靠上面四条就能锁定；后者，也就是 handler 表、虚拟寄存器布局、字节码语义，那是去虚拟化的目标，不在确认这一步里。把”确认归属”写成”已经还原”，是这类分析最容易夸大的地方。

语义恢复与兼容复现由目标区分#

确认算法体在虚拟化节里之后，有两条路。

语义恢复是去虚拟化：恢复调度器、虚拟栈与寄存器、handler 表、字节码语义，再用动态轨迹逐条对照静态语义，最终得到等价的高层逻辑。产出是”这个函数内部怎样执行”。

兼容复现不解释节内程序，而是在限定输入输出空间里验证候选实现。产出是”一个在声明语料上与目标行为相容的实现”。

选哪条，看你要什么：

你的目标该走哪条为什么
复现它的输出（解资源、解协议、离线重跑）兼容复现只要声明范围内输入输出一致，不需要复刻调度器
读它的源语义（讲清算法、写报告、审计）语义恢复兼容实现不能代替内部执行过程
改它的行为（修改校验或控制分支）语义恢复外部复现无法改变节内判断
只想确认归属和边界都不必第二节的四条证据就够下结论

关键的范围变化发生在第一行：目标限定为兼容实现后，待解问题从”恢复内部指令语义”变成”验证候选输入输出行为”。后者可以由足够多、彼此独立的约束闭合，但结论范围也随之收窄。

兼容复现的四个成立条件#

兼容复现并不自动比语义恢复可靠，它有四个硬前提。缺少前提时，试错结果不能升级为事实。

第一，一个强判据。 你得有一个便宜的、结构性的”对没对”的检验。CRC、MD5、校验和、严格输出长度、格式能否重新解析、下游能否消费（解压器不炸、通用解析器能枚举对象），都是强判据。反面是弱判据：“解出来有可读字符串”——错误的 key、错误的顺序、甚至错误的算法都有相当概率蒙过弱判据，尤其当保护只改一小部分字节、大面积原文本来就可读的时候。判据弱，兼容结论就无法闭合。

第二，多条彼此独立的约束。 一条约束能被巧合满足；要几条来源不同的约束在同一组数值上同时成立，才不是巧合。物理区间闭合、严格解压长度、节点覆盖、路径语义——每条挂在不同的字段公式上，错一个地方就有一条不闭合。约束越独立，能通过的错误假设越少。

第三，最好有一个候选实现。 有候选，问题从”凭空还原算法”变成”验证这个假设”，难度差一个量级。候选可以来自公开的兼容实现、同系列的旧版本、有文档的格式族。没有候选，你就是在从输入输出反推算法本身，那要难得多。

第四，能拿到足够多的输入输出对。 一个样本能解只说明没在这个样本上暴露问题。要把”能解一个”升级成”稳定”，得拿全量样本跑，让实现暴露它对单一头长度、单一块大小、单一分支的隐式依赖。

这四条凑齐，兼容复现才成立：候选实现是可执行假设，强判据和独立约束把错误假设逐一否掉，全量样本把”能解一个”升级成”在声明语料内稳定”。结论成立不是因为程序跑通，而是因为几个来源不同的约束在同一组数值上交汇。

一个 .tvm0 段的兼容复现案例#

这个案例的资源归档解密采用了兼容复现。完整过程在资源两层保护，这里只提炼它怎样满足上面四条前提。

定位边界，先把算法体归属到 .tvm0。托管侧资源加载入口最终调用 AssetBundle.LoadFromFile，沿 GameAssembly.dll 没有第二套托管解密；归档头读取函数 UnityPlayer.dll + 0x674090 第一条指令就跳进 0x23CBC05，归档失败字符串的唯一引用落在 0x23CD155，都在 .tvm0 节内（RVA 0x23C6000）。第二节的四条证据在这里齐了：节独立、实现整体转交、错误路径同归属、入口是调度式控制流。结论只到”定制归档逻辑归属于 .tvm0”，没有恢复它的 handler。

然后是四条前提：

  • 候选实现：内层的稀疏 AES、字段变换和 LZ4 方言取自一份公开的第三方兼容实现，作为可执行假设，不当客户端逐指令结论。
  • 强判据：.blc 尾部 CRC32、文件记录 MD5、块目录声明的严格解压长度、manifest.hgmmap 展开后能被 Brotli 消费。任何一处只出现”可读字符串”都不算成功。
  • 独立约束：dataOffset + compressedSize 落在物理文件尾、所有 node 的 offset + size 恰好覆盖解压数据、路径构成合法的 Unity CAB / .resS 关系——四条同时闭合才把候选公式提升为本机事实。
  • 全量样本：从 2461 字节的最小样本，到 InitBundle 全组 1048 个包、19,370 个 Unity 对象、解包错误 0，再到数十 MB 的 Shader 包。

所以本案例的准确结论是：外层有直接指令证据；内层由候选实现经样本约束逐层闭合，输出能被通用解析器和全量扫描消费。它不等于 .tvm0 被翻译成了 C++，也不证明兼容实现与客户端在所有未见输入上同构。

可以复现的范围不能据此声明的范围
当前客户端样本的归档识别、解密、目录恢复与 UnityFS 重建.tvm0 的 dispatcher、handler、虚拟寄存器和字节码
InitBundle 1048 包与已验大型 Shader 包未纳入语料的版本、平台、历史状态和异常输入
各层校验失败时的明确拒绝客户端内部常量与每条兼容公式的逐指令来源

兼容复现在什么条件下失效#

兼容复现不是万能的。有几类情况会让前提失效，此时需要恢复内部语义，或直接收窄目标。

拿不到候选，且输出空间太大。 如果算法族无法收敛，又没有公开实现或同系列旧版可参照，问题就变成从输入输出反推算法本身。对一个带未知 key 的密码变换，约束只能排除已有假设，不能凭空生成可验证候选。这个案例能够采用这条路线，很大程度上是因为已有公开实现提供了候选形态。

算法带隐藏状态。 兼容复现通常假设可见输入足以决定输出。如果被虚拟化的例程跨调用保存不可见计数器、依赖历史的演进 IV，或使用系统时钟与硬件指纹，那么现有输入输出对不足以确定函数。同一个可见输入在不同历史下给出不同输出，约束就失去鉴别力。

目标要求修改内部判断。 兼容实现只能重放行为，不能编辑受保护函数。目标若是改变节内分支，就必须取得足够的内部语义；外部实现不能代替内部修改。

没有强判据。 如果数据里没有校验和、严格长度或能拒绝错误结果的下游消费者，就无法可靠区分候选。弱判据会让未发现的错误继续传播，症状往往出现在更远的阶段。

这四类条件出现时，兼容复现的证据链无法闭合。此时应转向语义恢复，或把交付范围明确缩到仍可验证的部分。

语义恢复的工作形状#

如果目标确实需要内部语义或修改行为，就要进入去虚拟化流程。这里只勾勒工作形状和代价；这个案例没有执行这条路线。

去虚拟化大致是四步。动态轨迹先跑起来：用调试器或动态二进制插桩，让受保护函数在真实输入上执行，记录它实际走过的指令，把调度器和 handler 从静态解不开的字节流里暴露出来。handler 识别与提升：把每个 handler 的语义翻成一条中间表示——这个 handler 是加法、那个是取内存、那个是条件跳。字节码解释：拿着 handler 语义顺着 VIP 把整段虚拟程序翻回一串 IR 操作，这才是你原来的函数。化简：常量折叠、死代码消除、把混淆抹掉，直到 IR 读得出原始逻辑，再用动态轨迹逐条校验静态语义。

代价集中在前两步：handler 常常自身也被混淆过，操作码可能逐条编码，商业级保护还会加多态、假分支和反调试。这是一整条工具链的投入，量级远高于只验证资源输入输出的兼容实现。

因此第三节按目标分流：当交付只要求限定语料上的输出复现、且四个前提都成立时，去虚拟化不会增加交付所需的证据；当目标要求解释或修改内部逻辑时，这项成本则无法省略。

复盘#

确认归属和恢复语义是两回事。 四类证据叠加能锁定”算法体在这个节里”，这一步不需要去虚拟化。把”确认归属”写成”已还原”是最常见的夸大。

目标决定工作层级。 解释或修改内部逻辑需要语义恢复；限定输入上的行为复现可以采用兼容实现。两种产出不能互相冒充。

兼容复现有硬前提。 强判据、独立约束、候选实现、全量样本，四者齐了才成立。缺少前提时只能降低结论强度。

失效条件应尽早确认。 没有候选且空间太大、存在隐藏状态、目标要求内部修改、没有强判据，都会使兼容复现失效。

边界必须显式声明。 兼容复现的产出是”与声明样本行为相容”，不是”完整还原”；确认归属的产出是”功能路径进入这个节”，不是”已经翻译成 C++“。这样读者才能判断哪部分可以复用，哪部分必须重新取证。

这个案例选择兼容复现，因为交付目标是恢复资源，而且四个前提都具备。目标或证据条件变化时，同一个 .tvm0 需要重新选择分析层级。
