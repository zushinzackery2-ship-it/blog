Vulkan 渲染的游戏，在抓帧工具、Overlay 或 Present Hook 中常能命中 DXGI/D3D12 对象。基于对 NVIDIA 用户态驱动 nvoglv64.dll 的静态逆向，这些对象来自驱动内部的呈现路径：Vulkan 完成渲染，驱动把最终图像接到内部的 DXGI/D3D12 呈现层输出。

现象#

在 NVIDIA 平台分析 Vulkan 游戏时，常见三类观察：

  • 抓帧工具（RenderDoc、PIX）里出现 IDXGISwapChain 对象。
  • 进程加载了 d3d12.dll，内存中存在 ID3D12Device 实例。
  • 在 DXGI / D3D12 的 Present 上挂 Overlay、录屏、延迟统计都能正常工作。

游戏业务代码只调用了 Vulkan，这些对象不由它直接创建。问题是它们从哪条路径进入进程。

结论#

  • 交换链图像由 Vulkan 路径创建并绑定内存，主渲染资源留在 Vulkan 一侧。
  • 最终 present 由驱动内部的 DXGI/D3D12 呈现路径提交到窗口。
  • 因此进程里的 DXGI/D3D12 对象来自 NVIDIA 驱动的呈现路径，既非游戏业务代码创建，也不代表 Vulkan 被转译成了 D3D12。

这条路径同时解释了工程现象：在 NVIDIA 平台，Vulkan 游戏的 present 会落到驱动内部的 DXGI/D3D12 呈现对象上，所以在这一层做 Hook 往往有效。

逆向样本与边界#

结论基于对 nvoglv64.dll（NVIDIA 用户态 GL/Vulkan 驱动）的静态逆向，观察对象是交换链创建、交换链图像内存绑定、present 排队与呈现线程提交四个环节。

需要先划清边界：这是当前驱动版本的实现模型，足以解释多数 Vulkan 游戏的 present 行为，但不覆盖所有驱动版本、GPU 型号和 Windows 版本。全部证据来自静态结构，不含运行期调用栈或内核态观测。

交换链图像由 Vulkan 路径创建#

判断主渲染在哪一侧，关键不在驱动是否加载 dxgi.dll，而在交换链图像由谁创建、图像内存由谁绑定。两个函数给出直接证据。

CreateVulkanSwapchainApiImages（0x180DD6A60）创建交换链图像对象，内部调用 CreateSwapchainApiImageObject，失败路径打印 Failed to create swapchain API image (%s)。这里创建的是 Vulkan 侧的交换链图像对象，而不是包装一个现成的 D3D12 纹理。

CreateAndBindVulkanSwapchainImageMemory（0x180DD5FB0）处理这些图像的内存，调用链固定为三步：

失败路径的字符串为 Failed to create swapchain image device memory (%s) 与 Failed to bind swapchain image (%s)。图像的内存需求、内存对象、内存绑定全部走 Vulkan 侧。若由 D3D12 承担主渲染，更自然的实现是以 D3D12 资源为主对象、Vulkan 侧只做互操作包装；当前实现顺序相反，主渲染资源模型在 Vulkan 一侧。

最终呈现由 DXGI/D3D12 路径提交#

图像渲染完成后，把它交给窗口系统的是另一条路径，核心函数是 DxgiSwapchainQueuePresent（0x180DE27A0）。

它不构造场景资源，做的是典型的呈现层工作：把 present work item 压入呈现队列，释放信号量唤醒呈现线程，记录共享围栏信号的起止，更新图像 release / present 计数，等待呈现侧事件同步。代表性调用与字符串：

Shared ID3D12Fence Signal 表明 D3D12 侧参与了共享围栏同步。这条路径真实参与输出排队与同步，而非空壳对象。

DxgiSwapchainQueuePresent 只负责入队，最终提交在呈现线程 DxgiPresentWorkerEntry（0x180DE0020）→ DxgiPresentWorkerMain（0x180DDFBE0）里完成。主循环有三段关键证据：

  • WaitForSingleObjectEx 等待前面释放的信号量，确认被唤醒的是处理 DXGI 呈现队列的 worker。
  • 从队列取出前面压入的 present work item，入队与出队形成闭环。
  • 一处虚表调用完成提交，前后紧跟 back buffer / present slot 处理、present flags 计算、提交结果映射回 VkResult、帧计数与 release / present 计数更新。

最后这处虚表调用位于同步阶段之后，上下文已是 back buffer 与 present flag 处理，静态上能定位到接近最终 Present / flip 的提交点。

蓝色为 Vulkan 侧的渲染与资源，橙色为驱动内部的 DXGI/D3D12 呈现与提交。

驱动内部的模块分工#

这条路径跨了两个用户态模块。nvoglv64.dll 承载 Vulkan ICD、VK_LAYER_NV_present 呈现层与上面看到的 DXGI present 队列和呈现线程；nvwgf2umx.dll 是 NVIDIA 的 D3D 用户态驱动，具备 DXGI factory 创建能力。

模块角色DXGI/D3D 相关能力
nvoglv64.dllVulkan ICD + VK_LAYER_NV_present + 内部呈现路径交换链图像创建、DXGI present 队列与呈现线程
nvwgf2umx.dllNVIDIA D3D 用户态驱动静态导入 CreateDXGIFactory2，代码区存在 IAT 跳板

nvoglv64.dll 还静态导入 GDI32.dll!D3DKMTEnumAdapters2 并在代码区存在 IAT 跳板。D3DKMT 是 WDDM 的用户态接口，Vulkan 驱动经它枚举适配器、与显示基础设施交互，这也是 present 进入 Windows 显示栈的边界。

与 Vulkan 被转译成 D3D12 的区别#

最终 present 经过 DXGI/D3D12，不代表 Vulkan 被转译成 D3D12。差别在主渲染资源：当前证据里，交换链图像、图像内存、渲染目标都在 Vulkan 侧，DXGI/D3D12 只出现在最终窗口呈现链。驱动做的是把 Vulkan 的最终结果桥接到内部 DXGI/D3D12 呈现层，而非用 D3D12 重渲一遍场景。

工程含义：Present Hook 与 Overlay#

这条路径解释了几个工程现象：

  • Vulkan 游戏能稳定命中 DXGI / D3D12 Present：最终窗口输出层在驱动内部就落在 DXGI/D3D12 呈现对象上。
  • 在这一层做 Overlay 有效：命中的是驱动真正参与最终输出的 present 层，不是旁路对象。
  • 录屏能拿到真实帧：这一层已靠近最终窗口输出，不再是应用内部的中间渲染阶段。

因此在 NVIDIA 平台，Vulkan 游戏不一定要走纯 Vulkan Hook，直接挂 DXGI/D3D12 Present 常常可用。

运行态确认方法#

静态分析锁定范围，精确来源需要运行态证据。在以下 API 上断点并记录调用栈：

按调用栈落点判断来源：

调用栈落点来源
nvoglv64.dll / nvwgf2umx.dllNVIDIA 驱动 present 路径
SteamOverlayVulkanLayer64.dllSteam Overlay
graphics-hook64.dllOBS capture
UnityPlayer.dll / GameAssembly.dll游戏或引擎显式桥接

Overlay 与 capture 模块（Steam、OBS）也可能介入 Vulkan present，但在当前静态样本中没有 D3D/DXGI 创建入口，落点会明确区分开。

证据边界#

当前结论覆盖三个环节：渲染资源来自 Vulkan 交换链图像，图像内存由 Vulkan 侧管理，最终提交由 DXGI/D3D12 呈现线程完成。这条静态证据链足以支撑驱动行为解释与 Hook 实践。

它仍是静态逆向得到的实现模型。要进一步坐实，需要运行期调用栈、ETW 跟踪或内核态观测，把静态定位的提交点对应到实际 flip。

分析环境：Windows x64，NVIDIA GeForce RTX 系列 Laptop GPU，驱动 32.x 系列。静态证据来自 PE 结构、imports/exports、IAT 引用与字符串提取。
