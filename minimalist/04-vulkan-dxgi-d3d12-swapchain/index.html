一个使用 Vulkan 的游戏进程，也可能加载 D3D12，甚至出现 DXGI 交换链。单看模块列表，很容易产生疑问：游戏到底使用哪套图形 API，这些额外对象又在做什么？

分析 NVIDIA 用户态驱动 nvoglv64.dll 时，可以找到一条有解释力的线索：Vulkan 侧的交换链图像创建，与包含共享围栏、呈现队列和 worker 的提交过程，出现在同一组相关代码中。

这使“渲染使用 Vulkan，呈现借助另一组内部对象”成为可以沿代码继续展开的解释。本文记录的是这份驱动样本中的静态分析过程。

这里观察到的是交换链图像及其内存管理。场景中其他渲染资源、底层分配是否共享，以及完整绘制过程，仍要沿各自的调用继续认识；仅凭交换链创建顺序，无法替整个渲染器作出结论。

呈现队列把工作交给另一条线程#

DxgiSwapchainQueuePresent（0x180DE27A0）的关注点已经转到呈现工作。它把 work item 放进队列，释放信号量，更新图像的 release / present 计数，并参与等待与同步。

共享 ID3D12Fence 的日志，与周围的同步操作相互呼应，说明 D3D12 相关对象参与了这条实现。队列随后由 DxgiPresentWorkerEntry（0x180DE0020）进入 DxgiPresentWorkerMain（0x180DDFBE0）处理。

worker 等待信号量，从队列取出工作项，再处理 back buffer、present slot 与 flags。它把提交结果转换回 VkResult，并继续更新帧与图像计数。入队和消费两端连起来以后，呈现线程的职责就比较清楚了。

其中一处虚表调用位于这些操作之间，是值得继续确认的提交位置。它究竟对应哪个具体接口，要由运行时对象类型与调用目标确定。虚表调用附近有 present 处理，并不能单独确定它就是某个固定的 Present 方法。

图中保留的是样本代码连接起来的对象关系。最后一个调用与实际窗口输出的对应，可以通过目标进程里的对象和事件进一步确认。

模块关系为这条路径补充背景#

nvoglv64.dll 同时承载 Vulkan ICD 与 VK_LAYER_NV_present。另一模块 nvwgf2umx.dll 具有 CreateDXGIFactory2 的导入和代码引用，说明 NVIDIA 的用户态驱动中还存在 DXGI factory 相关实现。

这些信息解释了驱动为什么具备跨 API 组织呈现的条件，但两个模块都拥有相关能力，并不自动证明每次呈现都会依次经过它们。

nvoglv64.dll 中的 D3DKMTEnumAdapters2 调用，则把适配器枚举接到了 Windows 显示基础设施。Vulkan 应用与 Windows 显示栈之间的联系，可以在这些具体接口上观察到。

Present 命中还要对应到正在显示的内容#

Present 属于 DXGI 交换链接口；ID3D12Device 本身没有一个 Present 方法。通常所说的“D3D12 呈现”，是 D3D12 工作与 DXGI 交换链配合完成的过程。

这份分析解释了一种可能的对象来源，但进程里还可能有游戏显式创建的交换链、Overlay 或录屏工具的对象。一次 Hook 命中，只说明代码经过了那个位置。对象属于哪个窗口，当前图像来自哪里，才决定它与目标画面的关系。

因此，创建交换链时的调用栈、对象所属窗口，以及呈现时使用的资源，比单独出现一个 dxgi.dll 或 d3d12.dll 更有解释力。它们能把“进程里存在这个对象”推进到“这个对象参与了正在观察的输出”。

驱动内部出现 DXGI 与 D3D12，并不意味着整个 Vulkan 场景被转换成另一套 API 重绘。沿着交换链图像、同步与提交去理解，可以看到图形 API 与窗口呈现之间更具体的分工。

分析样本：Windows x64，NVIDIA GeForce RTX 系列 Laptop GPU，驱动 32.x 系列。函数名称与地址沿用该样本的分析记录。
