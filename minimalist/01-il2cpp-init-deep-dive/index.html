双击运行 Unity 游戏时，引擎内部经历的不只是“加载 GameAssembly.dll，然后调用 il2cpp_init”。UnityPlayer 负责把脚本后端接进引擎主循环；GameAssembly 负责把 AOT 代码、global-metadata.dat 和 registration 表组合成可查询、可调用的运行时世界。本文基于 Unity 2022.3.62 IL2CPP 产物的逆向观察，按启动序列拆开这条链路。

整条链的骨架#

UnityPlayer 在运行时动态加载 GameAssembly.dll，再用 LoadDynamicLibrary + LookupSymbol 把一批 il2cpp_* API 绑过来。这么做是为了让 UnityPlayer 跟脚本后端解耦——它只管调 il2cpp_init、il2cpp_class_from_name、il2cpp_runtime_invoke 这些 C API，导入表里并不硬绑 GameAssembly。

GameAssembly 的核心任务是把三类数据接起来：

启动完成后，IL2CPP runtime 才能回答这些问题：

  • 某个业务程序集里有哪些 image、class、method。
  • 某个业务方法最终关联到哪个 MethodInfo。
  • 一个字段在对象内存里的偏移是多少。
  • 一个普通方法、泛型方法、反射调用分别走哪个 native 入口。
  • UnityPlayer 或 IL2CPP runtime 通过 il2cpp_* API 查询类型时，从哪里取结果。

IL2CPP 启动的核心是两条会合的初始化链路：

理解这条链时，重点在于分清 registration 链和 runtime init 链：前者把 generated registration 表挂入 runtime，后者在 MetadataCache::Initialize 阶段消费这些表并建立运行期索引。

下面按运行时边界分块展开：UnityPlayer 和 GameAssembly 的职责、启动阶段、registration、metadata cache、运行时查询世界分别放在对应段落里看。

当前样本的证据边界也要先说清楚：本文已经核对 UnityPlayer 动态加载和 API 绑定、il2cpp_init → Runtime::Init → MetadataCache::Initialize 主链、MetadataLoader 定位并映射 global-metadata.dat 的调用链，以及 g_CodeRegistration / g_MetadataRegistration 的字段级 count/pointer。当前没有取得 global-metadata.dat 实体，因此本文不声明已解析 metadata magic、version、header、table 范围，也不把 registration count 直接等同于 metadata 文件表行数。

两个 DLL 的职责边界#

Unity IL2CPP Windows 产物至少有两个核心 DLL：

模块主要职责对 IL2CPP 启动的角色
UnityPlayer.dll引擎主体，窗口、输入、渲染、音频、主循环选择脚本后端，加载 GameAssembly，绑定 IL2CPP API
GameAssembly.dllC# AOT native code + IL2CPP VM提供 il2cpp_* 导出函数，初始化 metadata、registration、GC、线程、类型系统

这里要留意：UnityPlayer 和 GameAssembly 之间没有 PE Import Table 的静态绑定，il2cpp_* API 全是运行时一个个查出来的。脚本后端加载完，UnityPlayer 才挨个取函数地址。

启动链路分段，两个 DLL 交替入场#

从进程启动到 C# 世界可用，可以先概括成七步：

七步只是大方向，真正费劲的地方夹在第 ⑤ 和第 ⑥ 步之间：

  • UnityPlayer 传入的 dataDir 决定 GameAssembly 后续从哪里找 Metadata/global-metadata.dat。
  • s_Il2CppCodegenRegistration 决定 AOT 生成的 registration 表如何交给 runtime。
  • MetadataCache::Initialize 决定 metadata 文件和 registration 表如何合并成查询索引。

只说一句“调用了 MetadataCache::Initialize”是不够的，那样只讲清了启动顺序，没法回答跑起来之后 il2cpp_class_from_name 凭什么能查到类，字段偏移和方法地址又从哪来。

Assembly 和 Image#

Assembly 是程序集层概念，Image 是 IL2CPP 用来组织 metadata 和 codegen module 的关键单位。关系为：

Il2CppImageDefinition 的通用结构包含 nameIndex、typeStart、typeCount 三个字段，每项占 0x28 bytes。runtime 会构建 Il2CppImage 和 Il2CppAssembly 视图；具体 image 名称、类型范围和行数需要拿到 global-metadata.dat 后再对齐。

Il2CppClass 是运行时类型对象#

Il2CppClass 是 TypeDef 的运行时展开结果。它把 metadata 里的静态类型定义、registration 里的布局信息、runtime 初始化状态组合成可创建对象、查字段、查方法、做虚调用的类型对象。

这部分在本文里只作为运行时模型说明。当前证据已确认 Il2CppClass 中 name 和 namespaze 两个字符串字段的读取位置，但完整字段布局尚未复原，不把其余字段偏移写成当前样本已确认结果。

MethodInfo 连接 metadata 和 native code#

MethodInfo 是方法运行时描述，结构包含方法名、所属类型、参数/返回值、metadata token、native 入口和 invoker 入口。

这里有两个入口容易混：

字段语义
methodPointer目标方法的 native 代码入口，直接执行方法主体
invoker_methodruntime 统一调用包装入口，处理参数数组、返回值、反射调用、封送等

反射调用或 il2cpp_runtime_invoke 使用 invoker；理解业务方法的实际执行入口时，需要关注 methodPointer。managed method 到 native symbol 的注册链路存在，但不声明某个具体业务方法的 MethodInfo 字段已经逐项复原。

MetadataCache::Initialize 完成metadata 加载链路、运行期工作表、Image / Assembly 构建链、managed method 到 native symbol 注册链metadata header/table 实体内容、每个 Il2CppClass 的完整运行期细节
Class::Init 完成具体类型的运行期初始化结果其他未初始化类型的完整状态
GC、线程、基础程序集就绪对象创建、字符串、异常、runtime invoke 等高层能力被内联、共享泛型、延迟初始化路径的单一固定入口

这张表想分开的是“加载顺序”和“数据可用性”：il2cpp_init 是入口边界，MetadataCache::Initialize 是 metadata 和 registration 建索引的边界，Class::Init 才是具体类型补齐运行时信息的边界。

所以启动原理关心的不是某一个点，而是状态怎么一层层变得可查询：

IL2CPP 启动链最容易被搞混的也是这点：metadata、registration、runtime object 是三种东西。metadata 管名字和定义，registration 管地址和布局，runtime object 把这些拼成当前进程里能直接用的对象关系。

边界#

Unity IL2CPP 的启动链远不止“加载 DLL、调用 init”。拆开看是这样：

  1. UnityPlayer 负责脚本后端接入：动态加载 GameAssembly，批量绑定 il2cpp_* API，传入 data/config/memory/debugger 等运行环境。
  2. s_Il2CppCodegenRegistration 通过 il2cpp_codegen_register 进入 MetadataCache::Register / GlobalMetadata::Register，把 g_CodeRegistration、g_MetadataRegistration、CodeGenOptions 注册给 runtime。
  3. GameAssembly 负责 VM 初始化：il2cpp_init 进入 Runtime::Init，按当前样本观察到的依赖顺序初始化 OS、metadata allocator、metadata cache、GC、线程、allocator、assembly、class 等子系统。
  4. MetadataCache::Initialize 会通过 GlobalMetadata::Initialize / MetadataLoader::LoadMetadataFile 定位并映射 global-metadata.dat，随后构建 runtime 工作表、泛型配置、Image / Assembly 视图、managed method 到 native symbol 的注册关系。
  5. 当前样本已恢复 g_CodeRegistration 和 g_MetadataRegistration 的核心 count/pointer，其中 codegen module 为 60 个，registration 侧类型布局记录为 6,196 组，泛型方法相关 registration 达到五万级。
  6. 方法查询最终会落到 MethodInfo 这类运行期方法描述，methodPointer 指向方法主体的 native 执行入口，invoker_method 是 runtime invoke 的统一调用适配层。
  7. 字段偏移、类型大小、泛型实例等运行时答案需要 global-metadata.dat 与 generated registration 共同参与；当前没有 metadata 实体，因此不声明字段级 metadata 表解析已经完成。

把这条链路串起来之后，IL2CPP 启动就不再只是启动顺序，而是 C# 世界如何在 native 进程中被重建出来的完整过程：

也就是说，global-metadata.dat 不是单独工作的数据库，g_CodeRegistration 和 g_MetadataRegistration 也不是孤立的地址表。它们被 MetadataCache / GlobalMetadata 接起来后，UnityPlayer 才能通过稳定的 il2cpp_* 外观层进入一个已经建立好类型、方法、字段、泛型和调用关系的运行时世界。

分析样本：Unity 2022.3.62f2c1，Windows x64。当前证据已覆盖 UnityPlayer 动态加载/绑定链路、GameAssembly 初始化主链、MetadataLoader 调用链、generated registration 字段级 count/pointer。当前未取得 global-metadata.dat 实体，因此不声明 metadata header/table 已完成字段级解析；具体结构字段和偏移仍应以当前目标的运行时调用链、registration 原始数据和 metadata 实体为准。
