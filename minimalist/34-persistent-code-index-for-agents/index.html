Agent 代码导航：让查找服务于理解

让 Agent 修改一个熟悉的小项目，往往很顺畅。项目变大以后，时间却可能花在更早的地方：同名函数有几个，真正的实现在哪，眼前这段代码又由谁调用。

这些问题与最终修改有关，但大量重复查找会打断思考。模型刚形成一点理解，就又要翻目录、读搜索结果，再重新确认自己找到的是不是目标。

我更希望工作环境替 Agent 保留那些可以重复利用的结构。代码索引的意义就在这里：让查找更有方向，把注意力留给真正需要阅读和判断的内容。

找到一个名字之后，还有一段路#

文本搜索很直接，遇到日志、配置、陌生标识时尤其有用。但一个函数名可能同时出现在定义、声明、注释和测试中，搜索结果本身没有替读者完成区分。

如果环境已经知道哪里是定义，哪些文件引用它，模型就可以更快形成最初的结构认识。它不必每次都从一组散开的命中位置重新拼出关系。

这种帮助并没有让代码变得更简单，而是减少了进入代码之前的重复劳动。对长任务来说，这些节省会反复出现：回到同一个模块时，已有结构仍然可用。

索引更适合提供方向#

我不希望索引结果变成另一份需要完全信任的代码说明。它总会与实际项目存在距离：文件可能刚刚改变，某些语言特性很难分析，动态注册的调用也未必能完整呈现。

把索引当成阅读方向，这些特点就比较容易理解。它指出值得看的定义与关联，源文件解释具体行为。两者配合，既减少盲目翻找，也保留对实现细节的直接认识。

例如，某个函数没有静态引用，可能确实已经废弃，也可能通过配置、反射或插件注册被调用。索引提供了一个值得追问的现象，真正的判断仍发生在对项目工作方式的理解中。

这也是我更看重“带回源文件”的工具设计的原因。结论能够回到原文，才方便继续核实、修改和讨论。

文本工作区让查找与编辑接在一起#

导航工具如果只给一段摘要，模型得到了一次解释；如果能把相关文件和位置交到面前，模型就得到一个可以继续工作的对象。

在文本工作区里，找到定义、阅读上下文、修改内容、比较差异，本来就是连续的过程。索引加入其中以后，可以减少查找成本，而不必接管整段编辑。

人也能沿着同样的位置阅读代码。模型认为某处值得修改，使用者可以直接打开对应文件，看它引用的内容，再判断这个解释是否成立。

因此，索引与文本工具之间的联系，比索引单独返回多少信息更重要。它们共同支持的是从问题进入代码，再把修改留回代码的过程。

环境保留结构，模型形成判断#

一个 Agent 可能只参与项目的一小段时间，项目结构却会长期存在。把可复用的导航信息放在环境里，新的会话就不必从完全空白开始。

这种分工也与我对 MCP 的整体看法一致。工具让已有知识更容易取得，工作区保留内容与变化，模型在这些材料上进行理解和选择。

我希望代码导航最后带来的体验很朴素：少一点重复找路，多一点连贯阅读。真正困难的问题仍然需要思考，但进入这些问题的过程可以更顺畅。
