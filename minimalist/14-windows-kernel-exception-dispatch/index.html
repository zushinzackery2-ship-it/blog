用户态程序看到的异常，是内核已经整理好的现场：EXCEPTION_RECORD 和 CONTEXT 被填充完毕，VEH/SEH（向量化/结构化异常处理）链可以直接使用。这个现场从哪里来？本文从 CPU 异常进入内核开始，还原异常分发的完整路径。

问题：异常记录和线程上下文从哪里来#

用户态 VEH/SEH 处理异常时，拿到两个现成的结构：

  • EXCEPTION_RECORD：异常类型、触发地址、附加参数
  • CONTEXT：寄存器、栈指针、标志位

它们看起来像”凭空出现”，实际上来自内核的整理。内核从 CPU 硬件保存的现场（Trap Frame 陷阱帧）提取信息，构造成用户态能读懂的格式，再通过特定入口交给用户态处理链。

这条路径包含三次关键交接：

  1. CPU → 内核：硬件保存部分寄存器，内核补全成 KTRAP_FRAME
  2. 内核 → 调试器：构造异常记录，调试器优先观察和决策（first chance，第一次机会）
  3. 内核 → 用户态：在用户态栈上布置 EXCEPTION_RECORD 和 CONTEXT，跳转到 ntdll!KiUserExceptionDispatcher

完整分发路径#

从用户态视角，异常”突然到来”。从内核视角，这是 CPU → 内核 → 调试器 → 用户态 → 内核的完整闭环。

1. CPU 异常：硬件进入内核的路径#

CPU 异常触发机制#

CPU 执行过程中遇到异常时（访问违规、除零、断点），触发 CPU 级中断：

  • x86-64 通过 IDT（Interrupt Descriptor Table）找到对应异常向量的处理入口
  • CPU 自动切换到内核态（特权级 CPL 0）
  • 硬件保存部分寄存器到内核栈（Rip、Rsp、EFlags、SegCs、SegSs）
  • 跳转到内核异常处理程序

常见异常向量：

异常向量内核入口
除零0KiDivideErrorFault
调试异常（断点/单步）1KiDebugTrapOrFault
断点3KiBreakpointTrap
非法指令6KiInvalidOpcodeFault
缺页14KiPageFault

内核补全现场：KTRAP_FRAME#

硬件只保存部分寄存器，内核异常处理程序负责补全完整现场，形成 KTRAP_FRAME 结构。

x64 KTRAP_FRAME 关键字段：

字段含义
Rip异常发生时的执行地址
Rsp用户态栈指针
Rax, Rcx, Rdx…通用寄存器
EFlags标志寄存器（包含 TF（Trap Flag，单步标志）、方向标志等）
SegCs, SegSs代码段、栈段选择子
Dr0-Dr7调试寄存器（硬件断点状态）
ExceptionFrame指向更外层栈帧（嵌套异常时）

Trap Frame 是内核内部维护的完整现场记录，供后续流程使用：

  • 判断异常是否需要分发到用户态
  • 构造用户态可见的 EXCEPTION_RECORD 和 CONTEXT
  • 在异常处理完成后恢复线程执行
  • 支持嵌套异常（异常处理过程中再次异常）

Trap Frame 与 CONTEXT 的关系#

KTRAP_FRAME 是内核格式，CONTEXT 是用户态格式。它们描述同一份线程现场：

  • 内核从 KTRAP_FRAME 提取字段填充 CONTEXT（下发给用户态）
  • 用户态修改 CONTEXT 后，内核通过 KeContextToKframes 写回 TrapFrame（影响线程恢复）

这意味着用户态 VEH/SEH 对 CONTEXT 的修改（如改 Rip、清 TF 标志、设置硬件断点）最终会体现在 TrapFrame 中，决定线程恢复后的执行状态。

构造 EXCEPTION_RECORD#

EXCEPTION_RECORD 描述”发生了什么”：

内核根据异常类型填充：

异常ExceptionCodeExceptionInformation
访问违规EXCEPTION_ACCESS_VIOLATION[0] = 读/写/执行
[1] = 访问地址
断点EXCEPTION_BREAKPOINT空
单步EXCEPTION_SINGLE_STEP空
Guard Page（保护页）STATUS_GUARD_PAGE_VIOLATION[0] = 访问类型
[1] = 地址

ExceptionAddress 从 TrapFrame->Rip 提取。用户态看到的异常地址就是 CPU 触发异常时的 Rip 值。

判断分发目标#

KiDispatchException 根据 PreviousMode 判断异常来自哪里：

  • KernelMode：异常发生在内核态 → 内核态处理链（KiKernelExceptionHandler）
  • UserMode：异常发生在用户态 → 准备分发到用户态

本文聚焦用户态异常分发路径。

3. 调试器 First Chance：优先于用户态处理链#

调试器通知流程#

如果进程被调试器附加，KiDispatchException 会先调用 DbgkForwardException：

调试器收到的是 EXCEPTION_DEBUG_EVENT（异常调试事件），包含：

  • ExceptionRecord（异常记录）
  • FirstChance 标志（表示这是第一次机会）

调试器的决策权#

调试器可以选择：

响应含义
DBG_CONTINUE调试器已处理，内核直接恢复线程执行
DBG_EXCEPTION_NOT_HANDLED调试器不处理，继续分发到进程内部

如果调试器选择 DBG_CONTINUE，内核直接从 Trap Frame 恢复执行，用户态处理链（VEH/SEH）不会被调用。

First Chance 的价值#

First chance 让调试器先于进程内部看到异常。对调试器来说：

  • 可以在断点命中时读取/修改现场
  • 可以拦截特定异常（如访问违规）做条件断点
  • 可以选择继续交给进程内处理链处理

这也是为什么调试器能”隐形”处理断点：调试器在 first chance 读取断点地址、恢复原指令、调整 Rip，返回 DBG_CONTINUE，进程内部完全无感知。

8. 结论#

Windows 异常分发是一条贯穿内核和用户态的完整链路：

  1. CPU 产生异常，硬件切换到内核态
  2. 内核保存 KTRAP_FRAME，捕获完整线程现场
  3. KiDispatchException 从 Trap Frame 提取信息构造异常记录
  4. 有调试器时先走 first chance，调试器优先处理
  5. KiUserExceptionDispatcher 切换到用户态，在栈上布置 EXCEPTION_RECORD 和 CONTEXT
  6. 用户态遍历 VEH/SEH 处理链
  7. NtContinue 或 NtRaiseException 返回内核，决定恢复执行还是进入 second chance
  8. 内核从修改后的 CONTEXT 恢复线程，或终止进程

用户态看到的 EXCEPTION_RECORD 和 CONTEXT 来自内核从 KTRAP_FRAME 的整理。用户态对 CONTEXT 的修改会写回 TrapFrame，影响线程恢复后的执行状态。

对逆向分析来说，理解这条完整路径可以回答：

  • 断点为什么能停住执行？（CPU 异常 → 内核 → 调试器 first chance）
  • VEH 为什么能修改执行流？（修改 CONTEXT → 内核写回 TrapFrame）
  • 为什么调试器能拦截异常？（first chance 优先于用户态处理链）
  • 崩溃为什么会弹窗？（second chance → UnhandledExceptionFilter）
