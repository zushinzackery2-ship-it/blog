一帧抓取里可能有几百到几千条 Draw、Dispatch、Copy、Clear 与 Present。把调用按时间打印出来，只能回答“发生过什么”；它回答不了“最终这张输出依赖哪一次写入”“同一资源被覆盖三次后，当前读取对应哪个版本”“少抓了一段初始内容时，重放为什么仍能跑到最后”。

可行的处理方式是把捕获当成一条不可变事实链：原始事件与 Blob 先版本化，再从目标输出反向求依赖闭包，之后才生成 Pass、Shader IR 和目标工程。任何派生物都保留到原始证据的引用，缺少生产者、Blob、管线状态或目标能力时直接产生阻塞诊断。

核心结论有四条：

  • 资源身份必须包含子资源、字节区间和写入版本；资源对象 id 本身不足以表达依赖。
  • 闭包从选定输出反向遍历生产事件，只保留真正参与该输出的事件与初始根。
  • 反汇编、语义名、Method 和目标源码都是派生物，不能覆盖 Shader 二进制、资源字节与 Pipeline 快照。
  • 验证必须落在 Pass 输出检查点，并报告第一个失败事件；只比较最终画面会丢掉故障位置。

下面的结构体、诊断码和分层测试口径取自一套 D3D11/D3D12 的捕获重放实现，用来给每条判据一个可对照的落点。

从调用列表到事实链#

正式链路以 Native .stcap 为唯一捕获来源。RenderDoc 只读取已有 .rdc，用于离线参考对照和纹理取证，不参与正式捕获，也不会在 Native 事实不完整时充当补丁。

这条链的关键是单向性。CapturedTrace 进入 ResourceVersioner 后生成新的 TracePackage；ClosedTrace、RenderIR、MethodSpec 继续消费上一层公开值。派生层可以增加解释，不能回写或“修正”原始命令、Shader Blob 与资源内容。

Blob 使用完整 SHA-256 内容寻址。归档读取时会重新计算内容身份，引用存在但 Blob 缺失、Blob 名称与内容不一致，都会在进入分析前失败。这样 Method 报告里的语义名即使后来被推翻，原始二进制仍能独立复核。

资源对象不等于资源版本#

同一个纹理在一帧里可能先被 Clear，再被 Draw 写入，最后被后处理覆盖。若依赖图只记 resourceId=42，三次内容会被压成同一个节点，消费者无法知道自己读到哪一份。

ResourceSlice 再区分 mip、array slice、depth slice、plane、view format；Buffer 还带字节区间。每次写入让对应子资源的版本递增，并把当前事件记为生产者。读取发生时，不是绑定“这个资源”，而是解析为读取范围内最后一次覆盖每个字节的版本。

纹理按子资源跟踪，不接受 Buffer 风格字节区间。事件 id 还必须严格递增。版本化在这里同时承担两项职责：把时间关系变成显式数据依赖，并尽早拒绝无法解释的读取。

从目标输出反向求最小闭包#

版本图建立后，才能回答“为了重放目标输出，最少需要哪些事件”。闭包算法从目标 ResourceVersion 开始：

  1. 如果该版本是初始资源或显式外部根，记录为闭包根并停止。
  2. 否则读取 producerEventId，确认该事件确实写出了这个版本。
  3. 递归访问生产事件读取的所有资源版本。
  4. 把生产事件加入集合，最后按原始事件顺序输出。

闭包的判据是版本依赖，与事件类型无关。一个 Copy、Clear 或 Dispatch 只要生产了目标链需要的版本，就必须保留；一个看起来重要的 Draw 若只写无关纹理，就不会进入闭包。

闭包还维护递归栈。资源依赖形成环时返回 closure.resource_cycle；版本没有生产者、生产事件不存在、或事件并未写出声明版本时，也都阻塞重放。输出因此是一条“所有输入都有来源”的 ClosedTrace。

RenderIR 不改写捕获事实#

当前 RenderIrBuilder 的粒度很克制：一个闭包事件对应一个 Pass。Draw 与 DrawIndexed 标为 Graphics，Dispatch 标为 Compute，Copy、Resolve、Clear 标为 Transfer，Present 单独成类。

每个 Pass 原样携带：

  • 命令参数与事件 id；
  • 完整 PipelineSnapshot；
  • 已版本化的输入与输出；
  • 捕获证据 id，并追加自己的 event:<id> 引用。

依赖边由“输入版本的生产事件 → 当前消费事件”生成。这里没有根据调试名自动合并 Pass，也没有把若干 Draw 猜成一个高层效果。更高层的语义可以后来添加，但底层 Pass 与事件的对应关系保持可审计。

MethodCompiler 再从 Pass 的 Pipeline 中收集实际绑定的 Shader，构建 Shader IR，并把相关资源 Blob 与 Shader 原始二进制复制进 Method 包。缺少 Shader artifact 或任一被引用 Blob，会产生 blocking diagnostic；反汇编结果不能替代原始 Shader。

检查点把错误定位到首个事件#

只比较最终 BackBuffer 有两个问题。多个错误可能在后续 Pass 中互相抵消；即使最终不同，也不知道第一个错误从哪里出现。

普通格式使用 byte-exact 比较。Native 捕获中 view_format 含 FLOAT 时使用浮点合同：当前默认允许 1 ULP，绝对与相对容差为 0，并要求 NaN payload 一致。预期与实际长度不同、预期 Blob 缺失、重放未给出该检查点，都会直接失败。

VerificationReport 按检查点顺序寻找第一个 passed=false 的记录，将其事件 id 写成 firstDivergenceEventId。报告同时保留首个差异字节、最大 ULP、最大绝对误差和最大相对误差。这样故障从“画面不一样”收敛为“事件 145 的第 2 个输出从字节 8192 开始不同”。

首分歧仍不是自动根因。错误也可能来自更早的常量，只在事件 145 第一次影响可观察输出；但它给出了稳定的最小排查边界，后续可以回看该 Pass 的输入版本、Pipeline 和 Shader 证据。

能力声明必须重新审计#

一个 Schema 能表达完整 Pipeline，不代表某份捕获真的包含完整 Pipeline。Native import 会重新运行 NativeTraceAuditor，不信任归档 manifest 里自报的 capability。

审计会检查：

  • 事件是否存在且 id 严格递增；
  • 资源描述、初始内容与已观察输出是否闭合；
  • Shader 二进制、反射与绑定是否存在；
  • 子资源与 Buffer 字节区间是否精确；
  • ResourceVersioner 是否发现无来源读取。

当前 D3D12 路径会明确关闭 complete_pipeline_state，原因是动态状态捕获仍不完整。源重放、late attach 与 multi-frame roots 也不会被 Native audit 宣称为可用。这个边界很重要：工程里有对应字段，不等于当前 Provider 已经满足它。

Unity URP 与 Unreal RDG 的目标生成同样走能力门禁。当前目标能力明确不支持 history resource、custom blend 与 depth/stencil；Method 使用这些能力时返回不支持诊断，而不是生成一份近似代码。

证据范围#

这类系统的测试应当分四层：

  1. 单元测试证明版本化、闭包、序列化、比较合同与 fail-closed 规则。
  2. D3D11/D3D12 fixture 证明真实 API 调用能进入捕获、审计和导入链。
  3. 代理 fixture 证明启动、Bridge、触发与 Shader 完整 SHA-256 能贯通。
  4. 具体游戏正证还必须在游戏捕获中证明目标 Shader 哈希、非零 watched command、目标 Draw 绑定和完整资源事实。

低层测试不能冒充高层证据。把 fixture 放进一个游戏命名目录，不会改变它的来源。

单次 Trace 也只证明一次执行。动态分支、Shader Variant、历史帧、分辨率、相机、灯光、材质与动作要形成受控语料，才能把“一次执行闭合”升级成“方法覆盖完整”。事实闭包解决的是每个样本内部的可追溯性，不自动解决样本集合是否充分。

结论#

渲染逆向里最难维护的不是某条 Shader 公式，而是公式与原始事件之间的证据关系。资源版本化让每次读取有明确来源，反向闭包让 Method 只包含目标真正依赖的事件，不可变 Blob 让后续解释可被推翻而事实仍可复核，逐 Pass 检查点则把差异定位到首个可观察事件。

四条拒绝划出了它的边界：无来源读取不补零，缺失 Blob 不猜，Provider capability 不自证，目标后端表达不了就不生成。最终得到的是一条能够指出自身缺口的渲染事实链。
