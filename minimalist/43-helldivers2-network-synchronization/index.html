四人合作射击游戏要在四台机器之间维持一个一致的战场，最省事的做法是架一台权威服务器算好一切再下发。Helldivers 2 没这么做——它是 P2P，四名玩家里一人当 host，其余是 client。这带来一个具体问题：没有中立服务器，谁说了算？大状态（比如整张地图）怎么在四台机器上保持一致而又不把带宽打爆？

Helldivers 2 的答案是一套 host 权威 + 确定性重建 的组合：host 通过一族单向的 rpc_from_host_* 指令驱动 client，client 在一个「全员就绪才推进」的同步屏障上对齐后才进入战斗；地图这类大状态不在网络上搬运，而是每台机器用同一个 seed 各自本地生成，事后只用哈希对账。下面的判读都基于 Steam Build 24036910 的游戏模块 game.dll。

先说结论#

这套联机方法可以拆成六件事：

  • 权威：一名 peer 是 host，所有 gameplay 指令都是 host 单向下发（rpc_from_host_*），client 只回执，不发号施令。
  • 加入：client 走一条 Joining → … → Ready → Alive 的状态机，每一种失败都归一成同一张枚举里的一个状态码。
  • 屏障：从「同步中」跨到「就绪」靠一个跨 peer 的屏障，全员同步后 client 才把自己置为 Ready 并回报 host。
  • 对账：地图各自本地生成，只同步 seed，用逐步哈希比对，不一致就上报，不搬运几何。
  • 迁移：host 中途离开时推选新 host，把每个 peer 的进度平移过去，而不是重开一局。
  • 复制：真正在网络上复制的 gameplay 状态里最清晰的是装备与战备，走一套玩家历史系统，支持掉线重连续用。

这六件事各自回答一个问题——谁说了算、怎么进场、什么时候一起开打、大状态怎么对齐、host 走了怎么办、什么东西真的在网上传。合起来就是一套不依赖专用服务器、又能保证一致性的 P2P 同步。

谁说了算：host 单向驱动#

所有 gameplay 方向的 RPC 都叫 rpc_from_host_*，方向单一：host 下发，client 执行。游戏模块里有两个对称的类型 ClientSynchronizer 和 HostSynchronizer，client 那个不自己推进会话状态，它等 host 的指令。这一族指令做的事很有代表性：client_ready 通知 client 推进到下一个同步任务，abort_network_play 中止联机，peer_disconnected 广播某人掉线，kicked 踢人，migrated_host_peer_state 在迁移后补发 peer 状态。

反方向没有对称的 rpc_from_client_* gameplay 指令族——client 往 host 送的是「我就绪了」这类回执，不是命令。连托管本身都是一组显式动作：start_hosting、stop_hosting、pause_hosting、resume_hosting。权威集中在一处，是这套模型后面所有机制的地基。

怎么进场：加入是一条状态机#

一名 client 加入会话不是一步到位，而是走一条状态机。主干路径是：

先是 Joining，然后停在 WaitForLoadout 等玩家选好装备，再进入同步阶段（Synchronizing / Synchronized），全员对齐后到 Ready，最后 Alive 真正入场。中途加入进行中的战局（hot-join）走一条独立分支——由 host 把新玩家单独塞进已在跑的会话、补齐装备，而不是让所有人陪它重走一遍同步。但无论冷启动还是热加入，成功的终点是同一句日志：Join accepted and synced!。

值得一提的是失败也走同一张枚举：断线是 HostConnectionBroken，版本对不上是 GWVersionMismatch，密钥不匹配是 PublicKeyMismatch，被踢是 Kicked，因迁移被踢是 KickedMigration，装备中途取消是 LoadoutAborted。把每一种退出都收敛成一个状态码，好处是「这个人为什么没进来」永远有一个明确答案，而不是散落在各处的错误分支。

什么时候一起开打：同步屏障#

Synchronizing 到 Ready 的跨越靠一个跨 peer 的屏障。这道屏障保证的是「不让任何一台机器抢跑」：所有人都完成了同步任务，战斗才开始。屏障两侧是成对登记的工作项（on_synchronized_tasks_started / on_synchronized_tasks_done，单项执行时打印 Performing synced task %s），这些工作项在每台机器上成对进入、成对退出。

client 侧的判定逻辑很简单，可以完整还原出来。同步器维护一张「待同步 peer」表，每一项带两个标志：这个 peer 是否已加入会话、是否已完成同步。每一轮把两个标志都为真的 peer 移出表；表清空，就代表全员到齐：

要点在最后三行：屏障清空后，client 把自己的状态字段写成 Ready，再经会话对象回报 host。也就是说，client 从不自己宣布「开打」——它在一个由 host 主导的就绪屏障上等待，全员到齐才推进。这就是「host 权威」落到最细一层的样子：连「大家准备好了吗」这个判断，最终也是汇报给 host、由 host 侧收齐。

那个「已同步」标志由谁置上？正好接回第一节那条带参数的指令：host 用 client_ready（带 task / active_target / target 三个参数）告诉 client「推进到哪个同步任务」，client 每完成一项登记的工作就把对应标志置真。于是「host 下发推进 → client 完成任务 → 屏障清空回报就绪」构成一个闭环，节奏始终握在 host 手里。

大状态怎么对齐：只同步 seed，不同步几何#

地图不靠网络搬运。每台机器用同一个 seed 在本地各自生成地图——上一篇讲地图生成流水线时已经看到，整条生成跑在客户端 game.dll 里，只有 seed 上行到后端。网络侧要做的只是保证四台机器拿到的 seed 一致，然后用哈希核对结果。

对账藏在一条 client 侧的事件 LevelGenerationMismatch 里。它逐字段拼出这样一组内容：

同一个 seed 喂进同一套生成阶段，host 和 client 本该逐步得到相同的哈希；一旦某一步的两个哈希对不上，就把种子、分歧的阶段名和双方软硬件一起上报。载荷里同时带 host_hash 和 client_hash 这一点本身就说明了方法：如果地图是 host 算好下发的，client 根本不需要一份独立的 client_hash 去比。联机同步的是种子，不是几何。

这是把大状态放进 P2P 最省带宽的做法——同步确定性输入 + 事后校验，代替逐帧同步整张地图。代价是对确定性要求极高，所以载荷里连 CPU/GPU 名都记下来：任何一处平台相关的浮点或迭代顺序差异都可能变成一次不匹配，得靠这些字段去归因。做自己的程序化内容时，这套「同步种子而非结果」的思路是最值得照搬的一块。

host 走了怎么办：主机迁移#

host 会中途退出，所以会话权威必须能转移。迁移集中在一个函数里完成：host 掉线后，其余 peer 里推选出新 host，由它触发 start_host_migration，再逐个把每个 peer 的当前状态广播过去（日志 Sending migration state! (peer=..., state=...)，其中的 state 正是加入状态机那张枚举的数值）。新 host 上线的那一刻会打出 Host has left! I'm the new host, migrating session!。

迁移期间的几处细节把它和「重开一局」区分开：被迁移波及而掉出的 peer 记为 KickedMigration，新 host 补发的 peer 状态走 migrated_host_peer_state，还有一个 lobby_host_propagation_timeout 约束新 lobby host 的传播时限。迁移复用的是同一套 peer 状态，把权威和每个人的进度平移到新 host 上继续，而不是让四个人从头再同步一遍。

什么东西真的在网上传：装备与战备#

真正在网络上复制、又能看得清的 gameplay 状态是装备与战备（loadout / stratagem）。它走两条 RPC：一条 rpc_sync_stratagems 同步整份战备，一条 rpc_sync_stratagem_changes 同步增量变更，两条都带 peer id 和战备数量。承接的是一个玩家历史系统 PlayerHistorySystem，按 peer 保存一份 loadout 记录（主武器、副武器、投掷物、战备列表、装备类型）。

这个历史系统还管两件同步相关的事。一是每个 peer 带一个「已同步」状态位，非活跃的 peer 会被清理出历史系统（日志 Clearing [was_synced] status for peer ...）。二是重连续用：玩家掉线重进同一局时，Found history, player is rejoining a previous game. Loadout is overridden with previous data.——用历史里的装备覆盖当前，省掉重新配装。「已同步位 + 历史覆盖」合起来，正是让「掉线再回来」不至于把队友的配置状态搞乱的那层机制。

至于逐帧的实体、投射物和 AI 预算怎么复制，它们不像装备那样留下清晰的 RPC 名和历史结构，从静态一侧看不出唯一答案，得靠实际网络流量才能定。

别把遥测当成同步协议#

游戏模块里还有大量 ,"字段": 形式的 JSON 键，很容易被误当成同步协议。它们其实是上报后端的分析遥测，和上面的 gameplay RPC 是两条独立的路。区分标志很清楚：遥测是拼 JSON 上报统计，gameplay 权威流转是 rpc_from_host_*。

通道典型内容
遥测 NetworkStatsping、packet_loss、player_count、loadtime_level_generation——都是测量结果
遥测 NetworkProfilelobby_id、nat_type、wifi、lobby_host、disconnected_peer
遥测 GameLoadedis_host、seed、planet_hash——把 seed 上报后端，正对应上一篇的「seed 上行」
gameplay rpc_from_host_*会话权威指令：就绪、踢人、迁移状态

关键在于 NetworkStats 里连 ping 和 packet_loss 都是被测量出来的数字，不是控制输入——它描述「会话里已经发生了什么」，供后端统计和排障。看到一堆网络字段名，不等于看到了同步协议本身，这是这个主题最容易搞混的地方。

结论#

Helldivers 2 的联机是一套不靠专用服务器的 host 权威 P2P 同步：一名玩家持有会话权威并用 rpc_from_host_* 单向驱动其余人；加入走状态机、失败归一成状态码；开打前所有人在一道同步屏障上对齐，client 全员到齐才把自己置为就绪并回报 host；地图这类大状态用同一 seed 各自本地生成、靠 LevelGenerationMismatch 的哈希对账兜底；host 掉线由主机迁移平移权威；装备战备走玩家历史系统复制并支持重连续用。

如果只带走一条，那应该是确定性对账：凡是能用共享输入本地重建的大状态（地图、程序化内容），就同步种子而不是同步结果，再用逐步哈希兜底一致性。带宽省在刀刃上，代价是把「确定性」当成硬约束来维护——这正是 LevelGenerationMismatch 存在的理由。至于每条 RPC 的线上字节格式和 Steam 传输可靠性层，位于独立的网络模块和运行时流量里，静态一侧看不到，得靠网络抓包才能补齐。
