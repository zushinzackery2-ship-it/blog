四名玩家加入同一场战斗，各自机器上的加载与生成速度却不会完全相同。有人仍在选择装备，有人已经完成地图生成，还有人可能在战局进行中才加入。

Helldivers 2 的 game.dll 中，可以看到围绕这些过程组织的 HostSynchronizer、ClientSynchronizer 与 peer 状态。一名玩家承担会话主机角色，其他参与者通过同步任务和就绪回报与它协调。

下面的分析来自 Steam Build 24036910。重点是这些会话过程如何相连，以及地图生成与装备记录怎样参与其中。

主机组织会话推进#

同步器周围有一族 rpc_from_host_* 入口。client_ready 推进同步任务，abort_network_play 中止联机，peer_disconnected 通知掉线，kicked 处理移出会话，migrated_host_peer_state 则参与迁移后的状态恢复。

这些入口共同指向会话管理上的主机角色。client 完成相关工作后再回报，host 据此协调后续状态。

这里看到的是同步器中的一组指令。玩家输入、实体复制、投射物与其他玩法通信，可能采用不同路径；不能由这组名称推出“所有 gameplay 消息都只由 host 发出”。玩家主机的逻辑角色，也没有单独说明底层流量是否经过中继或其他网络服务。

加入过程保留每一步的状态#

常见的加入主线经过 Joining、WaitForLoadout、Synchronizing、Synchronized、Ready，最后进入 Alive。

这些状态解释了加载界面里看起来相似的等待：有的是等装备选择，有的是等同步工作，有的是已经完成本地任务但仍未进入战斗。

中途加入另有分支，围绕已经进行中的会话补齐新玩家的状态。失败也会留下具体原因，例如 HostConnectionBroken、GWVersionMismatch、PublicKeyMismatch、LoadoutAborted 或 KickedMigration。

它们让“没有加入成功”分解成不同经历。网络断开与装备选择中止，虽然都可能把人带回界面，却不属于同一条恢复路径。

就绪表把不同速度的参与者接起来#

client 同步器维护待同步 peer 表。已加入且已完成同步的项目会被移出；表清空以后，client 将自己的状态写成 Ready，再向 host 回报。

屏障等待的是当前参与这组同步工作的 peer，并不是把整个程序的所有活动都锁在同一时刻。热加入、掉线与任务切换会改变参与者和等待关系。

on_synchronized_tasks_started、on_synchronized_tasks_done 与 Performing synced task 等记录，把具体工作与这组等待联系起来。host 推进任务，client 完成本地工作，再由就绪状态把不同机器的进度汇合。

地图生成留下了双方结果的对照#

地图生成篇中，客户端具有完整的阶段组织与几何计算路径。联机记录里的 LevelGenerationMismatch 又同时包含 seed、生成阶段、host_hash 与 client_hash，说明系统会比较双方的生成结果。

这与共享输入、本地生成的思路一致。地图的大量结构可以在本地形成，再用摘要发现分歧，从而减少直接交换完整生成结果的需求。

但 seed 只是输入之一。配置、资源版本、算法与执行行为也会影响输出。哈希相同提供了比较结果，哈希不同则指出双方已经分歧；对账本身不会自动修复地图，也不能独自证明网络上只传种子、完全不传其他状态。

载荷中的 CPU、GPU 与阶段名称，对理解分歧很有用。平台相关计算、迭代顺序或输入差异都可能在某一步显现，阶段记录能把问题从“地图不同”缩到更具体的位置。

主机迁移尝试延续已有会话#

主机离开后，代码包含 start_host_migration 与逐 peer 发送迁移状态的过程。新主机路径会记录 Host has left! I'm the new host, migrating session!，随后通过 migrated_host_peer_state 等消息重新组织参与者。

迁移复用了已有 peer 状态，这说明它尝试保留会话进度，而非一律重新开始。与此同时，KickedMigration 和传播超时也说明迁移可能失败或失去部分参与者。

真正需要移交的不只是“谁是主机”这个标记。参与者各处于什么阶段，谁已经同步，哪些状态还在等待，都属于继续会话所需的信息。

装备历史让重连有内容可恢复#

装备与战备留下了较清楚的复制路径。rpc_sync_stratagems 处理整份战备，rpc_sync_stratagem_changes 处理增量，PlayerHistorySystem 则按 peer 保存 loadout。

重连日志中出现 Found history, player is rejoining a previous game，随后采用历史装备。这让重新加入可以接回之前的配置，而不是只恢复一个在线身份。

历史系统还维护已同步状态，并在相应清理路径中更新它。装备内容、peer 身份与会话阶段因此在这里再次相遇。

遥测记录的是这些过程的结果#

NetworkStats 中的 ping、packet loss 和加载时间，GameLoaded 中的 seed 与 planet hash，描述的是已经发生的会话与生成活动。它们可以帮助分析问题，但 JSON 字段本身并不是网络同步消息的完整定义。

例如，LevelGenerationMismatch 解释了怎样报告分歧，却没有直接给出生成输入如何在网络上传递。消息发送路径与遥测上报在功能上相关，承担的工作却不同。

把同步器、就绪表、生成对账和玩家历史连起来，可以看到这套会话设计在努力保留的东西：参与者的进度、可比较的本地结果，以及重新接入时仍然有意义的内容。
