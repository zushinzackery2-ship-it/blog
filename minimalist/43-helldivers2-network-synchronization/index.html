Helldivers 2 是四人 P2P 联机：一名 peer 当 host 持有会话权威，其余 peer 是 client。方法不是「服务器算好世界再下发」，而是 host 通过 rpc_from_host_* 单向驱动 client，client 在一个同步屏障上对齐后才进入战斗，地图这类大状态靠同一个 seed 各自本地生成、事后用哈希对账。

本文的判读对象是 Steam Build 24036910 的运行时内存映像 dump_7312_game.dll.bin（PID 7312，SHA-256 5E34567B…C0C91BDD）。它是一份代码内存映像：能锁定字符串锚点、lea 交叉引用、以及这些引用所在的函数区间与指令序列。下面每个 RVA、每段函数区间都能按这个 SHA 复算。至于每条 RPC 的线上字节格式和 Steam 传输可靠性层，位于独立网络模块与运行时流量里，代码映像本身给不出——这一条留到最后一句说清。

一名 peer 持有会话权威，RPC 只有 host → client 一个方向#

所有 gameplay 方向的 RPC 都叫 rpc_from_host_*，方向单一：host 下发，client 处理。模块里有两个对称的同步器类型：ClientSynchronizer（0x1FC4CD0）与 HostSynchronizer（0x1FC55C0）。client 不自己推进会话状态，它等 host 的指令。整族 RPC 的字符串锚点是这样的：

RPC 字符串字符串 RVA引用/处理
rpc_from_host_client_ready task=%d active_target=%d target=%d0x1FC54380xB16CB7–0xB16DEF、0xD6ECB0–0xD6EDD5
rpc_from_host_abort_network_play0x1FC5484host 令 client 中止联机
rpc_from_host_peer_disconnected0x1FC55E4host 广播某 peer 断开
rpc_from_host_kicked0x1FC5644host 踢出
rpc_from_migrated_host_peer_state0x1FC53F0迁移后新 host 补发 peer 状态

注意第一条的格式串 rpc_from_host_client_ready task=%d active_target=%d target=%d：host 通知 client「就绪」时带三个整型参数（task / active_target / target），推进的正是下一节的同步任务。反方向没有对称的 rpc_from_client_* gameplay 指令族——client 往 host 送的是「我就绪了」这类回执，不是命令。

托管本身也是一组显式动作，字符串从 0x1FC55B0 起成组排列：start_hosting、stop_hosting、pause_hosting、resume_hosting、deeplink_temporary_hosting。

会话与 lobby 的握手字段都在 game.dll 里，传输层不在#

会话由 Steam 会话 + PlayFab live lobby 两层标识拼起来，握手字段作为字符串常量留在映像里：

字段RVA含义
sessionId0x1FC2950会话标识
lobbySeed0x1FC3660lobby 种子
connectionString0x1FC3830连接串
crossplayMode0x1FC3848跨平台联机模式
numSessionMembers0x1FC3858会话成员数
numLobbyMembers0x1FC3890lobby 成员数
%i.%i.%i.%i:%i0x2016A18地址格式串（IPv4:port）
lobby_host_propagation_timeout0x1FC4F90lobby host 传播超时

两个成员计数字段是分开的：numSessionMembers 数的是已进入游戏会话的 peer，numLobbyMembers 数的是 lobby 里的成员——lobby 是加入前的集合点，会话是加入后的战局，两者人数在热加入、掉线、迁移这些时刻会短暂不一致。%i.%i.%i.%i:%i 是记录 peer 连接时用的 IPv4:port 地址格式串，说明连接层是按 endpoint 寻址而不是纯 Steam id 中转。

具体传输实现不在这份映像里：SteamNetworkingSockets、ISteamNetworking、reliable_ordered 在两份映像中的出现次数都是 0（这不是「没有传输」，而是传输在别的模块）。信道、可靠/有序语义、NAT 穿透位于独立网络模块，本文只到「会话层用哪些字段握手」为止，不越界去讲字节怎么打包。

peer 加入与移除在日志里留下成对的锚点：

日志字符串RVA
on_ready_peer_added - peer_id: %llx, loadout: %s0x1FB6F20
on_mission_start - peer_id: %llx, loadout: %s0x1FB7238

Peer already added! 和 Peer already confirmed! 是加 peer 路径上的幂等守卫：重复的加入/确认消息不会往数组里塞第二份，而是命中这两条日志被丢弃。这和屏障末尾那次 [rbx+0x1d0]==5 的复查是同一种设计——P2P 下消息可能重发或乱序，所以每个会改状态的入口都先查一遍当前状态。

其中 Adding syncing peer %llx 在函数 0xD6DA80–0xD6DB03 内被 lea 引用（引用点 0xD6DABB）——它就在下一节那个屏障函数（0xD6DCD0）的隔壁，加 peer 与轮询 peer 是同一套数据结构（+0x40 那张数组）上的两个操作：一个往里塞项，一个把已同步的项压缩出去。

on_ready_peer_added 和 on_mission_start 两条日志都带 peer_id: %llx, loadout: %s——peer 就绪时记一次 loadout，任务开始时再记一次。loadout 在加入和开打两个时点各被快照一次，正好对应后面 PlayerHistorySystem 里那份按 peer 保存的记录。

热加入是独立分支，最终汇回同一条终线#

中途加入进行中的战局（hot-join）走的是另一组入口：is_hotjoining、has_hotjoined、from_host_added_to_session、on_hotjoin_loadout_complete。它不复用冷启动那条「等所有人一起同步」的路径，而是由 host 把新 peer 单独塞进已在跑的会话，补齐它的 loadout。但无论冷启动还是热加入，成功的终点是同一条日志：Join accepted and synced!（0x1FC5130）——加入被接受，且已完成同步。

同步屏障：0xD6DCD0 把「全员就绪」写成一次数组压缩#

Synchronizing 到 Ready 的跨越靠一个跨 peer 的屏障。屏障两侧是成对注册的工作项：on_synchronized_tasks_started（0x1FB72A0）与 on_synchronized_tasks_done（0x1FB7208），单个工作项执行时打印 Performing synced task %s（0x1FC5228）。on_synchronized_tasks_started 至少被五个函数 lea 引用（0xA602E0、0xAE839B、0xB18282、0xD6C270、0xD6FADB），_done 被 0xA5F420、0xA66A50 引用——同步任务是一批登记的工作项，在所有 peer 上成对进入/退出，而不是一段直线代码。

三个字段偏移把整套机制钉死了：计数在 +0x38，每个 peer 的 added/synced 是相邻两个字节 +8/+9，状态字段在 +0x1d0，被写成常量 5（Ready），最后经会话对象虚表槽 +0x470 尾调用回报 host。屏障清空后先查一次 [rbx+0x1d0]==5 再置位，保证「回报就绪」是幂等的。client 不会自己宣布「开打」——它在一个由 host 主导的 ready 屏障上等待，全员到齐才推进。这就是 host 权威落到指令层面的样子。

那个 synced 标志由谁置位，正好接回首节那条带参数的 RPC：rpc_from_host_client_ready task=%d active_target=%d target=%d。host 用它告诉 client「推进到哪个同步任务」，task 是当前任务索引、target/active_target 是要抵达的目标。每完成一项登记的同步工作（on_synchronized_tasks_started/_done 成对进出、Performing synced task %s 逐项打印），对应 peer 的 synced 就被置上；屏障函数每轮轮询这张数组，直到没有 synced=0 的项。于是「host 下发推进指令 → client 完成任务置 synced → 屏障清空回报 ready」构成一个闭环，推进的节奏握在 host 手里。

确定性对账：只同步 seed，用 LevelGenerationMismatch 兜底#

大状态不靠网络搬运。地图是每个 peer 用同一个 seed 在本地各自生成的——上一篇讲地图生成流水线时已经看到整条生成跑在客户端 game.dll 里、seed 上行到后端。网络侧只需保证 seed 一致，再用哈希对账。

对账的证据是一条 client 侧 JSON 分析事件 LevelGenerationMismatch（0x1FBA1F0）。它的发射函数在 0xB783B0–0xB786C0，逐字段把内容拼出来，末尾以事件名长度 22（mov r9d, 0x16，位于 0xB78683）调用共享事件发射器：

同一个 seed 喂进同一套 pass，host 和 client 本该得到逐 step 相同的哈希；一旦某个 step 的 host_hash 与 client_hash 不等，就把种子、分歧的 step 名和双方软硬件一起上报。载荷里同时带 host_* 和 client_* 两份哈希这一点本身就划清了边界：如果地图是 host 算好下发的，client 根本不需要一份独立的 client_hash 去跟 host_hash 比。联机同步的是种子，不是几何。

这也是把大状态放进 P2P 最省带宽的做法：确定性输入 + 事后校验，代替逐帧同步整张地图。代价是对确定性要求极高——载荷里连 CPU/GPU 名都记下来，正说明任何平台相关的浮点或迭代顺序差异都可能变成一次 LevelGenerationMismatch，得靠这些字段去归因。

seed 本身也走遥测上行：GameLoaded 事件（0x1FBA5B0）携带 is_host、seed、planet_hash，确定性 JSON 键里 ,"seed":（0x1FBA100）、,"is_host":（0x1FBA600）都在场。这和上一篇里「生成跑在客户端、seed 上行到后端」是同一件事的两个面：seed 由 host 定、随 GameLoaded 上报，各 peer 用它本地生成，LevelGenerationMismatch 只在结果对不上时才发。后端因此既拿得到「这局用了哪个 seed」，又拿得到「谁和谁生成结果不一致」，而不必接收整张地图。

主机迁移集中在 0xD70970 一个函数里#

host 会中途离开，所以会话权威必须能转移。迁移逻辑集中在 0xD70970–0xD7159A 一个函数内：start_host_migration（字符串 0x1FC5778，lea 于 0xD70990）和 Sending migration state! (peer=%llx, state=%u)（字符串 0x1FC5738，lea 于 0xD71150）都从这里发出。触发路径由日志串串起来：Host has left! I'm the new host, migrating session! (new_host=%llx)（0x1FC4D70）——host 掉线后，其余 peer 里推选出新 host，由它逐个把每个 peer 的当前 state 广播过去（Sending migration state! 里的 state=%u 正是上面那张枚举的数值），让全体在新权威下对齐。

迁移期间的特殊性写在几处状态和参数里：KickedMigration（0x1FC4CC0）是迁移导致的踢出，rpc_from_migrated_host_peer_state（0x1FC53F0）是新 host 补发的 peer 状态，lobby_host_propagation_timeout（0x1FC4F90）约束新 lobby host 的传播时限。迁移不是重开一局，而是把权威和每个 peer 的进度平移到新 host 上继续——所以它复用的是同一套 peer state，而不是走一遍冷启动同步。

复制装备与战备的是 PlayerHistorySystem#

真正在网络上复制、且能从类型信息看清的 gameplay 状态是装备与战备（loadout / stratagem）。它走两条 RPC：

RPC 字符串RVA引用点
rpc_sync_stratagems from %llx (stratagem count: %u)0x1FAC6500x621DE0、0xB0CA3A
rpc_sync_stratagem_changes from %llx (stratagem count: %u)0x2016D88—

两条都带 peer id 和战备数量：一条同步整份战备，一条同步增量变更。承接的是 PlayerHistorySystem（0x2016D70），按 peer 保存一份 loadout 记录，字段名以 phs.%s[%u].loadout.* 形式出现：primary、sidearm、throwable、stratagems[%u]、load_type，另有 peer_id。

历史系统还负责两件同步相关的事。一是每个 peer 有 was_synced 状态位，非活跃 peer 会被清理，清理函数在 0x10146A2–0x10149AC，打印 Clearing [was_synced] status for peer %llx. is_inactive=%s, clean_up=%s（0x2016AC0，lea 于 0x10146DD），批量清理时另有 Clearing inactive players from history system clean_up: %s（0x2016B18）。二是重连续用：Found history, player is rejoining a previous game. Loadout is overridden with previous data.（0x2016E50）——玩家掉线重进同一局，用历史里的 loadout 覆盖当前，省掉重新配装。was_synced 加「历史覆盖」，正是让「掉线再回来」不至于把队友的配置状态弄乱的那层机制。

逐帧的实体、投射物和 AI 预算怎么复制，类型信息和静态引用给不出唯一答案；它们不像 loadout 那样留下清晰的 RPC 名与历史结构。刷怪那侧另有独立的 64 位 LCG（见刷怪相关分析），未发现它与会话 RPC 之间的调用边。

遥测通道和 gameplay 通道是两条独立的路#

模块里有大量 ,"field": 形式的 JSON 键，很容易被误当成同步协议。它们是后端分析遥测，和上面的 gameplay RPC 是两条独立通道。区分标志很清楚：遥测是拼 JSON 上报后端，gameplay 权威流转是 rpc_from_host_*。

通道事件 / 载荷RVA
遥测NetworkStats：ping、packet_loss、packet_loss_accurate、player_count、loadtime_level_generation、loadtime_total0x1FBA560（发射 0xB79B50–0xB79D10）
遥测NetworkProfile：lobby_id、nat_type、wifi、lobby_host、disconnected_peer0x1FBA3A8
遥测GameLoaded：is_host、seed、planet_hash0x1FBA5B0
遥测LobbyJoinFailed：error_code、reason；另有 PeerRemoved、ClientDisconnected、EndpointErrorEvent、GameStart、GameEnd0x1FBA480 / 0x1FBA438 / 0x1FBA448
gameplayrpc_from_host_*（见首节表）：会话权威指令0x1FC5438 起

账号标识用 steam_account_id（0x1FBCA9A）、np_account_id、psn_account，这些也只出现在遥测里。判据是：遥测描述「会话里已经发生了什么」，供后端统计和排障，它的 NetworkStats 里连 ping 和 packet_loss 都是测量结果而非控制输入；gameplay 的权威流转始终走 rpc_from_host_*。看到一堆网络字段名，不等于看到了同步协议本身——这也是这个主题最容易失真的地方。

结论#

Helldivers 2 的联机是一套 host 权威的 P2P 同步：一名 peer 持有会话权威并用 rpc_from_host_* 单向驱动其余 client；client 走 Joining → … → Ready → Alive 状态机，加入的每次退出都归一成枚举里的一个状态码；0xD6DCD0 的屏障函数把「全员就绪」实现成一次数组压缩，count 归零后把 +0x1d0 写成 5 再经 +0x470 虚表回报 host；地图这类大状态用同一 seed 各自本地生成、靠 LevelGenerationMismatch 的 host_hash/client_hash 对账兜底；host 掉线由 0xD70970 的迁移函数平移权威；装备战备走 PlayerHistorySystem 复制并支持 was_synced + 历史覆盖的重连续用。

做自己项目时最值得照搬的是那道确定性对账：能用共享输入本地重建的大状态（地图、程序化内容），就同步种子而不是同步结果，再用逐步哈希兜底一致性——带宽省在刀刃上，代价是把「确定性」当成硬约束来维护，这正是 LevelGenerationMismatch 存在的理由。至于每条 RPC 的线上字节格式、migration state 与 stratagem sync 的 wire 编码，以及 Steam 传输可靠性层，落在独立网络模块与运行时流量里，代码映像给不出，得靠 network_logs 抓包或活体 trace 才能定。
