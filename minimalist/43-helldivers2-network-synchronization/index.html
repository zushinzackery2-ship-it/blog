Helldivers 2 是四人 P2P 联机：一名 peer 当 host 持有会话权威，其余 peer 是 client。方法不是「服务器算好世界再下发」，而是host 通过 rpc_from_host_* 单向驱动 client，client 在一个同步屏障上对齐后才进入战斗，地图这类大状态靠同一个 seed 各自本地生成、事后用哈希对账。运行时 game.dll 映像的类型信息、字符串锚点和指令序列把这套结构钉得很清楚。

这篇按六层展开：谁持有权威、加入怎么走状态机、同步屏障怎么保证全员对齐、大状态怎么用 seed 对账、host 掉线怎么迁移、以及哪些东西真的在网络上复制。

一名 peer 持有会话权威#

所有 gameplay 方向的 RPC 都叫 rpc_from_host_*，方向单一：host 下发，client 执行。模块里有两个对称的同步器类型：ClientSynchronizer 和 HostSynchronizer。client 不自己推进会话状态，它等 host 的指令。

没有反方向的 rpc_from_client_* gameplay 指令族；client 往 host 送的是「我就绪了」这类回执，不是命令。托管本身也是一组显式动作：start_hosting、stop_hosting、pause_hosting、resume_hosting、deeplink_temporary_hosting。

ClientState_Joining 之后先做 loadout（WaitForLoadout），再进入同步阶段。热加入（hot-join，中途加入进行中的战局）有独立分支：is_hotjoining、has_hotjoined、from_host_added_to_session、on_hotjoin_loadout_complete，最终汇到 Join accepted and synced!。异常出口也在同一张枚举里：Leaving、Kicked、KickedMigration、JoinFailed、LoadoutAborted、HostConnectionBroken、BadPeerConnection、GWVersionMismatch、PublicKeyMismatch、CrossplayDisabled。

同步屏障：全员就绪才推进#

Synchronizing 到 Ready 的跨越靠一个跨 peer 的屏障。屏障两侧是成对注册的工作项：on_synchronized_tasks_started 与 on_synchronized_tasks_done，单个工作项执行时打印 Performing synced task %s。这些名字被多个函数引用，说明同步任务是一批登记的工作，在所有 peer 上成对进入与退出，而不是一段直线代码。

client 侧的屏障判定可以从指令序列完整还原。同步器维护一张「待同步 peer」表，每项带两个相邻标志：added（已加入会话）和 synced（已完成同步）。每轮把两标志都置位的 peer 从表里剔除，表清空即代表全员同步：

关键在最后三行：屏障清空后，状态字段被写成常量 5（Ready），然后经会话对象的虚表回报 host。client 不会自己宣布「开打」——它在一个由 host 主导的 ready 屏障上等待，全员到齐才推进。这就是 host 权威落到指令层面的样子。

待同步 peer 表 peer A added=1 synced=1 peer B added=1 synced=0 peer C added=1 synced=1

确定性对账：只同步 seed，不同步几何#

大状态不靠网络搬运。地图是每个 peer 用同一个 seed 在本地各自生成的——上一篇讲地图生成流水线时已经看到生成整条跑在客户端 game.dll 里、seed 上行到后端。网络侧只需保证 seed 一致，然后用哈希对账。

同一个 seed 喂进同一套 pass，host 和 client 本该得到逐 step 相同的哈希；一旦某个 step 的 host_hash 与 client_hash 不等，就把种子、分歧的 step 名和双方软硬件一起上报。这条事件顺带划清了边界：如果地图是 host 算好下发的，client 侧根本不会有独立的 client_hash 去和 host_hash 比。联机同步的是种子，不是几何。

这也是把大状态放进 P2P 最省带宽的做法：确定性输入 + 事后校验，代替逐帧同步整张地图。代价是对确定性要求极高——任何一处平台相关的浮点或迭代顺序差异都会变成一次 LevelGenerationMismatch。

主机迁移：host 离开后重新推选#

host 会中途离开，所以会话权威必须能转移。迁移逻辑集中在一个函数里，start_host_migration 和 Sending migration state! (peer=%llx, state=%u) 都从这里发出。触发路径由日志串串起来：Host has left! I'm the new host, migrating session! (new_host=%llx)——host 掉线后，其余 peer 里产生新 host，由它把每个 peer 的当前 state 广播出去，让全体在新权威下对齐。

迁移期间的特殊性写在状态里：KickedMigration 是迁移导致的踢出，rpc_from_migrated_host_peer_state 是新 host 补发的 peer 状态，lobby_host_propagation_timeout 约束新 lobby host 的传播时限。迁移不是重开一局，而是把权威和每个 peer 的进度平移到新 host 上继续。

复制目标：装备与战备走玩家历史系统#

真正在网络上复制的 gameplay 状态里，能从类型信息看清的是装备与战备（loadout / stratagem）。它走两条 RPC：rpc_sync_stratagems 和 rpc_sync_stratagem_changes，都带 peer id 和战备数量。承接的是 PlayerHistorySystem，按 peer 保存一份 loadout 记录（primary、sidearm、throwable、stratagems、load_type）。

历史系统还负责两件同步相关的事。一是每个 peer 有 was_synced 状态位，非活跃 peer 会被清理：Clearing [was_synced] status for peer %llx. is_inactive=%s, clean_up=%s。二是重连续用：Found history, player is rejoining a previous game. Loadout is overridden with previous data.——玩家掉线重进同一局，用历史里的 loadout 覆盖当前，省掉重新配装。

逐帧的实体、投射物和 AI 预算怎么复制，类型信息和静态引用给不出唯一答案；它们不像 loadout 那样留下清晰的 RPC 名与历史结构。

遥测通道与 gameplay 通道是两回事#

模块里有大量 ,"field": 形式的 JSON 键，很容易被误当成同步协议。它们是后端分析遥测，和上面的 gameplay RPC 是两条独立通道。NetworkStats 事件携带 ping、packet_loss、packet_loss_accurate、player_count、loadtime_level_generation、loadtime_total；NetworkProfile 带 lobby_id、nat_type、wifi、lobby_host、disconnected_peer；还有 GameLoaded（含 is_host、seed）、PeerRemoved、ClientDisconnected、LobbyJoinFailed（含 error_code、reason）。账号用 steam_account_id 之类标识。

区分这两条通道是这个主题最容易失真的地方：遥测描述「会话里已经发生了什么」，供后端统计和排障；gameplay 的权威流转始终走 rpc_from_host_*。看到一堆网络字段名，不等于看到了同步协议本身。

结论#

Helldivers 2 的联机是一套 host 权威的 P2P 同步：一名 peer 持有会话权威并用 rpc_from_host_* 单向驱动其余 client；client 走 Joining → … → Ready → Alive 状态机，在一个「全员同步才推进」的屏障上对齐；地图这类大状态用同一 seed 各自本地生成、靠 LevelGenerationMismatch 的哈希对账兜底；host 掉线由主机迁移平移权威；装备战备走 PlayerHistorySystem 复制并支持重连续用。至于每条 RPC 的线上字节格式和传输可靠性层，落在独立网络模块与运行时流量里，需要网络抓包才能定，代码映像本身给不出。

做自己项目时最值得照搬的是那道确定性对账：能用共享输入本地重建的大状态（地图、程序化内容），就同步种子而不是同步结果，再用逐步哈希兜底一致性。带宽省在刀刃上，代价是把「确定性」当成硬约束来维护——这正是 LevelGenerationMismatch 存在的理由。
