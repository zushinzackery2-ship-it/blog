从一个已知的 Unity GameObject 取运行中角色的网格、骨骼和 UV，常见做法有两种，各有代价：解包游戏根目录的静态资源，拿到的是打包态，不含运行时的实例覆盖，也没有 GPU 侧的真值；用完整的远程注入器接管进程，侵入性过强，容易被反作弊和意外崩溃波及。还有第三条路：主体用外部只读内存访问，从 GameObject 的组件槽沿 Renderer、SkinnedMeshRenderer 和 Mesh 向下解析，只在顶点缓冲确实仅存在于显存时，用一个最小注入模块补一次 GPU 读回。本文不讨论如何发现这个 GameObject。

这条路要同时具备两样东西：一套绑定到目标二进制指纹的实际偏移，以及一套判断这些偏移是否仍然成立的验证纪律。只有方法而没有数值，无法复现；只有偏移而没有身份和探针，版本更新后又会静默读错。一套纪律划定提取边界，另一套保证顶点数据可信。下面先给出本次目标构建的实际 profile，再按对象图分工、身份校验、能力门槛、骨骼姿态、顶点与 UV 审计展开。

两条路径按“CPU 内存拿不拿得到”分工#

主体路径用只读权限打开进程，以已知 NativeGameObject 为入口，读取组件槽、Transform 树、Renderer、网格 CPU 数据和材质属性表。这部分不需要注入，跨进程读内存即可，侵入面接近于零。

另一条路径是一个手动注入的最小 GPU reader，只补外部只读拿不到的那部分。对模型提取而言，它补的是只存在于显存、CPU 侧已被释放的顶点缓冲。它通过命名管道把读回的数据送出，不接管渲染、不 hook 游戏逻辑，读完即卸。这个 reader 还有一半能力是读回 provider 为空的纹理像素，那部分属于贴图提取的范畴，本文只用它读顶点缓冲的那一半。

这样分的好处是把侵入面压到最小：绝大多数结构信息不需要进程内代码，只有 GPU 独占资源才需要一小段注入代码。

先分清“能恢复”和“不能伪造”#

在写任何解析之前，先把边界列清楚。外部只读能如实恢复的：对象树与局部 TRS、各类渲染器与材质引用、经校验的网格顶点流/索引/bindpose/权重、直接骨骼向量与优化骨骼的原始索引表、材质属性表与实例覆盖、解析后的运行态属性名。

仅靠外部 CPU 内存不能保证的：只在显存的缓冲、未经验证的共享骨架映射、动画曲线、BlendShape 的未知布局。还有一类和外观相关的不确定项——provider 为空的纹理像素、从引擎着色器到通用 PBR 的等价外观——属于贴图提取要处理的边界，这里先不展开。

这两张清单是整套管线的地基。凡是落在“不能保证”一侧的，必须显式标成缺失，不能填默认值、不能猜地址、不能借静态资源顶替。把没验证的东西标成缺失，比填一个看似完整的假值更有价值——后者会在下游被当成真值继续传播，最后谁也说不清是哪一环伪造的。

对象身份靠双向回指闭环，不靠“指针看起来可读”#

Unity 的托管对象和原生对象互相持有指针：托管对象在某固定偏移指向原生对象，原生对象在另一固定偏移回指托管对象。校验一个对象是否可信，靠的是这组回指闭环，而不是某个指针看起来可读。具体要求完整地址范围可读、页面无保护属性、双向回指一致、类名符合预期，任一条不成立就停止采集该对象。组件身份用类名判断，不复用固定的类型 ID；递归遍历要带最大深度、节点数上限和已访问集合，避免环引用把遍历拖垮。

能力由探针门槛逐项开关#

外部读取不是一张跨版本的固定偏移表，它只在目标二进制指纹、字段关系和运行态探针全部通过时，才启用对应能力。把探针分组，任一必需探针失败就禁用它对应的能力，不拿另一个版本的地址硬跑。

目标身份用二进制指纹（内容哈希、映像大小、符号信息等）共同锁定；参考构建与目标指纹不一致时，所有参考地址一律禁用，必须由匹配的二进制、符号和运行态关系重新建立。所有具体偏移都只对匹配指纹有效，游戏或引擎更新后必须重新验证。结构参数（如顶点属性通道的合法范围）同样要从反汇编和运行态数据钉死，不沿用旧记录，否则越界会读出伪数据。

骨骼的姿态语义要一致，优化骨骼要克制#

骨骼是这套边界纪律的一个典型。一个常见错误是把当前帧的局部 TRS 和绑定姿态的顶点混用，得到错位的骨架：顶点停在绑定姿态，骨骼却摆成当前帧姿态。正确做法是从 bindpose 反推 rest pose，让骨骼载体和绑定姿态网格处在同一姿态语义里。

矩阵按引擎的行/列主序和缩放约定处理，并验证正逆矩阵相乘为单位阵，奇异缩放直接拒绝，不加粗糙 fallback。优化骨骼（把 joint 压成共享骨架的整型索引）是最需要克制的地方：索引可读，不代表能还原完整官方骨架。只有共享骨架、索引范围、父子关系和 bindpose 同时通过校验，才能宣称还原；否则保留占位状态用作 rest 载体，不宣称它可直接驱动动画，也不按相邻对象的槽序去猜骨骼。世界变换（渲染器的世界矩阵）只服务于场景放置、当前姿态、世界法线和光照，不写入 UV 或贴图。

顶点数据审计要引入独立真值#

前面那条最小 GPU reader 除了补显存里的顶点缓冲，还顺带提供了审计上极其关键的一样东西：一份不经过 CPU 解码路径的独立真值。有了它，顶点数据的验收才能跳出自证。

如果导出源和审计源是同一份 CPU 解码数据，审计只能证明“导出没改变这份数据”，不能证明解码本身对不对。要打破这个循环，得引入一个不经过被测解码路径的第二真值。直接读回显存里的顶点缓冲就是这样一个真值：它不经过 CPU 解码器，因此拿它和 CPU 解码结果、载体文件、最终导入的网格四方对照，才是真正的交叉验证，而不是自证。

这类审计只回答“数据有没有在搬运中变化”，它不读图片、不比较镜像候选，任一路不精确一致就直接失败。它和贴图方向的审计是两套，各自独立，互不牵连——把它们混在一起，一个通过掩盖另一个失败，是这类工作最常见的自欺。

结构参数要从反汇编钉死#

第二类静默错误来自结构参数取错。顶点属性的合法通道数是有上界的，超出上界去扫描，会撞进相邻的描述结构，读出结构上根本不存在的伪通道。旧记录里若把上界记大了（例如把 14 记成 16），扫描多出来的两个通道就会生成永远对不上真值的伪 UV，而且它们看着和真通道没有区别。

这条的通用做法是：通道数、维度、步长这些结构参数，要从反汇编和运行态数据确认，不沿用旧文档。导出器解码每个属性时按其流索引、偏移、格式、维度来，并校验“属性偏移加元素大小不超过步长”；对索引明确标注是局部还是全局，应用基顶点时做有符号扩展并逐项验证落在合法范围。任一越界或页面不可读就拒绝该网格，而不是读出一个看似合理的值。

顶点缓冲定位要复现引擎的选择规则#

顶点缓冲的定位也不能想当然。引擎取缓冲时可能先把非空的物理槽压紧、再按流序号选择；读回时必须复现这个选择规则，不能把流序号直接当物理槽号，否则会读错缓冲。这属于“照抄引擎规则”的又一例：凭直觉把逻辑序号映射到物理位置就会错位，而错位后读到的仍是一块合法缓冲，只是不属于当前网格。

多维 UV 与顶点色要用扩展属性承载#

第三个静默错误是维度被截断。有些网格的 UV 通道其实是三维或四维，只是被当成二维导出，多出的分量整段丢弃；已写出的两维和真值精确相等，看着没问题，实则缺了染色或区域逻辑要用的分量。

根子在载体格式：标准 glTF 的 TEXCOORD_n 只允许二维。解决方式是分两处写——两维写进标准属性供通用查看器读，完整维度写进扩展属性，导入器优先读扩展属性并按真实维度恢复。

同一类问题还出现在顶点 COLOR 上。有些网格的 COLOR 不是 glTF 意义上的顶点颜色，而是描边或 toon 控制数据；若写成标准颜色属性，通用查看器会把它乘进 base color，模型整体偏色。处理方式相同：写成扩展属性，导入侧恢复，通用查看器不自动拿它调色。载体的取舍要明确——它服务于你自己的复现管线，不承担通用查看器的默认外观；通用查看器的默认 PBR 外观不能当作正确性判据。

UV 采样行为常由材质常量门控#

还有一类容易犯的错是按着色器名硬编码采样策略：某个变体用 atlas 重映射，其余用直接采样。反汇编后往往发现，各变体的字节码里都含相同阈值的重映射块，只是被一个材质常量门控——常量为 1 时开，为 0 时退化成直接采样。

所以正确的复刻是始终实现重映射块，由那个门控常量插值，而不是按着色器名写死分支。这里要和贴图的行序分清层次：重映射发生在着色器的 UV 语义层，处理的是采样坐标；行序归一化发生在编码层，处理的是像素排布，属于贴图提取的问题。两者不能互相替代。序列化边界上 UV 一律原样写出，不做 atlas 预处理，也不改 V。

边界与迁移#

这套模型提取的边界很清楚：输入是一个已知 GameObject，数据一致只覆盖从组件到网格的解析与顶点数据搬运，不覆盖对象发现、贴图方向、染色和世界姿态之外的外观。可迁移的判断集中在几条：按“CPU 拿不拿得到”决定注入面，把侵入压到最小；对象和组件身份靠双向回指与 owner 关系闭环，不靠指针可读；能力由探针门槛逐项开关，换版本偏移全部作废；缺失项显式标记，不填默认、不猜、不伪造；顶点数据审计必须引入不经过被测解码路径的独立真值，否则是循环证明；通道数、维度这类结构参数从反汇编钉死；多维 UV 和顶点色用扩展属性承载，别被有损的标准格式截断或误解。

换一款 Unity IL2CPP 游戏时，偏移全部重来，但这几条决定了导出的模型到底是“看起来对”还是“逐点等于运行态”。
