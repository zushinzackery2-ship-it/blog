模型导出成功，通常只说明文件格式能被读取。它没有回答骨骼是不是绑定姿态、UV 有没有丢掉分量，也没有证明那段看似合理的顶点数据属于当前网格。

运行态提取最容易出错的地方，往往正是这些仍能生成正常文件的细节。一次 Unity 角色提取中，顶点描述符的扫描范围多了两个通道，就生成了两组伪 UV；把骨骼矩阵放进错误的空间，则会得到结构完整、姿态却不一致的模型。

这类工作需要同时保留数据和它的含义。地址提供读取入口，身份与空间关系说明读到的是什么，逐阶段比较才能发现含义在哪个边界丢失。

沿组件关系找到当前网格#

提取从一个已知的原生 GameObject 开始，沿组件进入 Renderer，再取得 Mesh、材质和骨骼引用。这条链看起来直接，但一个可读地址并不能证明对象身份：已释放对象、错误偏移和碰巧落在有效内存里的指针，都可能通过最初的读取。

在所分析的构建中，托管对象与原生对象之间存在双向回指。结合类名、组件归属和计数范围，可以交叉确认当前对象是否符合预期。遍历对象树时还需要识别重复访问，否则损坏引用可能被解释成无限延伸的层级。

运行中的对象会变化，多次跨进程读取未必构成同一时刻的快照。指针链自洽只能支持这次观察，不能把持续变化的内存变成静态文件；遇到对象更替时，应重新取得一致的数据来源。

原始分析使用的构建标识是 star-unityplayer-2025-02-19-pdb-0b158128。它绑定目标二进制与对应符号。字段位置、通道布局和缓冲选择规则都属于该样本，不能只凭“同样是 Unity”就迁移到另一版本。

CPU 与 GPU 保存着不同阶段的数据#

CPU 路径适合读取组件关系、Transform、网格描述、材质属性和仍保留的顶点副本。一些资源上传后会释放 CPU 数据，这时描述结构仍在，真正的字节却只存在于显存。

因此，原有提取方案将 GPU 读回限制在这部分资源上，其余结构继续沿外部只读路径解析。这样的分工使每份数据的来源清楚，也避免为了一个缓冲而把全部对象解释逻辑搬进目标进程。

但“从 GPU 读回”本身不等于取得独立真值。缓冲可能已经经过蒙皮、形变或其他计算。CPU 原始顶点与 GPU 变形后顶点，本来就不应该逐点相等。比较前必须确认两者属于同一网格、同一属性阶段与同一坐标空间，并考虑格式转换产生的精度差异。

确认这些前提后，比较才有定位价值：

比较对象能发现的问题
CPU 解码与对应 GPU 输入描述符、流映射或解码错误
解码结果与导出文件序列化时的截断、重排和精度损失
导出文件与导入后网格导入器的维度、空间和属性解释差异

最终画面适合发现异常，分阶段的数据比较才能指出异常出现在哪里。

两组伪 UV 来自越过结构边界#

样本中的有效顶点属性通道是 0..13。按十六个通道扫描时，后两项已经进入相邻结构，解析器却仍把字节解释成属性描述符。数值未必立即越界，因此错误可以一路进入导出文件。

这个例子说明，合理的结果不一定来自合理的读取。通道数量需要由结构与访问代码确认，不能由“常见数组大小”推测。

每个属性还同时依赖流索引、偏移、格式、维度与步长。例如，属性偏移加上元素大小超过流步长，说明当前解释已经不成立。索引缓冲也要结合索引类型、子网格范围和 baseVertex 理解，不能把所有索引直接当作全局顶点编号。

GPU 缓冲的选择还有一层间接关系。这个构建会先压紧有效物理槽，再按逻辑流序号选择缓冲。直接用逻辑序号访问原始槽数组，在中间存在空槽时就会读错。复现引擎的选择规则，比尝试哪个缓冲“看起来像顶点”更可靠。

恢复父子层级时，还要把子骨骼变换转成父骨骼局部空间；根骨骼则要与所选的网格或场景根保持一致。若实现采用行向量，矩阵乘法顺序也会改变。

矩阵与逆矩阵相乘接近单位阵，只能检查可逆性和部分数值问题。真正的语义检查，是让绑定姿态下的蒙皮保持网格不变，再检查当前姿态是否按相同空间关系作用于顶点。

优化骨骼还可能经过共享骨架和索引映射。只有名字或数量相似，不足以确认映射。父子关系、索引范围和绑定矩阵共同匹配后，才能把它解释成完整骨架。

导出格式可能丢掉运行态需要的属性#

有些网格的 UV 通道是三维或四维，额外分量用于染色区域、材质选择或其他着色器输入。通用查看器只需要前两维，目标着色器却可能需要完整数据。

标准 glTF 的 TEXCOORD_n 是二维属性。若直接把四维 UV 写进去，要么违反格式约定，要么在序列化或导入时被截断。原有方案将二维部分写入标准属性，把完整分量及维度放入约定好的自定义属性或扩展，由配套导入器恢复。

这种做法保留了通用预览能力，也明确了额外信息依赖专门的读取支持。扩展数据存在于文件中，并不代表任意查看器都会使用它。

顶点色也有类似问题。字段被命名为 COLOR，并不意味着它只表示可见颜色；它可能参与描边或 toon 控制。导出时需要保留原始值与用途，避免通用材质把控制量误当作颜色乘到底图上。

外观处理留在它发生的阶段#

一些样本中的 atlas 重映射由材质常量控制。同一份原始 UV，在不同材质状态下可以参与不同采样。若提取时提前烘焙重映射，就把某次材质状态写死在了几何数据里。

更容易解释的结果是保留原始顶点属性，让着色器按捕获到的常量完成采样。贴图行序在图像编码边界处理，骨骼空间在变换链中处理，各阶段都有明确的数据含义。

最终的模型文件可以同时包含已恢复的数据和明确的缺失项。尚未确认的骨架映射或 BlendShape，保留为未知，比填入看似合理的值更有用。后续分析才能知道哪些差异来自目标本身，哪些仍来自提取链。

模型提取的质量，体现在这些关系能否一起保存。几何形状只是第一层；让另一套程序继续正确使用它，还需要保住身份、维度、空间与材质输入之间的联系。
