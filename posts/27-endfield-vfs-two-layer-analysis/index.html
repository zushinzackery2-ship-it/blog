终末地资源的两层保护：判据、排除矩阵与兼容复现

从"MD5 校验通过但 UnityPy 枚举出 0 个对象"这一矛盾出发，区分 VFS 文件层与 AssetBundle 归档层。记录 key、counter、处理顺序和压缩方言的排除矩阵，以及算法体落入 .tvm0 后如何用强判据、独立约束和全量样本形成兼容实现。

2026-08-19 53 分钟 10568 字 Unity 逆向
#Reverse Engineering#Unity#IL2CPP#AssetBundle#ChaCha20#LZ4#Methodology

终末地的资源读不出来，但读不出来的方式很奇怪。

.blc 索引解密后是一份结构完整的 VFS 清单，文件路径、偏移、长度、MD5、encrypted 全都在。按索引里的偏移从 .chk 容器切出一个 .ab，逐字节比对 MD5 —— 对上了。文件记录标的是 encrypted=false，也就是说这个文件根本没经过文件级加密。然后把它交给 UnityPy：不报容器异常，枚举出的对象数是 0。

校验通过、提取范围正确、标记未加密、解析结果为空。这四件事必须同时成立，才是这套资源的真实形态。

本文记录的是从这个矛盾推到”1048 个包、19,370 个对象、解包错误 0”的过程——判据是怎么定的、哪些假设是怎么被否证的、失败点各自贡献了什么信息、以及算法体落进虚拟化节之后推进方式发生了什么变化。结论列在下一节，正文是过程。

先说结论#

  • 保护层是两个。VFS 文件层的 ChaCha20 与 AssetBundle 归档层彼此独立，encrypted=false 只关闭前者。
  • 外层归 GameAssembly.dll 的托管 VFS 代码，公共 key、nonce 构造与 counter 都有直接指令证据。
  • 内层归定制 UnityPlayer 的归档路径，实现体在 PE 的 .tvm0 虚拟化节里，本轮没有做完整去虚拟化。
  • 内层由”候选实现 + 本机样本约束”逐层收敛：在当前语料中，稀疏 VFSAES、块目录标准 LZ4、数据块 LZ4Inv 方言与整数混淆逆变换是唯一通过全部判据的兼容候选；这不等同于 .tvm0 的逐指令恢复。
  • 验收半径分三级：最小样本 → InitBundle 全组 1048 包 → 数十 MB 的 Shader 包。全程解包错误 0。
  • 客户端 Unity 版本 2021.3.34f5。

第一个判断：先数保护层，不要先猜算法#

面对”读不出来”的第一反应通常是猜算法：文件头不是 UnityFS，那就是整文件加密了，找 key 去。这个反应在这里会直接走死。

因为矛盾本身已经给出了信息：MD5 对上了。索引里记录的 MD5 是按解密后的文件内容算的，我按 encrypted=false 原样读出来的字节能匹配这个 MD5，说明我读到的东西正是客户端拿到的东西。如果整个文件被一层我不知道的密码保护着，我不可能同时满足”字节和记录一致”和”内容不可解析”。

所以真正的问题不是”key 是什么”，而是”这个字节流在进入 Unity 之前还要经过谁”。这是一个层次问题。层次数搞错，后面所有努力都会归因到错误的地方——最常见的错法是把非标准头归因成提取偏移不对，然后花几天调偏移。

要回答层次问题，先得把”我自己弄错了”这个可能性彻底排掉。

判据先于方法：什么才算”解对了”#

这是整个过程里最该先想清楚的一件事，也是这类分析最容易糊过去的一件事。

试错法的问题不在于试，而在于判据太弱。如果判据是”解出来的内容里有可读字符串”，那么错误的 key、错误的处理顺序、甚至错误的密码算法都有相当概率蒙过去——尤其是稀疏加密这种只改动一小部分字节的方案，大面积原文本来就是可读的。一旦弱判据放过了一个错误分支，后面所有推理都建立在它上面，而且症状会出现在很远的地方。

所以在动手之前，我先把这套资源里所有能当判据的结构性约束列出来，按强度排序：

判据来源为什么强
CRC32 / MD5 / SHA-256.blc 尾部 CRC、文件记录 MD5错误 key、错误 counter、错误算法实现同时通过的概率可忽略
严格解压长度块目录声明的 uncompressedSize解压器必须恰好产出该长度，多一字节少一字节都算失败
物理区间闭合dataOffset + compressedSize == 文件长度与头字段的理解直接挂钩，错一个字段就不闭合
node 覆盖所有 node 的 offset + size 恰好铺满解压数据与块目录的整数混淆公式挂钩
尾部无剩余索引/块目录解析后必须恰好读完结构理解错误会留下残字节
语义可解析UnityPy 枚举对象、Shader 内部 entry table最后一道，验证字节完整性而非仅结构合法
可读字符串——不作为判据

后面每一步的成立与否，都只用这张表里的东西判。这个约定带来的直接好处是：失败会失败在一个具体的位置上，而位置本身携带信息。 后文出现的 invalid match distance 26037、distance 22、distance 34048 三个数字，都是因为判据够强才浮出来的，它们各自否掉了一条处理顺序。

外层：沿入口收敛，而不是全局搜关键词#

外层是有源码级信息的那一层，所以推进方式和内层完全不同：这里可以顺着调用链走。

入口表从类型和方法名建，不从字符串建#

IL2CPP 的 dump.cs 提供了完整的类型、方法名和 RVA。我按 VFS 相关类型名把入口表建出来：

方法RVA作用

key 是从指令语义读出来的#

GetCommonChachaKeyBs 的反汇编显示它先拼 5 段字符串、Base64 解码，再调用 Beyond.Security.IOOO000iiI::IooiIIO。继续进内层函数 _IIiiIIIoO（RVA 0x2F800B0），关键循环只有三行语义：

对应的指令是从 key 与 cipher 各取一个无符号字节、sub eax, ecx、写回低 8 位。这里要强调的是 sub 不是可以随便替换的：加法、异或、减法在这类”逐字节混淆”里经常被当成同一类操作糊过去，但它们给出三个不同的 key。指令写的是减法，那就是减法。

counter 不靠默认值#

ChaCha20 的初始 counter 是 0 还是 1，是个协议参数，不同库的默认值不一样。这种地方最容易顺手填一个默认值然后一路错下去。

不用猜：DecryptCreateBlockGroupInfo 在构造 XXE1 之前，0x3076C52 处是 mov r9d, 1，紧接着 0x3076C62 调用构造函数。第四个整型参数就是 counter，值是 1。

排除矩阵：只测成功组合等于没测#

到这里 key 和 counter 都有直接证据了，按理可以直接跑。但我还是把矩阵完整跑了一遍——不是为了找到能用的那一个，而是为了确认其他组合都会失败。

对 0CE8FA57.blc 的 4×3 矩阵，判据是尾部 CRC32：

key 变换counter 0counter 1counter 2
Base64 原始字节CRC32 失败CRC32 失败CRC32 失败
逐字节加 unlockCRC32 失败CRC32 失败CRC32 失败
逐字节 XOR unlockCRC32 失败CRC32 失败CRC32 失败
逐字节减 unlockCRC32 失败成功CRC32 失败

12 格里 11 格失败、1 格成功，这个形状本身才是证据。它说明的不只是”减法 + counter 1 能解”，还说明：key 变换不是可互换的混淆（加/异或都不行），counter 不是库默认差异（0 和 2 都不行）。如果只跑对角线上那一格，我拿到的是一个能用的实现，不是一个被证明的实现——两者的区别会在下一个版本、下一个资源组、下一个游戏上暴露出来。

成功项解析出组名 InitBundle，存储 CRC32 与计算值同为 2FD48B5F，解密结果 SHA-256 为 a788fbd3ded1a5ec1ca90f44edb9e44b742481fe0e6a36618d96052dd1fc4fe8。

第二层：先定所有权，再谈算法#

现在回到那个 2461 字节的样本。它的头是 40 19 9A FE ...，不是 UnityFS。问题是：是谁把它变成这样的？

这个问题必须先回答，因为它决定接下来去哪里找代码。如果改写发生在托管层，我可以继续读 dump.cs；如果发生在引擎层，托管层再怎么翻也翻不出来。

用否证走到跨模块边界#

托管侧的资源加载入口是 Beyond.VFS.UnityFileLoaderHelper::ReadAssetBundle（RVA 0x3BB2FF0）。顺着走：

ReadAssetBundle 的分支只决定选哪条文件路径，然后把 dir/fileName/offset/crc 交给 ReadStreamAssetBundle；后者组路径、传 crc 和 offset，直接进 AssetBundle.LoadFromFile。整条链上没有任何一处把 .ab 改写成标准 UnityFS 的托管代码。

LoadFromFile_Internal 是 IL2CPP 生成的 native 包装，行为是固定套路：先从全局槽取缓存的函数指针，槽为空时加载字符串

调 sub_59FC0 解析 internal call，把结果写回槽，最后 jmp rax。该字符串的两处关键引用在 0x3BB36CC 和 0x3BB373D。

跨模块边界就在这个 jmp rax 之后。这一节的产出不是一个算法，而是一句”别在托管层继续找了”。这种否证式的结论在实际工作里的价值经常高于正面发现：它关掉了一整个搜索空间。

.tvm0：四类证据叠加，不看节名#

进 UnityPlayer.dll 之后，归档头读取函数在 0x674090。它的第一条指令是跳转到 0x23CBC05。

看到一个独立命名的 PE 节就断言”这是虚拟化”是不够的——节名可以是任何东西。我要的是四类彼此独立的证据同时指向同一结论：

  • 节布局独立：PE 节表里确实有 .tvm0，RVA 0x23C6000，虚拟大小 0x17FFEA，原始数据区 0x22C9200 + 0x17B000。它与普通 .text 的布局和代码归属是分开的。
  • 实现整体转交：0x674090 第一条指令就跳进 0x23CBC05。这不是编译器常见的尾调用形态，而是把整个函数实现交出去。
  • 错误路径同归属：归档失败字符串 Failed to Decrypt data when creating archive '%s'! 在文件偏移 0x1D8ACC8、RVA 0x1D8C0C8，唯一的 RIP-relative 引用落在 0x23CD155，同样在 .tvm0 内。
  • 控制流形态：入口附近能看到寄存器取反、交换、临时压栈、运行时拼接跳转目标再 jmp reg。从 0x23CBC20 往后线性解码很快撞到 sti、浮点指令和越界跳转目标。这是 VM 调度/解释路径的特征，不是按普通函数边界能恢复 CFG 的字节流。

四条叠起来，可以确定的是：定制归档逻辑归属于 .tvm0，入口和错误路径都经过它。 可以确定的仅此而已——VM handler 表、虚拟寄存器布局、字节码格式，本轮一个都没有恢复。

顺带记一个假线索。我在 UnityPlayer 里搜到过 PROTECTED 字符串，一度当成归档保护标志。查交叉引用发现它属于 Vulkan 的 memory-property 枚举。字符串命中永远要配调用上下文看，单独的命中不是证据。

推进方式切换为兼容复现#

这是整个分析里我认为最值得单独讲的一段。

面对一个虚拟化过的算法体，通常有两条路：一条是去虚拟化——恢复 dispatcher、虚拟栈与寄存器、handler 表、字节码语义，然后用动态轨迹逐条对照静态语义；另一条是不解释内部程序，改为在输入输出空间里验证候选兼容实现。

选哪条取决于目标。我的目标是恢复资源，也就是构造一个与客户端在同一批输入上行为一致的兼容实现。这个目标不要求复刻 VM 的调度器，只要求声明语料内的输出一致。分析问题因此从”恢复内部指令语义”收窄为”用足够多、彼此独立的约束验证候选行为”。

于是推进方式换成四件事的组合：

层次手上有什么对收敛的作用
调用边界ReadAssetBundle → LoadFromFile_Internal → UnityPlayer确认谁负责读文件，关掉托管层搜索空间
外层协议protocol=3、12 字节 nonce、公共 key、counter 1有直接指令证据，完全不依赖 .tvm0
识别式与物理布局正式版头部两个大端字段、40/48 字节头用最小样本锁定头长度和数据区间
候选算法稀疏抽取、自定义 SBox AES、字段变换、LZ4 方言作为可执行假设输入，不当成客户端结论
样本约束稀疏差分位置、解压失败距离、node/文件尾闭合排除 key、稀疏规律、处理顺序、距离端序、压缩方言的错误组合
全量验收17 索引、1048 包、19,370 对象把”某个样本能解”升级为”当前正式版资源集上稳定”

第四行需要说清楚来源：内层的几个常量与字段变换公式，我不是从 .tvm0 逐指令恢复的，而是先从公开兼容实现（Escartem/AnimeStudio）取到候选形态，再拿本机正式版样本一层层验。这一点必须写明白，否则整篇文章的证据等级就是假的。

也正因为如此，本文关心的不是那些常量本身，而是怎么把一个候选算法压成本机事实：一个候选实现摆在面前，你如何设计实验让它在错的时候必须以可观察的方式错？下面五节都在回答这个问题。

所以”分析完了”的准确含义是：外层有直接证据，内层由候选实现经样本约束逐层闭合，输出能被通用解析器和全量对象扫描消费。它不等于”.tvm0 已经被翻译成 C++“。要声称完整去虚拟化，得另做一轮完全不同的工作。

头字段：物理文件尾是第一个强约束#

按大端读 40/48 字节候选头，得到：

flags & 0x200 要求块目录之后按 16 字节对齐，所以 0x30 + 0x65 = 0x95 对齐到 0xA0。

这里第一个强约束就位了：后面那个压缩块的长度必须让 dataOffset + compressedSize 正好等于 2461。这个等式把”头字段理解正确”和”块尺寸理解正确”绑在了一起，任何一边错，等式都不成立。选最小样本的第一个理由在这里兑现——如果换个有 30 个块的包，某个块的尺寸算错了，总长仍可能凑巧落在文件内，等式就没有鉴别力了。

一个字段与它的名字不符，不要替它圆场#

头里有个混淆的 size 字段。按候选公式解出来是 0xE370CDAAE370C437；就算截成 32 位也只是 0xE370C437。样本物理长度是 2461。

这时候有两种处理。一种是认为自己解错了，继续调公式直到它等于 2461；另一种是接受这个字段在这批资源上就不承载物理长度，把边界约束建立在别处。

我选第二种，理由是别处的约束已经自洽了：物理长度来自输入流本身，块目录区间必须落在输入流内，每个压缩块必须落在输入流内，解压总长必须覆盖所有 node 的 offset + size。这四条已经把边界锁死，不需要 size 参与。反过来，如果强行让 header.size == 文件长度 成立，就会错误拒绝合法包——这条已经被本机样本直接否掉了。

一个字段的名字不等于它的语义。让约束系统里的其他部分承担职责，比给一个不符的字段编解释要安全。

差分实验：稀疏加密的判定#

把数据块拿出来看，现象很别扭：里面能看到大片像 Unity SerializedFile 的结构，类型树、路径、版本号都是可读的，但某些 token、长度或距离持续损坏。

这个现象本身就能区分两个假设，只要想清楚每个假设预测什么：

  • 假设 A：整块连续加密。 那么 2301 字节会整体变成随机字节，大面积可读内容不可能存在。
  • 假设 B：稀疏加密。 只有少量位置被替换，其余原样。这与观察相符。

假设 A 与观察直接冲突，排除。接下来要验的就不是”是不是稀疏”，而是”稀疏的选择规律是什么”——这是个可以精确预测再核对的问题。

候选规律给出的预测是：

也就是说：只有每个 16 字节块的开头 1 个字节被处理，一共 143 处。跑一遍变换，做输入输出字节差分，实测结果是：

  • 实际发生变化的位置有 141 个；
  • 所有变化位置都满足 offset % 16 == 0；
  • 最后一个变化位置是 2272。

offset % 16 == 0 和末位 2272 与预测严格一致。但数量是 141，不是 143。

这个差 2 值得停一下。诱惑是把实现改成”只选 141 个”去对上观察——那就彻底错了。差分集合记录的是”值发生了变化的位置”，不是”被处理的位置”：其中两处的输入字节恰好与解密后的字节相同，变换发生了但差分看不见。差分数量不是算法参数。 这类”用观测数据反向修正算法定义”的错误一旦犯下，会在别的包上立刻炸掉，而且现场离原因很远。

块目录走的是同一入口的另一个分支：它只有 101 字节，length <= 256 时直接对整个缓冲做流变换，不走抽取。数据块才走”抽取到 256 字节临时区 → 变换 → 散回”。同一个函数两个分支，这也是为什么两者后面接的解压器不一样——它们从一开始就是两条路。

变换本体是一个 OFB 形状的构造：用自定义 SBox 的 AES-128 加密当前 IV 得到 keystream，与输入异或，然后由 keystream 推出下一块 IV。

注意它的用途不是解密 AES 密文块，而是拿 AES 当 keystream 发生器。密钥编排是标准 AES-128 的形状（含标准 RCON），只是把 SBox 换成了自定义的 256 字节表。轮结构仍然是 SubBytes → ShiftRows → MixColumns → AddRoundKey，末轮省略 MixColumns。

用失败点锁定处理顺序与压缩方言#

现在有两个未定项：稀疏解密和解压的先后顺序，以及用哪种 LZ4。组合起来是四种可能，而且块目录和数据块可能各不相同。

如果判据是”能不能解压出东西”，这一步会很难判——LZ4 是自同步的，错误输入常常能吐出一段前缀再失败，容易被当成”基本对了”。所以判据必须是严格解压长度：解压器要求恰好产出块目录声明的长度，多一字节、少一字节、有尾部残留都算失败。

块目录里的整数混淆#

块目录经过 VFSAES 和标准 LZ4 之后仍然不是标准 UnityFS 的 blocks info：计数、尺寸、flag、offset 和名称还各自套了一层整数混淆。

有一个坑：计数字段中间有一次小端读取加端序反转，不能简化成”对大端原值直接异或一个常量”。实现必须按原始字节顺序复现整个过程，否则在某些取值上恰好等价、在另一些上不等价——这是最难查的一类错误，因为它间歇性成立。

让每一层能独立失败#

到这里算法链全通了，接下来是工程问题：怎么组织实现，让以后出错时能立刻定位到层。

我把它拆成六个文件，拆分依据不是代码量，而是失败条件是否独立：

文件职责关键失败条件
vfs_crypto.pykey 变换、参考 ChaCha20、PyCryptodome 对照、两种 noncekey/nonce 长度错误、两个实现输出不一致
vfs_format.py.blc 结构、CRC、计数、可选字段CRC 不符、负计数、尾部剩余、声明文件数不符
vfs_access.py.chk 区间读取、可选文件解密文件越界、恢复后 MD5 不符
vfs_bundle_crypto.py自定义 AES 流、IV 演进、稀疏抽取与散回输入区间或稀疏选择规律不符
lz4_inv.py标准 / LZ4Inv 共用状态机非法距离、输出越界、尾部剩余、长度不符
vfs_bundle_format.py头、目录、block、node、UnityFS 重封装目录越界、未知 flag、node 越界、目录尾部剩余

每个文件只对自己那一层的判据负责，并且在判据不满足时抛错而不是返回部分结果。这样一个新包解不开的时候，异常类型直接告诉我是密码层、容器层还是语义层的问题。

重封装那一步刻意不做任何”修补”：解码头、目录、block、node，解压全部块并验证 node 区间，然后写标准 UnityFS\0 + version 6 + 2021.3.34f5，以解压数据的 MD5 作为 blocks-data hash，每个块写成 compressedSize == uncompressedSize 的 None 压缩，最后原样追加解压数据。只换容器，不动 SerializedFile 和 .resS 的任何一个字节。 这条纪律保证了后续所有分析看到的都是客户端看到的字节。

三级验收：把”能解”变成”稳定”#

一个样本通过不代表实现正确，只代表实现没有在这个样本上暴露问题。所以验收半径要主动扩大，而且每一级要针对不同的失效模式。

第一级，最小样本。 恢复结果 6319 字节，SHA-256 858c6bd23289be88b88c9e1f98af7d63958241669372d0fd307219fdd11dbc96，头为 UnityFS\0。UnityPy 读到 Unity 版本 2021.3.34f5、一个 4x4 的 Texture2D T_default_mro_MRO、一个 AssetBundle，对象总数 2，解析错误 0。这一级验的是全链路通。

第二级，完整组。 扫 InitBundle 的全部 1048 个包：

这一级验的是实现没有隐式绑定单一头长度、单一块大小或单一 node 数——2461 字节样本只有 1 个块 2 个 node，覆盖不到多块、多 node、BlocksInfoAtTheEnd 这些分支。

第三级，大载荷。 恢复三个数十 MB 的角色 Shader 包，并继续解析 Unity 2021.3 的 subShaderBlobs、segment、entry table 直到 DXBC。这一级验的是长块、资源 node 和大二进制载荷的字节完整性——能枚举对象只说明容器对了，能一路解析到 DXBC 内部结构才说明每个字节都对。

三级下来，密码层用 CRC32/MD5/SHA-256 判，容器层用物理区间/严格解压长度/node 覆盖判，语义层用 Unity 对象和 Shader 内部结构判。任何一层出现”可读字符串”都没有被当成成功。

复盘：可迁移的部分#

抛开终末地这个具体目标，这次过程里真正能带到下一个自研容器上的东西是这些。

先数层，再猜算法。 矛盾观察（校验通过 + 解析为空）比任何单点现象都有价值，它直接给出层次数。层次数搞错，后面所有努力都会归因错位置。

判据先于方法。 动手之前把所有可用的结构性约束列出来排序，然后只用强判据判成败。可读字符串不算判据。这一条决定了失败会不会失败在有信息的位置上。

只测成功组合等于没测。 12 格里 11 格失败的形状，比 1 格成功更能说明问题。它同时排除了”参数可互换”和”默认值差异”两类误解。

否证是廉价的推进。 画一次调用图否掉 index_main.json，走一次调用链否掉”托管层还有第二套解密”，成本都远低于对着错误输入调参数。关掉一个搜索空间和找到一个答案同样有价值。

最小样本优先。 挑组里最小的那个，让每一个约束都保持鉴别力。包越大，巧合越容易发生。

不要让观测数据反向修正算法定义。 143 与 141 那个差 2 是这次最险的一个坑。观测量和算法参数是两回事，对不上时先怀疑自己对观测量的解释。

字段名不等于字段语义。 一个叫 size 的字段不承载物理长度是完全可能的。让约束系统的其他部分承担职责，比给它编解释安全。

目标决定是否需要语义恢复。 算法体在虚拟化节里，如果目标是恢复资源，就可以把问题限定为兼容复现：用足够多、彼此独立的约束验证输入输出行为。这个降级必须写进结论：能说的是”输出与本机正式版资源相容”，不能说”已完整还原”。

边界要显式声明。 本轮没有恢复 .tvm0 的 dispatcher、虚拟寄存器和 handler 表，也没有把内层常量做成逐指令的独立恢复。写清楚这些，别人才能判断哪部分可以直接引用、哪部分需要自己重做。
