终末地角色湿润 Shader：逐 Draw ABI 与三类材质坐标

终末地的角色湿润由一条跨控制器、参数 blob 与 Shader 的链路驱动。水体、雨水与玩法湿润先编码进 CustomPerDrawData，衣服用稳定角色坐标三平面生成水滴和流痕，面部沿模型 UV 做双相位滴流，头发则由 packed wet 标量驱动程序化湿膜与各向异性高光。这条链必须由控制器实参、参数 blob 与 DXBC 三类证据交叉才能闭合。

2026-08-21 20 分钟 4012 字 图形逆向
#Unity#Shader#DXBC#Wetness#Reverse Engineering#Rendering

角色“变湿”看起来是一个连续标量，实际至少有三种来源和三套材质响应。水体需要一条能跟随世界水面的水线；雨水需要衣服表面的水滴与流痕，还要处理遮挡后的延迟干燥；玩法事件则可能不依赖天气或水体，直接把一队角色推到目标湿润度。

这三条状态最终被压进一份逐 Draw 数据，但不同材质没有共用一套采样坐标：

  • 衣服与身体使用稳定的角色坐标做三平面投影，水线另用绝对世界高度。
  • 面部使用特定脸部 UV，沿 V 轴做双相位滴流。
  • Hair 基础变体不绑定四张角色雨水纹理，而是消费同一 packed wet 状态，用程序化 cell、法线扰动与各向异性高光生成湿膜。

结论来自三类证据交叉：IL2CPP 控制器的写入实参确认状态通道，Unity Shader 参数 blob 确认局部纹理寄存器，ps_5_0 DXBC 确认位解码、采样坐标、通道消费和 BRDF 数据流。单靠字段名、纹理画面或某一份反汇编，都不足以闭合整条链。

状态、资源与材质响应分成三层#

状态层只决定角色“有多湿”和水面在哪里；纹理资源提供不同尺度的水迹；材质层再按自己的几何参数化解释这些输入。把三层合成一个 Wetness 参数，会丢掉水线、遮挡、面部 UV 约束和 Hair 高光方向。

局部泼水还有一条 decal projector 链：按模型节点找 Transform，在给定时长内插值 projector alpha。场景表面的 Wetness、VerticalFlow 与 Ripple 则属于相机级 Rain Wetness Feature。它们都不应与角色逐 Draw 湿润合并成同一系统。

三个湿润来源编码进一个浮点槽#

控制器通过 EntityRenderHelper.SetFloatToCustomPerDraw 写四个原始通道：

原始通道值稳定语义写入证据
1世界空间水面高度水体控制器写 relativeHeight + characterPivotY
8雨淋强度雨水控制器写平滑后的雨强
16水体浸润强度水体控制器写 m_wetness
24玩法湿润强度玩法控制器写目标值的平滑结果

这些语义来自具体调用上下文，不是从一个可见枚举定义里直接抄出的名称。Shader 端给出了第二次独立确认：CustomPerDrawData[2].x 先被 asuint，再按字节移位。

x 的类型表面是 float，语义却是四个 UNorm8 借浮点槽传输。若在移植端直接把它当普通浮点强度插值，四个通道都会被破坏。y 保留独立浮点精度，用于和像素世界高度比较。z 属于角色溶解调度偏移，不进入湿润计算。

u * u * (3 - 2u) 是 DXBC 展开的 Hermite smoothstep。0.2 与 2.857143 是目标程序里的立即数，不是通用湿润参数。这里能确认的是算法形状：世界水面高度减像素世界 Y，经过一段软边后乘水体强度。

这种表示比角色空间的一张动态“浸水 mask”更直接：角色走入斜坡水面时，水线仍由世界高度决定；玩法湿润则通过 max 提供不依赖水面的全身基底。移植到使用 Z-up 的引擎时要转换轴和单位，不能原样照搬 Y。

雨淋检测是带预算的角色级调度#

角色传感器分别保存 waterRaycastAge 与 rainRaycastAge，按对象类型读取检测间隔。反汇编中的 rain cast 会写入批量 RaycastCommand 队列，并结合命中数组、睡眠集合与 round-robin 调度；停雨分支清零 age、撤销 isRaining 并触发状态回调。

磁盘 .rdata 中三个候选 float 代入后得到近零方向和零距离，与有效射线矛盾。因此当前证据不能发布具体射线方向、长度和无命中公式。能够移植的是调度边界：集中式异步 Trace 队列、按角色类型与 age 到期入队、每帧固定预算、对象销毁或传送时取消旧请求。具体几何参数需要运行时正证。

雨水、水体与玩法强度都经 SmoothedFloat 演化。环境改变先设置目标与平滑时间，当前值逐帧逼近；来源消失后等待各自 dry delay，再平滑回落。它不是一个从 0 到 1、再按固定速度减回 0 的全局计时器。

四张共享纹理的职责由消费端确认#

角色雨水预设引用四张 1024 × 1024 BC7 纹理：

纹理绑定材质已确认用途
T_actor_common_rain_01_MClothing t10全身水滴法线、覆盖与两级阈值噪声
T_actor_common_rain_02_MClothing t11纵向流痕法线、硬覆盖与软幅度
T_actor_common_rain_03_MSkin t11面部滴流法线与移动轨迹
T_actor_common_rain_04_MSkin t12面部水珠与脸部 UV 区域约束

纹理观察只能提供候选语义。例如 02.B 与 02.A 的图像相关系数约为 0.753，说明两者相关，但不能据此说它们重复。DXBC 显示 B 进入流痕覆盖、A 独立调制法线幅度，消费端才把用途分开。

04.B/A 呈现特定脸部 UV 分区，因此不能把这张图当作任意网格可平铺的通用水滴图。复用湿润材质时，衣服纹理可以依赖空间投影，面部纹理必须重新绘制区域遮罩或 rebake 到新脸部 UV。

衣服使用稳定角色坐标三平面#

Clothing 程序的 t10/t11 都做三平面采样。投影权重来自法线：

三个平面的坐标分别采样后按 weight 混合。这样水滴与流痕密度不依赖 UV 岛，分开的衣服部件也能保持相近尺度。

坐标证据需要保留一个边界。绝对位置 v2.xyz + cb0[44].xyz 明确用于水线比较；雨水与积雪三平面使用独立的 v8.xyz。当前恢复到的 Bundle 只有像素程序，没有写入 v8 的顶点程序，因此可以把它定义为“稳定的对象/角色坐标类输入”，不能写死为已确认 Object Space。

移植时可先用 Pre-Skinned Local Position 或 World-to-Local 后的角色稳定坐标实现，并通过三项测试区分坐标错误：

  • 角色平移时，水滴纹理不应在身体表面滑动。
  • 角色旋转时，投影应跟随角色，而水线仍保持世界水平。
  • 蒙皮与 LOD 切换时，空间尺度不应突然变化。

全身水滴 A 通道进入 0.8 - A 与 0.45 - A 两级阈值链；R/G/B 参与法线和覆盖。程序还用 _Time 与多组立即数生成 cell/hash 错相，所以效果并非简单滚动静态纹理。

流痕纹理的 R/G 按 2*x-1 解码法线 XY，B 进入覆盖，A 调制法线幅度。最终水滴、流痕和程序化滴落 mask 汇合，再把扰动法线与角色原法线组合。

面部沿 UV 做双相位滴流#

Skin 程序使用模型 v1.xy。同一张 FaceDrip 沿 V 轴采样两个相近相位：

两个相位相差 0.005，用于构造连续移动边缘，不代表两份纹理。实际通道关系是：

  • FaceDrip.RG 解码法线 XY，并重建 Z。
  • FaceDrip.A 的两次相位采样与 FaceDroplet.B 相乘，形成移动覆盖。
  • FaceDrip.B 与 FaceDroplet.B 形成另一层滴流/水珠 mask。
  • FaceDroplet.B 约束脸部有效区域。
  • FaceDroplet.A 在另一条视角/法线链中调制湿高光。

采样指令是 sample_b_indexable，bias 来自常量缓冲；Clothing 与 Hair 的相关采样也使用同类 bias。复现端应保留导数采样和可调 Mip Bias，固定 SampleLevel(..., 0) 会在远处、斜视角和 LOD 变化时产生闪烁。

现有程序确认法线、遮罩与 BRDF 标量，没有证据支持面部一定使用视差、折射或独立清漆 Pass。

Hair 不绑定雨水图，但仍消费湿润状态#

Hair 参数表里能看到四个角色雨水属性名，但 132 个相关记录的局部 texture register 都是 0xFF，有效绑定数为 0。这个事实只覆盖当前基础变体：它没有通过这些属性采样四张共享雨水纹理。

同一 Hair ps_5_0 仍读取 packed wet ABI。湿润阈值通过后，程序使用 v9 与尺度常量构造稳定坐标，再由时间 hash 和程序化 cell 生成局部湿膜法线、覆盖与高光。后续的 t11 采样绑定 _CharacterSnowEffectTex，且只在 packed snow 通道超过 2.55/255 时进入，不能把它误标成雨水纹理。

参数反射确认 Hair 已有 _Specular、_Metallic 和一组各向异性参数。湿润分支没有把这些字段重写成另一套材质，而是用程序化湿膜改变法线、颜色调制与各向异性高光强度。这种分工也解释了为什么 Hair 可以共享角色湿润状态，却不必共享衣服的三平面水滴纹理。

湿润同时改变法线、粗糙度、颜色与高光#

Clothing 数据流先形成：

超过阈值后，湿膜、水滴和流痕分别进入材质响应。已具名交叉确认的部分包括：

  • baseRoughness = 1 - _Smoothness。
  • 第一层湿膜把粗糙度拉向 min(baseRoughness, 0.05)。
  • 后续水滴与程序化层继续在约 0.9 和 0.01 之间调制局部粗糙度。
  • 局部湿遮罩执行 lerp(_Metallic, 0, wetMask)，把表面响应拉向水膜的 dielectric 方向。
  • 标准高光色链包含 0.04 * _Specular，并与有效 Metallic、Base Color 合成。

所以“湿润 = 把 Roughness 设成一个常数”是不完整的。湿膜、水滴和流痕有不同空间尺度；法线扰动与粗糙度变化共同决定闪光，颜色还会进入目标 NPR 的中间色空间。

当前没有完成整个 NPR 常量缓冲的具名映射。反汇编里出现的 0.308、0.88 等颜色中间值不能直接当作所有材质通用的线性 Base Color 暗化比例；也没有证据发布一个固定 wet roughness 终值或清漆公式。

Shader Blob 的恢复需要参数与指令交叉#

这次像素程序不是从运行时 draw 抓取得到的，而是从已恢复的 Shader 资源离线提取。资源保护层见资源的两层保护；这里从标准 Unity Shader 对象开始：

这条路径里有五个容易制造假证据的点。

高层 m_Name 为空不代表 Shader 没名字。 这批对象的真实名称位于 m_ParsedForm.m_Name。

Unity 2021.3 的真实程序列表在 m_PlayerSubPrograms。 只读常为空的 m_SubPrograms 会得到“Shader 没程序”的错误结论。

序列化字段名不等于实际阶段。 有效引用放在 progVertex 字段，但 m_GpuProgramType=25 与 DXBC 头确认它是 ps_5_0。按字段名强制筛 progFragment 反而会得到零条结果。

entry offset 属于各自 segment。 主 Shader 的 segment 0 只有 entry table；把所有 segment 拼接后按全局 offset carve，会截到错误字节。

属性名存在不等于当前变体已绑定。 参数记录起点 +10 是局部 texture register，0xFF 表示未绑定。Hair 的边界正是靠这项证据确认。

参数 blob 还提供 cbuffer 成员 byte offset，DXBC 再把 cbN[index] 与 tN 的真实消费串起来。名称、槽位和指令三者同时对上，材质语义才算闭合。

证据边界#

结论证据强度保留边界
packed wet ABI 与世界水面高度控制器实参 + DXBC 位解码枚举名来自稳定语义映射
衣服三平面、面部 UV 双相位参数 register + DXBC 坐标链Clothing v8 的精确顶点空间尚未确认
Hair 程序化湿膜0xFF 未绑定记录 + DXBC wet 分支只覆盖当前基础关键字变体
湿润进入法线、粗糙度、颜色与高光DXBC 数据流 + 具名材质 offset完整 NPR 光照模型未具名恢复
rain cast 的集中调度字段、调用签名与批量队列方向、长度、命中公式未恢复
UE5 可移植结构已确认数据流的工程映射当前资料不构成已完成的视觉或性能验收

结论#

角色湿润的稳定边界落在“状态 ABI + 材质参数化”这一层，而非任何单张水滴贴图。水体、雨水和玩法湿润先保持独立，再压进逐 Draw packed 数据；衣服、面部和 Hair 各自选择适合自身拓扑与材质的坐标和细节生成方式；最终湿遮罩同时驱动几何细节与 BRDF。

这条链也给出一套更可靠的 Shader 逆向纪律：控制器说明谁写值，参数 blob 说明值落在哪个寄存器，DXBC 说明它怎样被消费，纹理通道图只承担视觉辅助。三类证据交叉后，才能把“画面看起来像水”提升为可移植的数据流。
