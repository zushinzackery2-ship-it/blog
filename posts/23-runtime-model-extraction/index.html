运行态角色模型的外部提取：双路径架构、身份校验与顶点数据审计

从已知的 Unity GameObject 出发提取运行态角色的网格、骨骼与 UV，主体沿组件、Renderer 与 Mesh 做外部只读解析，只在显存独占的顶点缓冲上补一次最小 GPU readback。记录关键字段偏移、身份校验、骨骼姿态语义与顶点数据审计。

2026-08-11 17 分钟 3361 字 Unity 逆向
#Reverse Engineering#Unity#IL2CPP#Mesh#Skeleton#GPU Readback

输入是一个已知的 Unity GameObject。提取链从组件槽进入 Renderer、SkinnedMeshRenderer 和 Mesh，恢复运行态网格、骨骼与 UV；显存独占的顶点缓冲由最小 GPU reader 读回。静态资源解包只提供打包态数据，完整远程注入器则扩大进程内代码范围；本文聚焦 GameObject 之后的数据链。

这条路由两部分组成：绑定目标二进制指纹的实际偏移，以及验证偏移有效性的运行态探针。实际偏移提供复现入口，身份和探针负责在版本变化后及时关闭失效能力。下面先给出本次目标构建的实际 profile，再按组件分工、身份校验、能力门槛、骨骼姿态、顶点与 UV 审计展开。

两条路径按 CPU 可见性分工#

主体路径用只读权限打开进程，以已知 NativeGameObject 为入口，跨进程读取组件槽、Transform 树、Renderer、网格 CPU 数据和材质属性表。

最小 GPU reader 负责读回 CPU 副本已释放、仅存在于显存的顶点缓冲，通过命名管道返回数据，请求完成后卸载。它也能读回 provider 为空的纹理像素；模型链只使用顶点缓冲读回能力。

这套分工把进程内代码限制在 GPU 独占资源读回，其他结构均由外部只读路径恢复。

本次目标构建的实际 profile#

本文后续所有 RVA、字段偏移和 stride 绑定 star-unityplayer-2025-02-19-pdb-0b158128。目标 UnityPlayer.dll 的映像大小为 0x1E64000，PE 时间戳为 0x67B55906，代码段 MD5 为 C9D7511A4455BC31FF770E3852A07FED，参考文件 MD5 为 2B393BDAD9C35E750EDB035F9FE102A9，PDB GUID 为 0B158128-4A3B-4E9B-95CE-840CC514FDAD。profile 以这些字段全部匹配作为启用条件。

本文把已知的 NativeGameObject 指针作为输入。表内 +offset 均相对左栏对象基址：

提取能力与缺失边界#

在写任何解析之前，先把边界列清楚。外部只读能如实恢复的：对象树与局部 TRS、各类渲染器与材质引用、经校验的网格顶点流/索引/bindpose/权重、直接骨骼向量与优化骨骼的原始索引表、材质属性表与实例覆盖、解析后的运行态属性名。

缺失项包括显存独占缓冲、尚未验证的共享骨架映射、动画曲线和未知布局的 BlendShape。provider 为空的纹理像素以及从引擎着色器到通用 PBR 的外观映射，由贴图提取链处理。

导出结果对这些缺失项显式记录状态和原因。默认值、推测地址或静态资源替代会污染下游数据语义，因此不进入正式结果。

对象身份由双向回指闭环确认#

Unity 的托管对象和原生对象互相持有指针：托管对象在固定偏移指向原生对象，原生对象在另一固定偏移回指托管对象。对象验收要求完整地址范围可读、页面属性有效、双向回指一致、类名符合预期；任一条件失败即停止采集。组件身份由类名确认。递归遍历同时设置最大深度、节点数上限和已访问集合，用于截断环引用。

能力由探针门槛逐项开关#

每项外部读取能力同时依赖目标二进制指纹、字段关系和运行态探针。探针按能力分组；任一必需探针失败时，对应能力进入禁用状态。

目标身份由内容哈希、映像大小和符号信息共同锁定。指纹变化会使全部参考地址进入禁用状态，随后由匹配二进制、符号和运行态关系重建 profile。顶点属性通道范围等结构参数也随 profile 重新确认，防止越界读取相邻结构。

骨骼的姿态语义要一致，优化骨骼要克制#

骨骼载体与网格顶点统一使用绑定姿态语义。rest pose 由 inverse(bindpose[i]) 推导，再转换到父骨骼局部空间；当前帧局部 TRS 仅用于姿态更新。

矩阵按引擎的行/列主序和缩放约定处理，并验证正逆矩阵相乘为单位阵；奇异缩放使该骨骼恢复失败。优化骨骼通过共享骨架、索引范围、父子关系和 bindpose 四项校验后写入整型索引；未通过的记录保留占位状态。世界变换（渲染器的世界矩阵）用于场景放置、当前姿态、世界法线和光照，UV 与贴图继续使用局部数据。

顶点数据审计要引入独立真值#

GPU reader 同时提供独立于 CPU 解码路径的顶点真值。显存读回结果与 CPU 解码、载体文件、最终导入网格进行四方逐点对照，分别覆盖解码、导出和导入过程。

这类审计覆盖顶点数据的解码、搬运和格式化，比较对象是四路数值。任一路出现差异即失败；贴图方向审计单独处理像素行序，两个结果分别记录。

结构参数要从反汇编钉死#

结构参数取错会生成静默错误。顶点属性通道具有固定上界；本构建的合法范围为 0..13，按 16 个通道扫描会进入相邻描述结构并额外生成两组伪 UV。

通道数、维度和步长由反汇编与运行态数据共同确认。导出器按流索引、偏移、格式和维度解码属性，并校验“属性偏移加元素大小不超过步长”。索引显式标注局部或全局语义；baseVertex 经过有符号扩展后逐项验证范围。越界或页面不可读会使该网格验收失败。

顶点缓冲定位要复现引擎的选择规则#

引擎先压紧有效物理槽，再按流序号选择顶点缓冲。读回路径复现同一选择规则：先枚举有效槽，再将逻辑流映射到压紧后的物理槽。这个映射保证返回的 D3D buffer 属于当前网格和目标流。

多维 UV 与顶点色要用扩展属性承载#

多维 UV 在二维载体中会出现维度截断。部分网格的 UV 通道为三维或四维；只导出前两维会丢失染色或区域逻辑使用的分量。

根子在载体格式：标准 glTF 的 TEXCOORD_n 只允许二维。解决方式是分两处写——两维写进标准属性供通用查看器读，完整维度写进扩展属性，导入器优先读扩展属性并按真实维度恢复。

顶点 COLOR 也需要先确认语义。描边或 toon 控制数据写入扩展属性，由导入侧恢复；标准 COLOR_n 只承载真正参与顶点着色的颜色。载体服务于运行态复现管线，外观正确性由目标着色器回放验收。

UV 采样行为常由材质常量门控#

各 shader 变体都包含同一段 atlas 重映射块，材质常量控制其插值权重：常量为 1 时使用 remapped UV，为 0 时保留原始 UV。

复刻端始终实现重映射块，并由门控常量控制插值。重映射位于着色器的 UV 语义层，负责采样坐标；行序归一化位于编码层，负责像素排布。序列化边界保持 UV 原始分量，atlas 重映射留给着色器执行。

边界与迁移#

这套模型提取以已知 GameObject 为输入，覆盖从组件到网格的解析与顶点数据搬运。对象发现、贴图方向、染色和其他外观项属于独立链路。实现按 CPU 可见性划分读取路径，以双向回指和 owner 关系确认对象身份，由探针控制各项能力状态，并对缺失项记录明确原因。顶点审计使用独立 GPU 真值；通道数和维度由反汇编确认；多维 UV 与控制型顶点色通过扩展属性完整承载。

迁移到其他 Unity IL2CPP 构建时，需要重新建立字段 profile，并以逐点一致性作为模型验收标准。
