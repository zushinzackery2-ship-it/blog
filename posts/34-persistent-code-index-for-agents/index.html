面向 Agent 的持久代码索引：快照式增量、符号级读取与置信边界

Agent 反复扫盘和读取整文件会消耗上下文，也无法稳定处理引用关系。把文件、符号、import、调用图和质量元数据写进持久数据库，冷启动复用已有索引、文件事件只重算受影响记录，导航就能降到「一个定义加一圈影响面」。本文拆解快照式增量为什么必须优于逐事件更新、三类搜索各自的成本曲线，以及静态索引在动态语言与生成代码上的语义边界。

2026-08-21 19 分钟 3728 字 MCP 架构
#AI Agent#MCP#Code Index#SQLite#Incremental Build#Developer Tools

代码 Agent 的导航成本通常被低估。第一次看项目时需要了解目录，改一个函数时需要找定义和引用，改完还要确认有没有深层嵌套或遗留入口。如果每一步都从文件系统重新扫描，再把整份源码塞进上下文，工具调用本身就开始消耗主要预算。

可行的做法是把代码库的结构信息变成一份跨会话存活的状态：

  • 文件、符号、import、行区间和复杂度写入数据库；
  • 进程重启后复用已有索引；
  • 新增、修改、删除文件只重算受影响记录；
  • 父工作区可以挂接子项目索引，不重复维护同一份源码；
  • 符号搜索、符号体读取和调用图让 Agent 先取最小证据；
  • 语义向量是可选加速层，词法精确搜索仍是主路径；
  • 质量检查随结论给出覆盖率和置信度边界。

索引把项目状态保存到会话之外，导航请求只取需要的结构片段。这份状态要多稳、增量要做到什么粒度、哪些结论不能从静态索引里推出，是下面要拆的三件事。

下面的表结构、增量步骤和错误契约取自一个具体实现——一个基于 SQLite 的 MCP 代码索引服务。引用它是为了让每条设计判断都有可对照的落点，结论本身不依赖这个协议。

索引把源码拆成几种可复用事实#

SQLite 主库的核心表是 files、symbols、symbol_nesting、child_indexes 和 FTS5 file_fts。文件记录保存相对路径、父目录、扩展名、语言、尺寸、修改时间、SHA-1、行数、imports、symbols、代码片段、质量发现和 active source 标记。

符号记录保存名称、kind、起止行、签名、复杂度、calls 与 called_by。symbol_nesting 单独保存父符号、深度、嵌套路径、子数量和最大块深度。把这些字段持久化后，Agent 不必为了一次“谁调用了这个函数”重新解析全项目。

向量不混在主索引里，而放在独立 embeddings.db。这是一个重要的生命周期边界：语义向量属于可重建派生物，主导航事实损坏或模型更换时，不需要删除文件与符号索引。

冷启动先绑定根目录，再复用状态#

MCP 会话首次调用任意工具时，服务按顺序解析项目根：

  1. 启动参数 --project-path；
  2. AUTO_INDEX_PROJECT_PATH 环境变量；
  3. MCP 客户端提供的 roots；
  4. 都没有时返回结构化 not-enabled 错误，并提示调用 auto_index_enable(root_path=...)。

找到根目录后，enable_reusing_index 检查对应 .auto-index-mcp/index.db 是否存在。已有索引可直接绑定，语义向量在后台补齐；没有索引才启动后台构建。

服务状态保持紧凑：

状态接口不把后台任务的完整日志、向量错误和重复结果嵌套进去。Agent 频繁轮询时，返回大小保持稳定；构建中的细节通过 index_build 与 watcher 状态读取。

父工作区只挂接子索引#

项目经常包含嵌套仓库或独立工具目录。父索引扫描时发现子目录已经有自己的 .auto-index-mcp，会在 child_indexes 表记录子根、数据库路径、文件数量、更新时间和版本，而不是把子项目所有文件再写入父库。

父索引的 total_file_count 可以包含子索引文件，file_count 仍表示当前库直接拥有的记录。这样概览能看到完整工作区规模，导航又能把写入责任留在实际子项目。

子索引发生新增、删除或结构性变化时，父 watcher 触发 structural rebuild；子索引只是记录内容变化时，父库刷新链接而不重复解析源码。这个区别避免“任何子项目改一个文件，父目录全量扫描”的级联成本。

增量更新依赖快照而非单个事件#

watcher 使用 watchdog 接收文件系统事件，但事件本身不直接写数据库。它先收集待处理路径，经过 debounce，再构造 WatchSnapshot：

快照记录文件的 size 与 mtime_ns，并保存子索引状态。事件丢失、编辑器采用临时文件替换或多个进程同时写入时，快照仍能以实际文件系统为准。

增量 updater 的步骤是：

  1. 子索引新增或删除：走结构性重建。
  2. 子索引仅修改：刷新 child link。
  3. 没有文件变化：只做 metadata refresh。
  4. 先从数据库取旧 FileRecord。
  5. 删除已消失路径，扫描新增/修改路径。
  6. 对所有活动记录重新解析调用者与项目级质量发现。
  7. 只替换真正改变的记录和被删除记录。

它还有跨进程去重：如果另一进程已经把同一 size/mtime 写入数据库，当前 watcher 返回 shared-index-current，跳过重复读取与写入。多 Agent 共用项目时，这比简单地“每个进程都重建自己的索引”更稳定。

文件解析失败不会把半份记录写入库。该路径会被标记为 unindexed 或重新排队；watcher 的错误状态会保留，下一次全快照重试。

文件导航与符号导航是两条成本曲线#

第一次接手未知项目，不需要逐个读取文件。auto_index_overview 返回语言分布、顶层目录和按目录平衡的代表文件；入口文件优先，测试与归档目录降权。auto_index_tree_get 再按目录深度给出文件数、语言构成和样例。

文件路径不确定时，auto_index_files 支持：

  • 路径子串；
  • 裸文件名；
  • glob；
  • 语言和目录过滤；
  • 找不到文件时按符号名回退。

找到目标后，auto_index_file(detail="summary") 只返回 imports、符号行区间和复杂度；detail="full" 才附带调用图与嵌套数据。真正需要源码时，auto_index_symbol_body 按符号名、路径和行号取单个函数体。

路径容错只做归一化与候选提示#

所有路径参数统一接受项目相对路径、反斜杠、项目内绝对路径和唯一文件名。服务会规范化成正斜杠相对路径；未命中时返回 {error, hint, candidates}，而不是抛出裸异常。

词法、符号和语义搜索有不同职责#

auto_index_text_search 是源码 literal/regex 搜索，适合找字符串、配置值和没有被符号解析器识别的调用。auto_index_symbol_search 面向定义，排序顺序是精确名、前缀、子串、签名；直接命中失败后才按 camelCase/snake_case 子词放宽，并返回 match_mode。

auto_index_symbol_refs 从持久化 calls / called_by 取 callers、callees 或两者。它的边界是索引内的静态调用：动态反射、函数作为值传递、宏和跨语言生成代码都可能落在索引边之外。工具文档把它定位为“改函数前看影响面”。

语义搜索使用本地 ONNX embedding，把长符号分块后做向量召回，再用词法重合校正排序。内置 MiniLM 是英文模型，中文查询主要依赖词法兜底；需要中文语义召回时，应配置多语言模型。向量不可用不会破坏文件、符号和 literal 搜索。

这种分层很重要：

问题首选工具
“这个名字定义在哪？”symbol search
“谁调用它？”symbol refs
“哪里出现了这个字符串？”text search
“描述这个行为的代码可能在哪？”semantic search
“我只需要函数体”symbol body

把所有问题都送进向量搜索会丢掉精确性；把所有问题都送进全文 grep 又会返回过多上下文。

持久状态需要生命周期协议#

auto_index_enable 可以复用现有库，也可以显式 rebuild=true。auto_index_manage 统一处理：

清空操作会检查后台索引和 embedding 构建是否仍在运行；运行中返回 clear-skipped-background-running，不会删除正在使用的数据库。delete_file=true 才会同时停止 watcher 并删除主库与 embeddings 库。

watcher 事件过滤会忽略项目自己的 index 目录、.git、__pycache__ 等永远不会改变源码索引的路径；子项目的 .auto-index-mcp 则不能一概忽略，否则父库无法感知 child index 变化。

忽略规则分成用户配置和自动忽略，写入 index store。重启服务后重新加载，不依赖当前 MCP 进程的内存状态。

质量检查输出置信边界#

质量工具消费已持久化的符号与调用图，不重新发明一套解析器。当前有三类检查：

  • nesting：符号层级和代码块深度超过阈值；
  • dangling：没有索引调用者的未使用符号、没有 import 或 caller 的孤立文件；
  • unreachable：Python AST 的终止语句后代码，以及 C/JS 等大括号语言的启发式终止路径。

Nesting 报告会给出 files_checked、symbols_checked、最大深度、缺失 nesting 元数据和 coverage；当覆盖率过低时标记 reliable=false。

Dangling 报告区分 high、medium、low confidence。默认不展示 low confidence，因为配置、文档和框架入口天然可能没有普通 import。Python AST 的 unreachable 置信度较高；C/JS 的大括号扫描只属于 medium，可能误报或漏报。

同样，符号只作为参数传递、FastAPI 注册、C++ RAII 构造和测试框架钩子都可能看起来没有 caller。质量工具的正确用法是产生审计清单，再结合项目入口和构建结果判断；不能把“索引没有引用”直接等同于“代码一定是死的”。

索引的语义边界#

索引保存的是导航事实和启发式关系，不是完整语义模型。它不能保证：

  • C++ 模板实例化、宏展开和链接符号完整；
  • Python 动态 import、反射和装饰器调用完整；
  • 生成代码与源文件在同一时刻一致；
  • 所有运行时路径都能从静态 callers 推出；
  • 质量检查没有误报。

因此改代码前仍需要读取目标实现、调用边界和构建合同。索引的价值是让这些读取更快、更小、更可重复。

与返回压缩协议的边界#

MCP 的紧凑返回格式可以减少一次调用进入上下文的字节数，但它解决的是“这次结果怎么编码”。持久代码索引解决的是“项目结构和符号关系是否跨会话保留”：

维度紧凑返回/字典索引持久代码索引
保存对象一次响应文件、符号、关系和元数据
生命周期随对话历史随项目数据库
查询重新执行工具直接查结构索引
增量依赖调用方watcher + snapshot
失败恢复重新请求结构化错误、候选和重建

两者可以一起使用：索引先找到最小符号，响应层再用有限格式返回。

结论#

这套结构最容易被误用的地方是把索引当成语义真相。“索引里没有 caller”只等于“静态解析没找到引用”，不等于代码是死的——符号作为值传递、依赖注入注册、RAII 构造和测试框架钩子都会落在索引之外。质量报告因此必须带覆盖率和置信度，把结论停在审计清单，而不是删除建议。

另外两条边界同样是设计约束而非缺陷。跨进程去重让多个 Agent 共用一份索引，代价是任一进程都不能假设自己独占写入；max 式的候选提示只做归一化和候选返回，不替调用方选实现——一旦服务开始猜“最像的那个”，路径歧义就从显式错误变成静默错误。

真正决定这份状态好不好用的，不是索引了多少字段，而是它在解析失败、事件丢失和模型更换时是否仍然可信：失败路径标记为未索引而不是写半份记录，事件丢失由全量快照兜住，向量库与主库分离所以换 embedding 模型不必重建导航事实。这三条不成立时，持久索引会比每次重扫更危险——它会稳定地返回过期结论。
