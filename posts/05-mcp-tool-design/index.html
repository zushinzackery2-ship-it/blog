Thin Facade MCP 工具设计：从 100 个 Operation 到 6 个 Tool

传统 MCP 的上下文压力来自两处：系统提示词中的工具定义 + 对话历史中的 tool result。Thin Facade 通过 6 个 facade 工具 + 内部 operation registry + response mode 控制，让 AI 决定加载什么、返回什么。

2026-06-03 24 分钟 4862 字 MCP 架构
#MCP#AI Tools#Architecture#Context Optimization

传统 MCP 的上下文压力来自两个维度：系统提示词中被强制加载的工具定义，以及对话历史中累积的完整 tool result。Thin Facade 通过架构设计，让 AI 自己决定要不要加载工具定义、要不要拿完整数据。

核心想法#

上下文压力来自两个维度：系统提示词中的工具定义 + 对话历史中的 tool result。传统 MCP 在两个维度都是环境强制喂入，Thin Facade 的核心是把控制权交还给 AI：

  1. 工具定义按需查询 —— 不需要的 operation schema 完全不进上下文
  2. 数据按需返回 —— 默认返回摘要，需要完整数据时显式请求，大数据用 artifact 避免进入对话历史

核心机制：少量 facade 工具 + 内部 operation registry + capability 查询 + response mode 控制。

MCP 协议的上下文占用来自两个维度：

两个维度的实际占用#

list_tools 返回的工具定义会进入系统提示词区域；工具调用的返回结果会进入对话历史。一个是常驻入口压力，一个是随轮次累积的历史压力。

两个维度叠加，上下文就这么迅速膨胀起来。

强制加载与完整返回的共同本质#

两个问题：强制加载与完整返回#

这两个问题说到底是一回事：AI 没有控制权，加载什么、返回什么都由环境说了算。

两个方向各自的收敛方式#

优化 1：工具定义按需查询#

在本文采用的示例口径中，100 个完整工具定义约占 15,000 tokens，6 个 facade 定义约占 500 tokens，因此常驻工具定义下降约 96.7%。这个比例来自示例输入，不是固定性能指标；实际结果取决于 schema 长度、客户端注入方式，以及一次任务中按需查询了多少 operation。

优化 2：tool result 按需返回完整数据#

对话历史的占用也随之大幅下降。

这个表不是在比较“工具数量”，而是在比较控制权的位置：传统 MCP 由环境决定暴露和返回，Thin Facade 由 AI 在每一步按需选择。

场景：AI 需要读取一个 UE 资产的元数据#

传统方案#

Thin Facade 方案#

如果 AI 后续确实需要完整数据：

两套方案的差异集中在三点：

  1. 系统提示词：15,000 tokens → 500 tokens
  2. 对话历史：默认只有摘要，需要时才拿完整数据
  3. 大数据通过 artifact 机制，避免直接进入对话历史

同一个读取任务在 Thin Facade 里的请求链路可以拆成这样：

阶段facade 入口AI 当前只需要知道什么返回应该长什么样不应该带进上下文的东西
找能力域context_get有哪些能力分组分组名 + 一行说明每个 operation 的完整 schema
找候选操作capability_get(detail="index")目标分组有哪些 operationoperation 名、读写类型、风险、一行描述参数细节、返回大对象示例
拿调用合同capability_get(detail="schema")当前 operation 怎么传参单个 operation 的参数 schema其他 operation 的 schema
先拿结果判断execute(response.mode="summary")结果是否符合预期一行摘要、状态、必要计数完整 asset / graph / diagnostics 对象
再拿细节分析execute(response.mode="full")需要完整数据时再展开小数据直接返回，大数据返回 artifact handle默认把大对象塞进历史
看写入影响diff_get / plan_validate改了哪里、风险是什么diff token、诊断和风险标记无关资源的完整快照

这张表表达的是 Thin Facade 的操作节奏：先定位能力，再拿单点 schema，再用 response mode 控制返回粒度。

返回粒度由调用方声明#

Thin Facade 的第二个优化，是让 AI 自己决定要不要拿完整数据。

Response Mode 层级#

任务意图推荐 mode对话历史里保留什么适合放到 artifact 的内容
判断资源是否存在、状态是否正常summary一句话结果、关键状态、必要计数完整元数据、依赖树、节点列表
执行写操作后确认影响delta变更摘要、诊断数量、风险标记完整 diff、完整前后快照
需要做深度分析fullartifact handle、摘要、数据规模大型 graph、批量 diagnostics、完整 asset dump
需要继续引用同一份大数据artifact / handle稳定 id、size、摘要原始大对象本体

response mode 的价值不在“压缩文本”，而在把默认返回从完整对象改成任务所需的最小状态。

Artifact 机制#

当返回数据超过阈值（如 2KB），不直接进入 tool result：

对话历史只保留 artifact handle 和摘要，实际数据存储在外部，按需访问。

实际效果#

假设 10 轮对话，每轮调用 1 个读操作：

方案10 轮读操作后的历史占用
传统方案：每轮返回完整数据，平均 2KB约 20KB，按 4 bytes/token 粗估约 5,000 tokens
Thin Facade：每轮默认 summary，平均 80 tokens约 800 tokens
Thin Facade：3 轮返回 artifact 摘要，其余 7 轮返回 summary约 1,010 tokens

按这组假设，对话历史占用约下降 80%–84%。真实比例受 JSON 结构、tokenizer、摘要字段和 artifact handle 长度影响；这里的价值是把大对象移出历史，并让返回粒度可控，而不是保证一个固定百分比。

能力查询必须分级#

第一个优化（工具定义按需加载）的细节：不是一次性给全部 schema，而是按需分级。

AI 通常的查询路径：

  1. context_get() → 有哪些分组？
  2. capability_get(group="asset", detail="index") → 这个分组有哪些 operation？
  3. capability_get(operation="asset_get", detail="schema") → 这个 operation 怎么调用？
  4. execute(operation="asset_get", ...) → 执行

其余 99 个 operation 的 schema 从未进入上下文。

安全边界是这套结构的副产品#

查询式设计不只优化上下文，还带来安全上的好处：

  • execute 必须拒绝 registry 外的 operation —— 白名单机制内建在架构中
  • 写操作默认 dry_run=true —— 不确认不执行
  • 高风险 operation 在 capability 中标注 risk —— AI 先知情再执行
  • 任意执行入口被架构排除 —— 不是”禁用了某个工具”，而是”架构本身不提供这类入口”

边界#

上下文压力来自两个维度：系统提示词 + 对话历史。

传统 MCP 在两个维度都是环境强制喂入：

  • 工具定义：环境决定加载什么
  • 返回数据：默认返回完整数据

Thin Facade 在两个维度都把控制权交给 AI：

  • 工具定义：AI 决定查不查某个 operation 的 schema
  • 返回数据：AI 决定要摘要还是完整数据，大数据用 artifact

归根结底，这套设计动的是控制权的归属，而非工具定义的大小或返回数据的压缩。

实践口径：来自 MCP 桥接工具面的架构抽象；重点是 Thin Facade、operation registry、response mode 和 artifact 边界，不绑定具体项目。
