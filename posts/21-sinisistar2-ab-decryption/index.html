SiNiSistar 2 资源加密逆向：Rijndael-256-CBC 的完整解密链路

SiNiSistar 2 的 2931 个 AssetBundle 全部被自定义加密保护，AssetStudio、UnityPy 都读不了。本文从 dump.cs 定位加密类，反汇编确认 Rijndael-256-CBC-PKCS7 参数，用 Frida 抓运行时密钥，最后发现代码里 IV 与 K 两个字段名是反的——按字面意思用会得到乱码。

2026-06-29 16 分钟 3293 字 Unity 逆向
#Reverse Engineering#Unity#IL2CPP#AssetBundle#Rijndael#Frida

SiNiSistar 2 的全部 AssetBundle 文件使用自定义加密方案保护，AssetStudio、UnityPy 等工具无法直接读取。本文记录从静态分析到批量解密的完整逆向过程，最终实现 2931 个 AB 文件全部解密，提取 959 个唯一资产文件。

依旧，先说结论：

  • 加密算法：Rijndael-256-CBC-PKCS7（256 位块宽，非标准 AES-128/256）
  • 密钥来源：Unity 运行时加载 Resources.Load("Manager/unique") 获取 Unique 对象的 x/y 字段，与硬编码常量拼接后 UTF-8 编码
  • 最终密钥（32 字节）：Key = 0BFAB106A793DCA7F06789412023ED45，IV = D9AB89AA56F5673001127802CDEF00BC
  • 性能：C# + BouncyCastle 批量解密 2931 个文件耗时约 70 秒（41 files/s）
  • 实现方式：纯脚本层 C# 加密，未修改 Unity 引擎底层，逆向难度属入门级

从文件特征确认加密存在#

游戏包里 SiNiSistar2_Data\StreamingAssets\Game_bin\ 目录下有 2931 个文件，文件名全是哈希值，没有扩展名。拿 AssetStudio 和 UnityPy 试了一下，都读不了。

随便看了一个文件的前 32 字节（00235320b5f75869b3f80ae096652）：

三个特征一看就是加密了：

  1. 文件头不是 UnityFS。正常 AB 文件开头都是 UnityFS 魔数，这里全是随机字节，整个文件被加密了。

  2. 文件大小全是 32 的倍数。块加密的典型特征，明文按块对齐，密文长度自然是块大小的整数倍。

  3. 文件名是哈希值。没有扩展名，游戏运行时应该有个映射表来识别文件。

既然游戏运行时要解密这些文件，那解密逻辑肯定在代码里。用 Il2CppDumper 导出 GameAssembly.dll 的元数据到 dump.cs，搜了一下 Rijndael、Crypto、encrypt 这些关键词，命中两个关键类：

RijndaelManaged 一出来就知道是 Rijndael 算法了。接下来就是搞清楚具体参数——密钥多长、块多大、什么模式。反汇编 GameAssembly.dll 的二进制代码，进入静态分析。

识别要点：

  1. [rip+0x...] 是 IL2CPP 静态字段引用。 IL2CPP 把类型信息和静态字段存在全局表中，通过 RIP 相对寻址加载。[rcx+0xB8] 中的 0xB8 是 Il2CppClass 结构中 static_fields 的偏移。

  2. [rax+0x20] 和 [rax+0x28] 是 Unique 的字段。 Unique 继承自 MonoBehaviour，MonoBehaviour → Behaviour → Component → Object → RuntimeObject 的继承链决定了 x 字段在对象偏移 0x20，y 在 0x28。

  3. call String_Concat 之前，rcx 和 rdx 分别是两个参数。 x64 调用约定：rcx = 第一个参数，rdx = 第二个参数，r8 = 第三个参数。

vtable 调用识别#

IL2CPP 的虚方法调用模式固定：

只要看到 [r8+0x<常数>] 后跟 call rax，就是虚方法调用。偏移值对应 .NET 接口/虚方法在 vtable 中的顺序，可通过 dump.cs 中的方法列表推断具体含义。

关键结论#

  1. 算法是 Rijndael-256，不是标准 AES。 set_BlockSize(0x100) = 256 位块宽。AES 标准（FIPS 197）只支持 128 位块，Rijndael 原始规范支持 128/192/256。Unity 使用的 Mono/IL2CPP 保留了完整 Rijndael 实现。

  2. Key/IV 的赋值在 get_aesManaged 之后的代码中。 设置完 Mode/Padding 后，函数继续调用 Encoding.UTF8.GetBytes(Util.IV) 和 Encoding.UTF8.GetBytes(Util.K) 分别赋给 aes.Key 和 aes.IV。变量名与实际用途是反的——Util.IV 字符串被设为 aes.Key，Util.K 字符串被设为 aes.IV。

  3. 密钥是 UTF-8 编码的 ASCII 字符串。 Encoding.UTF8.GetBytes() 对纯 ASCII 字符串等同于单字节编码，每个字符对应一个字节。32 个 ASCII 字符 → 32 字节密钥。

  4. 纯脚本层加密，不涉及 Unity 引擎底层。 整个加解密链路都是 C# 代码——Util 类是普通 IL2CPP 编译的 C# 类，用的是 .NET 自带的 RijndaelManaged，UnityPlayer.dll 没有任何改动。开发者就是打包 AB 时用 C# 加密一遍，运行时用同样的 C# 代码解密。本质是脚本层包装，不涉及引擎魔改。
