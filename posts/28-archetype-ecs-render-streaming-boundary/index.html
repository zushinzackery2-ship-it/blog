Archetype ECS 的两个边界：渲染提交与流式列补写

上一篇把这套自研 Archetype ECS 的列存储和查询切分拆开了，正文停在双 World。这一篇接着走列数据的两个边界——出口到 GPU 的渲染提交，入口从磁盘的流式补写。两个边界都有一层可验证的托管 ABI，也都在某个位置沉进不可见的原生层；本文把托管这一侧讲透，并明确标出原生底在哪。

上一篇拆的是这套 Archetype ECS 的内部：实体句柄、定长描述符、128 位掩码、查询切分、双 EntityManager。那些是”列怎么存、怎么查”。这一篇讲列的两个边界——列数据怎么出去、怎么进来。

出去是渲染：查询切出工作区间、Job 把矩阵算新，然后这些列要变成 GPU 上的 draw。进来是流式：磁盘上的预制数据在加载完成的那一刻被写进列。

两个边界有一个共同形状。托管这一侧都能还原出一套确定的 ABI——结构布局、参数顺序、id 编码、状态边；再往下一层（原生排序提交、原生磁盘解析）都沉进了不可见的实现。本文把托管侧讲清楚，同时在每个边界标出原生底的位置，不把边界之外的东西写成已还原的事实。

先说两个边界各自到哪为止#

  • 渲染出口：托管层填一份 0x1B0 的剔除参数、取回视角句柄，再把过滤条件交给原生列表构建入口，拿回一个 u32 列表句柄提交。能确认的是参数布局、过滤词汇和句柄流；列表内部的 128 位排序键、多视角掩码和共享大缓冲属于外部设计材料，当前样本没有展开。
  • 流式入口：blob 与属性 id 是几条位宽写死的短函数；ConvertFrom 只在三条状态边上预取或补写资源，选列走和查询相同的 popcount 寻址。能确认的是 id 编码、状态机和被写的列布局；磁盘文件头、列目录、对齐和整段搬入位于原生加载循环之后。

两个边界共享四个已经在存储篇闭合的不变量：

  1. Entity 是 {globalIndex, version} 两个 u32 组成的句柄；句柄先经槽位表取得 archetype id 与行号，旧句柄是否失效只由空槽和版本比较确认，当前材料没有展开回收算法。
  2. archetype 签名是两个 u64 组成的 128 位 ComponentMask；它限制全局组件 id 空间，描述符内联的 64 项组件表则限制单个 archetype 的组件数，两者不是同一个上限。
  3. 组件列按容量预留。描述符中的 offset 是前置组件尺寸之和，真实地址是 memory + offset * capacity + row * size，不能把 count 当作列间距。
  4. Gameplay World 与 Renderer World 各有独立槽位表和 archetype 表，句柄不跨表通用；跨 World 关系由玩法侧句柄表与渲染侧 Binder 显式连接。

渲染出口：查询结果与 draw 提交#

查询命中还画不了#

查询按组件签名过滤 archetype，切成工作区间，Job 更新 LocalToWorld。这一步只保证矩阵和 Binder 是新的。主相机、阴影、反射探针各自还得判断对象在不在自己的锥里、被没被挡住、用哪一档 LOD——命中不等于可见。

剔除开关打开时走原生入口。入口先分配一块 0x1B0 字节的参数，逐字段填，再把指针写回相机。参数里带着设备档、是否移动端路径、渲染 World 的实体表、原生剔除系统，以及一组视角句柄：

填完之后，原生入口把几个句柄抄回相机：主视角句柄、虚拟纹理反馈编号、细分句柄；若还有第二份相机数据，再抄一份 UI 视角句柄。当前可见调用此后只拿这些 u32 去建列表，没有继续传递托管 Renderer 对象；这确认了跨层参数形状，不单独证明整条路径的分配或性能收益。

视锥、LOD、低分辨率深度图和简化遮挡片是外部材料描述的剔除流程。当前样本能确认原生 culling system、视角句柄和这条调用边界，确认不到这些阶段的执行顺序、并行关系和可见位写在哪。

交给原生的是过滤条件，不是键#

建列表的入口带视角句柄、渲染标志的 mask / value、光照模式、关键字和几个提交开关。私有实现把参数收齐后跳进原生函数，返回一个 u32 列表句柄：

mask 和 value 成对出现，过滤语义是”指定位等于指定值”。具体按位与还是按位或，编码在原生层，托管只保证把这两项传下去。

三组枚举构成托管侧的过滤词汇。渲染标志是一张 u32：PreZ、双面阴影、负缩放、AlphaTest、不透明 / 透明的几档插入点、自定义属性、两种 dither、投射阴影、四级 CSM、静态 / 动态阴影、角色描边、光追、OIT、材质双面。光照模式是另一张 u32：GBuffer、移动端 GBuffer、Forward 的几条分支、ShadowCaster、DepthOnly、描边、扭曲、遮挡显示、地形 VT、光追、GPU 粒子。关键字只有 16 位，现用 CrossFade 和 Dither。能复现的是这三组名字，不是键里每一位的宽度。

同一套入口有两条变体。带 PreZ 的一次产出三个句柄：正常列表、PreZ 前半、PreZ 后半。另一条不走视角句柄，直接吃一组实体指针、相机位置和同一套标志，给已经圈定的实体子集用。提交是另一条短跳：命令缓冲为空就中断，否则带列表句柄进原生绘制。

这里有两个容易混的类型。ForwardPassUtils.ForwardOpaquePassData 是托管类，绝对对象偏移 0x18、0x20 放两个 RendererListHandle，0x28..0x38 放五个 ECS 句柄。ForwardPassConstructor.PassInput 是值类型，装七个 ECS 句柄和屏幕剔除参数。下面对值类型用归一化偏移，即统一减去 IL2CPP dump 标注的 0x10 基准：

这两个偏移约定不能混。值类型归一化后七个句柄落在 0x28..0x40；托管类的绝对偏移 0x28..0x38 恰好也是五个句柄，数值相近但语义不同——一个是归一化的值类型字段，一个是带 RendererListHandle 头的对象绝对布局。把数值巧合当成同一布局，是这类偏移复核里最容易犯的错。

Pass 构造函数接收这些句柄，绘制函数再把句柄交给 DrawECSRendererList。列表在原生剔除入口生成、以句柄提交，这条边界是硬的；“排序键在这里完成一次标准排序”是外部材料的描述，当前函数没有展开列表内部组织。

草另走一列#

草的实例数据不进这张 mesh 列表。批次信息是另一列：

batchGroupKey 在注册批次时钉上，是草自己的分批键，不是 128 位 draw sort key，但和 mesh 列表共用同一组 renderFlags。两种对象进同一条提交语义，只是建列表的入口不同。结构总长 0x18，末尾两个 padding 补齐——列步长按 0x18 算，漏掉尾部对齐会让整列错位。

出口到这层为止#

托管侧给出的硬边界：填 BeforeCulling 参数、取回视角句柄，把视角、flags、light mode、层掩码交给原生列表构建入口，最后以 u32 句柄提交。这条链上没有一处把排序键暴露给托管层。

两个 128 位不是一件事#

这条边界上有个命名巧合值得单独拆开：组件掩码和排序键都是 16 字节，职责完全不同。

组件掩码回答「这块有没有 Position、有没有 Renderer」，用途是查询时选列，它在托管侧可见、可复核。排序键回答「这条 draw 的屏幕顺序、pipeline、mesh、材质、距离是什么」，用途是提交时定顺序，它在原生侧、托管完全看不见。

宽度相同、都叫「128 位」，很容易在描述里并成同一张位图。一旦并了，会顺势推出一串错的结论：以为查询结果的顺序就是绘制顺序；以为加一种组件会影响 draw 排序；以为掩码位数上限（128 种组件）也是排序键的字段容量。

顺序上它们也不相邻——掩码选出列，可见性再经一层 32 位视角掩码筛，之后才编排序键：

排序键的字段构成——屏幕顺序、pipeline、mesh、材质、距离——来自外部分享，位宽没有公开，二进制里也没有 DrawSortKey 一类结构。「把易打断批次的状态放高位、距离放低位」是符合字典序比较的一种合理设计解释，不是从编码函数还原出来的布局。这里同样只能写到「字段有哪些」为止。

128 位排序键、32 位多视角可见掩码、一次标准排序、共享大缓冲加动态偏移，都是解释这条边界的外部设计材料。二进制里没有 DrawSortKey 同类结构，托管层拿到的自始至终是 u32 句柄。把键的位宽和编码写成已还原，就越过了当前样本的证据线——所以本文只写到句柄为止。工程上的调试边界也顺势清楚了：句柄生成前查 BeforeCulling 参数和过滤枚举，句柄生成后查原生列表内容与绘制入口。

流式入口：磁盘数据到列的补写#

编号是高低位拼出来的#

磁盘上的单位是 blob，按场景分块编号，再按块内下标取一份。编码只有三条指令：

高 32 位是场景块，低 32 位是块内下标。EncodeBlob 对场景块做符号扩展，负数块号会把 u64 的高位拉起来。旁边有个同形入口，参数名是格子和下标，高半段改成零扩展；它和按 uniqueKey 拆开的函数落在同一条地址上。blob 编号与 uniqueKey 是同一套高低 32 位，区别只在高半段有没有符号。组句柄又切一档：高半段只留 16 位，低 32 位仍是下标，中间 16 位空着。

同形不同符号是这里要盯住的点。三个入口共享一条位拼接，但符号扩展、零扩展、16 位截断各不相同，凭一份反汇编容易把它们并成一个函数。

componentIndex 和 propertyId 各只留低 8 位，0xFF 刚好占满类型槽。转换上下文对着已经映射进来的字节说话：能取指针的取指针，能按字节视图读的交出长度和地址，字符串和资源句柄走各自的出口。这些入口说明上下文能暴露字节视图、字符串和资源句柄，推不出全部组件列零解析——字段目录、对齐修正、压缩、版本检查和重定位是否存在，要看原生加载实现。

ConvertFrom 只在三条边上写槽#

每种可流式实体挂一对函数：磁盘到运行时、运行时到磁盘。转换发生在组的状态切换上，不在每帧重解整列。状态机按字节枚举往前排，托管侧比较 1、3、6；按声明顺序，它们对应未加载进入加载中、加载完成、卸载回到未加载。这个对应是按枚举顺序推的，dump 没写出数值。

1 预取引用 · 3 写入列槽 · 6 只回成功；其余边返回 false，不改列

水面把这三条边写死了。未加载进入加载中：用两张静态 id 去上下文里预取共享网格和配置，不写组件列，返回成功。卸载回到未加载：什么都不写，返回成功。加载完成才选列、写槽，其余边返回失败。

结构在 objectToWorld 后面还有六个 float4，总有效载荷 0xAC。写到 objectToWorld 就收尾会漏掉后半段，列步长跟着错。流式体积更窄：组件第一字节是 isEnable，加载完成写 1、卸载写 0，测的是掩码第 61 位，不预取属性 id，只翻这一位可见性。

入口到这层为止#

能确认的是：属性 id 用固定 12 字节标识，三条状态边预取或补写资源，组件列按 prefix * capacity + size * entityIndex 寻址，水面 / 水面贴花 / 流式体积的列布局和被写字段都成立。

磁盘是否直接保存这些列、文件头怎样记录对齐和重定位、加载时是一次 memcpy 还是逐列解析、版本变化后是否必须重导，都在原生入口之后。AllocateRuntimeChunk 只向原生层传两个路径字符串，证不到搬入方式。玩法对象另有一条 MemoryPack 路径，序列化的是面向对象那一层，不进 SoA 列，和 chunk 同构不是一条路。所以这个边界的诚实说法是”运行时列补写”，不是”磁盘同构已还原”。

两个边界靠 Binder 连起来#

玩法 World 和渲染 World 各一张表，跨 World 一对多：玩法实体最多记 512 个渲染句柄，渲染实体挂 Binder。

LocalToWorld 就是流进渲染出口的那份数据：更新 Job 把本地 TRS 收成 current，previous 留给运动向量，然后这份矩阵随渲染列进剔除和列表构建。RenderBinder 的 sharedDataIndex 反过来指回玩法侧的共享数据——入口补写的组件（meshID、materialID）和出口消费的组件（矩阵、rendererType）在渲染 World 的同一批实体上会合。

Renderer World 还有一张 ECSExplicitEntityType 枚举，列出网格、反射探针、水面、工厂、贴花等类别。它证明渲染实体存在显式分类；当前材料没把这些枚举值与描述符 chunkType、最终排序键编码逐项对应起来，所以分类是确定的，分类到 GPU 的最后一跳仍在原生侧。

复盘：两个边界的共同形状#

把渲染和流式放在一起看，会发现它们是同一种结构问题的两个方向。

列数据的进出都在托管层留下一套确定 ABI，再沉进原生底。 出口是 0x1B0 参数加 u32 句柄，入口是 12 字节 id 加三条状态边。这层 ABI 能靠结构布局和机器码闭环，因为它必须在托管和原生之间传参，参数形状藏不住。

再往下一层都不可见，而且不可见的恰好是”算法”那部分。 出口看不到排序键怎么编、怎么排；入口看不到磁盘怎么摆、怎么搬。当前样本呈现的是接口位于跨语言边界、具体实现留在原生侧的分层；它描述这套样本的证据形状，不外推为所有引擎的普遍结构。

所以边界必须显式声明，而不是用接口去反推实现。 拿到 u32 句柄不等于还原了排序键；拿到 ConvertFrom 不等于还原了磁盘格式。把能确认的写成确认、把外部材料标成外部材料、把原生底标成原生底，这篇才对得上它的证据等级。

值得带走的判断有三条：跨语言边界上的参数形状是最可靠的逆向抓手，因为它藏不住；数值相近的偏移（归一化值类型 vs 托管对象绝对布局）要按语义分开，不能按数字并；以及，接口的完整不代表实现的完整，边界之外要留白，不要圆场。

上一篇是一种有意思的 Archetype ECS 的设计与取舍，讲的是列怎么存、怎么查；这一篇补上列怎么进、怎么出。两篇合起来，覆盖了这套自研 ECS 从存储到边界的可验证部分。
